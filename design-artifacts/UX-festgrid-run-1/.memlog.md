Edit case gets new 'Default Location Pending Review' state pattern: immediate save, Pending Review badge, moderator accept/revert. Reason: defaultLocation moved to account-level (shared across subscribers) per architecture review; old flow's step 5 wrongly associated the value with the subscription and had no moderation touchpoint.

- (decision) Global navigation IA: 5 top-level items — Discover (/, Compass icon), Feed (/feed, Rss icon), Favorites (/favorites, Heart icon), Calendar (/my-calendar, CalendarDays icon), Profile (/settings, UserCircle icon). 'Feed' chosen over 'Following' to match the existing /feed route name in IA.
- (decision) Global nav is a 3-tier responsive pattern using Tailwind default breakpoints (matches AppShell.tsx's existing md: usage): <768px fixed bottom tab bar (icon+label always visible, all 5 items); 768-1279px left icon-only sidenav rail (logo pinned top, Profile pinned bottom via mt-auto, other 4 items top); >=1280px same rail permanently expanded with icon+label. No manual collapse toggle — purely breakpoint-driven.
- (decision) Active nav item indicator: leading accent-colored bar (vertical on sidenav rail, top edge on mobile bottom tab bar), at all 3 breakpoints, plus aria-current=page (UX-DR18/WCAG AA). Chosen over accent-background-pill and text-color-only for stronger visual weight.
- (decision) Icon-only rail (768-1279px) label reveal: on hover (mouse), label tooltip appears. On touch, a single tap both navigates AND briefly flashes the item's label (fades after a few seconds) — not a two-step tap-to-reveal-then-tap-to-navigate — so touch users get passive learnability without an extra blocking step.
- (event) Ran ad-hoc accessibility review (WCAG 2.1 AA) on the nav pattern before committing to spines. 10 findings (0 critical, 3 high, 4 medium, 3 low); full report at review-accessibility.md. All resolved into the spec before drafting.
- (decision) Accessibility fixes folded into nav spec: (1) new token nav_active_indicator=#E04347 (darker than base accent) for the active bar, meeting 3:1 non-text contrast vs neutral #FAFAFC (base accent #FF5A5F measured ~2.93:1, failed). (2) Rail hover tooltip also triggers on :focus-visible, persists while focused, dismisses on Escape/blur. (3) Single persistent <nav aria-label="Main"> across all 3 breakpoints, CSS-only layout changes — no duplicate nav landmarks; if markup must differ, only one variant may ever be in the a11y tree (hidden/inert). (4) Explicit 2px focus ring distinct from the active-bar color, meets WCAG 2.4.7. (5) Explicit aria-label on every nav item at all tiers, matching the >=1280px visible label text, independent of tooltip. (6) Nav is a persistent shell element, does not remount on route change; touch tap-to-flash label duration is >=2000ms, only extended (never shortened) under prefers-reduced-motion. (7) min-h-11 min-w-11 (44px) hit-area token per nav item. (8) Active state gets a second non-color reinforcement (filled vs outline icon variant) beyond the accent bar. (9) Label-fade/transitions wrapped in prefers-reduced-motion with instant fallback.

- (decision) Accessibility fixes for the Profile auth menu: (1) Authenticated menu is NOT role=menu/menuitem (APG reserves that for app command menus) -- trigger is a <button aria-haspopup=true aria-expanded>, popup content is a plain <ul><li><a>> list of links, Log Out is a real <button> in that list. - (decision) Soft Delete with Undo state pattern revised (EXPERIENCE.md State Patterns): delete now commits immediately at Trigger (real backend delete call at T+0), not deferred to unmount/navigate-away. Reason: deferred-commit meant closing the browser tab (not navigating within-app) silently skipped the commit entirely -- unmount never fired, so the item was never actually deleted despite the user believing it was. Applies to all Soft-Delete-with-Undo surfaces (Saved Locations today; API Keys/Subscriptions future) EXCEPT Favorites/event-list, which already implements immediate-commit informally (toggleFavoriteAsync fires at trigger, undo re-toggles) and is the precedent this revision generalizes, not a new exception.
- (decision) Soft Delete with Undo timing: undo toast/popup duration is 6000ms (chosen over sonner's ~4s default since a real backend delete now finalizes when it expires, not merely a notice; chosen over 10s/no-timeout to avoid multiple stacked toasts on rapid successive deletes). Timer pauses on hover/focus (WCAG 2.2.1 timing-adjustable). New DESIGN.md token: components.notification.undo_duration_ms.
- (decision) Soft Delete with Undo full state sequence: T+0 (Trigger) fires the real delete mutation immediately AND optimistically flips the item to its greyed-out/pending visual in the same moment (does not wait for the mutation response). If Undo is clicked within the 6s window, a separate reverse/restore mutation commits and the item reverts to normal. If the toast times out unactioned, the item is removed from the client's already-loaded list data with NO further network call (the delete already committed at T+0) -- chosen over a server refetch to avoid an extra round trip and avoid disrupting scroll position/pagination state on infinite-scroll lists (Locations today; API Keys/Subscriptions future).
- (decision) Soft Delete with Undo failure path (new -- prior spec had none, since prior deferred-commit design had no optimistic-before-confirmation window): if the T+0 delete mutation itself fails, the item reverts from greyed-out back to its normal visible state, the undo toast/timer is cancelled, and a distinct error toast is shown -- since nothing was actually deleted, there is nothing to undo.

- (decision) Multi-day segment repeats as a full compact card on every spanned day-row (not once on the start day with a duration indicator). Reuses WeeklyCalendarView.tsx's existing per-day bucket/segment model (dayBuckets, isFirstSegment/isLastSegment) unchanged -- mobile is a new render path over already-computed data, not new business logic. Keeps one interaction model (each day's segment independently focusable/clickable) consistent across breakpoints, matching the desktop AC4/AC8 Gate 2 finding already on record in 1-3g's Dev Notes.
- (decision) Skipped-day interaction resolved without special-casing: a day within a multi-day event's span always has >=1 bucket entry (its own segment), so the vertical list's 'skip days with zero events' rule never skips a day a multi-day event is spanning -- no pull-back/jump logic needed, it falls directly out of existing bucketing. This guarantee only holds if mobile never hides a segment behind an overflow cap (see next decision).
- (decision) Mobile day-list drops the desktop grid's maxEventsPerDay cap + '+N more' popover entirely -- always renders every schedule for a visible day inline, uncapped. Reason: that mechanism exists specifically because of the desktop grid's fixed h-32 day_cell height (1-3g Dev Notes 'Design Decisions Confirmed With User'), a constraint that doesn't exist in a naturally-flowing vertical list; keeping the cap on mobile would risk hiding a multi-day segment behind '+N more' on some spanned days, breaking the prior decision's visibility guarantee.
- (decision) Visual treatment: a repeated small badge ('Day X of N' + a calendar-range icon), not a connecting bar/line. Reason: the desktop grid's continuity cue (suppressed border/rounding between adjacent day columns, WeeklyCalendarView.tsx multiDayRoundingClass) only works because those columns are directly touching; the vertical list's day-rows are each preceded by their own day-header, breaking DOM/visual adjacency between a multi-day event's consecutive segments -- neither that trick nor a literal connecting line is implementable without new absolute-positioning/measurement machinery, and no existing packages/ui/src/core primitive (PageContainer/GridContainer/WeekPicker/BlockingLoader/MultiSelect/etc.) provides timeline/connector layout. Badge numbering (X = calendar-day offset from the schedule's true eventStartDate, N = total inclusive span length) is computed from the schedule's actual date range, not clamped to the visible week -- consistent with how isFirstSegment/isLastSegment already work today.
- (decision) Mobile card line order (applies to every calendar item, not just multi-day, since fitting favoriteCount's already-confirmed second line alongside the new badge requires defining the whole stack): (1) title + existing favorited/added-to-calendar icons; (2) time range for that day-segment, now always visible as inline text rather than gated behind the desktop's hover/focus tooltip -- necessary corollary, since CalendarCard's existing tooltip handlers explicitly no-op on pointerType==='touch', so touch users get no time info at all today; (3) favoriteCount line when present (sprint-change-proposal-2026-08-24-ux-rework-batch.md Section 4.5, confirmed OK as calendar's second line); (4) 'Day X of N' badge, multi-day segments only. No line competes for space since list rows have natural height, unlike the desktop grid's h-32-capped cell.
- (decision) Same-week-relative/>7-days-absolute date display rule (Section 4.9) confirmed non-conflicting, no calendar-side change needed: that rule is explicitly scoped to card/list views only ('calendar already positions items by absolute day column'), and the vertical list's day-row headers remain each day's own absolute-date anchor -- unchanged from the existing grid's day_header formatting.

# Story 3.6: Process posts from the queue and extract event information

## Story Details

- **Epic:** 3
- **Story ID:** 3.6
- **Status:** review

## Story

**As a** system,
**I want** to process posts from the queue, call the Gemini API (through the AI Gateway adapter) to extract event information, and enqueue the validated result for ingestion,
**So that** new events can be reliably added to the application without this Lambda also owning the database write.

## Acceptance Criteria

1. **Given** there is a message in the `AIProcessingQueue` (Story 3.5's `ProcessingJobMessage`: `postId`, `accountId`, `content`, `imageUrl?`, `postUrl`, `publishedAt`), **when** the message is consumed by the AI Processor Lambda, **then** the Lambda calls the Gemini API exclusively through the AI Gateway adapter (Story 0.13's `callGemini`) to extract event information — analyzing both the post's image (`imageUrl`, when present, since `EventInfo` is PRD-defined as "the information extracted from an event poster" and `isEvent` is documented as "true if the **image** is an event poster") and its caption text (`content`) together as multimodal input; when no `imageUrl` is present, extraction runs on `content` text alone. [epics.md AC1, extended per PRD §4.7's `EventInfo`/`isEvent` doc comments]
2. **And** `callGemini` is invoked with `subscriberUserIds` set to the post's source account's currently-active subscribers (Story 3.1a's `subscriptions`, `activeOnly`-filtered) — never a hardcoded or empty list — since Story 0.13's own AC3 requires this to determine Tier 1 (single subscriber) vs. Tier 2 (shared, round-robin) key selection.
3. **And** the raw Gemini response is validated with AJV against the full extraction schema (`isEvent`, `eventName`, `types[]`, `categories[]`, `schedules[]`, optional `location`/`organizerName`/`contactInfo`/`description`, and a required `confidenceScore`) before any further processing. [epics.md AC2]
4. **And** if `isEvent` is `false`, or the AJV validation fails, no message is enqueued to `DataIngestionQueue`. A `false` `isEvent` is a **successful** extraction outcome (the post genuinely isn't an event) and the post is marked processed per AC8. An AJV validation failure is a **failed** extraction attempt and the post is left unmarked so a future re-attempt remains possible.
5. **And** if the Gemini response does not include an explicit event location, the transform falls back to the source post's account's `SocialMediaAccountProfile.defaultLocation` (via `posts.accountId`, Story 3.1a/3.3a) when one is set (PRD §3.7); if no `defaultLocation` is set either, the resulting message's `location` is left absent rather than fabricated. [epics.md Amendment 2026-08-01 — see Dev Notes "Absent-Location Data Type Gap" for how this reconciles with `EventInfo.location`/`events.location` both being non-nullable]
6. **And** (PRD FR33, Tier 1 — "location-based inference" — only; see Dev Notes "FR33 Timezone Inference — Scope Decision" and the new Story 3.6a for Tiers 2-3) for each schedule whose location is resolved (explicit from Gemini, or the account's `defaultLocation` fallback), the transform calls the existing Geolocation adapter (Story 0.16's `resolveLocation`) to populate that schedule's `locationDetails`, including its IANA `timezone` — reusing the adapter's own cache; this Lambda never calls Geoapify directly.
7. **And** the validated, transformed extraction result (a new `ExtractedEventMessage`, not a full `EventInfo` — see Dev Notes) is enqueued to the `DataIngestionQueue`. This Lambda does not write the extracted event/schedule data to the database directly (Story 3.6b handles ingestion). [epics.md AC (final)]
8. **And** once an extraction attempt for a post completes successfully — producing an event message (AC7) or determining the post is not an event (AC4) — the post's `is_extracted` flag is set via the existing `markPostExtracted` (Story 3.3a, whose own AC6 already names Stories 3.6/3.6b as its consumers) so Story 3.5's duplicate-enqueue guard stops it from ever being re-selected. A failed/transient attempt (AJV validation failure, or `AiGatewayExhaustedError`) does **not** mark the post.
9. **And** if the AI Gateway adapter throws `AiGatewayExhaustedError` (all candidate keys exhausted/rate-limited/invalid) or any other unexpected error occurs while processing one SQS record, that specific record is reported back to SQS as a batch item failure (`reportBatchItemFailures`, see Dev Notes "Partial-Batch-Failure Retry Strategy") so only that message — not the whole received batch, and not already-succeeded records — is redelivered per the queue's existing retry/DLQ policy (`maxReceiveCount: 3`).

**Note:** AC corrected by Gate 1 (`story-split-gate.md`) — the original draft had this Lambda both call Gemini and save directly to the database, bypassing the separate Ingestor Lambda shown in `docs/infrastructure/high-level-overview.md`.

**Amendment (2026-08-01, PM pass following Epic 3 readiness re-sweep):** Added the `defaultLocation` fallback AC. PRD §3.7 has required this behavior since before Story 3.3 existed, but no AC in this story ever implemented it.

**Amendment (2026-08-10, added via `bmad-create-story` during this story's own creation):** ACs 1-2, 6, 8-9 above are new/expanded beyond the original 4-bullet epics.md draft. Four real tradeoffs, not resolvable from epics.md's AC text alone, were resolved with the user via `AskUserQuestion` during this story's creation:

1. **PRD FR33 (timezone inference) scope** — no Epic 3 story's AC text implements it, and `epic-3-readiness.md`'s sweep didn't flag the gap either. **Decided:** absorb Tier 1 (location-based, via the already-built, already-cached Geolocation adapter) into this story (AC6); Tiers 2-3 (which subscriber's timezone for a shared account; a "flagged for clarification" state that doesn't exist in the data model yet) are split into a new forward story, **Story 3.6a** (see epics.md and `## Out of Scope` below), not silently dropped.
2. **The `EventInfo.location`-required vs. AC5's "left absent" conflict** — `packages/shared-types`' `EventInfo.location: string` is required (no `?`) and `events.location` is a DB `NOT NULL` column, but AC5 explicitly allows an absent location. **Decided:** keep this story's own `DataIngestionQueue` message type (`ExtractedEventMessage`) decoupled from `shared-types`' `EventInfo` — mirroring Story 3.5's `ProcessingJobMessage` precedent exactly — with `location` left optional, and forward-note the `NOT NULL` resolution to Story 3.6b (not yet built, owns the DB write). This story does not touch `packages/database/schema.ts` or `shared-types`.
3. **A pre-existing gap this story's own work touches:** `apiLambda`'s CDK environment never sets `GEOAPIFY_API_KEY`, despite `high-level-overview.md` documenting it as a Geoapify caller (an Epic 2/2.4b-range gap, not caused by this story). Since this story must add `GEOAPIFY_API_KEY` to `aiProcessorLambda`'s environment anyway (AC6), the user confirmed fixing `apiLambda`'s missing var as a one-line drive-by in the same file/same variable, documented here rather than silently bundled in unlabelled.
4. **Failed/exhausted-job retry strategy** — the one existing SQS-Lambda precedent (`scraper.ts`) never rethrows per-record and has no `reportBatchItemFailures` configured, meaning a returned-without-throwing Lambda invocation causes SQS to delete the **entire received batch**, including records that failed inside the loop. Since quota exhaustion (`AiGatewayExhaustedError`) is a PRD §3.8-documented, expected MVP scenario, silently losing that post's message forever (no DLQ, no redelivery) was judged a real gap rather than an acceptable-by-precedent tradeoff. **Decided:** add `reportBatchItemFailures: true` to `aiProcessorLambda`'s `SqsEventSource` (this story's own CDK edit) and have the handler return `{ batchItemFailures: [...] }` for exactly the records that hit `AiGatewayExhaustedError` or an unexpected error — AJV-validation failures and successful records are still acknowledged normally (AC9).

**Depends on:** Story 0.13, Story 3.1a, Story 3.3a, Story 3.5, Story 0.16 (Geolocation adapter, for AC6).

### FR33 Timezone Inference — Scope Decision

PRD §3.7 defines a three-tier timezone-inference strategy: (1) location-based (via the geolocation service), (2) the subscribing user's own timezone as a fallback, (3) flag for manual clarification if still ambiguous. Only Tier 1 is implemented by this story (AC6), via the already-built, already-cached Story 0.16 `resolveLocation` adapter — a low-incremental-cost addition since the adapter and its cache already exist. Tiers 2-3 are **not** implemented here: Tier 2 is ambiguous for a Tier-2 (multi-subscriber) account — "the subscribing user" has no single answer when several users subscribe to the same account — and Tier 3 ("flag for manual clarification") requires a data-model/UI concept (a "needs clarification" event state) that doesn't exist anywhere in the schema or any story today. Both are split into a new prerequisite story, **Story 3.6a: Infer event timezone from subscriber context and flag ambiguous cases for clarification** (see `_bmad-output/planning-artifacts/epics.md` and `sprint-status.yaml`, added as a lettered suffix directly off this story per `story-split-gate.md`'s "single-story split" numbering rule), rather than silently left unimplemented with no trace.

### Absent-Location Data Type Gap

AC5 says a fully-unresolved location is "left absent rather than fabricated," but `packages/shared-types`' `EventInfo.location: string` is required (no `?`) and `packages/database/schema.ts`'s `events.location` column is `text('location').notNull()`. This story does **not** touch either — its own `ExtractedEventMessage` (Task 2) is a decoupled, `DataIngestionQueue`-message-only type (mirroring Story 3.5's `ProcessingJobMessage` precedent) with `location` left optional, so the conflict never surfaces inside this story's own code. It is a real, unresolved data-type-compatibility question for whichever story writes the DB row — forward-noted for **Story 3.6b** (not yet built) to resolve at insert-time (a placeholder string, a reject-and-flag-for-moderation policy, or a schema migration to nullable are all open options; this story does not pre-decide it). See `## Data Type Compatibility & Migration Requirements` below.

### Why Validation Failures Don't Retry (but `AiGatewayExhaustedError` Does)

Gemini's response is requested under a `responseSchema` constraint (Task 5), making a structurally-invalid response rare, not the common case. When AJV validation still fails (Task 7 step 4), retrying via SQS redelivery would call the paid Gemini API again for a response shape that already violated the structural constraint the model was given — unlikely to be fixed by a blind retry, and directly costs API quota (a first-class MVP concern per PRD §3.8). This story treats it as a skip-and-log, non-retryable outcome, leaving the post `isExtracted: false` so a future manual re-selection (Epic 5, not yet built) remains possible. `AiGatewayExhaustedError`, by contrast, is a transient infra condition (all keys rate-limited/exhausted right now) where retry-with-backoff is exactly the intended recovery — hence AC9's `reportBatchItemFailures` redelivery applies to it, not to validation failures.

### Partial-Batch-Failure Retry Strategy

The one existing SQS-Lambda precedent in this codebase, `apps/backend/src/lambdas/scraper.ts`, catches per-record errors inside its loop and never rethrows, and its `SqsEventSource` (`apps/infrastructure/lib/festgrid-backend-stack.ts`) has no `reportBatchItemFailures` configured. Under that configuration, if the Lambda invocation returns normally (even though an inner record failed), SQS deletes the **entire received batch** — including records that failed inside the loop — since there is no way for the Lambda to signal "only these specific messages should be redelivered." For `scraper.ts` this was an accepted, unremarked tradeoff (a failed scrape job silently vanishes rather than retrying). For this story, the user confirmed via `AskUserQuestion` that this tradeoff is *not* acceptable here, since quota exhaustion is a PRD §3.8-documented, expected-to-happen-regularly MVP condition — losing that post's extraction attempt forever (no DLQ visibility, no automatic retry once quota frees up) is a real gap, not a benign simplification. This story therefore adds `reportBatchItemFailures: true` to `aiProcessorLambda`'s own `SqsEventSource` (Task 9) and returns the AWS-documented `{ batchItemFailures: [{ itemIdentifier }] }` shape from the handler (Task 8) for exactly the records that should be retried. This is a **local** decision scoped to `aiProcessorLambda`'s own event source — `scraper.ts`'s existing behavior is deliberately left unchanged (out of scope; a bug fix there, if wanted, is its own separate concern).

### Multimodal Extraction (Image + Caption)

PRD §4.7 defines `EventInfo` as "the information extracted from an event poster," and its `isEvent` field's doc comment is "True if the **image** is an event poster" — the image, not just the caption text, is the primary artifact Gemini must analyze. `gemini-client.ts`'s `GeminiCallRequest.contents: string | any` was already left loosely typed (not `string` only) specifically to accommodate this — this story is its first real caller and the first to exercise the multi-part `Content` shape. Gemini's `inlineData` file-part mechanism requires embedded bytes (base64) or a File-API upload; it cannot fetch an arbitrary external URL itself, so Task 5 downloads `message.imageUrl` and inlines it. A failed image fetch degrades to text-only extraction rather than aborting the job — a broken/expired scraped image URL should not block extracting whatever the caption text alone can offer.

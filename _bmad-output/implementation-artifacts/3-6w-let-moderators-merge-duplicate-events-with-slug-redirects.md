# Story 3.6w: Let moderators merge duplicate events, with slug redirects

## Story Details

- Epic: 3
- Story ID: 3.6w
- Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a moderator,
I want to merge two events that turned out to be duplicates,
so that users keep their favorites and calendar entries and old links still work (BUG-052/BUG-055).

## Acceptance Criteria

1. **Given** a mid-confidence suggested match (`event_match_candidates`, written by Story 3.6v: `eventId` = the newly-ingested event, `candidateEventId` = the existing event it may duplicate) with `status = 'pending'`, **when** a moderator clicks **Accept** on it and confirms, **then** `eventId` (B, the loser) is merged into `candidateEventId` (A, the winner) in one transaction: B is soft-deleted with `merged_into_event_id = A`; B's `favorites` are repointed to A (`eventId` updated), **deduplicated per user** — if the same user already has an active favorite on A, B's row is soft-deleted instead of repointed (never left as a second active row); B's `reports` are repointed to A (`eventId` updated; `reports` has no per-user uniqueness constraint, so every row repoints, with no dedup needed); B's `calendar_additions` follow schedules — each B schedule maps to the A schedule with the same `eventStartDate` (copied onto A when no date match exists) and the row's `eventId`/`scheduleId` are repointed to A's matching/copied schedule, **deduplicated on `(user_id, schedule_id)`** (soft-deleted instead of repointed on a conflict); B's slug becomes a permanent alias of A (`event_slug_aliases`) and every existing alias that targeted B is repointed to target A instead (no alias chains); `notified_at` keeps the earlier non-null value between A and B. **No `event_posts` row is ever deleted**: for each post B links that A does **not** yet link, that `event_posts` row's `event_id` is updated to A (same `post_id`/`extraction_ordinal`, so the existing `(post_id, extraction_ordinal)` unique index is unaffected); for each post both A and B already link, B's row is left exactly as-is on the soft-deleted B (excluded from reads, AD-30 Rule 9) — never deleted, since deleting it would free that post's `(post_id, extraction_ordinal)` slot for a future re-run to recreate the duplicate. The suggestion row's own `status` becomes `'accepted'`, `resolvedAt`/`resolvedByModeratorId` are set.
2. **And** every repointed/deduplicated row id this merge touches (favorites, calendar additions, reports, `event_posts` link post-ids, slug aliases) plus B's prior slug and any changed `notified_at` value is written to a new **merge journal** row (`event_merges`) in the same transaction — this is what makes the undo window in AC6 possible, and is this story's own scope per AD-30 Rule 9 ("the journal that makes the undo window work is owned by this story and must preserve those link rows").
3. **And** rejecting a suggestion (**Reject**) requires no confirmation and performs no merge: the suggestion's `status` becomes `'rejected'`, `resolvedAt`/`resolvedByModeratorId` are set, and it disappears from the pending list — "a recorded dismissal, no further action" (AD-30 Rule 7).
4. **And** old links redirect to the survivor through Story 3.6v's existing alias mechanism, unchanged: `eventBySlug` already resolves `event_slug_aliases` on a canonical-slug miss (Task 6 of Story 3.6v) and both Next.js event-detail routes already redirect when the fetched event's `slug` disagrees with the requested one (Task 7 of Story 3.6v). **This story writes the correct alias rows (AC1) and needs zero new redirect code** — the only thing this story adds to that path is the data (B's old slug becomes an alias of A), not any new resolver/route logic. Verified by a regression test that merges two events and then requests B's pre-merge slug through both existing routes, asserting the already-built redirect still fires correctly for a merge-created alias, not only a promotion-created one (Story 3.6v only ever tested the promotion case).
5. **And** the suggested-match review list and its Accept/Reject/merge-confirmation UI live as a **fourth tab, "Duplicate Events,"** on the existing `/moderator/tools` `TabbedShell` (`apps/web/src/app/[locale]/moderator/tools/moderator-tools-content.tsx`) — after Actor Runs, Unprocessed Payloads, and Accounts (the tab Story 3.6g already added, left-to-right order unchanged) — reusing Story 4.7a's route guard (`useRequireModerator()`) exactly as the other three tabs already do, with no new shared layout. This resolves a genuine ambiguity between `EXPERIENCE.md`'s CC-024 pass (which calls this "two additions to the Moderator Tools tabbed shell") and that same document's earlier, more specific Component-Patterns entry for Shell B (which at the time of its own writing listed only two tabs and said `/moderator/items` stays separate) — **user-confirmed via `AskUserQuestion` during this story's creation**: a new tab here, not a new section on `/moderator/items`, both because it matches the CC-024 entry's literal route citation and because Story 3.6g already extended this same shell to a third tab once before without objection, establishing direct precedent. `EXPERIENCE.md`'s Shell B entry is amended (see Dev Notes) to list all four tabs.
6. **And** both the suggested-match-list **Accept** action requires an explicit confirmation step before it commits — a focus-trapping modal built on Story 0.47's new `ConfirmActionDialog` primitive (a hard prerequisite for this story), matching `EXPERIENCE.md`'s stated contract exactly: opening moves focus into the dialog; **Cancel** returns focus to that row's Accept button, dialog closes, nothing else happens; **Confirm** commits the merge, closes the dialog, returns focus to that same Accept button, and only then does the Undo toast (AC7) appear and announce. **Reject** (AC3) needs no confirmation step at all.
7. **And** after a merge commits, an undo window opens matching the existing Soft Delete with Undo pattern exactly (`EXPERIENCE.md` State Patterns § Soft Delete with Undo, Accessibility Floor § Soft Delete with Undo (Notification Toast)) via the existing `useSoftDeleteWithUndo` hook/`SoftDeleteToaster` (Story 0.18) — same `{components.notification.undo_duration_ms}` (6000ms) timing, pause-on-hover/focus/AT-virtual-cursor-entry, live-region announcement, and non-color "marked" cue on the resolved suggestion row. The one difference from a plain soft-delete, already anticipated by `EXPERIENCE.md`: "Undo" here reverses the merge's **full** repoint set recorded in AC2's journal (links, favorites, calendar entries, reports, slug aliases, `notified_at`) — not a single-record restore — via a dedicated `undoEventMerge` mutation; this reversal logic is this story's own backend concern, not a new frontend interaction pattern.
8. **And** `Query.moderatorPendingItemCount` (the Moderator Pending-Item Badge, `apps/backend/src/schema/moderator.graphql`) is extended to also count pending (`status = 'pending'`) `event_match_candidates` rows, per the PRD's own 2026-10-02 amendment to that badge ("Suggested cross-post event matches awaiting moderator review... also count toward this same combined total") — a requirement the badge's own doc comment and the PRD already state, which this story is the one that can actually satisfy it (no suggestion rows existed before Story 3.6v, and no moderator-facing read of them existed before this story).
9. **And** `restoreEvent(id, action: RESTORE)` (the existing moderator soft-delete/restore mutation, `apps/backend/src/schema/resolvers.ts`) rejects with a clear error when the target event has `merged_into_event_id IS NOT NULL`, directing the caller to use `undoEventMerge` instead — a merged event's restore path is not a plain soft-delete, and un-deleting it through the generic mutation would leave it "active" with none of its favorites/calendar entries/links (all already repointed to the winner), a broken state this story must not leave reachable just because the generic mutation technically still accepts the id.
10. **Explicitly out of scope (user-confirmed via `AskUserQuestion` during this story's creation):** a free-form "pick any two arbitrary events and merge them" manual flow (`EXPERIENCE.md`'s "direct duplicate-cleanup flow" phrase) — this story builds only the suggested-match-list-driven path (AC1-AC3). `epics.md`'s own AC text for this story never described a manual picker either. Tracked forward as **IDEA-061** (see Change Log) for a future story, not built here.

**Depends on:** Story 3.6v (status: `review` — standing rule accepts), Story 4.7b (status: `review` — standing rule accepts), **Story 0.47** (new — "Build the reusable ConfirmActionDialog primitive," a hard prerequisite for AC6, created by this story's own Gate 2 finding; must reach `review`/`done` before this story's Task 5 can complete).

- [ ] **Task 2 (AC1, AC2, AC9) — Backend: the merge + undo write module.** New `apps/backend/src/lib/events/merge-events.ts`:
  - `export async function mergeEvents(executor: DbExecutor, winnerId: string, loserId: string, moderatorId: string, suggestionId: string | null): Promise<{ merge: EventMergeRow; winner: EventRow }>` — reject if `winnerId === loserId`, if either event is already soft-deleted/merged, or if `loserId === <some event already pointing mergedIntoEventId at winnerId's own merged target>` (a merged event is never itself a valid winner or loser again — the "winner must not itself be merged" rule, AD-30 Rule 9). Inside one `executor.transaction`-composable sequence (this function takes an injected `executor`/`tx`, same `DbExecutor` type `set-event-primary-post.ts` already exports and this file imports, so a caller — the resolver — wraps the whole call in `db.transaction(...)`):
    1. Read both event rows and both events' current schedules.
    2. **Favorites:** select B's active favorites; for each, check whether A already has an active favorite for the same `userId` — if yes, soft-delete B's row (`deletedAt = now()`) and record its id in `dedupedFavoriteIds`; if no, `UPDATE favorites SET eventId = winnerId WHERE id = ...` and record its id in `repointedFavoriteIds`.
    3. **Schedule mapping (reusing the exact same date-match-or-copy logic Story 3.6v's `mergeSchedules` already established, extracted into a small shared helper rather than re-implemented — see Dev Notes "Reuse, not duplicate")**: for each B schedule, find an A schedule with the same `eventStartDate`; if found, that's the target; if not, insert a copy of B's schedule onto A (never mutating B's own schedule row — unlike enrichment, a merge does not need to update A's schedule fields from B's, since both schedules remain independently readable from each event's own JOIN until B is excluded by `activeOnly`). Build a `Map<loserScheduleId, winnerScheduleId>`.
    4. **Calendar additions:** select B's active `calendar_additions`; for each, resolve its target winner schedule via the map from step 3; check whether A already has an active `calendar_additions` row for the same `(userId, targetScheduleId)` — if yes, soft-delete B's row and record its id in `dedupedCalendarAdditionIds`; if no, `UPDATE calendarAdditions SET eventId = winnerId, scheduleId = targetScheduleId WHERE id = ...` and record `{ id, previousScheduleId: <B's original scheduleId> }` in `repointedCalendarAdditionIds`.
    5. **Reports:** `UPDATE reports SET eventId = winnerId WHERE eventId = loserId` (no dedup — `reports` carries no per-user uniqueness constraint; see Dev Notes "Why reports need no dedup logic"), collecting the updated ids into `repointedReportIds`.
    6. **`event_posts`:** select B's `event_posts` rows; for each whose `postId` is **not** already linked to A, `UPDATE eventPosts SET eventId = winnerId WHERE eventId = loserId AND postId = thatPostId` (the `(postId, extractionOrdinal)` unique index is unaffected — only `eventId` changes, `postId`/`extractionOrdinal` stay as they were) and record the `postId` in `repointedEventPostIds`; for each whose `postId` **is** already linked to A, leave B's row untouched (AC1). No ordinal reassignment is needed (unlike AD-30 Rule 8's deletion-triggered promotion case) — see Dev Notes.
    7. **Slug aliases:** insert `{ slug: loserEvent.slug, eventId: winnerId }` into `eventSlugAliases` (B's own slug becomes a permanent alias of A); `UPDATE eventSlugAliases SET eventId = winnerId WHERE eventId = loserId` for every existing alias that targeted B, collecting the updated ids into `repointedAliasIds`.
    8. **`notified_at`:** if B's `notifiedAt` is non-null and (A's is null or later than B's), set `winnerNotifiedAtChanged = true`, record A's prior value in `winnerPriorNotifiedAt`, and `UPDATE events SET notifiedAt = loserEvent.notifiedAt WHERE id = winnerId`.
    9. Soft-delete B: `UPDATE events SET deletedAt = now(), mergedIntoEventId = winnerId WHERE id = loserId`.
    10. Insert the `eventMerges` journal row with every array/marker collected above plus `loserPriorSlug = loserEvent.slug`, `loserPriorNotifiedAt = loserEvent.notifiedAt` (its value **before** any change in this function — there is none, since this function never mutates B's own `notifiedAt`, only reads it for step 8's comparison; recorded anyway so `undoEventMerge` has a single source of truth rather than re-deriving "B's notifiedAt was always X").
    11. If `suggestionId` is non-null, `UPDATE eventMatchCandidates SET status = 'accepted', resolvedAt = now(), resolvedByModeratorId = moderatorId WHERE id = suggestionId`.
    12. Return the inserted `eventMerges` row and the re-selected winner event row.
  - `export async function undoEventMerge(executor: DbExecutor, mergeId: string, moderatorId: string): Promise<EventRow>` — load the `eventMerges` row (404 if missing or already `undoneAt IS NOT NULL`); inside one transaction:
    1. `UPDATE events SET deletedAt = null, mergedIntoEventId = null, slug = merge.loserPriorSlug, notifiedAt = merge.loserPriorNotifiedAt WHERE id = merge.loserEventId`.
    2. If `merge.winnerNotifiedAtChanged`, `UPDATE events SET notifiedAt = merge.winnerPriorNotifiedAt WHERE id = merge.winnerEventId`.
    3. `DELETE FROM eventSlugAliases WHERE slug = merge.loserPriorSlug AND eventId = merge.winnerEventId` (removes the alias this merge created in step 7 above — now redundant since the loser's own slug is live again).
    4. For each id in `merge.repointedAliasIds`: `UPDATE eventSlugAliases SET eventId = merge.loserEventId WHERE id = id`.
    5. For each id in `merge.repointedFavoriteIds`: `UPDATE favorites SET eventId = merge.loserEventId WHERE id = id`. For each id in `merge.dedupedFavoriteIds`: `UPDATE favorites SET deletedAt = null WHERE id = id`.
    6. For each `{ id, previousScheduleId }` in `merge.repointedCalendarAdditionIds`: `UPDATE calendarAdditions SET eventId = merge.loserEventId, scheduleId = previousScheduleId WHERE id = id`. For each id in `merge.dedupedCalendarAdditionIds`: `UPDATE calendarAdditions SET deletedAt = null WHERE id = id`.
    7. For each id in `merge.repointedReportIds`: `UPDATE reports SET eventId = merge.loserEventId WHERE id = id`.
    8. For each `postId` in `merge.repointedEventPostIds`: `UPDATE eventPosts SET eventId = merge.loserEventId WHERE eventId = merge.winnerEventId AND postId = postId`.
    9. If `merge.suggestionId` is non-null, `UPDATE eventMatchCandidates SET status = 'pending', resolvedAt = null, resolvedByModeratorId = null WHERE id = merge.suggestionId` (the suggestion becomes reviewable again).
    10. `UPDATE eventMerges SET undoneAt = now() WHERE id = mergeId`.
    11. Return the restored loser event row. Schedules copied onto the winner during the original merge (step 3 above) are deliberately **not** deleted by undo — they are harmless, unreferenced leftovers once their `calendar_additions` repoint is reversed (see Dev Notes "Why copied schedules are never deleted on undo").
  - Unit/integration-test every branch: favorites repoint vs. dedup-soft-delete; calendar additions repoint (both date-matched and copied-schedule targets) vs. dedup-soft-delete; reports always repoint; `event_posts` repoint vs. untouched-on-B; alias insert + repoint; `notified_at` both directions (B's wins, A's wins, neither changes); the full undo path restores every one of the above exactly; undo-after-undo (already `undoneAt` set) is rejected; merging an already-merged or already-soft-deleted event on either side is rejected.

### Design decisions made directly during this story's creation (mechanical — not put to the user)

1. **Winner/loser direction for an accepted suggestion.** `candidateEventId` (the pre-existing event) is always the winner (A); `eventId` (the newly-ingested mid-confidence event) is always the loser (B). AD-30 Rule 9's general merge mechanic designates winner/loser by moderator choice, but the suggested-match list has only one directionality to offer per row (a suggestion already names which event is "the existing one" vs. "the new one") — reusing the already-established-in-the-system event as the survivor is the only sensible default here, and no data is lost regardless of direction (every table is repointed, AC1), so this carries no real user-facing stakes. A future direct/manual-merge story (IDEA-061) would need to let a moderator choose explicitly, since it has no suggestion row to inherit direction from.
2. **No ordinal reassignment during `event_posts` repoint (Task 2 step 6).** AD-30 Rule 8's "assign the post's next free ordinal" logic applies specifically to the deletion-triggered promotion path, where a post's slot must stay keyed by `(postId, extractionOrdinal)` consistently under a *changing* primary. A merge's `event_posts` repoint only changes which `eventId` a link row belongs to — `postId`/`extractionOrdinal` are untouched, so the existing unique index is never at risk and no reassignment logic is needed.
3. **Why reports need no dedup logic.** Unlike `favorites` (`unique(userId, eventId)`) and `calendar_additions` (`unique(userId, scheduleId)`), the `reports` table has no per-reporter uniqueness constraint — a user can file multiple reports against the same event today. Repointing every one of B's reports to A therefore cannot violate any constraint, and "deduplicated per user" (epics.md's own AC wording) is naturally satisfied by the fact that both rows end up correctly grouped under the same (now-merged) event in the existing `moderator-items-content.tsx` `reportsByEventId` grouping — no additional application-level merge-or-drop logic is written.
4. **Why copied schedules are never deleted on undo.** Task 2's merge step may copy a B schedule onto A (when no date-matching A schedule exists). Undo reverses the *calendar_additions* repoint (back to B's original schedule, which was never touched or deleted), leaving the copied A schedule orphaned-but-harmless — exactly the same "never delete, even if now unreferenced" posture AD-30 Rule 9 already mandates for a schedule a `calendar_additions` row references, applied here by omission rather than an explicit guard (there is simply no deletion step to add one to).
5. **`suggestedEventMatches` query has no `status` filter parameter.** Unlike `queryModeratorAccountProfiles` (a general filterable connection), this query always returns only `status: PENDING` rows — matching `pendingDefaultLocationChanges`/`pendingAccountTypeClassificationReviews`'s simpler, single-purpose precedent. There is no current need to list already-accepted/rejected suggestions anywhere in the UI.
6. **Why `mergeEvents`/`undoEventMerge` are not exposed as their own top-level GraphQL mutations.** Only `resolveSuggestedEventMatch`/`undoEventMerge` are exposed (Task 3); the former wraps the internal `mergeEvents()` function rather than exposing `mergeEvents(winnerId, loserId)` directly, since AC10 scopes this story to the suggestion-driven path only — an unused, untested-by-any-UI raw `mergeEvents` mutation would be speculative surface. IDEA-061's future story can expose it directly, reusing this same internal function unchanged.

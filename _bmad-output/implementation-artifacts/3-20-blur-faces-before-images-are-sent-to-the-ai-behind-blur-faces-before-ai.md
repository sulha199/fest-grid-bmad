# Story 3.20: Blur faces before images are sent to the AI, behind `BLUR_FACES_BEFORE_AI`

## Story Details

- Epic: 3
- Story ID: 3.20
- Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a bystander who appears in a post's photo,
I want my face blurred before the image leaves FestDaily for the AI vendor,
so that an identifiable face is not exposed to a vendor that may use free-tier content for product improvement (the extraction keys include subscribers' own keys whose billing tier is not verified).

## Acceptance Criteria

1. **Given** a new backend setting `BLUR_FACES_BEFORE_AI` (boolean, **default on** — only an explicit `false`/`0`, case-insensitive and trimmed, turns it off; parsed in `apps/backend/src/env.ts` beside `faceBlurMinRemainingTimeMs`; set explicitly in `aiProcessorLambda`'s environment block only, in `apps/infrastructure/lib/festgrid-backend-stack.ts`, with an infra test asserting it), **when** the setting is on and the post's owner has not opted in, **then** every image sent to Gemini — the cover and each carousel slide, up to `MAX_CAROUSEL_IMAGES` — is passed through Story 3.6n's WASM detect-and-blur (`detectAndBlurFacesSeam`) at original resolution first, **one image at a time**, and the *blurred* bytes replace the original bytes in the request's inline image parts.
2. **And** the **owner opt-in exception** applies: the owner is the account with role `PUBLISHER` on the post (`post_account_associations`, AD-31), never a co-author; if that account has `isImageStorageOptedIn = true` (**any** `imageStorageOptInSource`, `MODERATOR` or `ACCOUNT_OWNER`) the original image is sent unchanged and no pre-AI blur runs. A post whose publisher is unverified (`PUBLISHER_UNKNOWN`, or no `PUBLISHER`/`PUBLISHER_UNKNOWN` row at all) counts as **not** opted in. The role is read via a fresh, dedicated DB query in `processAiJob` — never the existing `message.accountId`/`posts.accountId` read already used for the Story 3.6e rehost gate (that column is not always the PUBLISHER; see Dev Notes).
3. **And** the stage **fails closed**: if detection or blur fails, times out, or the remaining-time budget (`FACE_BLUR_MIN_REMAINING_TIME_MS`) is too low before an image, that image is **not sent** — a failed carousel slide is dropped (the existing per-slide try/catch already does this for a fetch failure; the same path now also covers a blur failure), a failed cover makes the request caption-text-only (the existing text-only fallback path in `build-gemini-request.ts`) — and the original is never the fallback. Each failure is logged with the post id and image index.
4. **And**, with the setting off or an opted-in owner, the Gemini request is **byte-for-byte what it is today** (regression test), and `imageBytes` returned for Story 3.6e's re-host stays the original, unblurred bytes.
5. **And** the request builder also returns the blurred cover bytes and the cover's face count so Story 3.21 can reuse them (no second detection) — new, additive fields on `BuildGeminiExtractionRequestResult`, never required/consumed by this story's own callers.
6. **And** peak memory and total time are re-measured with a **six-image** post (the cover plus five slides: `MAX_CAROUSEL_IMAGES` caps only `additionalImageUrls`, so the worst case is six images, not five) against Story 0.46's 2 GB Lambda and the 300 s limit, and recorded in Dev Notes, including whether the WASM heap grows across six sequential detections.
7. **And** an **extraction parity check** runs six real posts through extraction twice (original vs. blurred), each arm run multiple times (default 3, overridable), and records any difference in event count, grouping, names and dates: the four CC-024 reference posts plus `https://www.instagram.com/suzurunberiman/p/Dd6SHRZzxI8/` and `https://www.instagram.com/merapiperformance/p/DdVwNyFATse/`. The two new posts have no recorded expected result, so their baseline is the extraction of the **original** image, which the user reviews and confirms as correct before it is used for comparison. Each run **re-scrapes the posts fresh** (`poc-ingestion-preview.ts --url <post-url> --force`) since the signed image links expire. **No post image is committed** (they show real people's faces): only extraction outputs and the compared differences are recorded, in a new `cc-028-blur-parity-posts/` folder beside `cc-024-reference-posts/`. A **material difference** (the blurred arm yields a result the original arm never did, across the repeated runs) **stops the dev** and is raised to the user; it is never a silent pass.
8. **And** unit and integration tests cover: setting parsing (default, `true`, `false`, `0`, case-insensitivity/trimming), per-slide blur and the carousel cap, the opted-in-owner skip, a co-author's opt-in being ignored, an unverified publisher being blurred, fail-closed for a slide, for the cover, and for the time budget, and that detection never runs on two images at once (sequential, not parallel).

- **Current flow (`processAiJob`, unchanged parts).** 1. look up `subscriberUserIds` + the account row (`accountType`, `isImageStorageOptedIn` — this read stays as-is, it still serves step 7.5a's rehost gate, which this story does not touch). 2. `buildGeminiExtractionRequest(message)` — fetches the cover, then up to `maxCarouselImages` slides, each in its own try/catch. 3. `callGeminiSeam`. 4-5. parse/AJV-validate; `isEvent: false` or zero events → write an audit row and return. 5.6-7. per-event loop (timezone/location resolution, `transformGeminiResponseToEventInfo`). 7.5 persist grouping facts. **7.5a** rehost (opted-in only, keyed on `message.accountId`). **7.5b** Story 3.6n's face-blur **thumbnail** stage: gated on `payload.hasFaceImage === true` (a model self-report, after the call), then 3.6o's relevance gate (needs extracted dates — only exists after the call), then the timeout-guard, then `detectAndBlurFacesSeam` + `uploadFaceBlurThumbnailSeam`. **This story's new pre-AI blur runs entirely inside step 2** (`buildGeminiExtractionRequest`), **before** the Gemini call — a completely separate call to the same `detectAndBlurFacesSeam`, for a different purpose (what gets *sent*, not what gets *stored*), reusing the exact same detection+blur primitive. Story 3.21 later teaches step 7.5b to reuse this story's blurred cover bytes instead of detecting a second time — out of scope here (see Out of Scope).

- **Why a builder *option*, not a builder-wide blur (Amendment, CC-028 readiness sweep Finding 1).** `buildGeminiExtractionRequest` has **four** callers today: `processAiJob` (the only one with Lambda-level `sharp`/WASM/model-weight bundling, 2 GB/300 s), `resolvers.ts`'s `extractEventDataFromUrl` at two sites (Story 4.2a, inside the 128 MB/30 s API Lambda, no image runtime), and `scripts/poc-ingestion-preview.ts`. Blurring unconditionally inside the builder would break the other three callers (no WASM/model bundle in the API Lambda) or silently change their behavior. The option is threaded as a second, optional argument so the three other callers are **completely unaffected** (they simply never pass it) and AC4's "byte-for-byte when off" is a structural property of the function signature, not a runtime flag that could drift.

- **Why the PUBLISHER opt-in needs a fresh query, not the existing `isOptedIntoImageStorage` read.** `processAiJob` already reads `isImageStorageOptedIn` via `message.accountId` (= `posts.accountId`) for the existing step-7.5a rehost gate. But `persist-scraped-post.ts` writes `posts.accountId = publisherProfileId ?? accountId` (falling back to the **scraping** account when no publisher resolved) — so `posts.accountId` is not reliably the PUBLISHER. Reusing that read for this story's gate would let a scraping account's own opt-in unblur a post it didn't actually publish — a privacy regression this story must not introduce. `resolvePostPublisherOptIn` (Task 2) queries `post_account_associations` for the `role = 'PUBLISHER'` row specifically (never `'PUBLISHER_UNKNOWN'`), joined to that account's `isImageStorageOptedIn`. The partial unique index `idx_post_account_associations_one_publisher_per_post` (`role IN ('PUBLISHER','PUBLISHER_UNKNOWN')`, `packages/database/schema.ts` ~line 392) guarantees at most one such row exists, so the query never needs its own `.limit(1)` disambiguation logic beyond what the index already enforces. Reading fresh (not from the SQS `ProcessingJobMessage`) also means a **revoked** opt-in is honored even for a message already in flight — no message-shape change needed.

- **The blur-before-AI stage vs. Story 3.6n's thumbnail stage are two independent call sites of the same primitive, by design.** Both call `detectAndBlurFacesSeam` from `detect-and-blur-faces.ts`, but at different points (before vs. after the Gemini call) for different images in different states (every sent image vs. just the cover, gated on different signals). This story does not change `detect-and-blur-faces.ts` itself — `FACE_BLUR_SIGMA`, the SSD MobileNetV1 model, the sharp-based composite-and-blur logic are all reused verbatim. Story 3.21 later **removes** the duplication for the cover specifically (reusing this story's blurred cover bytes for the thumbnail instead of a second detection) — this story does not attempt that consolidation itself, since 3.21 needs its own migration (`extraction_audit_logs.ai_image_input`) to record which path ran.

- **Time budget threading.** `buildGeminiExtractionRequest` has no `Context` today. `getRemainingTimeInMillis` is threaded through the new `options.blurFacesBeforeAi` object (not a new top-level parameter), sourced from the same `ProcessAiJobDeps.getRemainingTimeInMillis` Story 3.6n already added to `processAiJob` — no second Lambda-context plumbing path is introduced.

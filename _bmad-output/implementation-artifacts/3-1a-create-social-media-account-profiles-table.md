# Story 3.1a: Create social media account profiles table

## Story Details

- Epic: 3
- Story ID: 3.1a
- Story Key: 3-1a-create-social-media-account-profiles-table
- Status: ready-for-dev

## Story

As a developer,
I want a `social_media_account_profiles` table (matching the PRD's `SocialMediaAccountProfile` interface, PRD §4.5) that is shared across every subscriber of an account, with `subscriptions` narrowed to a pure per-user join (`id`, `userId`, `accountId` FK, `isNewlyAdded`, `createdAt`, `deletedAt`) instead of duplicating platform/displayName/username/profileImageUrl/description/lastPostDate on every subscriber's row,
so that account-level data — starting with `defaultLocation` (FR66/FR67, Story 3.3/3.3b) — has exactly one row per account instead of being ambiguously duplicated per subscriber.

## Acceptance Criteria

1. **Given** Story 1.1's tables exist, **when** the migration script runs, **then** a `social_media_account_profiles` table is created with `id` (uuid pk), `account_id` (text, not null — the platform-native identifier, e.g. a Twitter User ID or Instagram account ID), `platform` (text, not null), `username` (text, not null), `display_name` (text, not null), `profile_image_url` (text, nullable), `description` (text, nullable), `last_post_date` (timestamp, nullable), `default_location` (jsonb, nullable), plus standard `created_at`/`updated_at` timestamps. **And** `account_id` is unique per `platform` (a compound unique constraint on `(platform, account_id)`, not a bare unique on `account_id` alone).
2. **And** the `subscriptions` table is migrated to drop `accountId` (text), `platform`, `displayName`, `username`, `profileImageUrl`, `description`, `lastPostDate`, replacing them with a single `accountId` (uuid, FK to `social_media_account_profiles.id`, not null); `subscriptions` becomes the pure per-user join row described by the amended PRD §4.9. No production user data exists yet (Story 1.2's fixtures are dev/test-only per Story 1.2a's precedent), so this is a destructive schema change, not a backfill migration.
3. **And** `subscriptions.deletedAt` (timestamp, nullable) is added per AD-8 (Soft-Delete Convention) — the first consumer is Story 5.1a's `removeSubscription` mutation. **And** a partial index `idx_subscriptions_active ON subscriptions (user_id) WHERE deleted_at IS NULL` is added, matching the exact index AD-8 rule 3 already names for this table (hand-edit required — see Data Type Compatibility section).
4. **And** subscribing to an account that has no existing `social_media_account_profiles` row (matched by `platform` + `account_id`) creates one; subscribing to an already-profiled account only creates a new `subscriptions` join row — this lookup-or-create logic is exposed for Story 3.1/3.2's mutation to call, not reimplemented per-story.
5. **And** `packages/shared-types`'s `Subscription` and `SocialMediaAccountProfile` interfaces are added/updated to match.
6. **And** the `posts` table (Story 1.2a, Epic 1 — already exists by the time this story runs) is migrated: add `account_id` (uuid, FK to `social_media_account_profiles.id`), drop `subscription_id`, make `account_id` not null, with an index on `account_id` replacing the old `subscription_id` index. Story 1.2a itself is intentionally left creating `posts.subscription_id` — Epic 1 must stay buildable without this story existing yet; this story evolves the column once it runs.
7. **And** a new, unauthenticated `socialMediaAccountProfileByAccountId(platform, accountId)` query is exposed, returning the profile (including its internal `id`) — this is the lookup Story 3.11's public account page uses to resolve a URL's `platform`/`accountId` to the profile row, and it is deliberately not behind `requireAuth` (Story 0.17), since the account page itself is public.
8. **And** the lookup-or-create logic's check for an existing subscription join row (to decide "already subscribed" vs. "create new") excludes soft-deleted rows via `activeOnly(table)` (Story 0.22), not a hand-written `isNull(...)` clause.
9. **(Added by this story's Data Type Compatibility audit, 2026-08-07):** `subscriptions.isNewlyAdded` (boolean, default `true`, not null) is added. Story 3.2's AC requires subscriptions to be "created with `isNewlyAdded: true`," and Story 5.1a's `mySubscriptions` query/`markSubscriptionViewed` mutation read and clear this flag — but no story in `epics.md`, including this one's original AC list, ever defines the column it lives on. Since this story is the one that finalizes `subscriptions`'s post-migration shape, the column is added here rather than left for Story 3.2 to discover missing. See Data Type Compatibility section below.

**Depends on:** Story 1.1, Story 1.2a (for the `posts` table this story migrates), Story 0.22.

### Data Type Compatibility & Migration Requirements

- **Compatibility finding 1 (the `isNewlyAdded` gap, AC9):** `epics.md`'s Story 3.2 AC requires subscriptions to be "created with `isNewlyAdded: true`," and Story 5.1a's `mySubscriptions` query/`markSubscriptionViewed` mutation read and clear that flag per-subscription. The PRD's own §4.9 `Subscription` interface and this story's original AC list (before this audit) never actually placed the column anywhere — the PRD's §4.5 `SocialMediaAccountProfile` interface lists `isNewlyAdded` instead, which is incorrect for its intended meaning: it is explicitly a per-user "auto-activate this subscriber's tab" flag (PRD §4.5's own doc comment: "Used to auto-activate the tab in the post selection screen"), so it cannot live on the account-level profile row shared across every subscriber — one subscriber's "newly added" state would leak to every other subscriber of the same account. Since this story is the one that finalizes `subscriptions`'s post-migration shape, the column is added here (Task 2/AC9) rather than leaving Story 3.2 to discover the gap.
- **Compatibility finding 2 (the `idx_subscriptions_active` index):** AD-8 rule 3 in the architecture spine already explicitly names the target index for this table (`CREATE INDEX idx_subscriptions_active ON subscriptions (user_id) WHERE deleted_at IS NULL;`) — this story is the one that adds `subscriptions.deletedAt` (AC3), so it is also the one responsible for adding this index, using the same hand-edit-after-generate workaround already applied to `idx_user_locations_active` (`packages/database/migrations/0009_lumpy_blizzard.sql`) and `idx_favorites_active`, since the installed `drizzle-kit` still drops `.where()` clauses on generation (`drizzle-orm#3349`, confirmed still open).
- **Impacted fields/contracts:** `subscriptions` table (DB — full reshape), new `social_media_account_profiles` table (DB), `posts.subscription_id` → `posts.account_id` (DB), `Subscription` (new) and `SocialMediaAccountProfile` (updated) interfaces in `packages/shared-types`, `packages/database/seed.ts`'s fixtures and insert/delete ordering, `seed.integration.test.ts`'s assertions, the new `apps/backend/src/lib/subscriptions/subscribe-to-account.ts` function, and the new `socialMediaAccountProfileByAccountId` GraphQL query/resolver.
- **Required DB migration changes:** One `drizzle-kit`-generated migration (AD-3) covering: `CREATE TABLE social_media_account_profiles` (with the compound unique constraint), the full `subscriptions` reshape (drop 6 columns, add `account_id` uuid FK + `is_newly_added` + `deleted_at`), and the `posts` reshape (drop `subscription_id`, add `account_id` uuid FK not null) — per Tasks 1-3/5. The partial index on `idx_subscriptions_active` requires the hand-edit described above. Because `subscriptions.accountId`'s type changes from `text` to `uuid` FK with no valid backfill source (no `social_media_account_profiles` rows exist for old fixture data), and `posts.account_id` similarly has no backfill source until `subscriptions.accountId` is already migrated, this migration cannot preserve existing local fixture rows — Task 5 documents the required truncate-then-reseed sequence for any local dev DB that already has data from a prior `pnpm run seed`. This is safe because no production data exists yet (per AC2's own framing) and `packages/database/seed.ts`'s transactional seeding is idempotent by design.
- **Required TypeScript type changes:** `packages/shared-types`'s new `Subscription` interface and updated `SocialMediaAccountProfile` interface (Task 6) — see Compatibility finding 1 for the `isNewlyAdded` placement rationale. `Post` is intentionally left unchanged (no consumer reads a `Post`-level account reference through the API yet; Story 1.2a already established the precedent of deferring DB-only fields on this interface until a real consumer needs them).
- **Backward compatibility and rollout notes:** No production data exists, so there is no live-data rollout concern — only the local/CI dev-DB truncate-then-reseed sequence noted above (Task 5). `posts.account_id` and `subscriptions.account_id` are both `not null` from the start (no nullable-then-backfill-then-not-null two-step needed) precisely because there is no data to preserve.
- **Verification checks:** Task 12's extended `seed.integration.test.ts` proves end-to-end alignment for the reshaped tables (row counts, id sets, and new FK-orphan checks for `posts→social_media_account_profiles` and `subscriptions→social_media_account_profiles`) on both a first and idempotent second seed run. Task 13's new integration test proves the lookup-or-create function's actual behavior (profile reuse, subscription dedup via `activeOnly`, soft-delete exclusion) end-to-end against a real DB, not just at the schema level.

- (direction) Intent agreed with user 2026-11-09 (route: spec, then architecture decision before code). Cursor loop chosen over an upfront scout+plan: each step extracts a slide window, returns events plus a cursor, and code decides whether to continue.
- (constraint) Supersedes AD-13 Rule 1 (one Gemini request per post, always) and Rule 3 (completeness is a signal, never a driver; a multi-call loop was rejected, revisit if the batched cap proves insufficient) and amends AD-30 Rule 5 (one call per post; per-post event cap default 10). Evidence the cap is insufficient: post DfLcqoqj-al, cover+13 slides, '203 events', yielded 8 events. Only posts selected by the continue rules leave the one-request path.
- (constraint) AD-13's rationale still binds: request count multiplies against Gemini RPM/RPD quotas of the keys used (the AI gateway picks subscriber BYOK keys by tier, then the system key). Caps bound it.
- (capability) CAP-1 Scout: the first request of a multi-image post also returns a small cursor/postPlan (claimedItemCount, per-slide role intro/list/outro/ad, items per list slide, ordering and date range covered, whether more items are likely).
- (capability) CAP-2 The continue decision lives in code and is a pure, unit-tested function of cursor + result (rules table in SPEC).
- (capability) CAP-3 Each step is its own queue message carrying the cursor (stateless); it fits the per-message budget of PR #180 (45s budget, blur floor 60s + 40s margin); a redelivered step is idempotent.
- (capability) CAP-4 Probe-and-split safety net: the Gemini client exposes finishReason and candidatesTokenCount; truncation or at-risk output splits the window and retries down to 1 slide; a parse failure is no longer a silent drop.
- (capability) CAP-5 Later steps add events to the same post, deduped by normalized name + start date, as roundup stubs; (post, ordinal) idempotency (AD-30 Rule 3) holds across steps.
- (capability) CAP-6 Hard caps as env values (max extra steps default 6, max events per post default 120; no daily cap); a tripped cap marks the post partial and logs which cap fired.
- (capability) CAP-7 A failed step leaves the post partial with its cursor so extraction can resume while image URLs are valid (about 5 days).
- (capability) CAP-8 program-lineup / dependent-stages posts with unread slides get ONE follow-up call with all remaining slides (up to 10 images total), not chunking, because their schedules merge into one event.
- (capability) CAP-9 Roundup stub pages show an 'Also in this roundup' sibling list and, only when known partial, a 'Showing N of the events listed in this post' note linking to the source post; ordinary events are unchanged.
- (capability) CAP-10 Per-step observability: slides read, events added, tokens, finishReason, and which rule stopped the loop.
- (decision) Continue rules: chunk only when groupingReason is roundup or separate-events AND unread slides remain; also continue when the scout found 0 events and slides remain (text-free cover), max 2 empty steps; program-lineup/dependent-stages -> one all-remaining-slides follow-up; single-event with a complete result stops; stop when a step adds no new events after content was found. Step size starts at 2 slides and adapts to observed items per slide; per-call event cap about 25 (8192 output tokens / about 250 per event).
- (decision) Per-post guards are insurance, not the decision mechanism (clues come from the model; the poster is untrusted input). Daily cap dropped (no evidence of spikes). A tripped guard marks the post partial.
- (decision) UX: sibling list from existing event_posts links; partial note only when known partial; no total count M unless the model reported it with confidence.
- (constraint) Evidence (prod, 60 days, 4,296 extracted posts): 209 (4.9%) exceed the read cap of cover+5; 138 of those are single-event/dependent-stages photo carousels (must not chunk); 12 roundups, 7 with <=3 images, 6 hit the 10-event cap. One-event posts with 3+ schedules: 134 of 2,784, 58 single-image, max 20 schedules. 21-post experiment (single runs, noisy): 2 images mislabelled a roundup and a 4-event post; 3 images labelled both roundups roundup/separate-events; schedule counts grew with slides in 2 of 8 multi-schedule events; 2 of 8 big carousels had text-free first slides.
- (constraint) Cost (token counts measured, prices third-party $0.30/M in, $2.50/M out): system prompt 4,637 tokens, image about 1,120, output about 195-255 per event; ordinary post about $0.0025, URUP-scale roundup about $0.14. Output dominates, so reading images is cheap and event count is the lever. Thinking tokens not measured.
- (constraint) Face blur stays fail-closed (AD-28): each step blurs only its own images and never sends unblurred bytes. additionalImageUrls stay extraction-time-only and never durable (AD-13 Rule 2). Stub events never notify (AD-30 Rule 10).
- (constraint) Any addition to the Gemini response schema must be verified live: adding maxItems made Gemini reject the whole request with 400 INVALID_ARGUMENT once the item schema grew (build-gemini-request.ts comment). Added cursor fields are optional in the consumer AJV schema.
- (constraint) Model output is not trusted for limits: the prompt cap of 10 events was ignored (replays returned 17 and 26; AD-30 Rule 5 records 39 events in 4 of 9 runs, FIND-102); caps are enforced in code.
- (question) OPEN: default caps (max steps 6, max events 120): the 203-event example ends partial; confirm or raise.
- (question) OPEN (architecture decision): ordinal scheme for incremental steps. Options: (a) per-step ordinal ranges from a next-free ordinal carried in the cursor (precedent: AD-30 Rule 8 'next free ordinal max+1'; assignApplyOrdinals/PARKED_ORDINAL_BASE in apply-post-reextraction), (b) content-key idempotency (name + start date) replacing (post, ordinal). extraction_ordinal is smallint; unique (post_id, ordinal) and events(post_id, ordinal); the slug suffix follows the ordinal.
- (question) OPEN: GAP in the agreed scout. 'Scout = first 3 images' would read FEWER images in the first request than today (cover+5 = 6) and regress multi-schedule events with 4-6 images (their schedule counts grew with slides). 95% of posts have <=6 images and are already fully read. Recommendation: keep today's first-request window for every post and start the cursor after slide 6 (extra images cost about $0.0003 each); confirm.
- (question) OPEN: whose key pays and how many requests? Chunking multiplies requests against subscriber BYOK/system key quotas (AD-13 rationale). Also verify key tiers for ingestion: the system key secret festgrid-system-gemini-api-key-prod returned API_KEY_INVALID on 2026-11-09.
- (question) OPEN: partial/resume state: a new column (e.g. posts.extraction_partial) vs audit-row only; and who triggers resume (scheduled sweep, moderator Apply AD-40, or both).
- (assumption) Prompt and schema v2 (multi-date-row expansion for issue 2, locationContext for geocoding) lands first, or this spec depends only on the cursor/postPlan fields.
- (assumption) Sample sizes are small (21 posts, single runs); thresholds (3 images, 25 events per call, 90% token rule) are starting values to be tuned with the live regression harness.

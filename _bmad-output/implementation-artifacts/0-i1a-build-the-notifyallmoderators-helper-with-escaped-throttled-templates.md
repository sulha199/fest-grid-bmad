# Story 0.i1a: Build the notifyAllModerators helper with escaped, throttled templates

## Story

As a developer,
I want one `notifyAllModerators(templateKey, vars, options?)` helper that does the moderator lookup, the fan-out and the `moderatorReviewUrl` construction (today copied across three files), a single-recipient mode for a caller that must tell one moderator, an HTML-escaping fix in `render-template.ts` for every template, and a per-template, per-entity throttle,
so that no moderator-notification call site re-implements lookup, fan-out or escaping, no template can leak unescaped scraper- or user-influenced text into a moderator's inbox, and Story 10.13 (notify when a job finishes) has no blocker.

## Read this first (owner decisions that change the scope)

The full list is under "Decisions flagged for the owner" (Dev Notes). Four need the owner before a developer starts.

1. **No migration is planned (decision 1).** The throttle reuses the existing `alert_email_rate_limits` table (key text primary key, count, window start): one row per template and entity. The epic text for 0.i1a does not yet say so; this story adds that AC and does not edit `epics.md` (decision 12).

4. **Scope of migration of existing call sites (decision 4):** this story moves `send-dangerous-report-moderator-alerts.ts` and `send-scraper-provider-down-alerts.ts` onto the helper and deletes `get-moderators.ts`. ## Acceptance Criteria

Taken from `epics.md` Story 0.i1a; AC6 and AC7 are added by this story from the 2026-11-14 owner decision and from tracing the code. Sub-points marked "(design)" are this story's chosen mechanism.

1. **Given** any code path that needs to notify moderators of something, **when** it calls `notifyAllModerators(templateKey, vars)`, **then** it receives the same moderator lookup, fan-out and review-URL construction every other call site uses, with no duplicated logic at the call site. (design: the review URL is built only by the helper from `WEB_APP_BASE_URL` and a per-template path; a caller cannot pass `moderatorReviewUrl`.)
2. **And** `render-template.ts` HTML-escapes every interpolated field for every template, including `DANGEROUS_EVENT_MODERATOR_ALERT` and `SCRAPER_AUDIT_TRAIL_FAILURE_ALERT` (the template already exists in `packages/domain/src/email/templates.ts`; this story does not create it). (design: escaped in the `html` part only; the `subject` has line breaks and control characters removed; the plain `text` part is not escaped. Resolves FIND-021, render-template.ts has no HTML-escaping.)
3. **And** two calls for the same `templateKey` + entity within the cooldown window are deduplicated rather than sent twice. (design: one atomic claim in `alert_email_rate_limits` before any send; the second call returns `status: 'throttled'` and sends nothing.)
4. **And** the notification path is DB-backed, matching the decision already made for the sibling alert in Story 3.4q (fix the Bright Data auth failure and alert moderators when a scraper provider goes down): moderators come from the `users` table, mail goes through `sendTemplatedEmail`/SES, the throttle is a database row; no CloudWatch alarm or SNS topic.
5. **And** the helper writes the new architecture-spine invariant **AD-54** (one templated, throttled, escaped moderator-notification helper) covering BUG-003 (no email when a location change enters AWAITING_APPROVAL), FIND-020 (scraper audit-trail alert lacks throttling and dedup) and FIND-021.
6. **And (added, single-recipient mode)** `notifyAllModerators(templateKey, vars, { recipientUserId })` notifies only that user, and only if the user is an active moderator; any other id (a non-moderator, an unknown id, a soft-deleted user) is **refused**: nothing is sent, no throttle slot is spent, and the result says `refused_not_moderator`. It reuses the same escaping, throttle and template machinery; the throttle slot is per template, entity **and recipient**.
7. **And (added)** the helper never throws and always returns a typed result (`sent`, `failed`, `throttled`, `no_moderators`, `refused_not_moderator`, `error`), so a caller can act on it (Story 3.4r's provider alert marks itself sent only on `sent`).
8. **And** the existing duplicated lookup and fan-out in `send-dangerous-report-moderator-alerts.ts` and `send-scraper-provider-down-alerts.ts` is replaced by calls to the helper, and `get-moderators.ts` is deleted (decision 4). Behaviour that must not change: the dangerous-report resolver path still returns its normal result even if mail fails; the provider-down alert is still marked sent only after at least one moderator was mailed.

### Throttle design, and why this store fits

The need: at most one mail per (template, entity) per cooldown, safe under concurrent Lambdas. `alert_email_rate_limits` already gives an atomic, optimistic compare-and-swap per text key, proven by the `reportSystemError` budget, with the pure window rule shared with the AI-filter limiter. With `maxSends = 1` and the window set to the cooldown it is exactly "one per window per key". Reusing it means: no migration (so no clash with 0104 of Story 10.13), no new table to put row level security on, one concurrency mechanism in the codebase. Costs: (a) it is a **fixed** window opened by the first send, not a sliding "last sent" time, so a burst straddling a window edge can send two mails a few seconds apart (acceptable for alerts; recorded in decision 7); (b) one row per distinct entity (pruned, decision 9); (c) the table's name says "email", which is accurate (every moderator notification is an email today); if a push channel to moderators is ever added it needs its own key prefix, not a new store.

Claim-then-send order: the claim is taken before the sends so two parallel calls cannot both send. If every send then fails, the claim is released so the next occurrence is not silenced for a window for a mail nobody received (decision 8). If some sends succeed the claim stays (a moderator got it; re-sending to the rest would duplicate).

The throttle is deliberately **per entity** not per call site: Story 0.i1c's audit-trail alert uses the `source` as entity so repeated failures of the same write do not flood (FIND-020), while a different failing source still gets through.

### Escaping, precisely

- `html` part: every interpolated value is `escapeHtml(String(value))`. Template markup (`<p>`, `<strong>`, `<a href="{{moderatorReviewUrl}}">`) is the template author's and is not touched, because only the values are escaped. Quotes are escaped so a value inside the `href="..."` cannot break out of the attribute.
- `subject` part: a subject is a header; `\r\n` in a value is header injection. Values get control characters collapsed. HTML-escaping a subject would show `&lt;` to the reader, so it is not done.
- `text` part: `text/plain` is not interpreted by a mail client, so values are left as is (escaping would show `&amp;` to the reader). Decision 6 records this; the owner may ask for text to be left untouched or normalised differently.
- A URL variable placed in `href` is only protected against attribute break-out here, not against a `javascript:` scheme. Every URL variable today is built by the server (the helper's review URL from `WEB_APP_BASE_URL`, `apiKeyManagementUrl` from the web base URL); none is taken from scraper or user text. A future template that takes a URL from untrusted text needs a scheme check at its call site: noted for Story 0.i1z's reviewers, not built here (decision 6).
- Values are numbers or strings (`consecutiveFailureDays`, `confidenceScorePercent`); `String()` first, then escape, so a number never throws.

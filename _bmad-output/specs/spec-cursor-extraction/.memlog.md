- (decision) SUPERSEDES the 'scout = first 3 images' decision: the first request keeps today's window (cover + MAX_CAROUSEL_IMAGES slides, 6 images) for every post; the cursor starts after slide 6. Reason: 95% of posts have 6 images or fewer and are already fully read; a 3-image scout would regress multi-schedule events with 4-6 images (counts grew with slides); an extra image costs about $0.0003. User confirmed (use the recommendation).
- (decision) SUPERSEDES the per-post caps (max extra steps 6, max events 120): no tunable caps. The loop is bounded by construction: every step consumes at least one unread slide, splits only subdivide a window, so requests per post <= 2 x unread slides (about 28 for a 20-slide carousel); each response is bounded by the per-call event cap (about 25) and maxOutputTokens, and a runaway response is caught by finishReason. Replaced by (a) an invariant check that logs and stops if the bound is exceeded and (b) a kill-switch env value that disables the cursor loop (rollout and incident control). The per-post event cap of AD-30 Rule 5 (default 10) is lifted for posts on the cursor path; the per-call cap remains.
- (constraint) Transient provider errors are expected: 429 TooManyRequests and 503 ServiceUnavailable appear in the API key monitoring (user, 2026-11-09) and in our own Gemini calls (503 on 2026-11-09). A step that still fails after the gateway's key rotation is retried by the queue with a delay (redelivery, not an in-Lambda retry loop); steps of one post are serial, which spaces its requests.
- (question) OPEN, recommendation recorded: ordinal scheme. Recommend per-step ordinal ranges: the cursor carries the next free ordinal; the step assigns ordinals only after its window result is final; steps are serial so ranges cannot collide and a redelivered step reuses the same numbers (idempotent). Cross-step duplicates are removed by name + start date before numbering. Content-key identity was rejected: allocating 'max + 1' at insert races between parallel ingestion messages, and a unique violation is treated as an idempotent skip (AD-30 Rule 3), which would silently lose an event.
- (question) OPEN, recommendation recorded: partial/resume. Recommend one boolean on posts, set when a chain starts and cleared when the loop ends cleanly (a chain that dies stays flagged), and resume by redriving the dead-lettered step message (it carries the cursor) while the images are valid; no sweep job, no cursor column.

- (event) Re-derived SPEC and companions after user answers (scout window = today's window, no tunable caps, 429/503 constraint). Self-validate: coherence and preservation pass; open questions reduced to 2 (ordinal scheme, partial/resume), both with recorded recommendations.
- (direction) User 2026-11-09: asked how the 'about 28 requests for a 20-slide carousel' bound is derived; proposed numbering events by creation time (milliseconds apart) instead of an ordinal scheme; requires that resume of a partial post runs automatically with no human intervention.
- (note) Bound explained: the first request reads 6 images, so a 20-image carousel has 14 unread. Worst case every window is split down to single slides; a binary split of w slides takes at most 2w - 1 requests, so at most 2 x 14 - 1 = 27 extra requests (stated as 'about 28' = 2 x unread); typical is 7 steps of 2 slides.
- (decision) Ordinals stay per-step ranges (option A); numbering by event created_at rejected: the number must exist before the event (ingestion looks up (post, ordinal) before inserting, AD-30 Rule 3), and created_at reflects the race between parallel queue consumers, not the post's order, so a redelivered message could be numbered differently. Across steps ordinals already ascend in step (discovery) order, which gives the time ordering at step granularity; within a step the order stays (earliest start date, normalized name, original index), deterministic on redelivery.
- (decision) SUPERSEDES the 'dead-letter redrive by hand, no cursor column' recommendation: resume is AUTOMATIC. The cursor is persisted on the post (nullable jsonb, null when no chain is in flight or it ended) with the existing extraction claim timestamp. The AI Lambda's existing 5-minute poll-and-drain tick begins with a resume pass: posts with a cursor, a claim older than the claim TTL (30 minutes), images still valid and attempts below a limit get their next step re-enqueued from the cursor; attempts are counted in the cursor with growing delay. When the images expire or attempts run out the cursor is cleared and the post is flagged partial permanently (UI note). A dead-lettered copy of a step message is harmless: the step is idempotent through the cursor's ordinal range.
- (assumption) Resume starting values: claim TTL 30 minutes (existing POST_EXTRACTION_CLAIM_TTL_MINUTES), up to 6 resume attempts spaced by the 5-minute tick with growing delay, always bounded by the image expiry (about 5 days); tune with prod data.

- (direction) User 2026-11-09: before the final give-up, the automatic resume should also retry with a re-scrape when the images have expired, keeping the cursor throughout the retry and the re-scrape.
- (decision) Resume order before giving up: (1) queue retries of the step, (2) resume-pass attempts while images are valid, (3) when images are expired (or a slide fetch fails with 403/404/410) and slides remain, re-scrape the post for fresh image URLs, (4) only then clear the cursor and flag the post partial. The re-scrape replaces ONLY the image URLs held in the cursor; progress fields (next slide, next ordinal, events found, empty steps, attempts) and the persisted cursor stay untouched; the caption is never stored (AD-40) and the posts row is not rewritten.
- (constraint) Re-scrape is bounded and guarded: at most 2 per post, at least 10 minutes apart (REEXTRACT_RESCRAPE_COOLDOWN_MS precedent), only through the guarded vendor-call wrapper (AD-32), the account scrape gate (AD-34, isStoredPostAccountScrapable) and the one-scrape-per-URL lease (FIND-110, claimPostUrlScrape). Expiry is read from the URL itself (postImagesNeedRefresh / isImageUrlExpired in packages/domain). Scraper credit is metered (the prod Apify account is on a capped free plan), so a refused or failed re-scrape ends the post partial with the reason logged; no scrape retry loop.
- (constraint) The cursor's slide index is only valid if the fresh slide list has the same count and order as the stored one; if the count differs the post ends partial instead of resuming at a wrong slide.
- (assumption) Starting values for re-scrape: at most 2 per post, 10 minutes apart; a fresh scrape renews image validity by about 5 days.

# Story 0.23: Build the system error reporting and alerting foundation

## Story Details

- Epic: 0
- Story ID: 0.23
- Status: ready-for-dev

## Story

As a developer,
I want a generic, reusable backend mechanism — a `reportSystemError` GraphQL mutation and resolver — for reporting critical client-side errors (Service Worker registration failures, IndexedDB conflicts, or other unrecoverable frontend failures) that dispatches a developer/administrator alert email,
so that any current or future feature experiencing an unrecoverable client-side failure notifies the team through one shared, consistently-built pathway instead of each feature inventing its own error-alerting mutation and email template.

## Acceptance Criteria

1. **Given** Story 0.15's Outbound Email Adapter and its `EmailTemplateKey` enum (`QUOTA_EXHAUSTION_WARNING`, `INVALID_API_KEY_ALERT`, `DANGEROUS_EVENT_MODERATOR_ALERT`), **when** this story ships, **then** a 4th key, `SYSTEM_ERROR_ALERT`, is added with its own template (subject/html/text) rendering the error's `source`, `message`, `context`, and a server-generated `timestamp` to the configured developer/administrator email address. [epics.md AC1]
2. **And** a `reportSystemError(input: ReportSystemErrorInput!): Boolean!` mutation is added to the backend GraphQL schema, where `ReportSystemErrorInput` carries `source: String!` (e.g. `"service-worker"`, `"indexeddb"`), `message: String!`, and an optional `context: String` (e.g. serialized error details), each validated with AJV per the project's runtime-schema-validation rule (length-capped to prevent abuse, since this endpoint is reachable by any client regardless of auth state). [epics.md AC2]
3. **And** the resolver maps the validated input to the `SYSTEM_ERROR_ALERT` template and dispatches it exclusively through Story 0.15's Outbound Email Adapter interface (`sendTemplatedEmail`) — this story never calls a raw SMTP/provider SDK directly. [epics.md AC3]
4. **And** the mutation does not require `requireAuth` (Story 0.17) — unlike billed/quota-limited queries such as `addressAutocomplete`/`reverseGeocodePreview` — since a client can hit a critical Service Worker/IndexedDB failure before or without ever authenticating (e.g. during background FCM token registration), and it is still protected by the project-wide GraphQL depth/complexity limits (`@escape.tech/graphql-armor`, configured server-wide by Story 0.8). [epics.md AC4]
5. **And** a delivery failure inside the adapter (e.g. SES misconfiguration, or the recipient env var not being set) is caught and logged server-side (`console.error`) rather than thrown back to the caller, so a broken alerting path can never itself become a second client-facing failure — invalid *input* (failing AJV validation) is the one case that still surfaces a `BAD_REQUEST` `GraphQLError`, since that reflects a caller bug worth surfacing, not an alerting-pipeline failure. [epics.md AC5]
6. **And** no product feature calls this mutation in this story — it is a reserved, ready-to-consume capability, mirroring the "reserved slot" pattern of Stories 0.7/0.8/0.9/0.12/0.13/0.15. Story 2.10 ("Service Worker Lifecycle Updates and Database Self-Healing") is its first consumer. [epics.md AC6]
7. **Given** this story introduces the first-ever unauthenticated mutation and the first-ever resolver-level AJV integration in the codebase, **when** this story ships, **then** it is proven via: a `packages/domain` unit test achieving 100% coverage of the new `SYSTEM_ERROR_ALERT` template's rendering (Testing Rules — non-negotiable), and an `apps/backend` integration test (real GraphQL Yoga schema, mocked SES client via the existing `setSesClient` test-injection point) covering valid input (email dispatched, `true` returned), invalid input (AJV rejects, `BAD_REQUEST` thrown), unauthenticated access succeeding (no `UNAUTHENTICATED` error, unlike every other existing mutation), and a simulated SES failure being caught/logged without being thrown to the caller. [Derived — mirrors Story 0.15's AC5 testing-completeness precedent]

## Dev Notes

- **This story is pure backend infrastructure/plumbing — no product UI ships, and no feature story calls it yet.** Story 2.10 (currently blocked on this story's Task 3/4) is the first real, planned caller, wiring the frontend GraphQL document and dispatch call in its own separate story — this story never touches `apps/web`. Mirrors the "reserved slot, not implemented" pattern already established by Stories 0.7, 0.8, 0.9, 0.12, 0.13, and 0.15.
- **Why `reportSystemError` deliberately never calls `requireAuth`:** every one of the 8 existing mutations in `apps/backend/src/schema/resolvers.ts` calls `requireAuth(context)` — this will be the 9th mutation and the first that intentionally does not. This is a compliant use of AD-7 rule 3 ("Single enforcement surface": `requireAuth`/`requireModerator` are the *only sanctioned way* to enforce login *if* a resolver wants to — it does not mandate every resolver enforce it). A client can hit a broken Service Worker/IndexedDB path before ever authenticating, so gating this mutation behind auth would silently drop exactly the failures it exists to catch. It is still protected by the project-wide GraphQL depth/complexity limits (`@escape.tech/graphql-armor`, `server.ts`), which apply to every resolver regardless of auth state — no additional rate-limiting/throttling is added in this story beyond AJV's length caps and those pre-existing global limits (see Out of Scope).
- **Why `context` is required, not optional, in `EmailTemplateVariables.SYSTEM_ERROR_ALERT`, even though the GraphQL input's `context` field is optional:** `render-template.ts`'s substitution engine has no concept of an "optional placeholder" — it throws if any `{{variableName}}` in a template has no corresponding key in the passed `variables` object, and every existing `EmailTemplateVariables` entry today has 100%-required fields (no precedent for an optional one). Introducing optional-placeholder support to that shared, generic engine would be a broader behavioral change affecting all three existing templates' contracts, not something this story should do as a side effect. Instead, the resolver (Task 4) normalizes `input.context ?? 'None provided'` before calling `sendTemplatedEmail`, keeping `render-template.ts` and its type contract unchanged. Flagged in Pre-Coding Approval Gate as a design choice, not a silent assumption.
- **Why the AJV pattern is used here for the first time in a real resolver:** Story 0.11 ("set up runtime schema validation") already committed a generic `compileValidator<T>()` helper (`apps/backend/src/validation/validate.ts`) and one example schema (`extracted-event.schema.ts`), but as of this story's creation neither is imported by any resolver — only by `validate.test.ts`. This story is the first to actually wire AJV into a live GraphQL mutation, following the exact same `JSONSchemaType<T>` + `compileValidator<T>()` shape Story 0.11 established, compiled once at module scope for request-path efficiency (not per-call, unlike the test file's pattern).
- **No shared logger/observability convention exists yet, and this story does not introduce one.** A plain inline `console.error(...)` is used for the delivery-failure/misconfiguration log paths (Task 4) — this is a Lambda runtime, where `console.error` already flows to CloudWatch by default; no reusable logger utility is mandated anywhere in `project-context.md` or the architecture spine, and this story has exactly one call site needing it (the project's own precedent, per Story 0.22's `activeOnly()` extraction, is to build a shared abstraction once ≥2 real call sites exist, not speculatively for one).
- **No `packages/ui` component is introduced; no i18n strings (AD-6, scoped to the frontend only — this story's template renders and sends exclusively from `apps/backend`, mirroring Story 0.15's and Story 0.12's identical conclusion); no PostHog/analytics event (AD-5 — no user-facing interaction here; Story 2.10 owns any client-side `push_notifications_sw_error` analytics event, entirely separate from this mutation); no state-management categorization (Server State/URL State/Client Global State) applies — backend-only, nothing rendered; no async loader (blocking/non-blocking) categorization applies.**
- **No new database entity or migration is introduced** — see Data Type Compatibility section below.

- (capability) CAP-1 Vendor role normalization: intent - the ingestion pipeline classifies each post's vendor payload identities into three distinct axes (scraping/subscription-source account, canonical publisher account, coauthor accounts) per-vendor, never inferring publisher/coauthor status from array order or position. success - given a real scrape payload with coauthorProducers (Apify) or coauthor_producers (Bright Data) populated, the persisted result records a role-tagged identity for the publisher distinct from every coauthor and from the triggering subscription account, verified against the run-04/run-06 Apify fixtures in vendor-role-mapping.md.
- (capability) CAP-2 Deduplicated subscribable profiles: intent - every publisher/coauthor identity with a stable platform account ID gets or reuses one SocialMediaAccountProfile row (platform, accountId) unique, created unsubscribed by default; an identity with no stable accountId is retained only as an internal, non-public, non-subscribable provisional record, backfillable/mergeable once an accountId is known. success - re-scraping the same coauthor across multiple posts produces exactly one profile row (idempotent on platform+accountId); a caption-only or accountId-less mention never creates a public socialMediaAccountProfiles row.
- (capability) CAP-3 Normalized post-account associations + lossless migration: intent - a new association table records one row per (post, account) pair with an explicit role (publisher, coauthor, scraping-source, or publisher-unknown) and provenance; posts.accountId is preserved unchanged for backward compatibility and, for new posts, is populated from the verified canonical publisher only after vendor-role normalization -- never from producer-array order. success - a migration over existing production posts adds exactly one scraping-source/publisher-unknown association per row with zero data loss or ownership rewriting; a newly ingested post gets one publisher association plus N coauthor associations matching its vendor payload.
- (capability) CAP-4 Immediate coauthor subscribability: intent - a coauthor or publisher profile with a stable accountId is subscribable from event/post detail or direct account-ID lookup through the existing subscription contract without requiring prior direct scraping of that account, and may trigger the existing initial-scrape/classification flow. success - subscribing to a coauthor discovered only via another account's post (never itself scraped) succeeds and the coauthor's own feed begins populating through the existing initial-scrape path.
- (capability) CAP-5 Demand-gated discovery: intent - verified scrape-discovered profiles (even with a stable accountId) are excluded from broad account autocomplete/ranked discovery surfaces until a subscribe or vote signals intentional demand, limiting directory pollution without blocking contextual subscription. success - a freshly created coauthor profile does not appear in autocomplete/ranked discovery results until at least one subscribe or vote event exists for it, and becomes subscribable immediately from the originating event/post detail regardless.
- (capability) CAP-6 Union-of-associations account filtering: intent - user-facing account filtering matches the union of a post's active publisher, coauthor, and scraping-source associations, not just the legacy posts.accountId column, preserving existing subscribed-feed behavior while adding coauthor/publisher matches. success - a user subscribed only to a coauthor (never the scraping-source account) sees that coauthor's co-authored posts in their filtered feed.
- (capability) CAP-7 Event/post detail attribution UI: intent - event/post detail shows the post's posted-at timestamp via the existing short-date formatter, and renders coauthors below the original-post link using the existing shared-account-info pattern (packages/ui/src/features/subscriptions/SubscribedAccountCard.tsx, already reused in EventDetailView.tsx). Verified profiles expose a confirmed (not optimistic) accessible subscribe/unsubscribe icon toggle -- confirm before mutating, refetch/invalidate authoritative state after success, restore prior state on failure; provisional identities remain display-only. success - opening an event with 2+ coauthor associations shows each as a SubscribedAccountCard row with working, confirm-then-refetch toggles for verified ones and no toggle for provisional ones.
- (capability) CAP-8 Sanitized subscription-toggle analytics: intent - the toggle emits PostHog subscription_toggle_succeeded / subscription_toggle_failed events carrying action, platform, source, and (on failure) a sanitized backend errorCode -- never raw handles, account IDs, captions, or post content. success - a captured event payload for either event name contains only the four allowed fields, verified by a schema/allowlist check in tests.
- (constraint) Never infer publisher vs. coauthor role from producer array position/order -- always use each vendor's explicit role-bearing fields (Bright Data: user_posted/user_posted_id vs coauthor_producers; Apify apify/instagram-post-scraper: ownerId/ownerUsername/ownerFullName vs coauthorProducers[]).
- (constraint) Legacy posts.accountId rows must not be reinterpreted or have historical ownership rewritten without raw vendor evidence -- migrate them only as a scraping-source/publisher-unknown association, never guessed as publisher.
- (constraint) socialMediaAccountProfiles.displayName is NOT NULL (packages/database/schema.ts line 167) -- creating a profile from Apify's coauthorProducers entries (which carry accountId+username but no full name) must supply a non-null displayName via fallback, not attempt a null insert.
- (constraint) IDEA-008 owns the subscription cap's value, server-side guard, and upgrade CTA -- this spec's toggle (CAP-4/CAP-7) must stay cap-agnostic while surfacing a typed future cap error so IDEA-008 never needs another shared-component redesign.
- (constraint) The event-detail subscribe/unsubscribe toggle (CAP-7) must be confirm-then-refetch, not optimistic -- a deliberate deviation from this app's existing default optimistic-mutation convention (e.g. BUG-008/Story 2.i1a's toggleFavorite ±1 pattern), scoped to this new toggle only; see the still-open house-convention question logged below.

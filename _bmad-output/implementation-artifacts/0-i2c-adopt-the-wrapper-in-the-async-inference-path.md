# Story 0.i2c: Adopt the wrapper in the async inference path

## Story Details

- Epic: 0.i2 (Guarded outbound vendor calls)
- Story ID: 0.i2c
- Status: ready-for-dev

## Story

As a developer,
I want `callGemini` (`apps/backend/src/lib/ai-gateway/adapter.ts`) and `system-key-adapter.ts`'s AD-10 system-key fallback to call through the guarded `callVendor` wrapper (Story 0.i2a), and Story 3.6s's now-superseded inline `AbortController` timeout guard deleted rather than stacked on top,
so that unlocked duplicate-billable calls, missing retry backoff, and the missing request-level timeout (BUG-012) are all closed by one mechanism — including the pipeline's highest-volume and highest-payload-variance call site — without the extraction call ending up bounded by two independent, drifting timeouts.

## Acceptance Criteria

1. **Given** `callGemini`'s existing tiered candidate/exclusion loop (`adapter.ts`, AD-10, unchanged), **when** it has selected a candidate key and decrypted it, **then** it calls `callVendor('gemini', { lockKey: \`gemini:key:${candidate.id}\`, timeoutMs: env.geminiExtractionTimeoutMs, isTransient: isGeminiErrorTransient, call: (signal) => callGeminiGenerateContent(plaintextKey, request, signal) })` instead of calling `callGeminiGenerateContent` directly — serializing concurrent duplicate-billable calls against the same key (closes BUG-011's `callGemini` half) and bounding the call by the wrapper's timeout (closes BUG-012). [AD-32 Binds]
2. **Given** `callVendor` throws `VendorKeyBusyError` (another concurrent call already holds this key's lease), **when** `callGemini`'s loop catches it, **then** it is treated exactly like this-key-only exhaustion — `excludedKeys.add(candidate.id)`, then `continue` to the next candidate — never re-thrown as a fatal error and never excluded via `recordInvalidAttempt` (a busy lock says nothing about key validity). [AD-32 Rule 4, explicit requirement]
3. **Given** `callVendor` throws `VendorCallTimeoutError` (the wrapper's own bound elapsed), **when** `callGemini`'s loop catches it, **then** it propagates immediately, unretried and without excluding the key — the same "never retried, never excludes a key" contract Story 3.6s established for the old `GeminiTimeoutError`, now carried by the wrapper's own error type. **Given** `callVendor` throws `GeminiRateLimitedError`/`GeminiInvalidKeyError` (thrown by the `call()` thunk itself, i.e. by `callGeminiGenerateContent`), **when** `callGemini`'s loop catches them, **then** they continue to drive the existing rate-limit/invalid-key exclusion branches exactly as today — `callVendor`'s own `isTransient`-gated same-key retry never fires for these two classes (AD-32 Rule 4: "never transient"), so they always surface to `callGemini`'s outer loop on the first attempt, unchanged. [AD-32 Rule 4]
4. **Given** `system-key-adapter.ts`'s `callGeminiForLocationInference` and `callGeminiForAccountClassification`, **when** either falls back to the AD-10 system key after `callGeminiRef` throws `AiGatewayExhaustedError` and `env.systemGeminiApiKey` is configured, **then** the fallback calls `callVendor('gemini', { lockKey: 'gemini:system', timeoutMs: env.geminiExtractionTimeoutMs, isTransient: isGeminiErrorTransient, call: (signal) => callGeminiGenerateContent(env.systemGeminiApiKey, request, signal) })` instead of calling `callGeminiGenerateContent` directly — closing the third of AD-32's three named entry points into `callGeminiGenerateContent` (`callGemini`, `verifyGeminiApiKey` — 0.i2b's scope, not this story's — and this fallback). The existing `if (!env.systemGeminiApiKey) throw error;` guard is unchanged and still runs before this call. [AD-32 Binds]
5. **Given** `gemini-client.ts`'s `callGeminiGenerateContent`, **when** this story lands, **then** its signature gains an optional third parameter, `signal?: AbortSignal`, which — when provided — is set as `config.abortSignal` passed to the SDK (same `GenerateContentConfig.abortSignal` field Story 3.6s already confirmed is honored by `@google/genai`); when omitted, `config.abortSignal` is not set, exactly matching today's "no timeoutMs configured" behavior. [AD-32 Rule 1, Binds — "a thunk that does honor the signal... gets real cancellation"]
6. **Given** `callGeminiGenerateContent`, **when** this story lands, **then** its own internal `AbortController`/`setTimeout`-based timeout guard (Story 3.6s's `timeoutMs`-triggered `controller.abort()` + `timedOut` flag) is deleted entirely — the wrapper-level `VendorCallTimeoutError` (via `callVendor`'s own `AbortController` created in `callWithTimeout`, per 0.i2a AC5) is the only timeout bound from this story forward, never stacked with a second, independent one. The `GeminiCallRequest.timeoutMs` field and the `GeminiTimeoutError` class are both removed (nothing production-throws `GeminiTimeoutError` once the inline guard is gone); `build-gemini-request.ts`'s `timeoutMs: env.geminiExtractionTimeoutMs` line (which populated the now-deleted field) is deleted. `maxOutputTokens` (the separate response-size cap, also Story 3.6s/AC7) is untouched by this AC — it is not part of the timeout guard being deleted. [AD-32 Binds — "Supersedes Story 3.6s's inline... guard... 0.i2c deletes it... rather than stacking a second timeout"]
7. **Given** a new exported `isGeminiErrorTransient(error: unknown): boolean` helper added to `gemini-client.ts` (the Gemini vendor-adapter file — AD-32 Rule 4: classification is "the vendor adapter's responsibility, not the wrapper's"), **when** it classifies an error, **then** it returns `true` only for a `GeminiUnknownError` whose `originalError` shows a 5xx-range status (`status`/`statusCode`/`status_code` in `[500, 599]`) or a common connection-level error code (`ECONNRESET`, `ETIMEDOUT`, `ECONNREFUSED`, `EAI_AGAIN`, checked via `originalError?.code` or `originalError?.cause?.code`); it returns `false` for every `GeminiRateLimitedError` and `GeminiInvalidKeyError` instance unconditionally (AD-32 Rule 4: "never transient"), and `false` for any other `GeminiUnknownError` shape (e.g. malformed-request/validation-style errors) — never a blanket `true` for the catch-all class. [AD-32 Rule 4; Pre-Coding Approval Gate, user-decided 2026-10-06]
8. **Given** `vendor === 'gemini'` passed to `callVendor` from either adoption site above, **when** `callVendor` runs, **then** no DPA-confirmation check of any kind executes and no Gemini-specific env var is read — unchanged from 0.i2a's existing `assertDpaConfirmed` behavior, reconfirmed here as this story's first real exercise of that no-op branch in production code. [AD-32 Rule 5; user decision, not in DPA gate]
9. **Given** `resolvers.ts`'s `resolvePromptToEventFilter` and `process-ai-job.ts`'s extraction pipeline, both of which call `callGemini`/`callGeminiSeam` with no knowledge of its internals, **when** this story lands, **then** neither file is modified — both inherit per-key locking, the wrapper timeout, and the new transient-retry behavior transitively, exactly as AD-32 states ("transitively covers `process-ai-job.ts`... and `resolvers.ts`'s `resolvePromptToEventFilter`... with no separate adoption needed"). [AD-32 Binds]
10. **Given** this story's scope, **when** it ships, **then** it does **not** modify `verifyGeminiApiKey` (`gemini-client.ts` — Story 0.i2b's scope), does **not** touch `apps/backend/src/lib/scraper/{brightdata-client,trigger-apify-for-target}.ts` or add any Apify/Bright Data adoption (Story 0.i2d's scope), and does **not** add Gemini to the DPA gate (explicitly out of scope per AD-32 Rule 5 and the user's decision). [Gate 3 confirmation; user decisions]
11. **Given** this story's test suite runs, **when** `gemini-client.test.ts`, `adapter.test.ts`, and `system-key-adapter.test.ts` execute, **then** they prove, at minimum: (a) `callGeminiGenerateContent` forwards a provided `signal` to `config.abortSignal` and omits it when no signal is passed (replacing the deleted internal-timeout test cases); (b) `isGeminiErrorTransient` returns `true` for a 5xx/connection-coded `GeminiUnknownError` and `false` for `GeminiRateLimitedError`/`GeminiInvalidKeyError`/a non-network `GeminiUnknownError`; (c) a busy `vendor_call_locks` lease for one candidate key causes `callGemini` to exclude it and fall through to the next candidate, succeeding (new `VendorKeyBusyError` branch); (d) a `VendorCallTimeoutError` (or any error class `callVendor` itself throws before reaching the `call()` thunk) propagates out of `callGemini` unretried and without excluding the attempted key, mirroring the deleted `GeminiTimeoutError` test's intent; (e) both `system-key-adapter.ts` fallback functions claim/release the `gemini:system` lease around their `callGeminiGenerateContent` call, and a pre-held `gemini:system` lease causes the fallback to throw `VendorKeyBusyError` rather than silently calling the SDK. Every test that inserts a `vendor_call_locks` row cleans it up (`t.afterEach`/`t.after`), matching `guarded-call.test.ts`'s own precedent — zero leftover rows after the full suite.

## Dev Notes

- **This story is pure call-site adoption of an already-built mechanism — no new table, no new module, no new AWS resource.** `callVendor`, `VendorKeyBusyError`, `VendorCallTimeoutError`, `VendorDpaNotConfirmedError`, and the `vendor_call_locks` table all already exist and are already tested end-to-end (Story 0.i2a, `apps/backend/src/lib/vendor-gateway/guarded-call.ts`, status: **review** — code and tests exist and pass; the user has confirmed treating it as built/usable for this story despite the sprint-tracking status not yet reading `done`). This story only changes what three existing Gemini call sites call.
- **The three AD-32-named entry points into `callGeminiGenerateContent`, and which story owns each:** `callGemini`'s candidate-exclusion loop (`adapter.ts`) and `system-key-adapter.ts`'s AD-10 system-key fallback (two functions) are **this story's** scope. `verifyGeminiApiKey` (`gemini-client.ts:168`, invoked from `createApiKey`) is explicitly **Story 0.i2b's** scope — do not touch it, and do not add `GEMINI_VERIFICATION_TIMEOUT_MS` here (that's 0.i2b's own new env var per AD-32 Rule 3). [Source: `festgrid-architecture-spine.md#AD-32`, Binds]
- **Full AD-32 text was read in full** (`festgrid-architecture-spine.md`, lines 1785-1907) before drafting this story — it is the authoritative source for every Rule citation above, including the explicit "Supersedes Story 3.6s's inline `AbortController` timeout guard... 0.i2c deletes it... rather than stacking a second timeout" directive (AC6) and the literal `lock_key` naming convention (`gemini:key:<apiKeys.id>` / `gemini:system`, AC1/AC4).
- **Why `isGeminiErrorTransient` classifies only a narrow slice of `GeminiUnknownError` as transient, not the whole class (AC7, user-decided via `AskUserQuestion` during this story's creation):** AD-32 Rule 4 states transient-failure classification "is not yet distinguished anywhere in this codebase today" and is explicitly "the vendor adapter's responsibility, not the wrapper's" to supply when adopting `callVendor` — confirmed via repo-wide grep that no `isTransient`-style classifier exists anywhere today. Two options were considered: (a) classify likely-network `GeminiUnknownError` shapes (5xx status, connection-level error codes) as transient, giving `callVendor` something real to retry on same-key with backoff — a net-new improvement, since **today** any `GeminiUnknownError` already fails the entire `callGemini` call immediately with zero retry (its catch-all branch is an unconditional `throw error;`, never a `continue`); or (b) always return `false` for Gemini, leaving `callVendor`'s retry-with-backoff mechanism dormant for this vendor until a future story adds real classification evidence. **The user chose (a).** `GeminiRateLimitedError`/`GeminiInvalidKeyError` remain unconditionally non-transient regardless (AD-32 Rule 4: "never transient" — these continue to be handled exclusively by `callGemini`'s own existing cross-key exclusion loop, unchanged).
- **Why the new catch branch for `VendorKeyBusyError` in `callGemini`'s loop doesn't increment `attempt` or sleep before continuing (AC2):** AD-32 Rule 4 states it explicitly — "treated like this-key-only exhaustion (`excludedKeys.add`, `continue`)" — the same immediate-exclude-and-try-next-key pattern `GeminiInvalidKeyError` already uses, not the `GeminiRateLimitedError` pattern (which does increment `attempt`/sleep, because a rate limit is time-bound and the same key may become usable again after waiting — a busy lock on this *attempt* is better resolved by trying a different key immediately, since the lock will free up for a future attempt regardless of whether this call waits).
- **Why `VendorCallTimeoutError` gets no dedicated `instanceof` branch in `callGemini`'s `catch` block, unlike the old `GeminiTimeoutError`'s explicit (if functionally redundant) branch:** The old branch was deliberately a no-op that fell through to the same `throw error;` as the generic catch-all — kept only "to make the... contract visible and protected against an accidental future regression" (its own comment, Story 3.6s). Since `VendorCallTimeoutError` (and every other error `callVendor` itself throws before/around the `call()` thunk, e.g. a non-transient `GeminiUnknownError` that exhausted `callVendor`'s own `maxAttempts`) already takes that exact same generic `throw error;` path with zero code change needed, re-adding a redundant explicit branch would only reintroduce the same dead-code pattern for a now-renamed error type. The replacement comment (Task 3) preserves the contract's *visibility* in prose without the dead branch.
- **`env.geminiExtractionTimeoutMs` is reused as-is, unrenamed, for both adoption sites' `callVendor.opts.timeoutMs`** — no new env var is introduced by this story. Its 120000ms default and Lambda-headroom rationale (300s AI Processor Lambda timeout, AD-13) were already sized for exactly this call shape; the mechanism *enforcing* that bound moves from `gemini-client.ts`'s own `AbortController` to `callVendor`'s, but the value and its sizing rationale don't change.
- **Response-size cap (`maxOutputTokens`, Story 3.6s AC3) is unrelated to this story and untouched.** Only the *timeout* half of Story 3.6s's inline guard is being superseded/deleted (AC6) — the response-size cap remains exactly as `build-gemini-request.ts` sets it today.

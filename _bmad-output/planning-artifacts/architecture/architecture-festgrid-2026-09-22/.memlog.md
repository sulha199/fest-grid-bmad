- (event) Session context: this amends the existing festgrid-architecture-spine.md (AD-1..AD-24, no prior memlog found for it -- legacy doc amended directly across sessions). Trigger: a visual-fidelity audit found EventCard/WeeklyCalendarView only ~70% matched design-reference prototypes; user wants a reusable, repo-resident tool to check prototype fidelity as an automatable acceptance criterion, general enough to catch overflow/position/color/size defects broadly, not just this case.
- (event) Re-pulled master mid-session: IDEA-046's 7 prototype-fidelity rules already shipped via Story 1.i1l (rules 1-6) + Story 1.i1m (rule 7, carved out -- forked a shared primitive's contract), both review, commits 6412792c/13861432. One NEW defect from this session's own audit remains unfixed and uncovered by any story: EventCardDateBox's day slot (text-5xl/text-3xl, no max-width/wrap handling) overflows when fed word/time content (Tomorrow/Today+time) instead of a numeric day -- confirmed still present in EventCardMediaPrimitives.tsx:273 post-pull.
- (decision) Compare mechanism is a hybrid: computed-style/DOM introspection as primary signal (precise, explainable), pixel screenshot diff as secondary/visual-confirmation layer. [ADOPTED, user-directed]
- (direction) User wants 4 additional checkable rule classes beyond basic prototype-vs-live diff: (1) row/column sibling-dimension consistency (e.g. all date boxes in one grid row share height, all in one column share width), (2) intra-box element size-ratio consistency (e.g. month-text:day-text size ratio) with a drift tolerance -- user asked us to design the tolerance mechanism, (3) color difference detection, (4) overflow detection including POTENTIAL overflow for content variants the static prototype never depicted (e.g. date-box word/time content the PNG never showed).
- (question) Open: how are row/column sibling groups identified for rule (1) -- manifest-declared selectors per component (precise, needs authoring) vs automatic visual clustering by bounding-box proximity (general, heuristic/fragile)?
- (question) Open: for rule (4)'s potential-overflow detection, where does the catalog of content variants per slot come from -- hand-authored fixture list per component (e.g. EventCardDateBox day slot: 1-digit/2-digit/Today/Tomorrow/Yesterday/time-string), or attempted static analysis of the formatting function's own branches (format-event-date.ts)? Hand-authoring is reliable but is new ongoing authoring burden per component; static analysis is appealing but fragile against arbitrary logic and may miss real cases.
- (decision) Row/column sibling-dimension grouping: auto-cluster by bounding-box coordinate overlap. [ADOPTED, user-directed] Scope clarified: the audit tool operates on a SINGLE isolated card/component instance per run (mounted with fixture props, not a live multi-card grid page) -- so rule 1 groups elements WITHIN one card (e.g. a date-box and thumbnail sitting side by side = same row, must share height), not sibling cards across a grid.
- (decision) Content-variant catalog source for potential-overflow detection: static analysis of the formatting function's branches (e.g. format-event-date.ts). [ADOPTED, user-directed] Accepted trade-off: won't capture arbitrary translated string content/lengths, only enumerable branch shapes -- i18n string-length variance is a known gap this decision accepts, not solved.
- (question) Raised by user, out of the per-card tool's scope: masonry GRID-level expectation is Pinterest-style -- each column shares one width, cards within a column vary freely in height. Since the audit tool operates on single card instances, this is a separate, deferred concern (multi-card grid layout, not per-card layout). Needs verification against current masonry CSS before deciding whether it needs its own mechanism.
- (event) CONFIRMED, not just deferred: GridContainer (packages/ui/src/core/grid-container.tsx) implements plain CSS Grid (grid-cols-N, default grid-auto-rows) for the 'masonry' variant -- NOT true Pinterest-style masonry. CSS Grid ties every row's height to its tallest cell across all columns; it cannot let column 2 flow independently past a short card in column 1 the way true masonry does. This is a real, separate implementation gap from the per-card visual-audit tool's own scope -- it's a multi-card grid-engine choice (candidates: CSS multi-column (columns-N), a JS masonry library, or experimental CSS grid-template-rows:masonry), not something the per-card audit tool would ever check.
- (version) Web-verified 2026-09-22: native CSS masonry (grid-template-rows:masonry, 'CSS Grid Lanes') ships only in Safari 26; Chrome/Firefox remain behind experimental flags, cross-engine spanning/edge-case behavior not yet interoperable. Ruled out for production use -- sources: caniuse.com/mdn-css_properties_grid-template-rows_masonry, stefanjudis.com/blog/how-to-use-and-feature-detect-css-grid-masonry-layout.
- (direction) User generalized the tool's scope while raising the masonry-grid gap: the masonry grid-engine mismatch has NO prototype HTML/PNG at all -- it's only described in prose (user's own stated Pinterest expectation / EXPERIENCE.md text). This means the visual-audit tool needs a second audit mode alongside reference-based (prototype vs live): a rule-based/prose-derived mode, where an invariant is hand-encoded as a structural rule (expected value or behavior) with no golden HTML/PNG reference, checked the same way (computed-style introspection) against the live render.
- (decision) Masonry grid engine: JS shortest-column placement (measure card heights, place next item into current shortest column -- the react-masonry-css/Pinterest algorithm), replacing GridContainer's plain CSS Grid for variant='masonry'. [ADOPTED, user-directed] Rejected: native CSS masonry (Safari-only in 2026, ruled out above); CSS multi-column (rejected -- changes reading order to column-major, a visible UX regression from today's row-major left-to-right).
- (decision) Ratio-drift tolerance: two-tier, both configurable per rule in the manifest. Same-row/column dimension equality checks: near-zero ABSOLUTE tolerance, default <=2px. Cross-element proportional ratio checks (e.g. icon:box scale): RELATIVE tolerance, default +/-8-10%. [ADOPTED, user-directed]
- (decision) Tool location: new workspace package packages/visual-audit (not a standalone script) -- importable as an assertion library from test files, not just CLI-invocable. [ADOPTED, user-directed]
- (decision) Default render mode: isolated-component-render (mount component directly with fixture props, no server/DB/auth) as the default CI-friendly mode. Live-route mode is a fallback only for defects that are genuinely route/data-dependent (e.g. auth-gated pages, server-fetched data shapes) -- directly motivated by this session's own audit hitting exactly this friction against my-calendar (auth-gated) and missing near-term/multi-day seed data. [ADOPTED, user-directed]
- (decision) Color difference detection: resolve the expected color from its DESIGN.md/Tailwind token (exact computed-style RGB/OKLCH match) as primary signal; pixel-level perceptual diff against the source PNG as fallback for anything not yet tokenized. [ADOPTED, no objection raised across multiple turns]
- (decision) AC integration: a manifest file per component/variant/viewport (one canonical entry per triple, prevents duplicate/conflicting entries for the same target), story ACs cite it by name. [ADOPTED, user-directed]

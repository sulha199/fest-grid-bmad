# Story 10.1a: Build the job engine core: record, lifecycle, runner and sweep

## Story Details

- Epic: 10 (Background vendor jobs: one engine, one Jobs page)
- Story ID: 10.1a
- Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a developer,
I want one job record with a typed lifecycle and a worker that runs it off the request path,
so that any vendor-backed action returns a job id at once and finishes inside its own budget.

## Acceptance Criteria

1. **Given** a job type registered in the engine's registry, **when** `startJob(type, input, ownerUserId)` runs in the API Lambda, **then** a `jobs` row (type, owner, input key, status, phase, deadline, result, attempts) is written and the scraper Lambda is invoked asynchronously (`InvocationType: 'Event'`) through a new invoke seam mirroring the existing `invokeAiProcessor`/AD-41 pattern; the call returns the job id in under one second regardless of whether the invoke itself succeeds (a failed invoke marks the job FAILED, same fail-to-start shape as `startManualExtractionJob`). [PRD §3.18 FR116; AD-41]
2. **And** the worker runs the registered handler inside the job's deadline (`JOB_ATTEMPT_DEADLINE_MS`, default 150000 — about 150s per attempt within the scraper/AI-processor Lambda's 300s), records phase changes as the handler reports them, and ends the job FAILED with a reason when the handler throws or the deadline passes before it resolves. [PRD §3.18 FR117]
3. **And** a new architecture decision (AD-45) explicitly resolves cross-Lambda phase hand-off: a job whose phases need different Lambda capabilities (a vendor-scrape phase, which needs the Scraper Lambda's vendor tokens and `BRIGHTDATA_DATASET_ID`, versus a Gemini/face-blur extraction phase, which needs the AI-processor Lambda's `sharp`/`face-api` bundle and has no vendor tokens at all) hands off between them via the same async-invoke seam as AC1, carrying only `{ jobId }` across the hop — the receiving Lambda reloads the job row and resumes from its stored `phase`, never a vendor token or a caption. This is not optional scaffolding: Stories 10.6 and 10.9 each describe a refresh-then-extract job that spans exactly this boundary, so this story must name the mechanism before either can be built. [epics.md Story 10.1a AC3, added by the Epic 10 readiness sweep]
4. **And** an hourly sweep ends `jobs` rows running past their `deadlineAt` (status → `EXPIRED`, reasonCode `TIMED_OUT`) and clears their worker claim, and separately clears retained re-extract-preview captions and extraction payloads older than their retention window on `manual_extraction_jobs` — absorbing FIND-086 finding 1 (a manual-extraction job inserted but never claimed keeps its caption past the 5-minute stale limit, with no sweep) and FIND-111 finding 1 (an unapplied re-extract preview keeps `result_data.extracted` on its row indefinitely past the 30-minute Apply window). [epics.md Story 10.1a AC4; FIND-086; FIND-111]
5. **And** the `jobs` table references `apify_pending_jobs`, `brightdata_pending_jobs`, `scraper_actor_runs` and `vendor_call_locks` rather than replacing them (a new `job_attempts` table, scoped to this story, FK's to `scraper_actor_runs` for a provider attempt that actually dispatched a vendor call), and `manual_extraction_jobs` is untouched in shape — the decision to migrate it onto this table is Story 10.9's (OI-4). [PRD §3.18 OI-4; epics.md Story 10.1a AC5]
6. **And** the CDK grants the API Lambda invoke on the scraper Lambda (mirroring the existing `aiProcessorLambda.grantInvoke(apiLambda)` grant) and the scraper Lambda invoke on the AI-processor Lambda (for AC3's hand-off), declares the new env vars each Lambda needs for this, and `docs/infrastructure/architecture-diagram.md` and `high-level-overview.md` show the new table and invoke paths. The checks this satisfies are described in the same shape Stories 0-i3b/0-i3c will later enforce automatically — Epic 0.i3's own invariant-sweep suite (0-i3a) is itself still unstarted, so there is no live CI check to "pass" yet; this bullet is satisfied by manual compliance with the pattern now, re-verified once 0-i3b/0-i3c land. [epics.md Story 10.1a AC6, reworded by the Epic 10 readiness sweep]
7. **And** a new architecture decision AD-45 records the engine rule (a vendor-backed action that can exceed a few seconds runs as a job, with one record, one registry, one deadline, one sweep) and AD-41 ("Subscribe Returns Fast") is amended with a pointer naming AD-45's engine as the worker mechanism that implements AD-41's never-built classify-account worker, instead of AD-41 being built a second, separate way later. [epics.md Story 10.1a AC7]

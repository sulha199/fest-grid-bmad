# Story 3.6v: Match new posts to existing events and enrich them in place

## Story Details

- Epic: 3
- Story ID: 3.6v
- Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a subscriber,
I want the same real-world event advertised by several posts to be one event,
So that a thin roundup entry becomes the detailed event when the organizer posts, with my favorites and calendar entries intact (BUG-052).

## Acceptance Criteria

1. **Given** an extracted event about to be inserted, **when** `processIngestionJob` runs, **then** matching runs **before** insert: first the AD-30 Rule 3 idempotency lookup (`event_posts(post_id, extraction_ordinal)`) — a hit means this exact item is already represented and the job skips/enriches via the existing path, never re-matches. On a genuine miss, candidates are selected by (a) schedule date-range overlap within ±2 days of any of the new item's schedules and (b) `pg_trgm` trigram name similarity against `events.event_name` (using the already-indexed, write-path-only GIN index from Story 3.6r). Candidates are scored on: same organizer account (a `PUBLISHER`/`COAUTHOR` association via the new AD-31 Rule 4 helper, or `organizerHandle` resolved to an account by `(platform, username)`) — **discounted/ignored entirely when the new item's source post has `grouping_reason = 'roundup'` or the posting account's `accountType = 'CURATOR_GUIDE'`**, since `organizerHandle` defaults to the *posting* account (curator/roundup aggregator) in that case, not a real organizer signal (Story 3.6s's extraction prompt; see Dev Notes) — a shared registration/ticket link (`events.links[].url`), date+name similarity, and venue (`schedules.location`/coordinates). **High** score auto-links (enrich the matched event in place, no new event row); **mid** score is ingested as its own new event **and** a suggested-match record is queued for moderator review (consumed later by Story 3.6w — no separate "pending" state on the new event itself); **low** score creates a new event exactly as today. An event absorbs at most one item per post (already structurally guaranteed by `event_posts`'s `(event_id, post_id)` primary key — no extra application-level guard needed, only a regression test).
2. **And** primary-post selection (AD-30 Rule 7), evaluated in this order: (1) organizer-authored (the shared AD-31 Rule 3 predicate, `isOrganizerAuthoredPost`, never re-implemented here) beats roundup/aggregator/curator-sourced; (2) the post whose extraction has more schedules with a complete date **and** location; (3) earlier post (`posts.published_at`, ascending); (4) lower post id (deterministic tie-break).
3. **And** this story ships the shared event-level account-match helper (AD-31 Rule 4) with its `posts.accountId` leg, and the `Query.events` account filter and `isFromSubscribedAccount` fieldMap entry both use it — so an event promoted from a roundup stays visible to the roundup account's subscribers. Story 3.18 later adds the `post_account_associations` leg. A source-scan ratchet test fails if either call site is built without going through the helper.
4. **And** enrichment is in place: a field with an approved correction or moderator edit (any `corrections` row with `status = 'applied'` whose `proposedData` names that field, for that event) is never overwritten by the matched extraction — it is instead queued for moderation the same way an unmatched correction would be, never silently discarded. Schedules match by date: an existing schedule with the same `eventStartDate` is updated in place, a schedule with no date match is added, and a schedule is **never deleted** while a `calendar_additions` row still references it (`calendar_additions.schedule_id`).
5. **And** on promotion (a match-driven primary-post change), the event adopts the matched candidate's `extraction_ordinal`, is re-slugged in the same transaction as the pointer change (AD-30 Rule 2 / AD-16 Rule 10) to name the new primary post, and the event's prior slug is recorded as a permanent tombstone in `event_slug_aliases`. `eventBySlug` looks up the canonical slug first (no behavior change on a hit); on a miss it consults `event_slug_aliases` and, on a hit there, returns the canonical event transparently (AD-16 Rule 11) — the caller detects "this was a redirect" structurally, by the returned event's own `slug` disagreeing with the slug it requested, not via a thrown error (see Dev Notes "Chosen redirect-signal mechanism").
6. **And** the redirect is wired into **both** Next.js routes that render `eventBySlug` by slug — `apps/web/src/app/[locale]/events/[slug]/page.tsx` (full page) and `apps/web/src/app/[locale]/@modal/(.)events/[slug]/page.tsx` (intercepted modal) — not only the backend resolver: both already call `getEventBySlugCached()` (`apps/web/src/features/events/get-event-by-slug-cached.ts`), which today swallows every failure (including a would-be redirect signal) into a plain `null` return (verified in source). This story changes both route files to compare the fetched event's `slug` against the requested URL param and issue a Next.js `redirect()` to the canonical path **before** `EventDetailWrapper` mounts, whenever they differ, so the "no not-found flash" contract (`EXPERIENCE.md` § CC-024 "Redirected slug") holds in both routes, not just one. `getEventBySlugCached` itself needs no signature change (see Dev Notes) — its existing `null`-on-failure behavior is untouched and remains correct for a genuine not-found/network error.
7. **And** the first organizer-authored primary post triggers one notification to that account's subscribers when `events.notified_at IS NULL`, setting it via the existing Story 3.6t notify helper (`notifyNewEvent`, AD-30 Rule 10) exactly as-is — this story defines no notification mechanism of its own.
8. **And** re-running either post (idempotent SQS redelivery) creates no duplicate event, no duplicate `event_posts` row, and no duplicate `event_match_candidates` row.
9. **And** promotion/enrichment never drops a user's favorite or calendar entry: because the matched/enriched event keeps its existing `events.id` (only `postId`/`extractionOrdinal`/`slug` change), rows in `favorites` and `calendar_additions` (both FK'd on `eventId`, the latter also on `scheduleId`) continue to resolve to the same event/schedule rows unless a referenced schedule itself is intentionally deleted — which AC4 already forbids while `calendar_additions` references it. A dedicated regression test proves this explicitly (see Testing Requirements) — this is the acceptance property the CC-024 wave plan calls out by name ("promotion keeps favorites/calendar entries").

**Depends on:** Story 3.6t, Stories 3.13–3.15 (roles), Story 3.4n, Stories 3.7g and 3.7h (slug builder and DB-free embed, which a re-slug must keep correct).

**Amendment (2026-10-04, `bmad-create-story`, CC-024 Wave 4B):** AC1's organizer-account scoring signal is narrowed from the original epics.md text ("score by same organizer account (`organizerHandle` or a `PUBLISHER`/`COAUTHOR` association)") to explicitly **discount** `organizerHandle` when the new item's source post is roundup-sourced (`posts.grouping_reason = 'roundup'`) or curator-sourced (posting account `accountType = 'CURATOR_GUIDE'`). Surfaced by the CC-024 wave plan (binding, Wave 4B) as a correction to Story 3.6s's as-built behavior: 3.6s's extraction prompt sets `organizerHandle` to the *posting* account when no handle is explicitly tagged on an item — by design, so the handle survives the curator caption being nulled by Story 3.4o — which means for a roundup/curator-sourced item, `organizerHandle` names the curator/aggregator, not the real organizer, and must not be allowed to falsely inflate a match score against an unrelated event the curator also covered. Both signals needed to make this discount (`posts.grouping_reason`, and `isOrganizerAuthoredPost`'s underlying curator check) are already computed by `processIngestionJob` today (Story 3.6t, `isRoundupSourced`/`isCuratorSourced`) — this story reuses them, it does not re-derive them.

### Design decisions made directly during this story's creation (mechanical/architecture-determined — not put to the user)

AD-30/AD-31 are unusually prescriptive for this story (primary-selection order, idempotency semantics, enrichment/merge rules, the account-match helper's exact ownership split with Story 3.18 are all already fixed architecturally), so the remaining open points are implementation mechanics with no real user-arbitrable tradeoff, resolved directly and recorded here for `dev-story`/review:

1. **Chosen redirect-signal mechanism (AC5/AC6).** epics.md's AC text says `eventBySlug` "returns a permanent redirect" and that `getEventBySlugCached` must "distinguish a redirect signal from a genuine null" — read literally, this could mean a new GraphQL field/error-extension channel. Chosen instead: `eventBySlug` transparently returns the canonical `Event` row on an alias hit (Task 6), with **no new field and no thrown/caught signal** — the caller (the two route files, Task 7) detects a redirect structurally, by comparing the slug it requested against the slug the returned event actually carries. This satisfies "distinguish from a genuine null" precisely because there is nothing for `getEventBySlugCached`'s existing `try/catch` to conflate: a `null` still means exactly what it means today (not-found/network failure, unchanged), and a non-null response whose `slug` disagrees with the request is the one new case. Chosen over a new field/error channel because it needs zero schema/codegen change, adds no new per-row resolver (AD-17's stated bias), and cannot regress the existing swallow-to-null behavior since it never touches that code path at all.
2. **`event_match_candidates` schema/name.** New, single-purpose table (Task 1) — not folded into an existing table, since a "mid"-confidence event is a real, fully-formed event row in its own right (not a draft/stub), and the suggestion is metadata *about* a relationship between two existing events, naturally a link-style table matching the `eventPosts`/`postAccountAssociations` precedent already in this schema.
3. **Scoring weights/thresholds (AC1).** AD-30 Rule 7 explicitly defers exact tuning to this story ("thresholds tuned in 3.6v itself, not fixed here"). Initial defaults chosen and documented in Task 3 (organizer 0.40 / shared link 0.20 / date+name 0.25 / venue 0.15; high ≥0.75, mid 0.45–0.75, low <0.45) — explicitly flagged as **tunable defaults to validate against real data during `dev-story`**, not an architectural mandate; record any adjustment in Completion Notes.
4. **`organizerHandle`-to-account resolution.** Resolved by `(platform, username)` against `social_media_account_profiles` (case-insensitive, `@`-prefix stripped) — the only handle-shaped identity column that table exposes; no new column needed.
5. **"An event absorbs at most one item per post" (AC1).** Already structurally guaranteed by `event_posts`'s composite primary key `(event_id, post_id)` — a second item from the same post attempting to link the same event would violate the PK. No extra application-level check is written; Task 4's test suite proves the PK does its job rather than re-implementing the guard in code.

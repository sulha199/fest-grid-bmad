idea: AI prompt-based custom event filter: user describes desired events in natural language via a chatbot-style interface; the app translates the prompt into a stored, structured query using the existing BYOK Gemini adapter (Story 0.13). The stored filter has no direct edit UI -- updates happen only by re-prompting.
goal: Validate whether the idea holds up and sharpen it -- resolve the open design questions identified in prior bmad-help validation before it goes to bmad-prd/bmad-spec.

- (crack) "No edit UI" was a starting assumption, not a hard requirement -- now open for revision.
- (decision) Filter must be stored and reused (not one-shot) -- implies it gets re-evaluated later, not just executed once at creation time.
- (crack) Complex prompts like 'community (one-day) events in Jakarta next weekend' need relative date tokens (next weekend relative to now-at-evaluation-time, not a frozen absolute date) and a location representation (Jakarta as a place, not raw text) -- these need a defined token vocabulary before any UI (edit or read-only) can exist.
- (assumption) User assumes common users would have difficulty understanding a complex filter (unverified -- to be pressure-tested).
- (lock) Location filter uses Option A: capture admin-area component (e.g. Kabupaten Sleman vs Kota Yogyakarta) from the existing Geoapify geocoding response into LocationDetails, filter by exact/fuzzy text match on an indexed column -- no PostGIS/polygon geometry. Rejected Option B (true point-in-polygon boundary query) as new geospatial infrastructure not justified by current use cases.
- (note) Unverified assumption to check before build: Geoapify's response for Indonesian addresses reliably separates Kota Yogyakarta from Kabupaten Sleman as distinct admin values (not folded together).
- (decision) Deterministic template-rendered summary (not AI-generated) from the resolved finite tokens, replacing the need for an edit UI as the transparency layer -- user confirmed.
- (note) Recommendation stated but not yet explicitly re-confirmed by user after location tangent: extend the shared Discovery/Widget filter shape (typed, not Record<string,unknown>) regardless of UI; no edit UI for v1.
- (lock) v1 scope is on-demand only: AI translates prompt into filter, user views matching events immediately. No scheduler/digest, no per-user recurring re-evaluation, no quota fan-out concern for v1. Recurring digest (daily/weekly notification against saved filters) explicitly deferred to v2.
- (lock) Degrade rule (general, not just price): any prompt fragment outside the supported/locked vocabulary is explicitly surfaced as an ignored caveat in the deterministic summary -- never silently dropped, never heuristically guessed.
- (direction) v2: normalize Schedule.ticketPrice into a global numeric value (estimated, cross-currency) so a prompt like 'under IDR 200K' can match events priced in USD or other currencies via estimated conversion. Requires: extraction-pipeline schema change to emit normalized amount+currency, plus an FX-rate source (cached, same pattern as Geoapify quota caching) -- not exact conversion, explicitly estimated.
- (crack) 'All Thursday events' is a day-of-week recurrence predicate, not a date-range token -- structurally different from NEXT_WEEKEND-style range tokens. Conflating them into one enum would misdesign the field.
- (direction) Restructure DateRangeFilterInput as anchor+offset (anchor: TODAY|THIS_WEEK|THIS_MONTH, offsetAmount: int, offsetUnit: DAY|WEEK|MONTH) instead of a flat enum -- more dynamic/composable per user request, still a closed structured grammar (compatible with the finite-vocabulary lock, not a regression to free text). Day-of-week recurrence ('every Thursday') needs a separate dedicated field, not folded into this range structure.
- (note) Open UX question: how does a user access a saved pull-only AI filter -- full 'AI mode' toggle that hides FilterHub (user's proposal) vs. a separate 'My AI Filters' list page (consistent with existing Favorites/Subscriptions pattern) that routes into Discovery with a read-only banner + deterministic summary. Recommending the latter, pending user decision.
- (direction) Chatbot is explicitly NOT a general app-wide QnA assistant -- scoped as a single-purpose prompt-to-filter extraction task (classification+extraction, not open dialogue). Off-topic/unrelated prompts reuse the already-locked degrade mechanism: an explicit, deterministic 'I can only help find events' fallback, never an AI-generated freeform reply.
- (crack) Framing this as an open chatbot (rather than a narrow extraction box) creates a BYOK abuse vector: users could use their own paid Gemini key through the app as a free general-purpose chat proxy. Narrow task-scoping (constrained system prompt, structured output only) mitigates this by construction rather than needing a separate safety/moderation layer.
- (lock) Resolves AI-filter/FilterHub coexistence: the deterministic summary is a LIVE render of current EventFilterInput state (renderSummary(state): string), not a frozen caption tied to AI creation -- so it always accurately describes whatever's applied, whether from AI or manual edits. Manual FilterHub interaction only changes the current session's query state (same last-write-wins behavior Discovery already has); it never mutates the saved 'My AI Filters' entity -- preserves the no-edit-UI lock, since touching chips is editing the session, not the saved object. To change the saved filter itself, the user re-prompts.
- (lock) FilterHub stays compact: (1) a single icon-only trigger (sparkle icon, no permanent label -- consistent with PageHeader's existing icon+hidden-label action pattern) appended to the existing quick-search/type/category/nearby row opens the AI prompt as an overlay/sheet, costing zero permanent width. (2) When an AI filter is active, FilterHub's default row is REPLACED by a single collapsed summary row (the live-rendered sentence + clear/expand actions), not shown alongside the full manual controls -- expanding reveals the normal controls pre-filled, collapsing returns to the one-line summary. Avoids ever showing two stacked filter rows by default.
- (note) Correction: no real production events exist yet, so the historical-backfill-quota-cost objection to venue-type (capturing place-category at extraction time) does not apply -- every future event already calls the geolocation adapter, so adding one more captured field is marginal cost, not a retroactive re-query cost. This does NOT resolve the separate open question: whether the geolocation provider actually returns a usable place-category for an AI-extracted place name/address in the first place -- that capability check still needs verification independent of backfill concerns.
- (direction) Stronger alternative to verifying Geoapify's POI-category capability: have the existing Gemini extraction pipeline (Story 0.13, already reads each post's full text/caption/image per event) classify venueType directly as one more field in the same extraction schema, instead of depending on the geolocation provider's POI database. Zero new API calls (reuses the call already made per post), more robust to informal/local Indonesian venue names a formal geocoder POI database may not have classified, and sidesteps the Geoapify-capability verification question entirely.
- (lock) venueType is sourced from the Gemini extraction pipeline (one more field in the existing per-post extraction schema), not from the geolocation provider's POI database. No new API dependency, no capability-verification risk.
- (crack) venueType (Gemini-inferred per-post) will systematically fail on exactly the events that use the account's Default Location fallback (Section 3.7) -- those are posts with no explicit location AND typically no explicit venue-type restatement either, since the account's own identity IS the venue (e.g. a mall's own account posting about its own event).
- (lock) venueType and adminArea both live on LocationDetails itself (attached at Schedule.locationDetails per the confirmed interface, Section 4.4), not as one-off per-post extraction outputs. When a Schedule's location falls back to the account's Default Location (Section 3.7), it inherits the ENTIRE LocationDetails object -- coordinates, adminArea, AND venueType -- exactly like coordinates already do today. The account-level Default Location's own venueType is set once (AI-classified from whichever post first gave enough context, or set explicitly during Default Location configuration, mirroring the existing moderator-oversight edit flow) rather than re-derived per event. Reuses the existing fallback/inheritance mechanism instead of inventing a new one.
- (decision) Sub-building detail (floor, wing, room -- e.g. 'Lantai 2, Hartono Mall') is not geocodable to a distinct point and is not a new problem: Schedule already has both location (raw extracted text) and locationDetails (resolved LocationDetails at building/place granularity). Floor-level detail lives only in the raw text field, is shown to users as-is, but is NOT filterable. A prompt asking to filter by floor reuses the already-locked general degrade rule (explicit caveat, never fragile-matched against free text) -- third confirmed instance of that same mechanism (after price and the Geoapify-capability fallback case), validating it as the right general-purpose answer rather than a one-off.
- (lock) Multi-turn re-prompting is OUT for v1: single-shot only -- each prompt is a complete, standalone restatement of the desired filter. No conversation history, no context-passing, no chat-style UI. Same mechanism already locked for prompt-to-filter translation, no new work.
- (note) Side discovery, not locked: 'free events' may be a cheap v1-feasible exception to the deferred price-filter -- ticketPrice is free text but often literally contains 'Free'/'Gratis', so a case-insensitive text match is plausible without the general numeric-threshold work deferred to v2.

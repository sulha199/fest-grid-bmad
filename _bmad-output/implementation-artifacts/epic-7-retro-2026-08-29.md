# Epic 7 Retrospective: AI Event Filters

**Date:** 2026-08-29
**Epic:** 7 - AI Event Filters
**Status:** Completed

## 1. Epic Review

**Delivery process:** All 5 stories (7.1a, 7.2a, 7.3, 7.4, 7.5) were delegated end-to-end to `cline` (create-story + code-review on `vertex:gemini-3.1-pro-preview`, dev-story on `vertex:gemini-3.5-flash`), with Claude independently verifying and, where necessary, correcting every stage before it was allowed to proceed. This section reports what that verification actually found — not a generic narrative — since it's the part of this epic's execution most worth remembering.

### What Went Well
*   **Backend-first sequencing held up in practice, not just in theory.** 7.1a's `EventFilterInput` → 7.2a's backend API → 7.3's renderer → 7.4/7.5's UI order meant each story's (corrected) spec built cleanly on the last, with zero circular rework once a spec was fixed.
*   **Reuse worked once dev-story was pointed at the real files.** `callGemini` (Story 0.13), `EventFilterInput`, `renderAIFilterSummary`, `SwipeToReveal`/`useSoftDeleteWithUndo` (Story 0.18/0.19), and `useHasApiKey` were all correctly reused rather than reimplemented, in every story where the spec named the actual file — see "Challenges" below for the stories where it didn't at first.
*   **The `packages/ui` (presentational) vs `apps/web` (data-fetching) architecture boundary was respected** by dev-story in both 7.4 and 7.5, once the corrected specs stated it explicitly — no GraphQL hooks or `useHasApiKey()` calls leaked into `packages/ui`.
*   **i18n wiring was consistently correct** across all frontend stories — every new label was sourced through `next-intl` at the `apps/web` call site, with no hardcoded English strings reaching a real render path.

### Challenges & Lessons Learned

**1. `create-story`'s grounding research was inconsistent, and ungrounded passes hallucinated real APIs.**
Quality varied story to story — 7.1a and 7.3 did real codebase research before drafting; 7.2a, 7.4, and 7.5 did not, and each produced concrete factual errors that would have sent `dev-story` implementing against things that don't exist:
- 7.2a invented a nonexistent `AIAgent` class and a hardcoded `gemini-1.5-pro` model, when the real, already-built integration point is `callGemini` in `apps/backend/src/lib/ai-gateway/adapter.ts`.
- 7.4 claimed the project uses Apollo Client (it doesn't — `graphql-request` + TanStack React Query) and invented a client-side `onboardingState.geminiApiKey` object (the real mechanism is the already-built `useHasApiKey()` hook).
- 7.5 proposed a bare `/ai-filters` route (the real convention is `/settings/<name>`) and cited a nonexistent `packages/ui/src/features/user/UserMenu.tsx` (the real file is `packages/ui/src/core/app-shell/UserMenu.tsx`, with menu items driven by a separate `profile-menu-entries.ts` registry).
**Lesson:** every `create-story` output needs its concrete file-path and API claims checked against the real codebase before `dev-story` runs — this was caught every time in this epic, but only because it was checked every time.

**2. `dev-story`'s own verification only covered the files it created, not the ones it changed.**
This let real regressions ship undetected in its own report:
- 7.1a's change to `Widget.filters`' GraphQL type broke the pre-existing `widgets.test.ts`, which wasn't caught until independent verification during *7.2a* — 7.1a's own dev-story pass never ran the backend's full test suite.
- 7.2a's dev-story papered over a real TS2367 build break in `buildEventsQueryCondition.ts` (a 7.1a file) with `any` casts, which would have failed `packages/domain`'s zero-warning lint — a real fix (comparing against the literal alone) was needed instead.
- 7.4's dev-story shipped a genuine functional bug: any AI-resolved filter that included a `keyword` field immediately self-collapsed back to manual mode instead of showing as the intended collapsed summary row, because a `useEffect` fired on the same render as a fresh resolve. It also wired `useApiKeyStatus` into a render path whose existing test mocks didn't cover it, crashing 3 of `feed-content.test.tsx`'s 4 tests on a pre-existing null-safety gap (`data?.myApiKeys.length` missing a second optional-chain link).
**Lesson:** running only the new test files a change added is not sufficient — the full test suite for every touched package needs to run before a story is considered done, every time, not just when something feels risky.

**3. The `code-review` pass, when it did find something, wasn't always right — and its fixes need the same verification as `dev-story`'s.**
7.2a's review flagged `deleteAIEventFilter`'s `action: SoftDeleteAction!` parameter as a "deviation" from the story's own AC text and collapsed it to id-only, removing `RESTORE` capability — but the AC text was under-specified, and the real codebase convention (`deleteWidget`, `deleteUserLocation`, and, on inspection, `removeSubscription`/`deregisterEmbedDomain` too) is action-based. It also removed an upfront `NO_API_KEY` check as "redundant," when that exact pattern is the established convention elsewhere in the same file (`extractEventDataFromUrl`). Both had to be reverted back to the correct implementation after this epic's own dev-story had already gotten them right the first time.
**Lesson:** a review pass's "patch" is a claim, not a fact — verify it against real sibling code the same way a `dev-story` diff gets verified, especially when the "fix" is a removal.

**4. `epics.md` itself has documentation drift worth fixing.**
Story 7.2a's own AC text claims `deleteAIEventFilter` should match a "simple id-only" convention shared with `Favorite`, `CalendarEntry`, `Subscription`, and `EmbedDomain` — but `Subscription` and `EmbedDomain` have since been upgraded to the action-based `DELETE`/`RESTORE` contract, and the epics.md text was never updated to reflect it. Not blocking, but worth a documentation pass.

## 2. Next Epic Preparation

### Action Items
1.  **Keep independently verifying every `create-story` output's concrete factual claims (file paths, existing hooks/components, client libraries) before letting `dev-story` run against it.** 3 of 5 stories in this epic needed this correction; skipping it would have sent real implementation effort at nonexistent APIs.
2.  **Always run each touched package's full test suite (not just new test files) after every `dev-story` pass**, regardless of how confident the story's own report sounds — this is what caught the regression in `widgets.test.ts`, the domain build break, and the AI-filter self-collapse bug, none of which `dev-story` itself reported.
3.  **Treat `code-review` patches as claims to verify, not fixes to accept** — cross-check against real sibling code before applying, especially when the "fix" removes something dev-story built.
4.  **Fix `epics.md`'s stale `deleteAIEventFilter` sibling-pattern citation** (Story 7.2a's AC) so future story creation for similar entities doesn't cite an out-of-date convention.

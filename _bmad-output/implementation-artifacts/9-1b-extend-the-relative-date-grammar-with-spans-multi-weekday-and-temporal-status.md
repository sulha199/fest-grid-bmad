# Story 9.1b: Extend the relative date grammar with spans, multi-weekday and temporal status

## Story Details

- Epic: 9
- Story ID: 9.1b
- Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user,
I want "next 7 days", "weekends" and "happening now" to work in a prompt,
so that common date phrasings become filters instead of caveats.

## Acceptance Criteria

1. **AC1 — `dateRange` span widening + THIS_MONTH DAY/WEEK offset semantics (epics.md AC1):** Given `dateRange` with optional `spanAmount`/`spanUnit`, when it resolves, then:
   - `spanUnit: DAY` extends the resolved window's `to` boundary by `spanAmount` days ("next 7 days": `anchor: TODAY, offsetAmount: 0, offsetUnit: DAY, spanAmount: 7, spanUnit: DAY` → `[today, today+7]`);
   - `spanUnit: WEEK` extends `to` by `spanAmount * 7` days ("next 2 weeks": `spanAmount: 2, spanUnit: WEEK` → `[today, today+14]`);
   - `spanUnit: MONTH` extends `to` through the end of the `spanAmount`-th calendar month counting the resolved window's own end-month as month 1 ("rest of this month": `anchor: TODAY, offsetAmount: 0, offsetUnit: DAY, spanAmount: 1, spanUnit: MONTH` → `[today, endOfCurrentMonth]`; `spanAmount: 2` → through the end of *next* month);
   - span is additive-only: omitting `spanAmount`/`spanUnit` leaves every existing resolution byte-identical to today's (zero behavior change for every current caller/fixture);
   - a **THIS_MONTH anchor with a DAY/WEEK offset already has defined, tested semantics in shipped code** (`resolveDateRangeFilter`'s `else` branch: the whole month window shifts by the offset, not a day-of-month slice) — verified via the 3 existing tests at `buildEventsQueryCondition.test.ts` lines 114-125 (`resolves THIS_MONTH shifted by DAY/WEEK/MONTH offset...`); this story adds no new behavior here, only confirms (and must not regress) it.

2. **AC2 — multi-value `dayOfWeek` + Gemini `temporalFilter` extraction (epics.md AC2):** Given `EventFilterInput.dayOfWeek` widened to accept `DayOfWeek[] | DayOfWeek | null` (backward-compatible union — every existing singular value stays valid), when 2+ weekdays are supplied (weekends = `['SAT','SUN']`, weekdays = `['MON','TUE','WED','THU','FRI']`), then `buildEventsQueryCondition` passes the full array straight to the existing array-capable `getDays(from, to, dow[])` (already generalized for AD-19; today's code only ever wraps a singular value into a 1-element array before calling it) and ANDs/ORs the resulting per-date `scheduleDateRange` conditions exactly as the existing single-value path already does. And: `transformGeminiResponseToEventFilter` (the pure Gemini-response-parsing function in `packages/domain`) is extended to also extract `temporalFilter` (`TODAY`/`UPCOMING`) from the raw payload — a field it does not read today at all — and to accept either a single weekday string or an array of weekday strings for `dayOfWeek`, filtering to valid enum members and preserving the existing singular-output behavior when exactly one valid value is found.

3. **AC3 — timezone-aware date resolution; explicit (not magic) fallback/no-match behavior; bounded `offsetAmount` (absorbs FIND-082: DW-074..077) (epics.md AC3):**
   - **DW-074 (timezone):** `buildEventsQueryCondition`'s date-range/day-of-week resolution accepts an optional IANA `timezone` string and computes "today" as seen in that zone (via `Intl.DateTimeFormat`'s zoned Y-M-D, degrading gracefully to the instant's own UTC calendar date on an absent/invalid timezone, matching `project-context.md`'s established Intl-degradation convention) instead of unconditionally using the raw instant's UTC calendar date. The `TODAY` temporal filter's `!ended` boundary check (`buildTemporalCondition`'s `now.toISOString()`) is **not** changed — it deliberately stays a true, timezone-naive instant comparison, matching `drizzle-where.ts`'s own documented "Timezone scope of the `!ended` mirror" precedent (no call site passes a real per-event timezone to that specific check; changing only one side would make the two sides disagree).
   - **DW-075 (90-day fallback):** the inline magic `+ 90` days used when `dayOfWeek` is set without `dateRange` becomes a named, exported, documented constant (`DAY_OF_WEEK_ONLY_LOOKAHEAD_DAYS`). Same numeric value (90) — this AC is about making the behavior explicit and testable, not changing it.
   - **DW-076 (epoch-fallback trick):** the inline magic `'1970-01-01'` used to force zero results when no date in range matches the requested weekday(s) becomes a named, exported, documented constant (`NO_MATCHING_WEEKDAY_SENTINEL_DATE`) with an explicit code comment explaining why it reliably guarantees no overlap (and why a real "always-false" DSL terminal is not introduced here — see Dev Notes).
   - **DW-077 (`offsetAmount` bounds):** a single, named, exported bound table (`DATE_OFFSET_AMOUNT_BOUNDS`, keyed by `offsetUnit`) caps the magnitude of `offsetAmount` (and, reusing the same table, the new `spanAmount`, which must additionally be a positive integer ≥ 1). `resolveDateRangeFilter` throws a descriptive `Error` when a bound is exceeded (caught by the existing generic try/catch at `resolvers.ts`'s one `buildEventsQueryCondition` call site, surfacing as `BAD_REQUEST` — no `resolvers.ts` change needed). `transformGeminiResponseToEventFilter` enforces the same bounds but degrades gracefully (omits the invalid `dateRange`/span rather than throwing), consistent with its existing "if unparseable, omit the field" pattern for untrusted model output.

4. **AC4 — absolute dates, time of day and holiday names still produce a caveat (epics.md AC4, non-regression guard):** this story does not add parsing for any of these to the locked vocabulary, `transformGeminiResponseToEventFilter`'s shape, or `DateRangeFilter`. Caveat *emission* for anything outside the locked vocabulary is produced by the live `resolvePromptToEventFilter` resolver's existing system-prompt/`caveats` mechanism (`apps/backend/src/schema/resolvers.ts`), which this story does not touch. This AC is verified by confirming (code review + a test) that the new span/multi-weekday/temporalFilter fields stay confined to the closed `filter-vocabulary.md` grammar and do not widen it.

**Depends on:** Story 9.1a.

### Date grammar design decisions (resolved defaults — minimised per this session's dispatch instruction, not left as open questions)

1. **Span semantics (AC1).** `spanUnit: DAY`/`WEEK` extend the resolved `to` boundary by `spanAmount` days/weeks — a simple forward widening. `spanUnit: MONTH` is defined differently (extend `to` through the end of the `spanAmount`-th calendar month, counting the resolved window's own end-month as month 1) specifically so `{anchor: TODAY, offsetAmount: 0, offsetUnit: DAY, spanAmount: 1, spanUnit: MONTH}` resolves to "rest of this month" (today through the end of the current month) — one of epics.md AC1's three named examples. This was chosen over redefining the existing `THIS_MONTH`-anchor base window (rejected: `buildEventsQueryCondition.test.ts`'s pre-existing fixture `{anchor: 'THIS_MONTH', offsetAmount: 0, offsetUnit: 'MONTH'}` already asserts the *whole* month, including past days, as its resolved window — redefining that base case to clamp at "today" would silently break an existing, currently-passing test and contradict the already-shipped meaning of `THIS_MONTH` + zero offset). Span is purely additive and never applied by any existing caller/fixture today, so this introduces zero behavior change to anything already shipped.
2. **`dayOfWeek`'s multi-value upgrade stays inside `EventFilterInput`'s own TypeScript union (`DayOfWeek[] | DayOfWeek | null`), not a GraphQL schema change.** The GraphQL `DateRangeFilterInput`/`EventFilterInput`/`EventFilter` types (`events.graphql`) keep `dayOfWeek: DayOfWeek` (singular) exactly as-is — widening that to `[DayOfWeek!]` is explicitly Story 9.3's scope ("Expose filter expressions through GraphQL, resolvers and Widgets... `dayOfWeek: [DayOfWeek!]`"). This story's new capability is therefore not yet reachable from any live GraphQL query/mutation, matching Story 9.1a's own "nothing in the app today imports this" precedent — `transformGeminiResponseToEventFilter`'s new array-output path and `buildEventsQueryCondition`'s new array-input handling are real, tested, and ready for Stories 9.3/9.4 to wire up, but produce zero live behavior change on their own.
3. **The timezone fix (DW-074) is scoped to the "what calendar day is 'today'" boundary only — never the `notEnded` instant comparison.** `drizzle-where.ts`'s own existing doc comment ("Timezone scope of the `!ended` mirror... a deliberate scope decision, not an oversight: no call site in this codebase passes a real per-event timezone today, so both sides already agree on the same lack of conversion") already establishes this exact boundary as intentional elsewhere in the codebase; this story's fix is consistent with, not a reversal of, that precedent. Concretely: `buildTemporalCondition` receives `timezone` and uses it only for `today`/`tomorrow` (date-boundary) computation, never for the literal `now.toISOString()` passed as the `notEnded` operator's real-time instant.
4. **"THIS_MONTH anchor with a DAY/WEEK offset has defined, tested semantics" (epics.md AC1's second clause) is already satisfied by shipped code** — `resolveDateRangeFilter`'s existing `else` branch (whole-month window shifted by the offset, with an explanatory comment about TS enum narrowing already in place) and the 3 existing tests at `buildEventsQueryCondition.test.ts:114-125` cover exactly this. This story adds no new logic here; Task 10 only confirms these 3 tests stay green after the span/timezone changes land in the same function.
5. **DW-075/DW-076 ("explicit behavior") is resolved as naming + documenting + testing the existing numeric values, not changing them.** A genuinely new "always guaranteed false" DSL primitive was considered and rejected for this story: `packages/graphql-select/drizzle-where.ts` already has one usable mechanism (`operator: 'in', value: []` → `sql\`false\``), but reusing it safely would require picking a field name guaranteed present in *every* caller's `fieldMap` (`Query.events`, Feed, AccountEvents, WeeklyCalendar, Widgets, etc.) — unverifiable from `packages/domain` alone without reading and auditing every consumer's fieldMap, and a new dedicated DSL "never" terminal would require extending `DSLOperator` and the SQL translator, which is explicitly Story 9.2/9.3's territory (`DSLOperator` today is `'and' | 'or'` only; extending it is "explicitly 9.2's job" per `ai-filter-boolean-nested-query-upgrade-plan.md`) and would conflict with Gate 1's "no new backend/API surface" finding for this epic. Keeping the existing `scheduleDateRange`/`overlaps` sentinel-date trick — but naming, documenting, and testing it explicitly — satisfies "explicit behavior" at the lowest risk and narrowest footprint.
6. **`offsetAmount`/`spanAmount` bounds (DW-077) are enforced in two different ways for two different trust levels**, both reusing the one shared `DATE_OFFSET_AMOUNT_BOUNDS` table (never two separate number sets): `resolveDateRangeFilter` (the domain/query-building layer, reachable by any caller including a direct GraphQL `EventFilterInput`, not just AI-produced ones) **throws** on violation — this is caught by the pre-existing generic try/catch around `buildEventsQueryCondition`'s one call site in `resolvers.ts` (`Query.events`), which already converts any throw from this function into a `BAD_REQUEST` GraphQLError (see the existing `coordinates`+`adminArea` conflict, which uses this exact same throw/catch path today) — so this defense-in-depth requires zero `resolvers.ts` changes. `transformGeminiResponseToEventFilter` (untrusted Gemini output) **degrades** on violation (omits the `dateRange` field, same as every other unparseable-field case in that function today) rather than throwing, since a single bad field from a model response should not fail the whole prompt.
7. **AC4 is a non-regression guard, not new capability — verified by what this story does *not* do.** `transformGeminiResponseToEventFilter` still has no field for an absolute date, time-of-day, or holiday name; `DateRangeFilter`'s only new fields are `spanAmount`/`spanUnit` (still relative-only, composable with the existing `anchor`/`offsetUnit`); `filter-vocabulary.md`'s locked vocabulary is unchanged by this story (that amendment is Story 9.9z's explicit job). Caveat *emission* for anything outside this vocabulary is produced entirely by the live `resolvePromptToEventFilter` resolver's pre-existing system-prompt/`caveats` array (`apps/backend/src/schema/resolvers.ts`), untouched here.
8. **`render-ai-filter-summary.ts`'s forced touch (Task 9) is scoped to compile-safety, confirmed by Gate 2 above.** Widening `EventFilterInput.dayOfWeek`'s type would otherwise fail `tsc` at this file's existing `clauses.push((labels.daysOfWeek && labels.daysOfWeek[dow]) ? ... : dow)` line (`clauses: string[]`, `dow` could now be `DayOfWeek[]`). The fix maps each array entry through the *existing* label lookup and joins with the existing default separator — it introduces no new label key, no new join-word grammar, and no new locale string, leaving Story 9.5's "deterministic template output with locale-safe and/or/not words... the new date phrasings... render in both locales through `next-intl`" fully open as its own, richer piece of work.
9. **`filter-node-schema.ts`'s `dateRangeFilterSchema` is updated even though `validateFilterNode` doesn't strictly require it for correctness today** (it walks the raw candidate and returns it as-is rather than Zod's own stripped/parsed output, so an un-validated extra field would currently pass through silently either way). It is updated anyway so the schema stays a complete, accurate contract for `DateRangeFilter`'s real shape — consistent with Story 9.1a's AC4 "single definition of limits" rigor — reusing `DATE_OFFSET_AMOUNT_BOUNDS` from `buildEventsQueryCondition.ts` rather than re-declaring the bound numbers a second time.

## Story

As a developer,
I want a dedicated Geolocation adapter that wraps all outbound calls to the Google Geolocation/Places API behind a single interface, with a caching layer for repeated lookups and a restricted, backend-only API key,
so that every feature that resolves coordinates, addresses, or timezones (map-based location picking, nearby-event search, timezone inference for extracted events) reuses the same client and cache instead of each feature calling the Geolocation API directly and re-incurring cost/quota.

## Acceptance Criteria

1. **Given** a feature needs to resolve a location (address, place ID, or coordinates) or infer a timezone, **when** it needs geolocation data, **then** it does so exclusively through this Adapter's exposed interface — never the raw Google Geolocation/Places SDK/HTTP API from feature code. [epics.md AC1]
2. **And** the Adapter caches lookups for the same location so repeated queries are served from cache rather than re-calling the external API (NFR14). [epics.md AC2]
3. **And** the Google API key used by the Adapter is restricted in the Google Cloud Console (API restrictions + application restrictions) per the PRD's API key security requirements. [epics.md AC3]
4. **And** the Adapter is backend-only — no direct Geolocation API calls are made from `apps/web`. [epics.md AC4]
5. **Given** no feature story yet calls this Adapter (Story 2.3a "Build the saved-locations backend GraphQL API layer", `ready-for-dev`, explicitly cites this Adapter in its own AC; Story 2.4 "Set location by current location or map" and FR33's timezone-inference logic are further future consumers, all currently `backlog`), **when** this story ships, **then** the Adapter is a reserved, ready-to-consume capability — no product/pipeline code invokes it in this story. This story proves the Adapter end-to-end via 100%-covered unit tests of its pure cache-key-normalization logic (`packages/domain`) plus a mocked-dependency integration test of the HTTP-calling orchestrator (`apps/backend`); a real call against a live, billing-enabled Google Cloud project is explicitly deferred (see Dev Notes "Google Cloud Billing & Live API Verification"). [Derived — mirrors the "reserved slot" pattern from Stories 0.7/0.8/0.9/0.12/0.13/0.15]
6. **Given** `docs/infrastructure/high-level-overview.md`'s architecture diagram currently shows only `Gemini`/`FCM` under `External Services` and has no Google Geolocation/Places node, **when** this story ships, **then** the diagram is updated to show `L_API` sending to a `Google Maps Platform` external-service node, and a new `docs/infrastructure/N-geolocation.md` shard (next available number — see Task 9) documents the service choice — mirroring the existing per-service shard convention already used by `4-push-notifications.md` and (once implemented) `5-outbound-email.md`. ## Dev Notes

- **This story is pure infrastructure/plumbing — no product UI ships, and no feature story calls it yet.** Story 2.3a ("Build the saved-locations backend GraphQL API layer", `ready-for-dev`, its own AC explicitly names this Adapter) is the first real caller, followed by Story 2.4 (map/current-location picking UI) and FR33's timezone-inference logic (Epic 3, folded into Story 3.6's extraction pipeline). This mirrors the "reserved slot, not implemented" pattern already established by Stories 0.7, 0.8, 0.9, 0.12, 0.13, and 0.15.
- **`packages/domain`/`apps/backend` scaffolding sequencing conflicts — same recurring Epic 0 pattern as Stories 0.9-0.15.** As of this story's creation, neither package has a committed `package.json` (`git ls-files` returns nothing for both). Tasks 1/2 handle both orderings explicitly, mirroring Stories 0.13/0.15's identical Task 1/2 resolution.
- **Why this Adapter reuses `@festgrid/shared-types`'s `Coordinates`/`LocationDetails` instead of defining new local types (unlike Stories 0.13/0.15):** Both interfaces already exist in `packages/shared-types/src/index.ts` (`Coordinates { latitude, longitude }`, `LocationDetails { coordinates, placeName?, placeId?, formattedAddress?, timezone? }`), created by the PRD's §4.2/§4.3 data-model definitions and already consumed by `Schedule.locationDetails`. Reusing them (rather than inventing a package-local equivalent, as Story 0.13's `ApiKeyCandidate` or Story 0.15's `EmailTemplateVariables` did, since no shared-type equivalent existed for those) keeps this Adapter's return shape identical to what `apps/web`/GraphQL will eventually expose for `Schedule.locationDetails`, avoiding a future mapping-layer duplication. Confirmed safe for `packages/domain` to depend on: `packages/shared-types/package.json` has zero runtime dependencies (no React/DOM), so this is the **first** workspace-package dependency `packages/domain` takes on, without violating `project-context.md`'s "no React in `packages/domain`" restriction.
- **Why the cache-key normalization logic lives in `packages/domain`, but the HTTP/DB-calling code lives in `apps/backend`:** `buildLocationCacheKey`/`buildTimezoneCacheKey` are pure functions over plain strings/numbers (no I/O, no SDK, no network) — exactly the "framework-agnostic business logic" `packages/domain` exists for, and the persistent "reusable mechanism → `packages/domain`" project rule applies cleanly (same precedent as Story 0.13's `selectApiKey`/Story 0.15's `renderEmailTemplate`). The Google Maps REST calls, the Drizzle cache-store reads/writes, and the env-var read are all I/O- and SDK-coupled — these stay in `apps/backend`, consistent with that same precedent.
- **Why Native `fetch` Instead of a Google Maps SDK:** The official `@googlemaps/google-maps-services-js` Node client (latest `3.4.2` on npm, last published roughly a year ago per this story's research) bundles the Geocoding API and Time Zone API this Adapter needs, but its own README explicitly recommends **against** using its bundled Places support for new work — Google designated the legacy Places API a frozen "Legacy service" in March 2025 (no new features, and Google's official policy requires ≥12 months notice before a hard deprecation date, which has not yet been set as of this story's creation) and instead directs new integrations to the **Places API (New)**, which the older client library does not cover. Rather than mixing one SDK (for Geocoding/Time Zone) with hand-rolled REST calls (for Places API (New)) — two different calling conventions for what is conceptually one adapter — this story implements all three as consistent, dependency-free native-`fetch` wrappers in a single `google-maps-client.ts`. This avoids a package-isolation surface for a dependency that (a) doesn't fully cover this story's needs and (b) is only thinly used (three simple `GET` calls, no complex request-building), mirroring Story 0.13's identical reasoning for hand-rolling `backoff.ts` instead of pulling in an ESM-only `p-queue`, and Story 0.15's identical reasoning for hand-rolling `render-template.ts` instead of pulling in a templating library.
- **API Key Application-Restriction Limitation (accepted assumption requiring Pre-Coding Approval Gate sign-off):** The PRD's API Key Restriction requirement (§External API Management) calls for both **API restrictions** (which API(s) the key may call) and **Application restrictions** (e.g. HTTP referrer or IP address, limiting which caller may use the key). This story applies API restrictions in full (the key is restricted to exactly the Geocoding API, Places API (New), and Time Zone API — Task 10). Application restrictions are **not** applied: HTTP-referrer restriction is a browser-call-site concept and does not apply, since AC4 mandates this key is *never* called from `apps/web`; IP-address restriction would require a **static outbound IP** for the calling Lambda, which requires routing it through a NAT Gateway with an Elastic IP — infrastructure `epic-0-readiness.md`'s Gate 1 pass explicitly confirmed is *not* part of Story 0.14's current IaC resource list ("Story 0.14's 4-Lambda IaC list is complete for the architecture diagram as drawn"). Adding a NAT Gateway solely to enable IP restriction on this one API key would be a nontrivial, ongoing-cost IaC change (NAT Gateways are not part of any AWS free tier) out of proportion to the risk it mitigates for a key that is API-restricted to three narrow, non-destructive read APIs. This story proceeds with API-restriction-only for MVP; flagged explicitly for human sign-off since it is a deliberate security-posture trade-off, not just a technical wiring choice — mirroring Story 0.13's "Billing-Cycle Interpretation" and Story 0.15's "SES Domain Verification" flagged-assumption precedent.
- **Google Cloud Billing & Live API Verification (accepted forward dependency, not a Gate 1 gap):** Unlike Gemini's AI Studio free-tier key (Story 0.13, no billing account required), Google Maps Platform requires an **active billing account** on the Google Cloud project even to consume its per-SKU free tier (Geocoding: 10,000 free requests/month; see "Latest Tech Information" below) — a one-time, per-account manual prerequisite this development environment has no access to set up. This story's `google-maps-client.ts` reads its API key lazily (mirrors Story 0.12/0.13/0.15's lazy-SDK-client-init pattern) so `apps/backend dev`/`build`/unit-tests all work without a real key/billing account; the full real-Google-Maps-Platform round trip is deferred to whenever Story 2.3a (or a later consumer) runs against a fully set-up Google Cloud project, the same way Story 0.12 deferred its full real-Firebase round trip and Story 0.13/0.15 deferred their full real-KMS+Gemini/real-SES round trips.
- **Caching has no TTL/expiration (assumption requiring Pre-Coding Approval Gate sign-off):** Neither the PRD's NFR14 nor epics.md's AC2 specifies a cache expiration policy — geographic coordinates for a fixed address, a stable Place ID, and a location's IANA timezone are all effectively permanent facts (address→coordinates essentially never changes; timezone boundaries change on the order of decades, not days). This story therefore implements the cache as **indefinite** (no TTL, no invalidation path) — a `geolocation_cache` row, once written, is served forever. Flagged for human sign-off since it is a product-behavior interpretation (same category as Story 0.13's billing-cycle assumption), not just a technical wiring choice; revisiting this later (adding a TTL column/backfill) would be a small, additive follow-up if a future story surfaces a real need (e.g. a business relocating).
- **Package dependency isolation (project-context.md, persistent fact):** No new npm dependency is introduced in `apps/backend` for this story (native `fetch` is used — see above). `packages/domain` gains its first workspace dependency, `@festgrid/shared-types` (reasoned above) — still zero third-party SDK dependencies, consistent with the restriction.

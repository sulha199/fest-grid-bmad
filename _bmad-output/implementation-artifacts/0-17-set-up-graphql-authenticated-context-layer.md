# Story 0.17: Set up GraphQL authenticated-context layer

- Status: ready-for-dev

## Story

As a developer,
I want the GraphQL server to verify a caller's Supabase Auth session/JWT on incoming requests and expose the authenticated user's identity and role via resolver context,
so that every mutation or query that requires "the current user" (favoriting, saved locations, subscriptions, reports, moderator actions) can enforce ownership/authorization consistently instead of each feature story inventing its own verification.

## Acceptance Criteria

1. **Given** the GraphQL server scaffold (Story 0.8) exists, **when** an authenticated client sends a GraphQL request carrying its Supabase session token in the `Authorization: Bearer <token>` header, **then** the server verifies the token's signature and expiry against Supabase Auth's own public JWKS and populates resolver context with the caller's `userId` (matching the `users` table, Story 1.1) — never trusting a client-supplied user ID. [epics.md AC1]
2. **And** requests without a valid session expose `context.user` as `null`, and resolvers/mutations that require authentication reject unauthenticated calls with a clear, consistent error. [epics.md AC2]
3. **And** the `users` table (Story 1.1) gains a `role` column (default `user`, supporting a `moderator` value per the PRD's "moderator access levels are assigned manually via the database" MVP scope), so resolver context also exposes the caller's role. [epics.md AC3]
4. **And** a reusable authorization helper (`requireAuth`/`requireModerator`) is exported for resolvers to import, rather than each resolver hand-rolling its own check. [epics.md AC4]
5. **Given** a request carries a malformed, expired, or otherwise unverifiable JWT (bad signature, unknown `kid`, expired `exp`), **when** the context factory processes it, **then** it is treated identically to no token at all (`context.user = null`) — an invalid credential is not a server error, and only `requireAuth`/`requireModerator` (AC4) surface the "must be authenticated"/"must be a moderator" error to the caller. [Derived — the server must degrade gracefully under malformed/expired input, not throw an unhandled 500]
6. **Given** a JWT verifies successfully but no `users` row exists yet for its `sub` claim, **when** resolver context is built, **then** a new `users` row is created (JIT-provisioned) using the JWT's `sub` as the row's `id` and `email`/`name`/`avatar_url` populated from the token's claims/`user_metadata` where present — satisfying Story 1.7's own AC ("a new user account is created in the system if it doesn't exist, persisted via the backend API layer") without Story 1.7 needing a separate signup mutation. Concurrent first-requests for the same new user must not fail or duplicate the row. [Derived — closes the undocumented gap between `users.id` (currently `defaultRandom()`, Story 1.1) and Supabase Auth's own user ID; see Dev Notes and Pre-Coding Approval Gate]
7. **Given** no feature story yet calls `requireAuth`/`requireModerator` from inside a real resolver (Story 1.7's login UI is `ready-for-dev`, not `done`; Stories 2.1a, 2.3a, 3.1, 4.1a, 4.3a, 4.4a, 5.1a are all `backlog`), **when** this story ships, **then** the auth-context layer is proven end-to-end using synthetically-signed test JWTs (a locally generated test keypair via `jose`, not a real Supabase project) — this story does not depend on a live, configured Supabase Auth project to be verifiable. Mirrors the "reserved slot, not implemented" pattern of Stories 0.7/0.8/0.9/0.12/0.13/0.15/0.16. [Derived]

## Dev Notes

- **This story is pure infrastructure/plumbing — no product UI ships, and no feature resolver calls `requireAuth`/`requireModerator` for real yet.** Story 1.7 (login UI, `ready-for-dev`) is the mechanism that will make real Supabase-issued JWTs exist; Stories 2.1a, 2.3a, 3.1/3.2, 4.1a, 4.3a, 4.4a, and 5.1a (all `backlog`) are the real future callers of the two helper functions. This mirrors the "reserved slot, not implemented" pattern already established by Stories 0.7, 0.8, 0.9, 0.12, 0.13, 0.15, and 0.16.
- **`apps/backend` already exists and is mid-flight (Story 0.8, `in-progress`) — this is an extension, not a scaffold.** Unlike Stories 0.13/0.15/0.16 (which had to handle a still-empty `apps/backend`), this story's Task 1 confirms the current shape directly from the working tree rather than branching on `git ls-files` emptiness.
- **Why JWKS/asymmetric verification, not a shared `HS256` secret (Pre-Coding Approval Gate item):** Supabase migrated Auth to asymmetric (ES256/JWKS-based) signing keys as the recommended default (Supabase's "JWT Signing Keys" guide, checked 2026-08-01) — new projects should use this from the start. Verifying against the public JWKS endpoint (`{SUPABASE_URL}/auth/v1/.well-known/jwks.json`) means **no shared secret ever needs to be stored** in `apps/backend`'s environment at all (a strictly smaller secret-management surface than the legacy `HS256`-shared-secret approach, which needed the Supabase project's JWT secret copied into `.env`). This story assumes the (not-yet-created, per Story 1.1's Dev Notes) Supabase project will use the modern asymmetric default and implements only that path — no legacy `HS256` fallback. Flagged for explicit human sign-off since it's a concrete assumption about a cloud project's auth configuration this development environment cannot verify directly (same category as Story 0.16's "API Key Application-Restriction Limitation" flagged assumption).
- **The `users.id === auth.users.id` JIT-provisioning convention — now formalized as AD-7 (approved 2026-08-01):** `packages/database/schema.ts`'s `users.id` is currently `uuid('id').defaultRandom().primaryKey()` — a self-generated ID with **no** column linking it to Supabase Auth's own `auth.users.id`. This story establishes (and `festgrid-architecture-spine.md`'s new **AD-7: Authenticated Context & Authorization** now formally binds) the convention by which they relate: `public.users.id` **is** the Supabase Auth `sub` (i.e. the same UUID as `auth.users.id`), enforced by always inserting with an explicit `id` in `getOrCreateUser` (Task 4) rather than letting `defaultRandom()` fire. This is the standard, common Supabase pattern (a `public.users` "profile" table keyed identically to `auth.users`) and avoids adding a second lookup column/index purely to bridge the two. It is binding — per AD-7 — on every future story that creates `users` rows from an authenticated context. AD-7 also formalizes JWKS-only verification (no legacy shared-secret path), `requireAuth`/`requireModerator` as the single sanctioned enforcement surface, and the app-level `users.role` vs. Supabase's JWT `role` claim distinction — see `festgrid-architecture-spine.md`.
- **Do not confuse the Supabase JWT's `role` claim with this project's `users.role` column.** Supabase's own JWT `role` claim is the caller's Postgres role (`authenticated`/`anon`/`service_role`) used for Supabase's Row Level Security — a completely different concept from the application-level `role` (`user`/`moderator`) this story adds to the `users` table (AC3). `requireModerator` (Task 5) must check `AuthenticatedUser.role`, sourced from the DB via `getOrCreateUser`, never anything read off the JWT payload directly. This is exactly the kind of subtle same-word-different-meaning mistake an LLM developer is likely to make without this explicit callout.
- **Why `SUPABASE_URL` is a separate env var from whatever Story 1.7 adds for the frontend:** This story is backend-only (`apps/backend/src/env.ts`, root `.env`, no `NEXT_PUBLIC_` prefix — AC1 never trusts the frontend, and the value itself isn't sensitive, so there's no security reason to share the exact variable *name*, only reuse the same underlying Supabase project). Story 1.7 (not yet built) will separately need its own `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` in `apps/web` for the Supabase JS client used to drive the actual Google OAuth redirect flow — that is Story 1.7's own env-var setup, not something this story should pre-empt or rename.
- **Why the JWT verification/JIT-provisioning code stays entirely in `apps/backend`, not `packages/domain`:** Every piece of this story's logic is either I/O-coupled (the JWKS HTTP fetch inside `jose`, the Drizzle DB read/write in `getOrCreateUser`) or GraphQL/Yoga-context-shape- and `GraphQLError`-coupled (`createContext`, `requireAuth`, `requireModerator`) — neither category is the "framework-agnostic business logic" `packages/domain` exists for (same reasoning precedent as Story 0.16's cache-key-normalization-vs-HTTP-client split, and Story 0.8's `buildOptimizedDrizzleSelect`-stays-Drizzle/GraphQL-coupled reasoning). Unlike Story 0.16, there is no leftover pure-function slice (e.g. a cache-key builder) worth extracting here — even the smallest unit, "is this role `'moderator'`", is a trivial one-line comparison not worth its own package. **No `packages/domain` change in this story.**
- **Package dependency isolation (project-context.md):** `jose` and `@festgrid/database` are added to `apps/backend` only. No change to `apps/web`, `packages/domain`, or any other package. `@festgrid/database`'s addition to `apps/backend` is an expected, already-anticipated dependency (Story 0.8's own Dev Notes flagged Story 1.3a as the first resolver to add it; this story is the first *context-layer* consumer, the same category of use, not a new isolation violation).
- **No `packages/ui` component is introduced.** Zero UI surface — confirmed via a fresh Gate 2 subagent dispatch (persona Freya) against both authoritative UX artifact sets plus the `design-artifacts/C-UX-Scenarios/00-login-flow/` and `06-data-quality/06.7-user-moderator-interfaces.md` scenario pages; the only auth/moderator-adjacent UI concepts found (Google-login modal, logout toast, Moderator Items page) are already owned by Story 1.7 and its own future moderator-UI story, not this one. **Result: No gap found** — see Architecture & UX Gate Findings below.
- **No Unified Query DSL (AD-1/AD-2) involvement** — this story never retrieves an event collection.
- **No PostHog/analytics events (AD-5)** — this story introduces no user-facing interaction to instrument; any signup/login analytics event belongs to Story 1.7, not this one.
- **No i18n strings (AD-6)** — this story ships no user-facing text; `UNAUTHENTICATED`/`FORBIDDEN` GraphQL error codes are protocol-level, consumed by client error-handling logic, not displayed as raw strings to end users (mirrors Story 0.12/0.15/0.16's identical "AD-6 does not bind backend-only code" conclusion).
- **No state-management categorization applies** — this is backend-only; nothing is stored in Server State/URL State/Client Global State.
- **No async loader (blocking/non-blocking) categorization applies** — no UI renders a loading state for this story's async functions.
- **Latest Tech Information:** `jose` latest stable is `6.2.5` (npm, checked 2026-08-01) — the actively maintained (panva/jose) library for JWA/JWS/JWT/JWK/JWKS in Node.js; `createRemoteJWKSet` + `jwtVerify` is the documented pattern for verifying Supabase's asymmetric-signed JWTs against `{SUPABASE_URL}/auth/v1/.well-known/jwks.json` (Supabase's own edge caches this endpoint for 10 minutes). Supabase's JWT payload carries `sub` (the `auth.users` UUID), `email`, and (for Google-OAuth-originated sessions, relevant once Story 1.7 lands) `user_metadata.{name,full_name,avatar_url}` populated from the Google profile — this story reads exactly those fields and no others. Supabase's own JWT `role` claim (`authenticated`/`anon`/`service_role`) is a Postgres-RLS concept, distinct from this story's new `users.role` column (see callout above).

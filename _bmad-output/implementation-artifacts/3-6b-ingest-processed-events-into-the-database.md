# Story 3.6b: Ingest processed events into the database

## Story Details

- **Epic:** 3
- **Story ID:** 3.6b
- **Status:** ready-for-dev

## Story

**As a** system,
**I want** to consume a validated `EventInfo` message from the `DataIngestionQueue` and write it to the database,
**So that** the AI Processor Lambda (Story 3.6) stays decoupled from the database per the architecture's queue-based pipeline design.

## Acceptance Criteria

1. **Given** there is a message (`ExtractedEventMessage`, `packages/domain/src/events/types.ts`) in the `DataIngestionQueue`, **when** it is consumed by the Ingestor Lambda, **then** a new `events` row is inserted with `eventName`, `types`, `categories`, `organizerName`, `contactInfo`, `description`, `confidenceScore`, `sourceSocialMediaAccountId`, and `postId` populated directly from the message; `slug` is left unset and generated by the DB's own `$defaultFn(generateSlug)` default, matching the existing `posts`/`schedules` convention.
2. **And**, **given** the message's `location` is absent (Story 3.6's AC5: no explicit post location and no account `defaultLocation`), **when** the `events` row is built, **then** the fixed placeholder string `"Location not specified"` is written to `events.location` instead of leaving it unset — resolving the `NOT NULL`-vs-optional conflict Story 3.6's Dev Notes forward-noted to this story, per the user's `AskUserQuestion` decision (see Dev Notes "Absent-Location Resolution").
3. **And** each entry in `message.schedules` produces exactly one `schedules` row linked via `eventId` to the newly inserted event, with `isMainSchedule`, `eventStartDate`, `eventEndDate`, `eventStartTime`, `eventEndTime`, `title`, `performers`, `location`, `ticketPrice`, and `locationDetails` mapped directly (a message with zero schedules produces zero schedule rows, not an error).
4. **And** `schedules.latitude`/`schedules.longitude` (existing nullable columns with no writer until this story) are populated from `message.schedules[i].locationDetails.coordinates.{latitude,longitude}` when `locationDetails` is present, and left `null` when it is absent.
5. **And** `schedules.timezone`/`schedules.timezoneStatus` (added by Story 3.6a, also with no writer until this story) are populated from `message.schedules[i].timezone`/`.timezoneStatus` when present, and left `null` when absent — per Story 3.6a's Amendment to this story.
6. **And** the `events` row and its `schedules` rows are written inside a single database transaction — a failure inserting any `schedules` row rolls back the `events` insert too, so no orphaned event-without-schedules row is ever left behind.
7. **And** duplicate/already-ingested events are handled gracefully: a new unique constraint on `events.postId` (this story's own migration) combined with `onConflictDoNothing` makes the `events` insert idempotent, so an SQS-redelivered message for a `postId` that already has an `events` row results in zero new `events`/`schedules` rows and is logged as a skipped duplicate, not treated as an error.
8. **And** the Ingestor Lambda's `SqsEventSource` has `reportBatchItemFailures: true`, and the handler returns `{ batchItemFailures: [{ itemIdentifier }] }` for exactly the records that threw (e.g. a transient DB error) — mirroring `aiProcessorLambda`'s own established partial-batch-retry precedent (Story 3.6) rather than `scraper.ts`'s no-partial-retry gap, since silently losing a fully-extracted event on a transient DB error is a real gap, not a benign simplification.

**Note:** This story exists because of Gate 1 (`story-split-gate.md`) — Story 3.6's original draft had the AI Processor Lambda both call Gemini and write to the database, bypassing the separate Ingestor Lambda (`L_Ingest`) shown in `docs/infrastructure/high-level-overview.md`. This story is that Ingestor Lambda.

**Amendment (2026-08-10, added via `bmad-create-story` while drafting Story 3.6a):** This story's DB write must also persist the two new `schedules` columns Story 3.6a adds (`timezone: text`, `timezoneStatus: 'RESOLVED' | 'NEEDS_CLARIFICATION'`), sourced from `ExtractedScheduleMessage`'s corresponding new fields — not just the fields already listed above. Flagged via Gate 1's traceability recommendation during Story 3.6a's creation, so this dependency doesn't stay implicit. (Implemented as AC5 above.)

**Depends on:** Story 3.6 (`review`, real code), Story 3.6a (`review`, real code — landed mid-way through this story's own creation; see Dev Notes "Dependency Timing").

### Absent-Location Resolution

Story 3.6's Dev Notes ("Absent-Location Data Type Gap") forward-noted an unresolved conflict to this story: `shared-types`' `EventInfo.location: string` and `packages/database/schema.ts`'s `events.location` are both required/`NOT NULL`, but Story 3.6's own AC5 deliberately leaves `ExtractedEventMessage.location` absent when a post has no explicit location and the source account has no `defaultLocation` set either ("left absent rather than fabricated"). This story is where that has to actually resolve at insert-time, since it is the first (and only) writer of `events` rows.

Three options were presented to the user via `AskUserQuestion` before drafting this story:
1. **Insert a fixed placeholder string** (e.g. `"Location not specified"`) into `events.location` — chosen. Satisfies `NOT NULL` honestly (a placeholder, not a fabricated real-looking location), requires no schema/`shared-types`/GraphQL/frontend change, and the event still reaches users rather than being silently dropped.
2. Migrate `events.location`/`EventInfo.location` to nullable end-to-end — rejected for this story as correct long-term but a materially larger, cross-cutting change (schema migration, `shared-types`, any `.graphql` field, every frontend consumer assuming `location: string` — `EventCard`, search/filter, detail view) that doesn't belong inside a single Lambda-write story.
3. Skip the event/log only, no `events` row — rejected because it silently discards an otherwise-fully-extracted, valid event over one missing field, cutting against AC5's own "left absent rather than fabricated" intent, which implies the event should still surface.

Implemented as AC2/Task 2's `buildEventInsertValues`. No schema, `shared-types`, or GraphQL change required for this decision.

### Idempotency & Atomicity Design

- **Idempotency (AC7):** follows this codebase's existing `onConflictDoNothing` idiom (`persist-scraped-post.ts`'s `postUrlUnq` pattern, `get-or-create-user-settings.ts`, `subscribe-to-account.ts`) rather than a racy select-then-insert check — SQS's at-least-once delivery means the same message can arrive twice concurrently, and only a DB-level unique constraint + `ON CONFLICT DO NOTHING` is race-safe. `events.postId` is the natural idempotency key since Story 3.6's own scope is explicitly "exactly zero or one event per post" (its Out of Scope explicitly rules out multi-event-per-post extraction), making a 1:1 `postId`-to-`event` mapping a safe, definitional invariant for this story to rely on. `events.postId` stays nullable (`onDelete: 'set null'`, unrelated to this story) — Postgres unique constraints permit multiple `NULL`s, which is irrelevant here since this pipeline always supplies a real `postId`.
- **Atomicity (AC6):** `db.transaction()` (existing precedent: `packages/database/seed.ts`, `apps/backend/src/schema/resolvers.ts`) wraps both the `events` and `schedules` inserts so a `schedules`-insert failure never leaves an orphaned `events` row with no schedules.

### Partial-Batch-Failure Retry Strategy

Mirrors Story 3.6's own `aiProcessorLambda` precedent, not `scraper.ts`'s gap: `dataIngestionQueue`'s `SqsEventSource` currently has no `reportBatchItemFailures` configured, meaning a normal Lambda return (even with an inner record failure swallowed) would cause SQS to delete the *entire* received batch, silently losing any events that failed to insert due to a transient error (e.g. a momentary DB connection issue). Since this Lambda is the final, sole writer of extracted event data, losing an insert here means the entire Gemini extraction (a paid API call) was wasted with no recovery path. Task 4/5 add `reportBatchItemFailures: true` and the `{ batchItemFailures: [{ itemIdentifier }] }` handler shape, consistent with `aiProcessorLambda`'s own established pattern — `scraper.ts` itself remains unchanged (a separate, already-accepted tradeoff from Story 3.6, out of scope here too).

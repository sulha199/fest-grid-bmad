- (decision) v1 scope is on-demand only: prompt -> filter -> results shown immediately. No digest/scheduler (that's v2).
- (decision) Prompts are single-shot: no conversation memory, no follow-up refinement, no chat UI.
- (decision) Confirmed: formalize a shared, typed EventFilterInput GraphQL input used by Discovery, Widget, and the AI filter. Widget.filters: Record<string, unknown> is replaced by this typed shape. Reason: an AI-produced filter needs a schema to validate against before persisting (project-context.md's Zod/AJV-at-entry rule); confirmed with user after being left open at end of forge session.
- (decision) Confirmed: 'free'/'gratis' gets a cheap exact-text-match isFree exception to the v2-deferred price filter -- locked-vocabulary text match against Schedule.ticketPrice, no numeric parsing, no FX normalization. Not a stepping-stone to the general numeric price-threshold filter, which stays fully deferred to v2. Reason: cheap to build, 'free events' is a highly likely prompt; confirmed with user after being raised-not-resolved in forge session.
- (assumption) Location region-mode text match runs against a normalized adminArea field on LocationDetails, populated from Geoapify's 'county' response field (fallback to 'city' when county is absent).
- (decision) Verified live against Geoapify (2026-08-28): county field DOES generally separate Indonesian admin areas -- Sleman addresses consistently return county='Sleman Regency'; Kota Yogyakarta addresses return county='Yogyakarta' (bare, no 'Kota' prefix). One boundary-adjacent Kota Yogyakarta test address (Jalan Malioboro) returned county='Depok', an unrelated Sleman sub-district -- an OSM boundary-tagging artifact. city field is less reliable for regency addresses (returns kecamatan-town names like 'Pakem' instead of 'Sleman'). Decision: proceed with county-based adminArea for v1, document occasional boundary misattribution as an accepted data-quality limitation, not a blocker.
- (capability) CAP-1 On-demand prompt-to-filter: user types a free-text prompt and immediately sees matching event results; no saved state or scheduling is created unless the user explicitly saves.
- (capability) CAP-2 Structured filter vocabulary: prompt can express account, type, category, keyword, date-range (closed anchor+offset grammar) or day-of-week recurrence, location (proximity or region/adminArea), venueType, and isFree; anything outside this locked vocabulary degrades to a visible caveat rather than being dropped or fragile-parsed.
- (capability) CAP-3 Save and reuse: user can save a resulting filter for later reuse from a dedicated 'My AI Filters' list page (same pattern as Favorites/Subscriptions); the only supported way to change a saved filter afterward is re-prompting -- there is no edit UI, ever.
- (capability) CAP-4 Transparent, always-current summary: every AI filter (session-active or saved) is represented only by a deterministic, template-rendered summary sentence describing its current state (live-rendered, never a frozen caption) -- this is the entire transparency/trust layer replacing an edit UI.
- (capability) CAP-5 FilterHub integration: the AI entry point is a zero-permanent-width icon-only trigger (sparkle) opening the prompt as an overlay; when an AI filter is active, FilterHub's manual-control row is replaced by one collapsed summary line (never stacked alongside full manual controls, always exactly one row tall); manual FilterHub edits made after loading an AI filter change only the session's query state, never the saved entity.
- (constraint) Not a general chatbot: constrained system prompt + structured output only. Off-topic prompts reuse the same degrade-caveat mechanism as any unsupported fragment, not a separate moderation layer. Rejected: open-dialogue/general QnA framing -- it creates a BYOK abuse vector (users burning their own paid Gemini key as a free chat proxy).
- (constraint) Date grammar is closed: {anchor: TODAY|THIS_WEEK|THIS_MONTH, offsetAmount, offsetUnit: DAY|WEEK|MONTH}, composable, resolved fresh at read time (never a frozen absolute date). Day-of-week recurrence ('every Thursday') is a separate predicate field with different semantics, not folded into the anchor/offset grammar.
- (constraint) Location: proximity mode reuses existing coordinates+radius unchanged. Region mode is indexed text match against adminArea (see Geoapify verification decision above), not true polygon/point-in-polygon. Rejected: PostGIS -- new infra not justified by current use cases. Floor/wing/room-level detail ('Lantai 2') is not geocodable and stays in Schedule's existing raw-text location field -- shown but never filterable.
- (constraint) venueType is sourced from the existing Gemini extraction pipeline (Story 0.13 per-post schema), not the geolocation provider (unverified capability, weak for informal local venue names). Lives on LocationDetails.venueType alongside adminArea. When a Schedule falls back to the account's Default Location (PRD Section 3.7), it must inherit the entire LocationDetails object including venueType -- a partial inherit would systematically break venueType filtering on exactly the accounts that rely on the fallback (their own posts rarely restate their own venue type).
- (constraint) Unsupported-request handling is one general mechanism, validated independently against three cases (price threshold, floor-level detail, off-topic chat): surfaced as an explicit caveat in the rendered summary, never silently dropped, never fragile-parsed case-by-case.
- (constraint) isFree is a locked-vocabulary exact-text-match exception only (see decision above) -- no numeric parsing, no FX normalization; explicitly not a stepping-stone to the general price-threshold filter.
- (note) Rejected: a full 'AI mode' toggle that hides FilterHub entirely. Chosen instead: icon-only trigger (CAP-5).

# Accessibility Review — FestDaily Global Navigation

Reviewed against: WCAG 2.1 AA
Spec source: proposed 3-tier responsive nav (Discover/Feed/Favorites/Calendar/Profile) described for `EXPERIENCE.md` + `DESIGN.md`, not yet committed to those files.
Design tokens referenced: `accent: #FF5A5F`, `neutral: #FAFAFC`, `primary (text): #1E293B` (from `design-artifacts/UX-festgrid-run-1/DESIGN.md`).

## Overall verdict

The foundations are sound: `aria-current="page"` covers assistive-technology users independent of any visual styling, and the touch tap‑to‑flash label doesn't create an actual WCAG 2.2.1 timing violation since navigation isn't gated by the fade timer. However, three items should block sign-off: the accent-bar's contrast against the neutral background measures ~2.93:1 — under the 3:1 minimum WCAG 1.4.11 requires for non-text UI indicators — the hover-triggered rail tooltip has no stated keyboard-focus equivalent (WCAG 1.4.13), and the spec doesn't pin down the DOM structure closely enough to guarantee the three breakpoint variants won't produce duplicate/conflicting nav landmarks. The remaining findings are tightening items (explicit focus styling, explicit aria-label requirement, hit-area sizing) that should be written into the spec text even though most aren't hard AA failures on their own.

## Findings

- **high** The accent active-bar's color contrast against the neutral page background fails WCAG 1.4.11 (Non-text Contrast). Computed relative luminance for `#FF5A5F` ≈ 0.294 and `#FAFAFC` ≈ 0.957, giving a contrast ratio of **≈2.93:1** — below the 3:1 minimum required for graphical objects/UI components conveying state. Since the bar is the primary visual carrier of "this is the current page," a low-vision user could fail to perceive it even where it's present. (Active-state indication, all 3 breakpoints.) *Fix:* Either use a darker/more saturated variant of the accent specifically for this indicator (target ≥3:1 against `#FAFAFC`, e.g. shift toward `#E04347`-range), thicken the bar, or add a 1px darker outline/shadow to push effective contrast over 3:1. Add the chosen value as an explicit token (e.g. `nav_active_bar: "#..."`) rather than reusing the base `accent` token as-is.

- **high** The rail's hover-triggered label tooltip (768–1279px tier) has no stated keyboard-focus equivalent. WCAG 1.4.13 (Content on Hover or Focus) requires that content revealed on `:hover` also be revealed on keyboard `:focus`, remain visible until dismissed/focus moves, and be dismissible without moving the pointer. As written, a sighted keyboard-only user (e.g. motor-disability, no mouse) tabbing through the icon-only rail gets no visible label at all — only mouse users and touch users get one. (Icon-only rail, 768–1279px.) *Fix:* Spec must state the tooltip triggers on `:focus-visible` as well as `:hover`, persists while focus remains on the item, and dismisses on `Escape` or focus-out — same visual tooltip, dual trigger.

- **high** The spec describes three visually distinct layouts for the same 5 nav items but doesn't specify the DOM structure that realizes them. If implemented as two separate `<nav>` elements (one for the bottom tab bar, one for the rail) toggled by opacity/transform/visibility rather than `display:none`/`hidden`, both would remain in the accessibility tree simultaneously, exposing duplicate/conflicting "navigation" landmarks to screen reader users — and the risk is highest exactly at the breakpoint boundary (browser resize, split-screen, foldables), where a screen reader user's focus could land in a landmark that's visually gone. (Cross-breakpoint DOM structure — not yet specified.) *Fix:* Require in the spec either (a) a single persistent `<nav aria-label="Main">` whose internal layout is purely CSS-breakpoint-driven (no duplicate item markup), or if the mobile/desktop markup must differ structurally, (b) explicitly mandate that only one variant is ever present in the accessibility tree at a time (true `display:none`/`hidden` attribute, ideally `inert` on the hidden one) and that both variants share the identical `aria-label` text so a transitional state never reads as two different regions.

- **medium** No distinct visible focus indicator is specified apart from the active-state accent bar. A keyboard user tabbing through the rail/tab-bar needs a way to tell "this item currently has my focus" apart from "this item is the current page" — if both states are only expressed via the same accent-colored bar (or if focus relies on an unstyled browser default that a custom nav skin may suppress), the two states become indistinguishable. (Keyboard navigation, all 3 breakpoints.) *Fix:* Define an explicit focus style (e.g. 2px focus ring/outline in a color distinct from the active-bar accent, meeting WCAG 2.4.7) that renders identically whether or not the item is also the active/current route, so both states can be visually combined without collapsing into one signal.

- **medium** The spec doesn't explicitly require `aria-label` (or equivalent accessible name) on the icon-only rail items (768–1279px). At that tier there's no visible text label in the DOM by default — only an SVG icon plus a hover/focus tooltip — so without an explicit accessible-name requirement, an implementer could ship icon-only buttons with no programmatic name, failing WCAG 4.1.2 (Name, Role, Value). (Icon-only rail, 768–1279px.) *Fix:* State explicitly that every nav item carries `aria-label` matching the visible label text used at the ≥1280px tier (e.g. `aria-label="Favorites"`), independent of and in addition to the hover/focus tooltip — the tooltip is a visual affordance, not the accessible name.

- **medium** The touch "tap navigates + flashes label" pattern doesn't trigger WCAG 2.2.1 (Timing Adjustable) since navigation completes immediately and isn't gated by the fade timer, and the accessible name is available via `aria-label` regardless of the visual flash. But its practical value for low-vision/cognitive-disability users depends on an unstated assumption: that the nav rail/tab-bar is a persistent layout element that survives the client-side route transition it triggers, rather than being unmounted and remounted with the new page (which would kill the flash mid-animation or prevent it from ever rendering). The flash duration itself is also left unspecified ("a few seconds"). (Touch tap-to-flash, 768–1279px tier.) *Fix:* Explicitly state the nav is a persistent shell element that does not remount across route changes, and specify a concrete minimum flash duration (e.g. ≥2000ms, extendable — not shortened — under reduced-motion preferences) rather than leaving timing to implementer judgment.

- **medium** Touch/tap target sizing for nav items isn't given an explicit minimum in the spec. Note this is not a hard WCAG 2.1 AA gap on its own — Target Size (Enhanced) is SC 2.5.5, which is AAA-only in WCAG 2.1, and the AA-level Target Size (Minimum) SC 2.5.8 wasn't introduced until WCAG 2.2 — but it's still the standard baseline platform guidance (Apple HIG ~44pt, Android ~48dp) and a real motor-accessibility risk if an implementer sizes the clickable hit area to the icon's visual bounding box (typically 20–24px) rather than the full nav-item cell. The rail width (64–80px) and tab-bar cell width (viewport/5) both leave ample room for a compliant hit area — the risk is implementation discipline, not available space. (Icon-only rail and bottom tab bar.) *Fix:* Add an explicit token to `DESIGN.md`, e.g. `nav_item: "min-h-11 min-w-11 flex items-center justify-center"` (44px), so the hit area is a spec requirement rather than left to per-implementer judgment.

- **low** Reliance on the accent bar plus `aria-current` for active-state indication is not a strict WCAG 1.4.1 (Use of Color) violation, since the bar's *presence/absence* is itself a shape-based cue (not color alone) and `aria-current` independently covers screen-reader users. But given the bar's low measured contrast (see first finding), a low-vision or color-blind sighted user may fail to perceive the bar as present at all, effectively collapsing the cue back down to something close to color-alone in practice. (Active-state indication, all 3 breakpoints.) *Fix:* Once the bar's contrast is fixed, still add a second, contrast-independent reinforcement on the active item — e.g. a filled vs. outline icon variant, bold label weight at ≥1280px, or a subtle background tint on the active item's own hit area — so the active state degrades gracefully even under poor viewing conditions.

- **low** If a future iteration of the active-bar evolves from a thin line into a filled background/pill behind the label (not what's currently specced, but a common evolution of this pattern), contrast of primary text `#1E293B` on accent `#FF5A5F` computes to ≈4.79:1 — passes AA for normal text (4.5:1) but with a thin margin, and would fail if the accent is darkened per the first finding's fix without re-checking. (Active-state indication — speculative/future risk.) *Fix:* If this pattern is later added, re-verify text-on-accent contrast against whatever the corrected accent value becomes, and prefer placing label text on the neutral background next to the bar rather than on top of it.

- **low** The label-fade animation (and any rail/tab-bar transition) isn't required to respect `prefers-reduced-motion`. This is not a formal WCAG 2.1 AA requirement — Animation from Interactions is SC 2.3.3, which is AAA — but it's standard practice and relevant here since users with vestibular disorders who set reduced-motion are a realistic segment of FestDaily's audience. (Label fade, tap-to-flash pattern; any transition tokens not yet defined.) *Fix:* Wrap the fade/transition in `@media (prefers-reduced-motion: reduce)` and fall back to an instant show/hide (or a much shorter, non-easing transition) for users with that preference set.

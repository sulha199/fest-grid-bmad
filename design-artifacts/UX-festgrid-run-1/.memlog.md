# UX for festgrid
- (decision) Default Location for Subscriptions flow (EXPERIENCE.md User Flows) split into first-time-set vs edit-existing cases, matching PRD/epics.md Stories 3.3/3.3b. Edit case gets new 'Default Location Pending Review' state pattern: immediate save, Pending Review badge, moderator accept/revert. Reason: defaultLocation moved to account-level (shared across subscribers) per architecture review; old flow's step 5 wrongly associated the value with the subscription and had no moderation touchpoint.
- (event) EXPERIENCE.md updated (targeted fix, not a full UX pass). DESIGN.md unchanged -- no new component/token needed, 'Pending Review' badge reuses existing Notification/badge visual language. No other touchpoints found assuming silent/unmoderated subscription edits. Moderator-side Moderator Items UX intentionally out of scope, owned by Epic 4's existing UX coverage.
- (decision) Global navigation IA: 5 top-level items — Discover (/, Compass icon), Feed (/feed, Rss icon), Favorites (/favorites, Heart icon), Calendar (/my-calendar, CalendarDays icon), Profile (/settings, UserCircle icon). 'Feed' chosen over 'Following' to match the existing /feed route name in IA.
- (decision) Global nav is a 3-tier responsive pattern using Tailwind default breakpoints (matches AppShell.tsx's existing md: usage): <768px fixed bottom tab bar (icon+label always visible, all 5 items); 768-1279px left icon-only sidenav rail (logo pinned top, Profile pinned bottom via mt-auto, other 4 items top); >=1280px same rail permanently expanded with icon+label. No manual collapse toggle — purely breakpoint-driven.
- (decision) Active nav item indicator: leading accent-colored bar (vertical on sidenav rail, top edge on mobile bottom tab bar), at all 3 breakpoints, plus aria-current=page (UX-DR18/WCAG AA). Chosen over accent-background-pill and text-color-only for stronger visual weight.
- (decision) Icon-only rail (768-1279px) label reveal: on hover (mouse), label tooltip appears. On touch, a single tap both navigates AND briefly flashes the item's label (fades after a few seconds) — not a two-step tap-to-reveal-then-tap-to-navigate — so touch users get passive learnability without an extra blocking step.
- (event) Ran ad-hoc accessibility review (WCAG 2.1 AA) on the nav pattern before committing to spines. 10 findings (0 critical, 3 high, 4 medium, 3 low); full report at review-accessibility.md. All resolved into the spec before drafting.
- (decision) Accessibility fixes folded into nav spec: (1) new token nav_active_indicator=#E04347 (darker than base accent) for the active bar, meeting 3:1 non-text contrast vs neutral #FAFAFC (base accent #FF5A5F measured ~2.93:1, failed). (2) Rail hover tooltip also triggers on :focus-visible, persists while focused, dismisses on Escape/blur. (3) Single persistent <nav aria-label="Main"> across all 3 breakpoints, CSS-only layout changes — no duplicate nav landmarks; if markup must differ, only one variant may ever be in the a11y tree (hidden/inert). (4) Explicit 2px focus ring distinct from the active-bar color, meets WCAG 2.4.7. (5) Explicit aria-label on every nav item at all tiers, matching the >=1280px visible label text, independent of tooltip. (6) Nav is a persistent shell element, does not remount on route change; touch tap-to-flash label duration is >=2000ms, only extended (never shortened) under prefers-reduced-motion. (7) min-h-11 min-w-11 (44px) hit-area token per nav item. (8) Active state gets a second non-color reinforcement (filled vs outline icon variant) beyond the accent bar. (9) Label-fade/transitions wrapped in prefers-reduced-motion with instant fallback.
- (event) Global Navigation spec written into EXPERIENCE.md (Information Architecture > Global Navigation, Component Patterns > Global Navigation, new Responsive & Platform section, new Accessibility Floor section scoped to nav) and DESIGN.md (nav_active_indicator color token, components.nav token block). Targeted addition, not a full UX pass -- status left as draft. Next: feed into a revision of Story 0.7's AC/Tasks (still 'review', not 'done') before re-running dev-story.
- (decision) Profile nav item now has two auth-dependent states. Unauthenticated: renders as 'Log In' (icon: LogIn), tap/click opens a login modal (reuses existing modal token + the GoogleLoginButton component named in project-context.md) rather than navigating to a separate /login page -- keeps user's browsing context.
- (decision) Authenticated: Profile nav item opens a dropdown (rail tiers) / bottom sheet (mobile tab-bar tier) anchored to the nav item -- not a full-page navigation, not a blocking modal. Confirmed against PRD 3.9.3 which already specifies a Reports page and (for moderator-role users) a Moderator Items page 'under the user menu' -- this decision formalizes that existing PRD intent into the nav spec rather than inventing a new pattern.
- (decision) Authenticated menu contents (top to bottom): avatar+display-name header (non-interactive); Profile (-> /settings); Locations (-> /settings/locations); Subscribed Accounts (-> /settings/subscriptions); API Keys (-> /settings/api-keys); Notifications (-> /settings/notifications); Reports (-> /reports, new IA route -- PRD 3.9.3 'Reports' page, status/history of the user's own submitted reports); divider; Moderator Items (-> /moderator/items, new IA route -- PRD 3.9.3, only rendered when users.role === MODERATOR per AD-7.4's role model); divider; Log Out (action, not navigation).
- (decision) New IA routes added: /reports (User Reports page, any authenticated user) and /moderator/items (Moderator Items page, role=MODERATOR only) -- both PRD 3.9.3, both reachable only via the Profile dropdown/sheet, not part of the primary 5-item nav.
- (event) Ran ad-hoc accessibility review on the Profile auth-menu spec before finalizing. 8 findings (2 critical, 3 high, 2 medium, 1 low, 1 informational-no-issue); full report at review-accessibility-profile-menu.md. All resolved into the spec.
- (decision) Accessibility fixes for the Profile auth menu: (1) Authenticated menu is NOT role=menu/menuitem (APG reserves that for app command menus) -- trigger is a <button aria-haspopup=true aria-expanded>, popup content is a plain <ul><li><a>> list of links, Log Out is a real <button> in that list. If Radix DropdownMenu is used for convenience it must be swapped for Popover+native list. (2) No focus trap on the authenticated dropdown/sheet (wrong for a link-disclosure) -- Tab past Log Out closes it and moves to the next focusable element in DOM order; Escape closes it and returns focus to the Profile trigger. Focus trap is reserved for the login modal only, which IS a true modal. (3) Login modal gets an explicit dialog a11y floor: role=dialog, aria-modal=true, aria-labelledby a visible 'Log In' heading, initial focus on GoogleLoginButton, real focus trap while open, Escape/backdrop-click dismiss returns focus to the Log In trigger. (4) Focus-return on close is now three explicit cases: Escape/outside-dismiss -> trigger; activating a nav item -> follows normal route-change focus management (destination page's main heading), not back to the (now-irrelevant) nav item; Log Out -> trigger (deliberate exception, same DOM node persists relabeled Log In). (5) Profile is explicitly excluded from the generic icon-only-rail tap-to-flash rule -- tap/click opens its menu directly, and opening the menu always dismisses that item's own tooltip immediately regardless of hover/focus-out state. (6) Bottom sheet gets an explicit always-reachable Close control (not just outside-tap/Escape) plus Android back-gesture support. (7) profile_menu_item token gets w-full so every row's hit area spans the full menu/sheet width, not just its label. (8) The two dividers around the conditional Moderator Items link are now paired -- both render together only when role=MODERATOR, so regular users see exactly one divider before Log Out.
- (event) Profile auth-menu spec (login modal for unauthenticated, dropdown/bottom-sheet for authenticated with Reports/Moderator Items per PRD 3.9.3) written into EXPERIENCE.md and DESIGN.md, accessibility-reviewed and all findings resolved. Targeted addition -- status left as draft. Not yet folded into any story file (0.7/0.7a only cover the base 5-item nav container + primitive; this Profile auth-menu content is new scope not yet assigned to a story).

- (decision) Story 2.8's original AC listed 'My Favorites' and 'My Calendar' as User Menu items -- confirmed redundant and removed, since both are now first-class items in the primary 5-item nav (Story 0.7). Favorite (bookmark/interest in an event) and CalendarEntry (event the user has actually added to their calendar) are two deliberately distinct, already-well-specified PRD concepts (PRD 3.2.1/3.2.2/4.10 vs 4.11, with their own visual-distinction and toggle rules at 3.5.1/3.5.2) -- their promotion to top-level nav items in 0.7 was correct, which makes keeping them ALSO in the User Menu pure duplicate navigation, not a meaningful second view.
- (decision) Story 2.8's User Menu final item list (Epic 2, supersedes original loose AC): Profile -> /settings; Locations -> /settings/locations; Subscribed Accounts -> /settings/subscriptions; API Keys -> /settings/api-keys; Notifications -> /settings/notifications; Reports -> /reports (consumed/registered by Story 4.6); divider; Moderator Items -> /moderator/items, role=MODERATOR only, paired with its own dividers (consumed/registered by Story 4.7); divider; Log Out. All ARIA/focus/dismiss/bottom-sheet accessibility resolutions from review-accessibility-profile-menu.md carry over unchanged -- only the owning story and the unauthenticated route changed, not the interaction design itself.

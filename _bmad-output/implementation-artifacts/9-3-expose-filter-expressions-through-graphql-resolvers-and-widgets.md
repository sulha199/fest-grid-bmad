# Story 9.3: Expose filter expressions through GraphQL, resolvers and Widgets

## Story Details

- Epic: 9
- Story ID: 9.3
- Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a developer,
I want expressions accepted and persisted by the events queries, saved AI filters and Widgets,
so that every consumer of `EventFilterInput` can carry an expression.

## Acceptance Criteria

1. **AC1 — `FilterNodeInput`/`FilterNode`, `dayOfWeek: [DayOfWeek!]`, resolver validation with `BAD_USER_INPUT` (epics.md AC1):** Given `events.graphql`, `ai-event-filters.graphql` and `widgets.graphql`, when extended with a bounded `FilterNodeInput`/`FilterNode` and `dayOfWeek: [DayOfWeek!]`, then:
   - `events.graphql` declares `input FilterNodeInput { op: String; children: [FilterNodeInput!]; child: FilterNodeInput; field: String; value: JSON }` and the mirrored output `type FilterNode { op: String; children: [FilterNode!]; child: FilterNode; field: String; value: JSON }` — the generic, flat-recursive encoding already established by `EventQueryConditionInput`'s `operator/conditions/field/value` shape, reused here (not reinvented) for Story 9.1a's `FilterNode`/`FilterLeaf` discriminated union, since GraphQL has no input-union construct.
   - `EventFilterInput.dayOfWeek`/`EventFilter.dayOfWeek` widen from singular `DayOfWeek` to `[DayOfWeek!]`, matching the TypeScript widening Story 9.1b already shipped and explicitly deferred to this story.
   - `DateRangeFilterInput`/`DateRangeFilter` gain optional `spanAmount: Int`/`spanUnit: DateOffsetUnit`, matching the `DateRangeFilter` TypeScript fields Story 9.1b added and explicitly deferred to this story ("GraphQL schema/resolver exposure... `spanAmount`/`spanUnit` on `DateRangeFilterInput`/`DateRangeFilter`... Story 9.3's exclusive scope").
   - `Query.events` gains an optional `expression: FilterNodeInput` argument. Every resolver that accepts a `FilterNodeInput` value (`Query.events`'s `expression`, `saveAIEventFilter`'s `expression`, `createWidget`/`updateWidget`'s `input.expression`) runs it through Story 9.1a's `validateFilterNode` before using it; an invalid expression is rejected with a `GraphQLError` carrying `extensions.code: 'BAD_USER_INPUT'` and a message built from the validation issues' `path`/`reason` pairs — never a silent drop or a generic 500.
   - Supplying both the flat and expression-shaped argument to the same call (`filter`+`expression` on `Query.events`; `resolvedFilter`+`expression` on `saveAIEventFilter`; `input.filters`+`input.expression` on `createWidget`) is also rejected with `BAD_USER_INPUT` ("provide either the flat filter or the expression, not both") — they represent the same concern at two levels, and silently preferring one would hide the caller's likely mistake. `updateWidget` is the one exception: `input.filters`/`input.expression` both stay independently optional (matching its existing partial-update semantics), mutually exclusive only *with each other* in the same call, not required.

2. **AC2 — Versioned persistence, v1 unchanged, Widgets through the same compiler, `Widget.filters` validated not cast (epics.md AC2):** Given a saved AI filter or a Widget, when it carries an expression, then:
   - `saveAIEventFilter`/`createWidget`/`updateWidget` store an expression-shaped save as `{ version: 2, expression: FilterNode }` in the existing `jsonb` column (`ai_event_filters.resolved_filter` / `widgets.filters` — no new column, no migration); a flat-shaped save stores the plain `EventFilterInput` object exactly as before, with no `version` key, so every pre-existing row's on-disk shape and the write path for every caller still using the flat argument are byte-identical to today.
   - `AIEventFilter`/`Widget`'s GraphQL field resolvers for `resolvedFilter`/`filters` and the new `expression` field both route through one new shared `packages/domain` helper (`resolveStoredFilter`) that normalizes either stored shape (v1 flat → `expressionFromFlatFilter`; v2 → the stored `expression` directly) into a validated `FilterNode` via `validateFilterNode` — replacing today's `parent.filters as any` cast with real, enforced validation — then derives a best-effort flat projection via `flatFilterFromExpression` (`null` when the validated expression is not flat-representable, i.e. contains `OR`/`NOT`/nesting). `AIEventFilter.resolvedFilter`/`Widget.filters` widen from `EventFilter!` to nullable `EventFilter` to honestly represent that "no flat projection" case instead of fabricating one or throwing a 500; both types gain an always-populated `expression: FilterNode!` field as the new canonical read path.
   - `Query.events`'s `expression` argument, once validated, compiles via Story 9.2's `compileFilterNodeToQueryCondition` and merges into the resolver's query condition exactly the way the existing flat `filter` argument already does — i.e. Widgets (and any other consumer) reach the live event data through the identical compiled-condition path a flat filter uses, never a second, parallel query mechanism.

3. **AC3 — `buildFeedQueryCondition`/`buildAccountEventsQueryCondition` accept expressions (epics.md AC3):** Given `packages/domain/src/events/buildFeedQueryCondition.ts` and `buildAccountEventsQueryCondition.ts` (the two pure client+domain functions the Feed and Account-events pages already call directly in the browser to build the `query: EventQueryConditionInput` value they send to `Query.events`), when either is called with an optional `expression?: FilterNode` input field, then it compiles that expression via `compileFilterNodeToQueryCondition` and merges it into the function's existing base-conditions result using the identical merge logic the function already applies to its `filter`-compiled condition (wrap the base conditions and the compiled condition in one `{operator:'and', conditions:[...]}`, or splice into an existing group).

4. **AC4 — Generated GraphQL types regenerated and committed (epics.md AC4):** `pnpm --filter @festgrid/backend codegen` (regenerating `apps/backend/src/generated/resolvers-types.ts`) and `pnpm --filter @festgrid/web codegen` (regenerating `apps/web/src/generated/graphql.ts`) are run after every schema change in this story, and the resulting diffs are committed.

**Depends on:** Story 9.2.

### GraphQL/persistence design decisions (resolved defaults — minimised per this session's dispatch instruction, not left as open questions)

1. **`FilterNodeInput`/`FilterNode` reuse the existing generic `operator/conditions/field/value`-style encoding (renamed `op/children/child/field/value` to mirror `FilterNode`'s actual TS shape) instead of a GraphQL union or per-leaf-field input.** GraphQL has no input union type, so a discriminated union like `FilterNode` (groups keyed by `op`, leaves keyed by `field`) cannot be expressed as a true GraphQL union on the input side. The flat/generic shape is the same pattern `EventQueryConditionInput` already uses for the lower-level `QueryCondition` DSL — reusing a project-established convention rather than inventing a second one. `value: JSON` (the pre-existing `JSON` scalar from `events.graphql`) carries a leaf's raw value (a string, a `DateRangeFilter`-shaped object including the new `spanAmount`/`spanUnit` fields, a `LocationProximityValue`-shaped object, etc.) without needing a dedicated GraphQL type per leaf field — the runtime shape is enforced entirely by `validateFilterNode` (Story 9.1a), which is exactly the validation boundary AC1 asks for, not by GraphQL's own (necessarily looser) type system.
2. **`DateRangeFilterInput`/`DateRangeFilter`'s new `spanAmount`/`spanUnit` fields are on the *flat* GraphQL types, independent of the `FilterNodeInput` work**, because a `FilterNodeInput` leaf's `value: JSON` already carries span fields for free (no GraphQL schema change needed there) — but the flat `EventFilterInput.dateRange` path had no GraphQL-level way to express span at all until this story, even though the underlying TypeScript `DateRangeFilter` has supported it since Story 9.1b. Closing this gap was Story 9.1b's own explicit deferral to this story, not new scope invented here.
3. **Exactly-one-of flat/expression is enforced per mutation/query at the resolver boundary, not at the GraphQL schema level** (GraphQL has no native "exactly one of these two optional arguments" constraint short of a oneOf input, which isn't used elsewhere in this schema and would be a bigger, inconsistent change for one case). `updateWidget` is the sole exception (both independently optional, mutually exclusive only with each other) because it already has "apply whichever of several optional fields are present" semantics for `displayMode`/`theme`, and requiring exactly one of `filters`/`expression` on every call would break that established partial-update pattern for a widget that only wants to change its theme.
4. **`resolveStoredFilter` throws (not degrades) on a validation failure**, unlike `transformGeminiResponseToEventFilter`'s "degrade on bad field" convention (Story 9.1b) — because the input here is already-persisted, previously-accepted application data (a data-integrity concern, surfaced as `INTERNAL_SERVER_ERROR` by the resolver's existing generic try/catch), not untrusted raw model output mid-extraction where graceful degradation is the right call. A row that fails this validation indicates either corrupted/hand-edited data or a bug in the write path — surfacing it loudly is correct.
5. **`AIEventFilter.resolvedFilter`/`Widget.filters` widen from `EventFilter!` to nullable `EventFilter` rather than staying non-null with a fabricated/lossy flat approximation of an `OR`/`NOT` expression.** A fabricated approximation (e.g. picking one branch of an `OR`) would silently misrepresent what the filter actually does — worse than an honest `null` a well-behaved client can check for. Every row that exists before this story (and every row any live caller can create *as of this story*, since nothing yet produces a non-flat expression to save — Story 9.4 is the first live producer) still resolves to a non-null flat value, so this widening changes zero observed behavior for any data that exists today; it only takes effect once Story 9.4 (or a direct API caller) actually saves a non-flat expression.
6. **`resolveStoredFilter` is computed independently by each of the two field resolvers that need it (`resolvedFilter`/`filters` and the new `expression` field) rather than memoized on the parent row.** It's pure, in-memory, small-tree computation (no DB/network call) — recomputing it twice per row is cheap and keeps each field resolver simple and independent, consistent with this codebase's general comfort with small redundant-but-cheap per-field computation elsewhere in `resolvers.ts`.

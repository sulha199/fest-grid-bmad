# Rubric Walker Review — AD-8 Soft-Delete Convention Extension

## Overall verdict

The intent behind this session's AD-8 extension (universal Binds + a shared `SoftDeleteAction` mutation contract) is sound in principle, but the extension is not yet load-bearing: its central enforcement claim (Rule 2, "enforced once in the shared query-building layer") is demonstrably false against the current `buildDrizzleWhere` implementation and the resolver code that actually filters `deletedAt` today, and three of the four newly-added Binds (`Schedule`, `Post`, `UserLocation`) contradict the PRD's own canonical interface definitions, which don't specify a `deletedAt` field for them. Rule 4's treatment of `deleteUserLocation` as equivalent to not-yet-built work also glosses over the fact that it is a shipped, tested, frontend-consumed mutation that currently hard-deletes — a materially different (and harder) migration than adding a brand-new `ApiKey`/`Subscription` mutation. This AD needs another pass before it can safely guide a builder implementing `UserLocation`'s delete mutation, let alone a future `ApiKey` one.

## Findings

- **critical** Rule 2 claims the `deletedAt IS NULL` default is "enforced once in the shared query-building layer — never per-resolver," but `packages/graphql-select/drizzle-where.ts` (`buildDrizzleWhere`, the actual shared query-building layer AD-1/AD-2 refer to) has no knowledge of `deletedAt` at all — it only ever emits SQL for whatever `field`/`operator`/`value` the caller's DSL condition supplies against an explicit `fieldMap`. The two tables that already have `deletedAt` today (`favorites`, `calendarAdditions`) are filtered by hand-written `isNull(favorites.deletedAt)` / `isNull(calendarAdditions.deletedAt)` calls scattered across `apps/backend/src/schema/resolvers.ts` (lines 297, 306, 349, 436, 451, 468) — i.e. exactly the per-resolver pattern Rule 2 says must never happen. Separately, `myLocations` (resolvers.ts:225-237) is a plain hand-written Drizzle query that never touches `buildDrizzleWhere`/the DSL at all, so for `UserLocation` (and, once built, `Subscription`/`ApiKey`) AD-1/AD-2 structurally cannot be "the" enforcement mechanism — those resolvers don't go through the DSL in the first place. *Fix:* Either (a) name and build the actual centralizing mechanism (e.g. a `withActiveOnly(table, tables[])` wrapper resolvers must call, or a change to `buildDrizzleWhere`/`buildOptimizedDrizzleSelect` to accept a set of soft-delete tables and auto-inject the filter), and retrofit `favorites`/`calendarAdditions` filtering to go through it instead of ad hoc `isNull()` calls; or (b) narrow Rule 2's claim to only the tables actually reached via the Unified Query DSL, and add an explicit, separately-named rule for non-DSL resolvers (`myLocations`-style) describing how *they* must apply the filter.

- **high** Three of the four newly-bound tables contradict the PRD's own canonical data model. `_bmad-output/planning-artifacts/prds/festgrid-prd-2026-07-10-2047/prd.md` Section 4.4 (`Schedule`, lines 362-421), Section 4.7 (`Post`, lines 513-556), and Section 4.6 (`UserLocationPreference`, lines 482-511) define none of these interfaces with a `deletedAt` field — unlike `EventInfo` (Section 4.1), which already specifies `deletedAt?: string` (line 316), confirming AD-8's claim that the `EventInfo` binding was "pre-existing but never implemented" is accurate for that one table only. `project-context.md` states "the PRD's TypeScript interfaces are the single source of truth for data structures" alongside the Drizzle schema — this session's spine change asserts a data-model addition to three tables that the equally-canonical PRD doesn't carry, with no companion PRD update. *Fix:* Either update the PRD's Section 4.4/4.6/4.7 interfaces to add `deletedAt?: string` (with the same rationale comment style used on `Favorite`/`Subscription`/`CalendarEntry`) as part of reconciling this AD, or narrow the Binds list back down until the PRD is updated in the same change.

- **high** `packages/database/schema.ts`'s `users` table already carries a live `deletedAt` column (line 37, comment `// Soft delete support`) but is entirely absent from AD-8's Binds list — not listed as bound, and not listed among the excluded log/cache tables either. No resolver anywhere reads or writes it (confirmed via repo-wide search), so it's currently a vestigial column with undefined semantics. Given AD-7 is built entirely on `public.users.id === auth.users.id` identity, a builder implementing account deletion/suspension later has no guidance here on whether `users` follows this convention, whether it needs the Rule 4 mutation contract, or how the "default query excludes soft-deleted rows" rule interacts with joins to a soft-deleted user's own content (a real correctness gap: e.g. would a deleted user's `favorites`/`posts` silently keep surfacing their name?). *Fix:* Explicitly add `users` to the Binds list (or explicitly exclude it with a stated rationale, e.g. "user deletion is out of MVP scope, tracked as future work") so the column's presence in the brownfield schema is accounted for rather than silently orphaned.

- **high** Rule 4 lists `deleteUserLocation` alongside genuinely not-yet-built mutations ("every new or not-yet-built soft-delete mutation (`deleteUserLocation` now; `ApiKey`/`Subscription` delete mutations, Epic 3/4, later)") but `deleteUserLocation` is not unbuilt — it is a shipped, tested mutation with GraphQL signature `deleteUserLocation(id: ID!): Boolean!` (`apps/backend/src/schema/user-locations.graphql:41`), implemented as a literal hard delete (`db.delete(userLocations)...`, `apps/backend/src/schema/resolvers.ts:130-135`, no `deletedAt`/soft-delete involved at all), and actively consumed by the frontend (`apps/web/src/features/locations/mutations.graphql:37-39`, `apps/web/src/app/[locale]/settings/locations/locations-content.tsx`, with its own test file). Reconciling it to the Rule 4 shape (`action: SoftDeleteAction!`, typed return instead of `Boolean`) is a breaking API change to a live, tested surface — not comparable in cost to authoring a brand-new `ApiKey`/`Subscription` mutation. AD-8 gives `toggleFavorite`/`toggleCalendarAddition` an explicit "accepted legacy exception" carve-out for exactly this kind of shipped-but-differently-shaped situation, but doesn't extend the same consideration (or an explicit "must break, here's how" instruction covering the frontend caller/migration) to `deleteUserLocation`. Two builders could reasonably diverge: one breaks the signature per the literal Rule 4 text, another treats it as a third grandfathered exception matching the toggle precedent. *Fix:* Add a sentence to Rule 4 explicitly resolving this: either "`deleteUserLocation` must be migrated to the Rule 4 shape as a breaking change; update `mutations.graphql`, `locations-content.tsx`, and their tests in the same story" or fold it into the legacy-exception list alongside the toggles.

- **medium** Rule 3's illustrative SQL uses table names that don't exist in the actual schema: `favorite`, `calendar_entry`, and `subscription` (singular) versus the real Postgres table names `favorites`, `calendar_additions`, `subscriptions` (all plural; see `packages/database/schema.ts` `pgTable('favorites', ...)` line 152, `pgTable('calendar_additions', ...)` line 163, `pgTable('subscriptions', ...)` line 55). The already-implemented indexes in schema.ts are correctly named `idx_favorites_active` (line 160) and `idx_calendar_additions_active` (line 172) — i.e. the real code already diverges from AD-8's own sample SQL. A builder copy-pasting Rule 3's `CREATE INDEX ... ON calendar_entry ...` example would get a "relation does not exist" error. *Fix:* Update the SQL block to use the actual table identifiers (`favorites`, `calendar_additions`, `subscriptions`, `user_locations`) matching schema.ts, not the PRD's singular interface names.

- **medium** `Post` is newly bound to the soft-delete convention, but no user-facing or moderator-facing action that would ever set or clear a `Post.deletedAt` is documented anywhere: not in the PRD (Section 3.7's Post-related content is about extraction/queue status only, no delete/hide action), and not in `design-artifacts/UX-festgrid-run-1/EXPERIENCE.md`'s "Soft Delete with Undo" pattern, which explicitly scopes itself to "a saved location, an API key, or a subscription" (plus the Favorites toggle exception) and never mentions `Post` or `Schedule`. `Post` rows are internally-generated scraped/ingestion artifacts, which arguably fits AD-8's own stated exclusion rationale ("a genuine append-only log/audit table... soft-delete-with-undo would let a user quietly erase their own audit trail, defeating the table's purpose") better than its inclusion rationale. *Fix:* Either identify the concrete mutation/actor that soft-deletes a `Post` (e.g. moderator content takedown) and cite it, or move `Post` to the excluded side alongside `GeolocationCache` with the same "log-like" reasoning already used there.

- **low** Naming drift: the PRD names this entity `UserLocationPreference` (Section 4.6), while AD-8, the GraphQL schema, and `schema.ts`'s `userLocations` table all use `UserLocation`. This isn't itself wrong (AD-8 correctly matches the live GraphQL/DB naming), but AD-8 doesn't note the rename from the PRD's term, so a reader cross-referencing Binds against PRD Section 4 by name won't find a `UserLocation` interface there. *Fix:* Add a one-line parenthetical in AD-8's Binds entry, e.g. "`UserLocation` (PRD Section 4.6, `UserLocationPreference`)".

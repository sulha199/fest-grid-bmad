Event dedup flow

How one extracted event is checked against existing events at ingestion, what each score band does, and where a moderator comes in. Reflects the code as of 2026-10-25 (Story 3.6v, AD-30 Rule 7, amended with the mid-to-high promotion and the stub-repeat rule).

From ingestion to merge

Each extracted item (one event from a post) goes through this path on its own. Everything above the split runs inside one database transaction.

High: auto-link / fixedMid: moderator queueLow / exit: new event

Promoting an obvious duplicate from mid to high

The score tops out near 0.65 (organizer 0.40 + name and date 0.25) when the venue or the shared link is missing, usually because one side has no location. A same-account, same-day, same-name pair therefore waited in the moderator queue. After scoring, decideMatchTier lifts a mid to high only when every row below holds; weights and thresholds do not change. The backlog script applies the same function to pending suggestions.

Repeated stub posts: a second way to HIGH

A curator or roundup account that posts about one event again creates a stub event each time. The organizer weight is discounted for stubs and such posts carry no links, so the pair scores at most 0.40 (name and date 0.25, venue 0.15): low, never even queued. Prod case: 11 stub events "Yonex French Open 2026" from one curator account. After scoring, decideMatchTier lifts a stub repeat to high, from low or mid, when all of these hold; the score, the weights and the account are not inputs. A step-by-step explainer: event-dedup-curator-repeat.html.

  • Both are stubs (the new item's isStub, the candidate's detail_level).
  • Strict names equal, at least two words (lowercase, punctuation and year removed; bracketed text kept, so "(Morning)" differs from "(Evening)").
  • Same start date on one schedule pair, and on that pair a positive venue match (same text, the same place spelled two ways, or coordinates within 150 m; two absent venues do not match) and equal start times when both are set. Same name and date at a different or unknown venue are different events.

The link is additive: empty fields are filled, nothing is overwritten, and no schedule is deleted (an ordinary high link overwrites and prunes). The oldest matching event always absorbs the repost. The decision log line carries promotionRule: "stub-repeat". A scan mode of the backlog script (--scan-stubs) merges existing clusters through the journaled merge and lists the near-misses it left apart.

Why the posting account no longer counts for roundups

Before the fix, the same pair of events could land in different bands depending on whether the posting account counted as organizer. Example: two events listed in an aggregator's roundup posts, similar names and dates, same venue string, no shared link. The middle bar is what the code used to do; the top bar is what it does now.

Where to look in the code

process-ingestion-job.ts runs the tier branch; the stub rule, organizer discount and match call live in evaluate-ingestion-match.ts, which the moderator re-extract preview (AD-40) also calls. match-event-to-existing.ts holds findMatchingEvent and the candidate query. match-scoring.ts in packages/domain holds the weights and thresholds. merge-events.ts and the resolveSuggestedEventMatch resolver handle the moderator side.

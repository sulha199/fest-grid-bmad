BMad Forge Idea — Session Report

AI Prompt-Based Event Filter

FestDaily · a natural-language filter that translates a prompt into a stored, structured event query

Outcome

Hardened. What began as "add a chatbot" turned into a scoped v1: a single-purpose, single-shot prompt-to-filter translator reusing the existing BYOK Gemini adapter, a formalized shared filter type, and one general mechanism for anything it can't do. The idea survived by shrinking — three things (the digest, price thresholds, multi-turn conversation) were deliberately cut to v2 rather than built into a first release, and one thing (an open chatbot) was rejected outright as an abuse vector.

Locked for v1

  • lockOn-demand only — prompt → filter → results now. No scheduler, no digest, no quota fan-out.
  • lockSingle-shot prompts — no conversation memory or follow-up refinement.
  • lockNo edit UI, ever — a saved filter changes only by re-prompting.
  • lockDeterministic, template-rendered summary — never AI-generated, always a live render of current filter state, not a frozen caption. This is the entire trust/transparency layer.
  • lockDate filter as a closed anchor+offset grammar (TODAY/THIS_WEEK/THIS_MONTH ± N days/weeks/months), resolved fresh at read time. Day-of-week recurrence is a separate field.
  • lockLocation — region mode via admin-area captured from the existing Geoapify response, indexed text match. No new geo infrastructure.
  • lockVenue type sourced from the Gemini extraction pipeline, not the geolocation provider — and inherited wholesale (with adminArea) whenever a schedule falls back to the account's Default Location.
  • lockOne general degrade rule: anything outside the locked vocabulary is surfaced as an explicit caveat in the summary — never silently dropped, never fragile-guessed. Validated independently three times (price, floor-level location, off-topic prompts).
  • lockChatbot is a narrow extraction tool, not an app-wide QnA assistant — constrained system prompt, structured output only.
  • lockCompact FilterHub: one icon-only trigger, saved filters live on their own "My AI Filters" list page, an active AI filter replaces (never stacks under) the manual control row.
  • lockAI filter and manual FilterHub share one live state — manual edits touch only the session, never the saved entity.

Rejected

  • cutTrue polygon / point-in-polygon geo queries (PostGIS) — new geospatial infrastructure the current use cases (Sleman-vs-Kota-Yogyakarta) don't actually require; admin-area text matching solves it.
  • cutVenue-type from the geolocation provider's POI database — unverified capability, weak for informal local venue names; the Gemini extraction pipeline already does this reliably at zero extra cost.
  • cutA full "AI mode" toggle that hides the entire FilterHub — too hard a context switch; replaced with a compact collapsed summary row.
  • cutAn open, general-purpose chatbot — creates a BYOK abuse vector (a user's own paid Gemini key used as a free chat proxy through the app).
  • cutFragile heuristic parsing of free-text price or floor/wing details — unreliable, replaced by the one honest degrade-caveat mechanism.

Deferred to v2

  • Recurring daily/weekly digest against saved filters (scheduler + per-user quota fan-out).
  • Global numeric ticketPrice normalization — estimated, cross-currency thresholds ("under IDR 200K" matching USD listings).

Weak points that survived scrutiny

  • openThe shared EventFilterInput schema extension was proposed and built upon repeatedly, but never given an explicit final yes after the location tangent pulled focus. Everything downstream assumes it.
  • openUnverified: whether Geoapify's response actually separates Kota Yogyakarta from Kabupaten Sleman as distinct admin values for real Indonesian addresses — a quick API check, not resolved in this session.
  • openWhether "free"/"gratis" deserves a cheap exact-text-match exception to the v2-deferred price filter — raised as a promising side discovery, never decided.
  • openHow an account's Default Location first acquires its own venueType — "AI-classified from whichever post first gave enough context, or set explicitly during configuration" was proposed but not fully specified as a mechanism.

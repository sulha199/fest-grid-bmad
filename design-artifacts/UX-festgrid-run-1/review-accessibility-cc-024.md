# Accessibility Review — CC-024 Multi-Event Posts and Cross-Post Event Matching

## Overall verdict
The new section is mostly careful about reuse — it correctly defers to existing, already-reviewed components (`SubscribedAccountCard`, `event_card_compact`, the thumbnail-fallback tokens, `EventListView`) rather than inventing new interaction surfaces, and the redirected-slug and stub-image contracts hold up on inspection. The real gap is contract 6: the merge action bolts a brand-new confirmation step onto the front of a pattern ("Soft Delete with Undo") that was written to start at Trigger with no confirmation step at all, and the inheritance claim glosses over the focus-management seam this creates. Two smaller gaps — no stated loading-announcement treatment for the Related Events Area, and no page-identifying heading contract for the new Post Collection Page route — are worth closing before implementation.

## Findings

- **high** The merge action's confirmation step has no focus-management spec, and "inherits wholesale" from a pattern that never had a confirmation step to inherit from (contract 6 / Moderator tools). The existing Soft Delete with Undo pattern (State Patterns § Soft Delete with Undo) starts at **Trigger** — a single click that immediately commits — with no prior dialog; its Accessibility Floor section (§ Soft Delete with Undo (Notification Toast)) correspondingly only specifies focus behavior for the *toast*, not for any pre-commit step. Merge explicitly adds "an explicit confirmation step before it commits," which is new surface area the inherited pattern doesn't cover: is the confirmation a focus-trapping modal dialog (unlike the toast, which is explicitly non-modal/no-trap)? Where does focus land when the dialog opens, and where does it return on cancel vs. confirm? After confirming, does focus move to the row/trigger before the toast's own (correctly specified) live-region announcement fires, or does the dialog's own closing focus-return race the toast's appearance? None of this is answered, and a developer told "same toast mechanics, same accessibility treatment" could reasonably build the confirmation dialog with no focus trap and no defined return target, since the thing being inherited never defined one. *Fix:* add a short confirmation-dialog sub-contract (standard modal rules — focus moves into the dialog on open, is trapped, and returns to the row's merge-trigger control on cancel; on confirm, focus returns to that same control before the Undo toast's live-region announcement fires, consistent with the existing pattern's Trigger-focus rule) rather than treating "inherits wholesale" as covering a step the original pattern doesn't have.

- **medium** No accessibility treatment is specified for the Related Events Area's lazy-load transition (contract 2 / Related Events Area). The section states the skeleton matches the real component's shape (satisfying `project-context.md`'s Keep Skeletons in Sync rule) but says nothing about `aria-busy` on the loading container, nor whether a screen-reader user who has already landed inside/near that region when it loads needs any announcement that content just appeared. This differs from how this document elsewhere treats similar omissions: State Patterns § Soft Delete with Undo explicitly says "No separate announcement is required for this removal... a deliberate decision, not an oversight" when it chooses not to announce something. Contract 2 has no equivalent sentence, so a developer can't tell whether the silence is a considered choice (matching the document's own no-live-region precedent in § Calendar Overflow's infinite-scroll section) or an unreviewed gap. *Fix:* add one sentence either marking this a deliberate non-announcement (consistent with the Calendar Overflow precedent) or specifying `aria-busy="true"` on the container during the fetch and what, if anything, should be announced once content resolves.

- **medium** The Post Collection Page contract doesn't specify a page-identifying heading, only a document `<title>`/meta (contract 3 / Post Collection Page). The section says `generateMetadata` sets "title/meta" and otherwise asserts wholesale reuse of `EventListView`/`PageContainer`/`PageHeader`/`GridContainer`, but never states what heading text `PageHeader` should render for this *specific* route — unlike contract 2's Related Events Area, which is careful to give each group a labelled heading ("Events from [post/account]," explicitly reusing the same account identifier as the Source Posts Area). A screen-reader user who jumps straight to this page via a shared link and navigates by heading (not by reading the `<title>`, which AT typically announces once on load but doesn't resurface) has no spec'd way to learn "whose post" this list belongs to from the page content itself. *Fix:* state that `PageHeader`'s heading text reuses the same account/post identifier convention as contract 2 ("Events from [post/account]"), not just the document title.

- **low** Source Posts Area relies on list order alone to convey which post is primary, with no text/ARIA cue (contract 1 / Source Posts Area). "Lists one entry per linked post, primary post first, then in link order" is DOM-order-only; nothing marks the primary entry as primary for a user who isn't reading linearly (e.g., jumping via list-item or heading navigation). This is a minor gap, not a functional blocker, since linear reading order does preserve the information — but it's inconsistent with this document's general practice elsewhere of adding an explicit non-positional cue once a visual distinction exists (here, the primary post is presumably visually first/possibly styled differently, same pattern that motivated the non-color-cue rules elsewhere in Accessibility Floor). *Fix:* consider a plain-text "Primary" label (or equivalent) on that entry, matching the project's general non-positional-cue convention.

- **none** Redirected slug (contract 4) — confirmed out of scope / no gap. The redirect is a server-side resolution before paint, using the existing `RouteLoader` route-level Suspense fallback, not a client-side navigation with its own focus-loss or unexpected-announcement risk; this is a correctness contract with no distinct accessibility surface.

- **none** Stub events' reused cover image (contract 5) — checked, no ambiguity risk beyond what's already covered elsewhere in the document. Although multiple stub-event cards from the same roundup post will share one literal image, Accessibility Floor § Masonry EventCard Badge Row's existing "Reading order" rule already establishes that "the card's own accessible name comes from `eventName`/`imageAlt`" — i.e., `eventName` (unique per stub event) is the operative accessible-name input, not the shared image's alt text alone, so two stub cards reusing the same cover image still get distinct accessible names from their distinct event names. No new contract is needed here beyond what the existing badge-row rule already guarantees.

- **none** Coauthor toggles and posted-at timestamps within Source Posts Area (contract 1) — checked, no distinguishability gap. Posted-at times are plain text, not interactive, so there's no accessible-name collision risk. Coauthor `SubscribedAccountCard` toggles derive their accessible name from the account, which is already unique per distinct account; if the same account happens to coauthor two linked posts on one event, both toggles share a name and perform the identical action on the identical underlying subscription state, which is not an accessibility defect (equivalent to any other duplicated control with one well-defined effect).

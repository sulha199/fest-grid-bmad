**Subject:** `festgrid-architecture-spine.md` as amended 2026-10-19: AD-36 (event groups, Rules 1-15), AD-37 (jsonb rows), AD-38 (event identity, split, backfill), AD-39 (place model), the amended paragraphs of AD-14 (Rules 3a, 4, 5) and AD-30 (Rules 5, 7, 10), against the unamended base (AD-30 Rules 1, 2, 3, 9; AD-16 Rules 8-11; AD-8 Rule 3).
**Reviewer lens:** ad-hoc, chosen because the amendments reshape the event data model (split events, groups, new place columns, a row migration).
**Method:** read the spine ranges, the decision log (`.memlog.md`, last entries), `packages/database/schema.ts`, `apps/backend/src/lib/events/merge-events.ts` (fully), `set-event-primary-post.ts`, `process-ingestion-job.ts`, `process-ai-job.ts`, `assign-extraction-ordinals.ts`, `notify-new-event.ts`, `resolve-account-and-locations.ts`, `merge-account-profiles.ts`, `delete-order.ts`, the relevant `resolvers.ts` ranges, migrations 0065 and 0079, the BUG-068 runbook, and the drizzle-orm 0.30.10 migrator source in `node_modules`. ## Verdict

The group and place model is sound in outline, but the split mechanics (AD-38 Rule 4) move schedules while leaving a second event pointer (`calendar_additions.event_id`) behind, the series stem rule and the Tier 1 title rule are the same pattern with opposite `kind` (and a series hides events), ordinal allocation is not reproducible between live ingestion and backfill, and no migration plan exists for the AD-39 columns, so as written the amendments would silently corrupt calendar entries and hide programme events before any of them reached review.

## Critical

### DI-1. A split moves schedules but leaves `calendar_additions.event_id` on the original event
**Where:** AD-38 Rule 4 ("schedule ids unchanged, so `calendar_additions` stay attached"); AD-30 Rule 9 ("calendar entries follow schedules"); `schema.ts` `calendarAdditions`.
**Scenario.** `calendar_additions` carries both `schedule_id` (FK cascade) and `event_id uuid NOT NULL` (FK cascade to `events`). The spine reasons only about `schedule_id`. After the split moves schedule S from original E to child C, the row `(user U, schedule S, event_id = E)` is stale:
1. Four Event-level reads use `calendar_additions.event_id = events.id` (`resolvers.ts` ~3423, ~3908, ~4040 and the `Event.isAddedToCalendar` field resolver ~4859). C reports `isAddedToCalendar = false` although its schedule is in U's calendar; E reports `true` for a schedule it no longer owns. The Schedule-level reads (by `schedule_id`, ~3999, ~4150, ~4919) say the opposite, so one page contradicts itself.
2. `toggleCalendarAddition` finds the row by `(user, schedule)` and flips `deleted_at`, so a user who sees "not added" on C and taps add actually removes the entry.
3. `mergeEvents(winner, loser = C)` selects the loser's additions with `eq(calendarAdditions.eventId, loserId)` (merge-events.ts step 4) and misses these rows, so they stay pointed at a soft-deleted event.
4. `deleteEventPermanently(E)` cascades by `calendar_additions.event_id` and deletes the entries of schedules that now live in C.
5. `undoEventSplit` cannot restore a pointer the journal never recorded.
Every split of an event with any calendar addition (active or soft-deleted: the unique `(user_id, schedule_id)` includes soft-deleted rows) hits this. `mergeEvents` already updates `event_id` together with `schedule_id` (step 4), so the pattern exists; the AD text is silent.
**Fix.** AD-38 Rule 4: "Moving a schedule changes two pointers: `schedules.event_id` and, for every `calendar_additions` row of that schedule (active or soft-deleted), `calendar_additions.event_id`. The split helper updates both in the same transaction and journals `{calendarAdditionId, previousEventId}`; `undoEventSplit` restores them. A consistency query (like `findEventsInconsistentWithEventPosts`) asserts no `calendar_additions.event_id` differs from its schedule's `event_id`, and runs in the split round-trip test and after every backfill batch. Only the split and merge helpers write `schedules.event_id` or `calendar_additions.event_id` (extend the ratchet that AD-38 already names)."

### DI-2. The series stem rule and the Tier 1 title rule are one pattern with opposite `kind`; a wrong `series` is hidden from Discovery
**Where:** AD-36 Rule 3 (amended Tier 1), Rule 12 (kind derivation, stem), Rule 13 (series = hard cap k = 1); AD-38 Rule 2 (sibling naming).
**Scenario.** The stem is "the name before the first spaced dash". Two production shapes share that syntax with opposite meaning:
- Riot Jogja: "Wednesday Night Run - Kenes Soho". Before the dash is the **activity**; after it is the **place**. Same activity at different places is a `series`.
- Sleman City Hall: "SCH 8th Anniversary - Circus", "... - Zumba", "... - Fireworks". Before the dash is the **umbrella**; after it is the **activity**. Different activities under one umbrella is a `programme`.
Rule 12 says a group made by "the series stem rule" is a `series`, and the stem rule fires on "same account, same stem". The 17 measured Tier 1 groups (52 events) are exactly the SCH shape: same account, same stem. Under the stem rule they become `series` groups, and Rule 13's hard cap `k = 1` collapses all but one member of each behind the cover. The `kind` column then hides roughly 35 of the 52 spot-checked-genuine events from Discovery, the opposite of what AD-36 exists to do, and with immediate-apply (Rule 4) there is no moderator gate before it happens. Nothing in a name distinguishes the two shapes, and the stem rule is "deterministic, no model call".
**Fix.** AD-36 Rule 12: "`kind` is never derived from the name pattern alone. A group is `series` only if it was created by the AD-38 place split, or every member's remainder after the first spaced dash equals that member's own `place_key` venue name (the place-split naming form). Every other Tier 1, stem, Tier 2, Tier 3 and moderator group is `programme`. The hard cap applies only to `series`. Add `series_stem` to `group_source_enum` so a stem-made group does not inflate Tier 1's measured precision. Test fixture: the SCH 8th Anniversary set (52 events) yields zero `series` groups."

## High

### DI-3. Ordinal allocation is not reproducible between live ingestion and backfill, and synthetic slots collide with re-extraction
**Where:** AD-38 Rule 3 ("first place keeps the index; further places take the next free ordinals after the last extracted index, in extracted-event order then earliest-date order"), Rule 5 step 2; AD-30 Rule 3; `assignExtractionOrdinals`; `insertEventWithPrimaryPost`.
**Scenarios (counter-examples).**
1. *"Index" is a rank, not an index.* `assignExtractionOrdinals` sorts by (earliest schedule date, normalized name, response index) and assigns that rank as the ordinal. The spine says "the extracted event's index" and "extracted-event order". If live uses response order for the further places and backfill (which can only see stored ordinals, because response order is not persisted; `events_completeness[].eventIndex` is not linked to an ordinal) uses rank order, a post with two multi-place events X and Y whose response order is [Y, X] but ranks are X = 0, Y = 1 gets Y's second place at 2 and X's at 3 live, and X's at 2 and Y's at 3 in backfill. Different events own different slots, so the next re-run mis-pairs them.
2. *Ties.* "Earliest-date order" for places ties when two places share a start date. At ingest, schedules have no ids, so payload position decides; at backfill, only random uuids or identical `created_at` exist. The same event splits into children with swapped ordinals.
3. *Pre-3.6s posts.* Migration 0065 gave every existing event ordinal 0. Backfill appends 1, 2 for a post that was extracted as one event. The Step 2 Flash Lite re-extraction (or any later re-extraction) of that post now yields several events whose ranks 1, 2 hit the children's slots: the lookup `event_posts(post_id, extraction_ordinal)` says "already represented" and the item is skipped or **enriched into the wrong event**. The "same caveat as AD-30 Rule 3" understates this: before, ordinals changed only if the extracted set changed; with "next free after the last extracted index", every synthetic ordinal shifts whenever the pre-split event count changes.
4. *What "free" means.* `events(post_id, ordinal)` covers primary pointers only; `event_posts(post_id, ordinal)` also holds secondary links (enrichment stores `newExtractionOrdinal` for a matched candidate). An allocator that checks `events` alone picks an ordinal held in `event_posts`; `insertEventWithPrimaryPost` then inserts the `events` row and its bare `.onConflictDoNothing()` on `event_posts` swallows the violation, leaving `events.post_id` with no link row (AD-30 Rule 2 consistency broken, silently).
5. *Concurrency.* Two backfill workers splitting two events of one post both compute the same `max + 1`; the helper returns `null` on conflict ("idempotent skip"), so a child is silently not created.
**Fix.** AD-38 Rule 3: "The normalizer runs after `assignExtractionOrdinals`. 'Extracted index' means that ordinal. A place sibling's ordinal is `1000 x place_rank + source ordinal` (smallint-safe for place_rank <= 31), where `place_rank` 0 is the first place and places are ordered by (earliest start date, earliest start time with nulls last, `place_key` ascending), never by payload position or schedule id. The same formula applies to every `event_posts` link the sibling copies. Because the slot is a function of (source ordinal, place rank) rather than of the post's event count, live ingestion, backfill and any later re-extraction address the same slot. 'Free' means no `event_posts` row for that (post, ordinal), soft-deleted events included. The split locks the post row (`SELECT ... FOR UPDATE`), calls `insertEventWithPrimaryPost` with an explicit ordinal and treats a `null` return or a swallowed link conflict as an error to retry, never as 'already represented'." (Slug effect: `ig_p_X~1000`, valid under AD-16 Rule 9; say so.)

### DI-4. A split can race enrichment, and enrichment deletes schedules by id with no event scope
**Where:** AD-38 Rule 4; AD-30 Rule 9; `set-event-primary-post.ts` (`enrichAndPromoteEvent`, `mergeSchedules`).
**Scenario.** Under READ COMMITTED, `enrichAndPromoteEvent` reads `currentSchedules` for candidate E at its start, with no row lock. The backfill split commits in between and moves schedules S2, S3 to child C. `mergeSchedules` then treats S2, S3 as "unmatched" (the new extraction has fewer schedules) and runs `delete(schedules).where(inArray(schedules.id, deletableIds))`, deleting them unless an *active* `calendar_additions` row references them. The delete is not scoped by `event_id`, so it removes C's schedules. The backfill runs against a live queue, so the window is real; the consequence is deletion. A related deterministic case: SQS messages enqueued by the old AI Lambda (unsplit multi-place items) processed after the normalizer ships re-create multi-place events (see DI-11).
**Fix.** AD-38 Rule 4 and AD-30 Rule 9: "The split takes `SELECT ... FOR UPDATE` on the original event row before reading its schedules. `enrichAndPromoteEvent` takes the same lock on the candidate before reading `currentSchedules`, and `mergeSchedules` deletes `WHERE id IN (...) AND event_id = $eventId`."

### DI-5. A split breaks the "exactly one main schedule per event" invariant that place filters rely on
**Where:** AD-38 Rule 4 and Rule 7 ("the main-schedule join of BUG-064 is correct for place filters"); `idx_schedules_one_main_per_event`; `Query.events` (`resolvers.ts` ~3714-3721).
**Scenario.** `Query.events` left-joins `schedules` on `is_main_schedule = true`. The unique partial index allows **at most** one main per event, not at least one. Moved schedules keep their flag, so of N children at most one has a main schedule, and the original loses its main if the main schedule sat at another place. A child with no main schedule has NULL location in every place filter (invisible to a strict "in X" filter) and sorts by the fallback chain. AD-38 Rule 7's premise ("one place-set per event, so the main-schedule join is correct") is false until every child has a main schedule at its own place. Undo has the reverse trap: moving a main schedule back to an original that was meanwhile given a new main violates the unique index and the undo fails.
**Fix.** AD-38 Rule 4: "After a move, each of the original and every child has exactly one `is_main_schedule = true`: the earliest schedule of the child's place (start date, start time, `place_key`) is promoted when none was moved, and the original's earliest remaining schedule is promoted when its main left. Flag changes are journaled; undo clears the child's flag before moving schedules back. A consistency query (events with schedules and zero main) runs after each batch."

### DI-6. "One group per event" cannot express AD-38's own shapes; a split of an already-grouped event or of an anchor is undefined
**Where:** AD-36 Rule 1 (`events.group_id` scalar, one group), Rule 6, Rule 12; AD-38 Rule 1 table and Rule 4 ("the group is created with `source = place_split`, kind `series`").
**Scenario.** A `program-lineup` item ("Zumba") held at two venues is, by AD-38's table, both a programme member (different activities under an umbrella) and part of a series (same activity, different places). With a scalar `group_id` it can be only one. The split of an event that already has `group_id = G` (a programme member, or an umbrella anchor) is not defined: creating the series group overwrites `G` (the event silently leaves the programme and `member_count` of `G` drifts), or the split skips the series. The journal also must record the original's prior `group_id` and whether it was an `anchor_event_id`.
**Fix.** AD-36 Rule 1 (decide before the migration, because 1:1 to 1:N later is a data migration): "Precedence: an event that already has a group keeps it, and a place split of a grouped event puts every child in that same group (no new series group, journal records `place_split` provenance only). A `series` group is created only for an ungrouped original. If series inside a programme is wanted, add `event_groups.parent_group_id` now. An event that is a group's `anchor_event_id` stays the anchor; its children are not."

### DI-7. The `events` / `event_groups` foreign-key cycle breaks `getTablesInDeleteOrder`, the CI row-count ratchet and the seed
**Where:** AD-36 Rule 1 (`events.group_id` -> `event_groups`, `event_groups.anchor_event_id` -> `events`).
**Scenario.** `packages/database/delete-order.ts` topologically sorts the FK graph and skips only **self**-references; any two-table cycle throws `Cycle detected in foreign key references`. It is called by `snapshotCounts()` in `apps/backend/scripts/run-tests-with-row-count-ratchet.ts` (the CI `pnpm --filter backend test` gate) and by `seed.ts` (`getTablesInDeleteOrder(['reports'])` before reseeding). The first migration that lands both FKs breaks CI and local seeding. Both FKs are `ON DELETE SET NULL`, so there is no real delete-order constraint; this is a tooling gap, not a schema defect.
**Fix.** AD-36 Rule 1: "Tooling ignores `ON DELETE SET NULL` edges when ordering deletes: `getTablesInDeleteOrder` skips foreign keys whose `onDelete` is `set null`, with a test using an `events` / `event_groups` fixture. The story that adds the tables runs the row-count ratchet and the seed on the new schema before merge."

### DI-8. Series groups have no uniqueness or concurrency control; the organizer key is a text copy that the account-twin merge does not repoint
**Where:** AD-36 Rule 1 (`organizer_account_id text null`, `stem text null`), Rule 12 (series roll); AD-38 Rule 3 (group attach after events exist); BUG-059 `merge-account-profiles.ts`.
**Scenarios.**
1. *Concurrent attach.* Ingestion runs one message per event, concurrently (`process-ingestion-job.ts`, one transaction per message, READ COMMITTED). Two siblings of one post, or two posts a minute apart, both look up the open series for `(account, stem)`, both find none, both insert a group. Two active series groups share a key. "Open" is a gap computation over member dates, so no static unique index can prevent it. Later lookups find two candidates and pick non-deterministically; there is no operation to merge two groups (Rule 5 only lists detach, rename, dissolve).
2. *Place-split groups.* If each sibling's ingestion creates the split group, the same race gives N groups of one.
3. *Key identity.* `organizer_account_id` is `text`. `events.source_social_media_account_id` is a text copy of the platform `account_id` (no FK, not unique across platforms: `social_media_account_profiles` is unique on `(platform, account_id)`). The key lacks the platform, and during BUG-059 twin profiles one real account has two ids. `merge-account-profiles.ts` rewrites `events.source_social_media_account_id` by text equality but knows nothing of `event_groups`, so after a twin merge the same series has two keys.
4. No index supports the lookup, and the stem is not stored on events, so "find the ungrouped earlier members" has no query path.
**Fix.** AD-36 Rule 12: "Series attach takes `pg_advisory_xact_lock(hashtextextended(organizer || '|' || stem, 0))` (transaction-scoped, released at commit, so the pooler keeps one backend for its whole life; the `vendor_call_locks` comment in `schema.ts` rejects advisory locks for a lease held across separate calls, which this is not; confirm on the scratch database) before the open-series lookup. A place-split group id is derived deterministically from (source post id, source ordinal) and inserted `ON CONFLICT (id) DO NOTHING` by whichever sibling arrives first. `event_groups.organizer_account_id` is a `uuid` FK to `social_media_account_profiles` (`ON DELETE SET NULL`), and the BUG-059 merge repoints it. Add `event_groups(organizer_account_id, stem) WHERE kind = 'series' AND status = 'active'` (hand-written predicate) and a 'merge groups' moderator action in Rule 5 (repoint members, journaled). A nightly check flags two active series groups with the same key."

### DI-9. AD-39 specifies columns but no migration: nullability, defaults, backfill and reader switch are missing, and the backfill is blind to unmigrated jsonb
**Where:** AD-39 Rules 1, 4, Deferred; AD-37 Rules 4-5; AD-14 Rule 4.
**Scenarios.**
1. *Defaults.* If `pin_trust` is `NOT NULL DEFAULT 'none'` (or `area_status DEFAULT 'unknown'`), a rolling deploy lets a straggling old-version Lambda insert pinned schedules with `'none'`, indistinguishable from a real no-pin row. With NULL as "not derived yet", the backfill selector is simply `IS NULL`.
2. *Blind backfill.* The pin-trust inputs (`confidence`, `matchType`) live in `schedules.location_details`, which is a jsonb **string** in 1,460 of 1,460 rows until the AD-37 runbook has run. A SQL-side backfill reads `->>'confidence'` as NULL and stamps all 1,460 pins `untrusted`/AREA: wrong stored values that look plausible, and every existing event loses EXACT. AD-37 Rule 5 forbids SQL-side readers before step 4 but does not name this one. A SQL re-implementation would also duplicate `isPinTrusted()`.
3. *Provisional leg.* `isPinTrusted` leg (c) needs the event's area keys, which do not exist for the 1,394 existing events; run first, the backfill trusts the 129 confident outside-Indonesia pins ("Online" -> Montpellier at 1.00). The result is provisional until area keys exist.
4. *Reader flip.* Rule 4 shows unknown-area events in tier 1 with a ranking penalty and a per-page cap. If `area_status` is NULL for all 1,394 existing events and readers treat NULL as `unknown` (the only safe reading, since "never null as national"), switching readers on before the resolver backfill penalises and caps the entire catalogue.
5. *Deferred area-key storage.* It does not block adding `area_status`, but it blocks the integrity constraint (`area_status = 'known'` iff the key set is non-empty) and the index. A link table adds a join to `Query.events`. Keys point into a gazetteer with no FK, so a gazetteer revision orphans stored keys.
**Fix.** AD-39 new Rule 7 (migration): "Expand, derive, switch, contract. (1) Migration adds `schedules.pin_trust`, `location_source`, `location_precision` and `events.area_status` as **nullable** with no default; NULL means 'not derived'. (2) After the writers are deployed and the AD-37 runbook is verified, a TypeScript job (Drizzle reads both jsonb shapes) calls `isPinTrusted()` and the area resolver, batch of 200, selector `IS NULL`, idempotent and resumable; it re-runs after area keys exist because leg (c) was vacuous. (3) Readers switch behind one flag, enabled only when `count(*) WHERE area_status IS NULL AND deleted_at IS NULL = 0`. (4) A later migration sets NOT NULL and adds CHECKs. The area-key shape is fixed now: `events.area_keys text[] NOT NULL DEFAULT '{}'` holding the key and its ancestors, hand-written `USING gin` (precedent `post_hashtags_idx`), CHECK `(area_status = 'known') = (cardinality(area_keys) > 0)`; gazetteer keys are immutable or carry a version."

### DI-10. `location_source` is unknowable for the 1,725 existing schedules and the spine has no value or rule for it
**Where:** AD-39 Rule 1 and Rule 3; BUG-065; `resolve-account-and-locations.ts`.
**Scenario.** The memlog states the premise: "today the copied account default is indistinguishable from a stated place". The spine writes `location_source` "at ingestion" and never says what existing rows get. The enum has no legacy value (`stated | geocoded_from_text | account_default | account_audience_area`), `stated` and `geocoded_from_text` are not defined operationally, and a NULL would be read as "stated" by the first reader that defaults it. The effect is that the 11 curators with an arbitrary default (and any non-venue account) keep EXACT pins on their legacy events, which is BUG-065, now with a provenance column that appears to vouch for them. A fingerprint does exist in the code: `resolveAccountAndLocations` geocodes `schedule.location || event.location || defaultLocation.formattedAddress ?? placeName`, so a schedule with no `location` text whose pin matches the account's `default_location` (place id, or coordinates within ~150 m, after unwrapping the jsonb string) came from the default.
**Fix.** AD-39 Rule 1/7: "`location_source` gains `legacy_unknown` (created with the enum, so no `ALTER TYPE`). `stated` = the post names the place in schedule text; `geocoded_from_text` = the pin came from event-level text; define each by the code path that writes it. Backfill (after AD-37 step 4 or via Drizzle): empty schedule `location` and pin matching the account default -> `account_default`; non-empty `location` -> `geocoded_from_text`; remainder -> `legacy_unknown`. Readers never give EXACT to `account_default` unless Rule 3's venue test passes, and never to `legacy_unknown` on a non-venue account. Report the three counts before the readers switch."

### DI-11. The split backfill can notify users, over-split, and be hard to stop or re-run
**Where:** AD-38 Rules 3-5 ("the backfill calls the same function"); AD-36 Rules 10, 14; AD-30 Rule 10.
**Scenarios.**
1. *Notifications.* Rule 14 couples group attach to a delayed claim per `(group, source post)`. If the backfill reuses the attach path, every backfilled series sends one "N sessions" push for a post that is weeks old. Separately, children copy nothing about `notified_at` (see DI-14), and a sibling that lands after the send "joins silently" but keeps `notified_at IS NULL`, so AD-30 Rule 10's "later primary change ... notified_at IS NULL -> exactly one notification" can fire for it later.
2. *Over-splitting.* `place_key` = normalized venue name plus the area key of the city. Area keys do not exist for existing rows, so the area-equal-and-similar leg is unavailable and place identity is name equality only: "Atrium & Plaza Rama, Sleman City Hall" vs "Sleman City Hall" are two places. Over-splitting multiplies events, copies every favorite N times, and creates false series groups; 627 of 1,460 pins have confidence < 0.5, so coordinates cannot arbitrate.
3. *Work queue and quota.* Step 2 spends Flash Lite requests (500/day shared with live traffic). The result is not persisted before the split, so a crash re-spends the quota on retry.
4. *No batch handle.* There is no `run_id` on the journal, so undoing a bad run means undoing N events by hand.
5. *In-flight messages.* Messages enqueued by the old AI Lambda (unsplit multi-place events) are processed by the new ingestor after the deploy and create multi-place events the backfill already passed.
**Fix.** AD-38 Rule 5: "The backfill never notifies: a backfill-created group is inserted with its `(group, post)` claim already taken, children copy `notified_at`, and a late sibling's `notified_at` is stamped at attach. It is two-phase: a dry-run writes `event_split_proposals(event_id, post_id, proposed_place_keys, model_output, status)`, which is also the work queue and the cache of Flash Lite output; a sample is reviewed; apply runs with a per-run cap, a kill-switch flag, `run_id` on every journal row, and a selector that is idempotent by state (`deleted_at IS NULL`, `merged_into_event_id IS NULL`, open schedule, more than one `place_key`). Until area keys exist a split needs two signals (distinct normalized names and, with trusted pins, more than 500 m apart). The selector also runs as a standing drift check until the old queue has drained."

## Medium

### DI-12. Corrections, reports and pending match candidates are not handled at split time
**Where:** AD-38 Rule 4 (only undo mentions reports); `getProtectedFields`; `submitReport`.
**Scenario.** (a) `corrections.event_id` is the original and `proposed_data.schedules[].id` names schedule ids. After the move, `getProtectedFields(child)` finds no applied corrections, so enrichment of the child can overwrite moderator-corrected values on the moved schedules. Pending corrections now name schedule ids that belong to another event. (b) `cancelled` reports are counted per event and soft-delete the event at the threshold; reports about a moved place stay on the original and can delete it. (c) A pending `event_match_candidates` row scored the unsplit event; accepting it later merges only the shrunken event.
**Fix.** AD-38 Rule 4: "Corrections whose targets are all moved schedules are repointed to the child; applied corrections naming event-level fields are copied to every child as applied; the journal records both. The backfill skips (and lists) events that have pending reports or pending corrections; a moderator split asks where reports go. Pending candidates touching the original are re-evaluated with exclusion (b); the old row is closed with a new `superseded` status."

### DI-13. `undoEventSplit` is under-specified for a child that changed, and the journal can be erased by a hard delete
**Where:** AD-38 Rule 4, Deferred ("what `undoEventSplit` does for a child edited since").
**Scenario.** After the split, the child can gain schedules (enrichment `mergeSchedules` inserts), `event_posts` links (a later post matches it and may promote it, re-slugging), corrections, a merge, a group change, user favorites and calendar additions on its new schedules. None of these are in the journal ("moved schedule ids, created events, created `event_posts`, copied favorites, the group"). The spine's "repoints what changed ... (new favorites, reports)" misses schedules, links, aliases, calendar additions and candidates. Undo that hard-deletes children breaks AD-8 (`deleteEventPermanently` is the only named hard-delete) and frees `(post, ordinal)` slots. `event_merges` declares its event FKs `ON DELETE CASCADE`; a split journal built the same way is erased with the original by `deleteEventPermanently`, destroying the only undo record. "Removes the favorites it created" also deletes a copy the user has since unfavorited and re-favorited (`toggleFavorite` flips `deleted_at` on the same row).
**Fix.** "`undoEventSplit` is the exact inverse only for an untouched child (`updated_at` unchanged and no row outside the journal references it); otherwise it is refused with `SPLIT_DIVERGED` and the moderator uses the sibling-safe merge of DI-17. Undo soft-deletes created children (`merged_into_event_id` = original, slug registered as an alias), keeps their `(post, ordinal)` slots, and removes only favorite copies untouched since creation. Journal FKs to events are `ON DELETE SET NULL` with ids also stored as columns, not CASCADE."

### DI-14. The child copy-set is under-specified
**Where:** AD-38 Rule 4 ("copy the organizer, category, links and `event_posts` rows").
**Scenario.** `events` has more columns than those named, and several matter: `location` (NOT NULL, the event-level summary: a child that copies "Kenes Soho, Fortuna Suites, BPD DIY" matches location text search for all places), `notified_at` (DI-11), `detail_level`, `has_private_contact`, `contact_info`, `confidence_score`, `source_social_media_account_id`, `types`, `categories`, `description`. Copied favorites get `created_at = now()`, and the Favorites list orders by `desc(favorites.createdAt)`, so every affected favorite jumps to the top as "just favorited". The sentence "a renamed original registers its old slug as an alias" is vacuous: the slug is derived from (post, ordinal) (AD-16 Rule 8), so a rename never re-slugs. A child slug must still check `event_slug_aliases` (AD-16 Rule 10).
**Fix.** "The split copies every `events` column except an explicit reset list (`id`, `slug`, `event_name`, `location`, `extraction_ordinal`, `group_id`, `merged_into_event_id`, `deleted_at`, timestamps); a unit test enumerates `getTableConfig(events).columns` and fails when a column is in neither list. Favorite copies keep the source `created_at`. Delete the 'renamed original' sentence."

### DI-15. `member_count` has no single writer; the Discovery partition expression does not type-check
**Where:** AD-36 Rule 1 (denormalized, "maintained on membership change"), Rule 7, Rule 13.
**Scenario.** Membership changes through attach, detach, dissolve, split, split undo, merge, merge undo, `deleteEvent`/`restoreEvent`, and `deleteEventPermanently` (a DB cascade, no hook). A relative `+1` per attach is atomic, but the soft-delete and hard-delete paths bypass it, and a recount inside a transaction without a lock loses updates under READ COMMITTED (two concurrent attaches each count 1 and write 1). Rule 13 also uses `coalesce(group_id, -id)`; `events.id` and `group_id` are `uuid`, which has no unary minus (the POC used integer ids).
**Fix.** "`member_count` is written only by `recountEventGroup(tx, groupId)`: lock the group row (`FOR UPDATE`), then `SET member_count = (SELECT count(*) FROM events WHERE group_id = $1 AND deleted_at IS NULL)`; every membership path calls it; a consistency query runs in CI and nightly. Alternatively drop the column: it is read only for the displayed rows (one page), where an indexed `count(*)` is cheap. Partition by `coalesce(group_id, id)`."

### DI-16. Stored derived place facts have no single writer, and `place_key` is never persisted
**Where:** AD-39 Rule 1; AD-14 Rule 4; AD-38 Rules 1, 5, 6.
**Scenario.** `pin_trust` is a function of (confidence, floor, non-place, event area keys); `location_precision` is a function of (`pin_trust`, area keys) and lives on `schedules` while `area_status` lives on `events`, so no CHECK can tie them. The floor (0.5) is declared uncalibrated and will change, the retry ladder changes area keys, a correction changes the pin, a split changes the place-set: every one leaves stored values stale. A child that copies the parent's `area_status`/keys carries the parent's union of areas. The AD-30 Rule 2 drift guard (one writer, a ratchet, a consistency query) is exactly the pattern needed and is not applied. `place_key` and the stem exist only as a function in `packages/domain`; the backfill selector, the matcher exclusion (b) and a "multi-place event" drift check cannot be SQL predicates, so they scan.
**Fix.** AD-39 Rule 1: "One writer, `writePlaceFacts(tx, eventId)`, recomputes `pin_trust`, `location_precision`, `area_status`, area keys and `schedules.place_key` whenever any input changes (geocode, ladder step, floor change, split, merge, correction); a re-derive job exists for a floor change; a source-scan ratchet allows no other writer; a consistency query checks `EXACT` implies `trusted`. `Event.locationPrecision` is defined as the main schedule's (or the best schedule's, pick one) precision. `schedules.place_key text null` is persisted by the same writer."

### DI-17. Sibling merges lose a place; the sweep can re-queue rejected pairs
**Where:** AD-38 Rule 6; AD-30 Rule 7 (sweep) and Rule 9; `merge-events.ts`.
**Scenarios.**
1. `mergeEvents` maps loser schedules to winner schedules by **start date** (`findScheduleByStartDate`). Merging sibling C (place B) into E (place A) when both have a schedule on the same date treats them as the same occurrence: C's occurrence is dropped and its calendar additions are repointed to E's schedule at the *other place*. Exclusions (a) and (b) are applied only in candidate generation; a moderator merge or the sweep's `high` merge can still call `mergeEvents` on a sibling pair or recreate a multi-place event.
2. `event_match_candidates` is unique on the ordered pair `(event_id, candidate_event_id)`. The live path fixes orientation (new event, existing event). The sweep has no "new" event; if it orients by random uuid (the recall-classes bug of 2026-10-19 was exactly that), a re-run can insert `(B, A)` for a pair already queued or already `rejected` as `(A, B)`, duplicating the queue (147 pending) and resurfacing dismissed pairs.
3. A sweep over clusters A~B~C merges B into A, then `mergeEvents(B, C)` throws `EventMergeInvalidStateError` (B already merged); the sweep must merge into the final winner.
**Fix.** "`mergeEvents` refuses a pair that is a split sibling pair (same post, different ordinals) or whose resolved `place_key`s differ unless the moderator forces it, and its date match requires the same `place_key`. Add a unique index on `(least(event_id, candidate_event_id), greatest(event_id, candidate_event_id))` (hand-written expression index) and orient sweep rows by `created_at`, ties by id. The sweep clusters pairs (union-find) and merges into the final winner; it is idempotent by state (candidates exclude merged and deleted events)."

### DI-18. No end-to-end migration sequence or per-step rollback; drizzle's one-transaction migrator constrains the plan
**Where:** AD-3; AD-8 Rule 3; AD-30 Rule 1 (hand-written SQL convention); AD-36 Rules 9-10 (gates); AD-37 Rule 4.
**Facts (verified in drizzle-orm 0.30.10 `PgDialect.migrate`).** All pending migrations run inside **one** transaction, so an `ACCESS EXCLUSIVE` lock from `ALTER TABLE events` or `schedules` is held until the last pending migration commits (trivial at 1,394 events, but ingestion blocks for the whole run), and a value added with `ALTER TYPE ... ADD VALUE` cannot be used by any later statement of the same run. A migration is applied only if its journal `when` is greater than the latest applied one; with four stories (IDEA-084, 086, 087, BUG-068 follow-ups) adding migrations in parallel branches (the memlog records a parallel-branch AD number collision), an entry merged late can be silently skipped in production. `CREATE INDEX CONCURRENTLY` cannot run in this transaction. The gates in AD-36 Rules 9-10 are prose ("writer deployed, row migration run and verified") with no machine-checkable form. No step has a stated rollback.
**Rows written between deploy and migration** are handled correctly for AD-37 (new rows are objects; `02-apply.sql` selects only `jsonb_typeof = 'string'`); they are *not* handled for the AD-39 columns (DI-9).
**Fix.** Add to the spine one sequence with rollback, and three rules:

| Step | Action | Rollback |
|---|---|---|
| 1 Expand | one migration: `event_groups` and its enums, `events.group_id`, nullable AD-39 columns, split journal | forward-only; leave columns, redeploy previous code (new columns stay NULL) |
| 2 Writers | deploy AD-37 `customJsonb` writer, AD-39 writers, group/split code behind flags (off) | redeploy previous build |
| 3 Rows | AD-37 runbook `01-look` -> `02-apply` -> `01-look`; re-run `02-apply` after every Lambda alias is on the new build | `03-rollback.sql`; keep `_bak_bug068` until step 6 is verified |
| 4 Derive | AD-39 TypeScript backfill (DI-9, DI-10) | set the columns back to NULL (selector is `IS NULL`) |
| 5 Switch | readers on by flag when NULL count is 0 | flag off |
| 6 Contract | `SET NOT NULL`, CHECKs | drop the constraint |
| 7 Split | gated by IDEA-085 (Rule 10): dry-run -> review -> apply by `run_id` | undo by `run_id` (DI-13) |

Rules: "(1) No migration SQL references an enum value added in the same release; backfills are jobs, not migrations. (2) A CI check requires the migration journal `when` values to be strictly increasing and greater than main's last entry. (3) Each gate (AD-36 Rules 9, 10) is a row or flag a reader checks, with the evidence query recorded."

## Checked and found sound

- **Favorites copy keys.** `favorites` is unique `(user_id, event_id)` (full, soft-deleted rows included). Copying to a *new* child cannot collide, and the copy is idempotent with `ON CONFLICT DO NOTHING`. Nothing is keyed on favorites except `favoriteCount` (a live subquery, no stored counter) and the favorited-at sort; there is no favorites-driven notification.
- **`calendar_additions` unique `(user_id, schedule_id)`.** Schedule ids are stable, so a move cannot create a unique violation or a new row; only the `event_id` column needs updating (DI-1).
- **The two ordinal uniques and the CHECK** (`events(post_id, extraction_ordinal)`, `event_posts(post_id, extraction_ordinal)`, `post_id IS NULL OR extraction_ordinal IS NOT NULL`) are the right guards, unconditional on `deleted_at`: a moderator-deleted child is not re-created by re-extraction. They work for children once allocation is fixed (DI-3).
- **The original keeps its id, slug, favorites and links.** No alias is needed for the original, existing aliases stay valid, and account-feed matching ("any linked post") keeps working because `event_posts` rows are copied to children.
- **Child slugs.** `{platform}_{type}_{postId}~{ordinal}` is deterministic from (post, ordinal) (AD-16 Rule 8-9), so child slugs are unique by construction; the legacy hex fallback is random but idempotence rests on `(post, ordinal)`, not on the slug.
- **ON DELETE choices.** `events.group_id` and `event_groups.anchor_event_id` both `SET NULL` never cascade-delete members or a group; the anchor repoint on merge (AD-36 Rule 7 amended) correctly covers the case where the merge soft-deletes and the FK never fires. Only the tooling cycle needs care (DI-7).
- **Placing the normalizer before the matcher** and the group after the events exist is coherent: the matcher compares same-shaped events, and exclusion (a) (same post, different ordinals) correctly covers the split siblings. Rule 6 as a candidate-generation exclusion leaves the spine-fixed weights alone.
- **No DB constraint for the duplicate key** is the right call (a 2-day window and a place identity cannot be a unique index); best-effort matching plus the sweep is consistent with AD-30 Rule 7.
- **Deferring the area-key storage does not block adding `area_status`**; it blocks only the CHECK and the index (DI-9).
- **AD-37 ordering and idempotence.** Deploy the writer, then convert: rows written between deploy and migration are already objects and are untouched by `02-apply.sql` (selected by `jsonb_typeof = 'string'`); apply is one transaction with per-column ceilings and a before-state table; reads work in both shapes, so a rolled-back or delayed migration never breaks Drizzle readers; `customJsonb` is migration-neutral. The rolled-back writer is also safe: drizzle 0.30's own `jsonb()` reads an object back unchanged.
- **Scale.** At 1,394 events, 1,725 schedules and 2,231 jsonb rows, lock hold times and transaction sizes are not a concern for any DDL or per-event split transaction; the concern is correctness and ordering, not throughput. A per-event transaction (one event, its children, favorites, journal) is small.
- **Hand-written SQL conventions** are stated correctly where the spine states them: the partial `events.group_id` index carries its predicate by hand, in line with AD-8 Rule 3 and migration 0065. The additions this review asks for (GIN on area keys, expression unique index, CHECKs, series-key partial index) follow the same convention.
- **Soft-deleted and merged events.** The backfill scope ("an open schedule") plus `deleted_at IS NULL` and `merged_into_event_id IS NULL` keeps split from touching them; the unconditional ordinal unique keeps a deleted child from being re-created.

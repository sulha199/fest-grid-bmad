#### RW-1. AD-38 Rule 5 contradicts AD-10 and the shipped key topology; the quota model it rests on is unverified
- **Where:** AD-38 Rule 5 (lines 2732-2747) vs AD-10 (lines 179-188), AD-32 Binds (line ~1930), code.
- **What is wrong:** Rule 5 says Flash Lite's 500/day and 20/min are "shared with live ingestion (the platform-funded `SYSTEM_GEMINI_API_KEY`, AD-10, through the AD-32 wrapper)" and that "the daily quota, not the database, is the first ingestion scaling limit". That is not how the code works. Live extraction calls `callGemini` with `subscriberUserIds` (`apps/backend/src/lib/ai-processor/process-ai-job.ts:142-146`), which selects subscribers' own BYOK keys (`apps/backend/src/lib/ai-gateway/adapter.ts:51-62`, `packages/domain/src/ai-gateway/select-api-key.ts:11-13`: tier 1 user-specific, tier 2 shared round-robin of contributed keys). The system key is reachable only through `callGeminiForLocationInference` / `callGeminiForAccountClassification`, and only after `AiGatewayExhaustedError` (`apps/backend/src/lib/ai-gateway/system-key-adapter.ts:36-68`). AD-10's whole purpose is a scope fence: "structurally unreachable from `callGemini`'s existing call sites (Story 3.6)", and its Rule 3 says "no additional rate-limiting is designed in for this key". AD-38 needs the opposite on both counts (backfill re-extraction on that key, plus a 20/min and 500/day budget that "yields to live traffic").
- **Why units diverge:** the backfill worker has no sanctioned key. One unit adds a third sibling function on the system key (an unrecorded AD-10 amendment, no rate limiter exists), another calls `callGemini` with some account's `subscriberUserIds` (spends users' BYOK quota without their consent, and "yields to live traffic" has no meaning). The forward-risk statement (813 posts/day exceeds one 500/day key) is about a key live ingestion does not use; the real scaling limit is BYOK key availability (Story 3.6z pre-flight), a different capacity model. "Yields to live traffic" has no mechanism: AD-32 only provides a per-credential lease row, not a daily/minute ledger. Also, 500 RPD / 20 RPM are owner-reported (memlog entry 82) and stated as fact; FIND-090 records that the same key was already consumed by hundreds of POC calls.
- **Fix:** replace Rule 5's key sentence with: "Re-extraction for the backfill is a new sibling in `system-key-adapter.ts`, `callGeminiForEventSplitBackfill`, which AD-10 is amended to name (Binds and Rule 2 gain it; Rule 3's 'no rate limiting' gains an exception for it). It is the only caller that may use `SYSTEM_GEMINI_API_KEY` for extraction. It enforces its own ledger: a `vendor_call_budget(key, window, count)` row incremented before the call, at most 20 per minute and (500 minus the day's measured live use on that key) per day, and refuses to start when live use is unmeasured." State separately that live ingestion runs on subscriber keys, so the "813 posts/day" figure sizes BYOK availability, not this key. Mark 500/20 as `[owner-reported 2026-10-19, verify against current Google limits]`.

#### RW-2. AD-38: "same place" has three non-equivalent definitions, and its inputs do not exist where the normalizer runs
- **Where:** AD-38 Rule 1 "Place identity" (lines 2680-2684), Rule 2 (2685-2698), Rule 6(b) (2749-2755), Deferred (2775-2779); AD-39 Rule 2, Deferred (2884-2889).
- **What is wrong:**
  1. Rule 1: same place = equal `place_key`, **or** equal area keys and name similarity >= a start value. Rule 2 groups schedules by `place_key` (equality only). Rule 6(b) excludes a pair only when both keys are "resolved" and "the keys differ" (equality only, and "resolved" is never defined). The same two venue texts ("Plaza Ambarrukmo" vs "Amplaz Yogyakarta") are the same place under Rule 1 and different places under Rules 2 and 6(b).
  2. `place_key` = normalized venue name plus "the area key of the venue's city (AD-39)". Area keys need the gazetteer, which is a hand-typed Indonesia-only sample in the POC (`apps/backend/scripts/poc-event-insight/area-resolver.ts` header: "non-Indonesian names fall through to the geocoder") and whose data source, licence and coverage are Deferred in AD-39. Production has real foreign events (Denmark 27, Egypt 13, per the prod-check §10.2). The fall-through to "the pin's administrative path" needs data that production does not have (`adminArea` written for 0 of 1,460 pins, BUG-063; AD-37 Deferred calls it "separate").
  3. Rule 2 says "The place split is a pure function of the extractor output". It cannot be: `place_key` depends on the gazetteer, and on the trusted-pin path (geocoder output, `pin_trust`). Geocoding happens per event in `process-ai-job.ts:252-277` (`resolveAccountAndLocations`), results are cached (`geolocation_cache`), and gazetteer or floor changes alter the key. A re-run after a gazetteer update produces different siblings, which breaks the Rule 3 idempotency claim.
  4. Whether `place_key` is stored (events? schedules?) or recomputed is not said; Rule 6(b) needs it for candidates inside `findMatchingEvent` and inside a set-based sweep.
- **Why units diverge:** IDEA-086 (normalizer), IDEA-085 (matcher exclusion, sweep) and the backfill each need "same place". The spec lets each implement equality, similarity, or "resolved" differently; the Deferred threshold is the sole parameter of the shared predicate.
- **Fix:** add to Rule 1: "One exported function `isSamePlace(a: PlaceRef, b: PlaceRef): 'same' | 'different' | 'unresolved'` in `packages/domain`, the only place-equality in the codebase; Rules 2 and 6(b) call it (6(b) excludes iff the result is `different`). `unresolved` (either side has no usable venue name, or its city has no area key) never splits and never excludes. `place_key` is computed, never stored, from `(venue name as extracted, area key resolved from the extracted text only)`; coordinates are never an input to the normalizer. The gazetteer is a versioned data file in `packages/domain`; non-covered places resolve to `unresolved`." Reword Rule 2's bullet to "a pure function of the extractor output and the gazetteer version" and list the gazetteer (Indonesia-only at first) as a prerequisite of IDEA-086 core in the Follow-ups.

#### RW-3. AD-38 Rule 4 / AD-36 Rule 15: moving a schedule to a sibling event strands `calendar_additions.event_id`
- **Where:** AD-38 Rule 4 (2718-2731), AD-36 Rule 15 (2523-2528); schema `packages/database/schema.ts:733-743`; reads `apps/backend/src/schema/resolvers.ts:3423, 3908, 4040, 4859`; precedent `apps/backend/src/lib/events/merge-events.ts:147-172`.
- **What is wrong:** the rules say schedule ids stay unchanged "so `calendar_additions` stay attached (AD-30 Rule 9)". `calendar_additions` carries both `schedule_id` and a NOT NULL `event_id` (FK `ON DELETE CASCADE`), and the My Calendar and `Query.events` joins use `calendarAdditions.eventId = events.id`. The merge code repoints **both** (`set({ eventId: winnerId, scheduleId: targetScheduleId })`). A split that moves only the schedule row leaves the addition pointing at the original event: it vanishes from the user's calendar (join on the wrong event) and is deleted outright if the original event is ever hard-deleted (`deleteEventPermanently`, AD-8). The journal list in Rule 4 ("moved schedule ids, created events, created `event_posts` rows, copied favorites and the group") omits the repointed additions, so `undoEventSplit` cannot restore them. Separately, `idx_schedules_one_main_per_event` (`schema.ts:711`) allows one main schedule per event: moved schedules arrive in the new sibling with no main schedule (and the original loses its main if the moved one was it), and `Query.events` LEFT JOINs `schedules` on `is_main_schedule = true` only (`resolvers.ts:3714-3735`, `mainSchedulesOnly`), which is the schedule the `scheduleLocation` and `scheduleCoordinates` place filters read (`resolvers.ts:3380-3381`); a sibling without a main schedule is invisible to place filters (the date leaves use independent `EXISTS` subqueries and are unaffected).
- **Why units diverge:** the split story and the calendar/My-Calendar code have different views of which column carries truth.
- **Fix:** add to Rule 4: "A schedule move also repoints `calendar_additions.event_id` for every addition on that schedule, and the journal records `repointedCalendarAdditionIds` (id, previous event id) exactly as the merge journal does; undo restores them. Each new sibling gets its earliest schedule marked `is_main_schedule` by the same `normalizeMainSchedule` rule as ingestion (`build-event-insert-values.ts:117-165`); if the moved schedule was the original's main, the original's next-earliest becomes main, in the same transaction." Reword Rule 15 and the "calendar additions follow the schedules" sentence to name both columns.

#### RW-5. AD-38 Rule 3: the normalizer's position in the pipeline and the ordinal scheme conflict with the shipped code
- **Where:** AD-38 Rule 3 (2699-2717); `process-ai-job.ts:252-299, 510-543`; `packages/domain/src/events/assign-extraction-ordinals.ts:28-43`; `process-ingestion-job.ts:15-169`.
- **What is wrong:**
  1. The flowchart goes Extraction -> Normalizer -> Matcher. In the code, between extraction and enqueue come: per-event `resolveAccountAndLocations` (geocoding), `resolveScheduleTimezones`, `transformGeminiResponseToEventInfo` (private-contact and performer guards, "run per event", AD-30 Rule 5), the audit-log write, `assignExtractionOrdinals`, then one SQS message per event. The spine does not say whether the normalizer runs before the per-event loop (geocoding then runs per sibling; guards are per sibling) or after it (siblings inherit already-geocoded schedules), nor whether it runs before or after `assignExtractionOrdinals`.
  2. "The first place keeps the extracted event's index; each further place takes the next free ordinal after the post's last extracted index" misdescribes the code: ordinals are **not** the extracted index; they are assigned after sorting by earliest date, normalized name, original index. After the sort there is no "extracted-event order" left to reference.
  3. Siblings take ordinals N, N+1, ... where N depends on how many events the extractor returned. The acknowledged non-determinism (7 vs 10 events from one caption) therefore shifts sibling ordinals into slots that a later re-extraction assigns to genuinely different events; the `(post, ordinal)` idempotency then "skips" a real event. AD-30 Rule 3's caveat re-pairs an ordinal; this makes slot collisions between siblings and extracted events likely.
  4. For a moderator split or backfill nothing was extracted, so "the post's last extracted index" is undefined; AD-30 Rule 8 uses "`max + 1`", a different rule.
- **Fix:** state the order exactly: "extraction -> per-event loop (geocode, timezone, guards) -> normalizer (post-geocode, so it sees `locationDetails`) -> `assignExtractionOrdinals` over the extracted events -> sibling ordinals from a reserved range: sibling ordinal = `100 + parentOrdinal * 10 + placeIndex` (placeIndex by earliest date; `smallint` allows it; the cap in Rule 2 bounds it) -> one message per event." Replace "next free ordinal after the post's last extracted index" with that formula for the write path, and "`max(ordinal in range) + 1`" for moderator split and backfill. State that the normalizer is invoked from `process-ai-job.ts` (fan-out cannot happen inside `processIngestionJob`, which handles one message per event).

#### RW-6. AD-14 Rule 4: `pin_trust` is a stored verdict over a tunable and an evolving input, misdescribes the shipped predicate, and clause (c) cannot run on current data
- **Where:** AD-14 Rule 4 (lines 416-426); `packages/domain/src/geolocation/is-location-trustworthy.ts:1-47`; `apps/backend/src/lib/geolocation/geoapify-client.ts:165`; AD-39 Rule 2 (2816-2832).
- **What is wrong:**
  1. "the confidence-only `isLocationTrustworthy` becomes its first leg" and "(a) stored confidence reaches the floor". The shipped predicate is confidence >= 0.5 **and** `matchType === 'full_match'`. It also rejects the synthetic `PLACE_ID_EXACT` (a user-picked place) that AD-14 Rule 1 itself defines. Whether leg (a) keeps `matchType`, and whether place-ID picks are trusted, is undecided; dropping `matchType` silently widens the shipped map-link gate.
  2. The result is "written at geocode time as `schedules.pin_trust`". Geocode results are cached (`geolocation_cache`) and are independent of the event; clause (c) needs the **event's** area keys, which are resolved later and by a ladder (AD-39 Rule 2 and Rule 4 retries add roundup-heading and account-area keys after the geocode). So the value cannot be computed at geocode time, and it goes stale when area keys arrive. Worse, the floor is a declared uncalibrated start value `[ASSUMPTION]`; because the verdict is stored, every recalibration (or gazetteer revision) is a data backfill over all schedules, with no re-evaluation job or version column specified. The consequence of a wrong floor is therefore not bounded: it is a migration.
  3. Clause (c) needs "the pin's administrative path"; production has none (`with_admin_area` 0 of 1,460, prod-check §1; BUG-063 is called separate in AD-37 Deferred) and the gazetteer is Deferred. "Intersects" is also vacuous: every Indonesian pin path and every ancestor-closed key set share the country key. The spine says "Confidence alone cannot separate good from bad pins ... which is why (c) exists", but does not say BUG-066 stays open until (c) can run.
  4. The tag `[ADOPTED, user-accepted with the place-model decisions]` is not supported by the decision log (see RW-17).
- **Fix:** (a) define "(a) = the shipped `isLocationTrustworthy` unchanged (confidence >= floor and `matchType` in {`full_match`, `PLACE_ID_EXACT`})" or state the deliberate widening. (b) Store the inputs, not the verdict: keep `confidence`, `matchType`, countryCode in `location_details`, add `pin_evaluated_with text` (floor + gazetteer version) next to `pin_trust`, and add "a recompute job re-evaluates rows whose `pin_evaluated_with` differs; consumers read `pin_trust` only". Say plainly that it is computed at **ingestion** (where event area keys are known) and recomputed whenever area keys change. (c) Define "(c): the pin's administrative path contains an area key of the event, or one of the event's keys lies inside the pin's leaf area; the country level never counts." (d) Add: "Until the area resolver and BUG-063 land, (c) is vacuously true and BUG-066 is not closed."

#### RW-9. AD-36 Rule 14 / AD-30 Rule 10: the delayed notification has no queue, no consumer, no failure handling, and the 60-120 s figure is unachievable in production
- **Where:** AD-36 Rule 14 (2505-2522); AD-30 Rule 10 (1835-1846); `apps/backend/src/lib/events/notify-new-event.ts:22-38`; `process-ingestion-job.ts:171-197`; `apps/infrastructure/lib/festgrid-backend-stack.ts:553-625`; `apps/backend/src/lambdas/ingestor.ts`; CLAUDE.md §4.
- **What is wrong:**
  - "an SQS `DelaySeconds` on the notify message" names no queue or consumer. The project has three queues (project-context; `architecture-diagram.md` lines 29-31) and `DelaySeconds` appears nowhere in `apps/backend/src` or `apps/infrastructure/lib`. Production Lambdas do not consume SQS continuously: an EventBridge rule runs a 5-minute **poll-and-drain** per queue (`festgrid-backend-stack.ts:604-625`; FIND-034). A drain that finds nothing visible ends, and a delayed message is invisible until due, so the real latency is up to 5 min plus the delay, not "about 60 to 120 seconds". Local dev uses the inline fallback with no queue at all.
  - The ingestion Lambda sends the notification **after commit**, awaited (FIND-061). If the enqueue of the delayed message fails there is no retry path: redelivery finds the slot "already represented" and exits at the idempotency lookup, so the group is never notified. No DLQ policy, no alarm.
  - "A sibling that lands after the send joins the group silently" does not say whether its `notified_at` is set. If not, a later primary change that makes it organizer-authored fires AD-30 Rule 10's "exactly one notification when `notified_at IS NULL`", i.e. a stray solo push, which Rule 14 exists to prevent.
  - Eligibility: Rule 10's roundup/curator "never notifies" test is per event and is not restated for the group claim. A series made of curator or roundup stubs could notify.
  - The current claim is `UPDATE events ... WHERE id = $1 AND notified_at IS NULL` with signature `(executor, event, sourceAccountId)`; a claim "atomic on `(group_id, source post)`" needs the source post id in the signature and a different statement. "Storage of the claim ... left to story time" is the one decision that defines the concurrency design.
  - CLAUDE.md §4 requires `docs/infrastructure/architecture-diagram.md` and `high-level-overview.md` to change in the same change when a queue or Lambda is added; Rule 14 does not say so.
- **Fix:** replace the SQS delay with a DB-state mechanism that fits the 5-minute drain: "Ingestion sets `events.notify_due_at = now() + 90 s` on each grouped event (no message). The existing 5-minute EventBridge rule runs a `notify-due-groups` job that claims, per `(group_id, source post)`, with one `UPDATE events SET notified_at = now() WHERE group_id = $g AND id IN (events linked to $post) AND notified_at IS NULL AND notify_due_at <= now() RETURNING id`; a non-empty result sends once with N = rows returned. A sibling landing later gets `notified_at` set at attach if its group already notified. Eligibility is AD-30 Rule 10's per-event test, applied to each covered event. Failure: the claim precedes the send as today; a failed send is logged and alerted via `reportErrorSilently`, never retried." Add the doc-update sentence and drop the 60-120 s promise ("up to about 6 minutes in production").

#### RW-10. AD-36: no single writer for group state, group creation is racy, "confirmed" has no transition, and the AD has no "Enforced by"
- **Where:** AD-36 Rules 1, 3, 4, 7, 10 (amended paragraphs), Deferred (2543-2551); contrast AD-30 Rule 2 (1656-1663); project-context lines 87-100.
- **What is wrong:**
  - `events.group_id` and `event_groups.member_count` are written by ingestion attach, the stem rule, the place split, `mergeEvents`/`undoEventMerge`, the moderator detach/dissolve, `undoEventSplit`, soft-delete mutations (AD-8: per-resolver, not centralized), `deleteEventPermanently`, and post/account erasure. AD-30 Rule 2 solved the same problem for `events.post_id` with one helper and a source-scan ratchet; AD-36 has none, and `member_count` ("denormalized, maintained on membership change") will drift on the first path that forgets it.
  - Series group creation: the identity key is `(organizer_account_id, stem)` plus the GAP rule, but there is no unique constraint or lock. Ingestion processes one message per event, in parallel Lambdas, and a scrape batch delivers many posts at once; two siblings or two posts of one series both see "no open series" and each create one. Rule 13's hard cap k=1 depends on exactly one open series per key; with two, the series shows twice.

# Story 3-4h: Capture and surface data format anomalies from scraper vendors

## Story Details

- **Epic:** 3 (Social Media Event Integration)
- **Story ID:** 3-4h
- **Status:** ready for implementation
- **Title:** Capture and surface data format anomalies from scraper vendors
- **Key:** 3-4h-capture-and-surface-data-format-anomalies

---

## User Story

**As a** platform operator and content moderator,
**I want** AJV validation failures detected by Story 3-4g to be captured, persisted, and surfaced in a daily digest email with full context,
**So that** I can investigate data quality issues from scraper vendors, reprocess failed payloads with historical parser versions, and track data anomalies over time without losing context when validation gates drop invalid data.

**Revision (2026-08-18, initial story creation):** Story 3-4g (AJV validation for scraped posts from Apify and Bright Data) detects format anomalies and logs them, but discards the malformed payloads immediately. This story captures those discarded payloads before they are dropped, persists them with full context, and provides moderators with tools to investigate and recover data using historical parser versions. Daily digest emails provide visibility into anomalies; re-processing workflow allows moderators to select an alternate parser version without blocking moderator action.

---

## Acceptance Criteria

1. **Given** Story 3-4g's AJV validation failures in `mapApifyItemToScrapedPost`, `processBrightDataResult`, or Gemini extraction paths,
   **When** validation fails (any of the three sources: Apify, Bright Data, or Gemini),
   **Then** before the payload is discarded, an `UnprocessedScraperPayload` record is persisted with:
   - `id`: UUID generated by database
   - `rawPayload`: full JSON of the malformed object (untruncated)
   - `validationError`: AJV error message (from `validate.errors`, formatted as JSON array for multiple errors)
   - `context`: JSON object containing:
     - `source`: `'apify'` | `'brightdata'` | `'gemini'` (which vendor/path failed)
     - `scraperVendor`: platform name (e.g., `'instagram'` for Apify, or blank for Gemini)
     - `accountId`: social media account ID (if available from context), or `null`
     - `postUrl`: the post URL being processed (if available), or `null`
     - `timestamp`: ISO timestamp when the failure occurred
     - `parserVersion`: semantic version string of the code path that failed (e.g., `'3.4g'` for the current AJV validator, or `'3.1a'` if Gemini path also gains version tracking)
   - `createdAt`: server timestamp
   - `deletedAt`: null (soft-delete convention)

2. **And** a `ParserVersionRegistry` lookup table is created and maintained with:
   - `id`: UUID
   - `version`: semantic version string (e.g., `'3.4g'`, `'3.4f'`, `'3.1a'`)
   - `description`: human-readable label (e.g., `'AJV validation for Apify/Bright Data'`)
   - `sourceFile`: code path (e.g., `'apps/backend/src/validation/scraped-post.schema.ts'`)
   - `deployedAt`: ISO timestamp
   - `isActive`: boolean (true = current/latest, false = historical)
   - `createdAt`: server timestamp

3. **And** the retention TTL is user-configurable via an environment variable `UNPROCESSED_PAYLOAD_RETENTION_DAYS` (default: `30`), and a daily background job (CloudWatch EventBridge rule + Lambda) soft-deletes any `UnprocessedScraperPayload` rows older than the TTL at 02:00 UTC each day.

4. **And** a daily digest email is sent to all users with `role = 'moderator'` at 08:00 UTC each day, listing all `UnprocessedScraperPayload` records created in the past 24 hours, grouped by `source` (Apify / Bright Data / Gemini), with counts and sample details, using the email adapter (Story 0.15). Email template includes:
   - Header: "Daily Data Format Anomaly Report for [Date]"
   - For each source group:
     - Source name and count of new anomalies
     - Summary table with columns: `postUrl` (or `scraperVendor`, or account info if no postUrl), `validationError` summary (first line or truncated to 100 chars), `parserVersion`, `timestamp`
     - Link to moderator tools (Story 3-4i) to view full details and reprocess
   - Footer: configuration note on TTL and count of payloads currently in retention

5. **And** two new GraphQL mutations are exposed (moderator-gated via `requireModerator`):
   - `reprocessPayload(payloadId: ID!, parserVersion: String!): ReprocessResult!`
     - Takes an `UnprocessedScraperPayload.id` and a `parserVersion` (enum or string from `ParserVersionRegistry.version`)
     - Enqueues the `rawPayload` to `AIProcessingQueue` with the selected `parserVersion` as context
     - Returns `ReprocessResult { success: Boolean!, queueId: String!, message: String! }`
     - Does not block moderator action (returns immediately; re-processing happens asynchronously)
     - If `parserVersion` is not found in registry, returns `success: false` with error message
   - `deleteUnprocessedPayload(payloadId: ID!): Boolean!`
     - Soft-deletes the `UnprocessedScraperPayload` record (sets `deletedAt` timestamp)
     - Returns `true` on success, `false` if not found or already deleted

6. **And** a new GraphQL query is exposed (moderator-gated):
   - `queryUnprocessedPayloads(filters: UnprocessedPayloadFilters, first: Int, after: String): UnprocessedPayloadConnection!`
     - Returns paginated list of active (non-soft-deleted) `UnprocessedScraperPayload` records
     - `UnprocessedPayloadFilters`: `{ source?: String, createdAfter?: DateTime, createdBefore?: DateTime, parserVersion?: String }`
     - Connection pattern: `{ edges: [{ node: UnprocessedScraperPayload, cursor }], pageInfo: { hasNextPage, endCursor } }`
     - Sorting: by `createdAt DESC` (newest first)
     - (Story 3-4i will consume this query to build the moderator UI)

7. **And** the `ParserVersionRegistry` is seeded at deployment time with an initial entry for the current AJV validator (version `'3.4g'`), and a cron/scheduled Lambda task runs daily at 23:59 UTC to detect new parser versions deployed since the last registry update, scanning git tags matching the pattern `parser-v*` and inserting any new ones (future extensibility; MVP may seed manually or via migration).

8. **And** data type compatibility is verified end-to-end:
   - `UnprocessedScraperPayload.rawPayload: jsonb` in Postgres (Drizzle: `json` or `jsonb` type)
   - `UnprocessedScraperPayload.validationError: jsonb` (array of AJV error objects)
   - `UnprocessedScraperPayload.context: jsonb` (flat JSON object with string/number/null values)
   - GraphQL types: `UnprocessedScraperPayload { id, rawPayload, validationError, context, createdAt, deletedAt }` (JSONB fields exposed as `JSON` scalar or fully-typed `RawPayload` / `ValidationError` / `PayloadContext` input types — see Dev Notes for decision)

## Database Schema Changes

### New Table: `unprocessed_scraper_payloads`

```sql
CREATE TABLE unprocessed_scraper_payloads (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  raw_payload JSONB NOT NULL,
  validation_error JSONB NOT NULL,
  context JSONB NOT NULL,
  created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
  deleted_at TIMESTAMP WITH TIME ZONE NULL
);

-- Indexes for fast queries by moderators
CREATE INDEX idx_unprocessed_payloads_created_desc ON unprocessed_scraper_payloads (created_at DESC) 
  WHERE deleted_at IS NULL;
CREATE INDEX idx_unprocessed_payloads_source ON unprocessed_scraper_payloads USING GIN (context)
  WHERE deleted_at IS NULL;  -- GIN index for JSONB context filtering on 'source' field
CREATE INDEX idx_unprocessed_payloads_cleanup ON unprocessed_scraper_payloads (created_at)
  WHERE deleted_at IS NULL;  -- For daily cleanup job targeting rows older than TTL
```

### New Table: `parser_version_registry`

```sql
CREATE TABLE parser_version_registry (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  version VARCHAR(50) NOT NULL UNIQUE,
  description TEXT,
  source_file VARCHAR(500),
  deployed_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
  is_active BOOLEAN NOT NULL DEFAULT FALSE,
  created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- Index for fast lookups by version string
CREATE UNIQUE INDEX idx_parser_versions_version ON parser_version_registry (version);
CREATE INDEX idx_parser_versions_active ON parser_version_registry (is_active DESC, version DESC);
```

      .where(isNull(table.deletedAt)),

### GraphQL Resolver Signatures

```typescript
// apps/backend/src/schema/resolvers.ts (or split to resolvers/unprocessed-payloads.ts)

import { requireModerator } from '../lib/auth-context';
import { db } from '@festgrid/database';
import { eq, isNull, desc, and, or, gte, lte } from 'drizzle-orm';
import { unprocessedScraperPayloads, parserVersionRegistry } from '@festgrid/database/schema';

export const queryUnprocessedPayloads = async (
  _: any,
  args: {
    filters?: { source?: string; createdAfter?: string; createdBefore?: string; parserVersion?: string };
    first?: number;
    after?: string;
  },
  context: { userId: string }
) => {
  requireModerator(context);

  const limit = (args.first || 10) + 1; // +1 to detect hasNextPage
  const offset = args.after ? decodeBase64ToNumber(args.after) : 0;

  const conditions = [isNull(unprocessedScraperPayloads.deletedAt)];

  if (args.filters?.source) {
    conditions.push(sql`context->>'source' = ${args.filters.source}`);
  }
  if (args.filters?.createdAfter) {
    conditions.push(gte(unprocessedScraperPayloads.createdAt, new Date(args.filters.createdAfter)));
  }
  if (args.filters?.createdBefore) {
    conditions.push(lte(unprocessedScraperPayloads.createdAt, new Date(args.filters.createdBefore)));
  }
  if (args.filters?.parserVersion) {
    conditions.push(sql`context->>'parserVersion' = ${args.filters.parserVersion}`);
  }

  const rows = await db
    .select()
    .from(unprocessedScraperPayloads)
    .where(and(...conditions))
    .orderBy(desc(unprocessedScraperPayloads.createdAt))
    .limit(limit)
    .offset(offset);

  const hasNextPage = rows.length > (args.first || 10);
  const edges = rows.slice(0, args.first || 10).map((row, idx) => ({
    node: row,
    cursor: encodeNumberToBase64(offset + idx),
  }));

  const endCursor = edges.length > 0 ? edges[edges.length - 1].cursor : null;

  return {
    edges,
    pageInfo: { hasNextPage, endCursor },
    totalCount: await db.select({ count: count() }).from(unprocessedScraperPayloads).where(and(...conditions)),
  };
};

export const reprocessPayload = async (
  _: any,
  args: { payloadId: string; parserVersion: string },
  context: { userId: string }
) => {
  requireModerator(context);

  // Verify payload exists
  const payload = await db
    .select()
    .from(unprocessedScraperPayloads)
    .where(eq(unprocessedScraperPayloads.id, args.payloadId))
    .limit(1);

  if (!payload.length || payload[0].deletedAt) {
    return { success: false, message: 'Payload not found or already deleted' };
  }

  // Verify parser version exists
  const version = await db
    .select()
    .from(parserVersionRegistry)
    .where(eq(parserVersionRegistry.version, args.parserVersion))
    .limit(1);

  if (!version.length) {
    return { success: false, message: `Parser version ${args.parserVersion} not found in registry` };
  }

  // Enqueue to AIProcessingQueue (Story 3.5)
  const queueId = await enqueueToAIProcessingQueue({
    payload: payload[0].rawPayload,
    source: payload[0].context.source,
    parserVersion: args.parserVersion,
    originalPayloadId: args.payloadId, // Track reprocessing origin
  });

  return {
    success: true,
    queueId,
    message: `Payload requeued to AIProcessingQueue with parser ${args.parserVersion}`,
  };
};

export const deleteUnprocessedPayload = async (
  _: any,
  args: { payloadId: string },
  context: { userId: string }
) => {
  requireModerator(context);

  const result = await db
    .update(unprocessedScraperPayloads)
    .set({ deletedAt: new Date() })
    .where(
      and(
        eq(unprocessedScraperPayloads.id, args.payloadId),
        isNull(unprocessedScraperPayloads.deletedAt)
      )
    );

  return result.rowCount > 0;
};

export const parserVersions = async (
  _: any,
  args: { onlyActive?: boolean },
  context: { userId: string }
) => {
  requireModerator(context);

  const conditions = onlyActive ? [eq(parserVersionRegistry.isActive, true)] : [];

  return await db
    .select()
    .from(parserVersionRegistry)
    .where(and(...conditions))
    .orderBy(desc(parserVersionRegistry.deployedAt));
};
```

## Dev Notes

### Architecture & Design Decisions

1. **JSONB for flexible context:** The `context` field is stored as JSONB (not separate columns) to accommodate future source additions (e.g., Twitter/X, custom adapters) without schema changes. A new source can add custom context fields without a migration.

2. **Capture before discard:** Payloads are persisted before AJV validation discards them, not as a post-hoc archive. This ensures no data loss at the boundary.

3. **Parser version as context field:** Storing `parserVersion` in the `context` JSONB (alongside other metadata) rather than as a separate FK column keeps the unprocessed-payload record self-contained and auditable (the exact version that failed is always in the record, never re-inferred).

4. **Async re-processing (non-blocking):** Re-processing is enqueued to `AIProcessingQueue`, not executed synchronously. This ensures moderator actions remain responsive and allows re-processing to be scaled independently. The moderator receives a `queueId` for tracking if desired.

5. **Soft-delete for audit trail:** Following AD-8, unprocessed payloads are soft-deleted (not hard-deleted) to preserve audit trail. Moderators can manually delete anomalies they've investigated; the cleanup job does the same after TTL expires.

6. **Daily digest over push notifications:** Email digests (once per 24 hours) are chosen over immediate notifications to avoid alert fatigue for high-volume anomalies. Moderators review daily, not per-anomaly.

7. **JSON scalar vs. fully-typed GraphQL:** For MVP, `rawPayload` and `validationError` use the `JSON` scalar in GraphQL (simpler schema, fewer types). Post-MVP, if moderators need to filter/query specific error types, these can be re-exposed as fully-typed objects (breaking change, but well-scoped to moderator-only API).

8. **No in-app notifications (for MVP):** This story provides email digests and a moderator tools page (Story 3-4i). In-app push notifications (Story 0.12 / FCM) are out of scope; moderators are expected to check email or log into moderator tools.

### Integration Points with Other Stories

- **Story 3-4g (AJV Validation):** Provides the detection point. Where 3-4g's validation fails (returns `null` or logs error), this story captures the payload.
- **Story 3.5 (AIProcessingQueue):** This story enqueues re-processing requests. Depends on `enqueueToAIProcessingQueue` helper.
- **Story 0.15 (Email Adapter):** Used for sending daily digest emails. Depends on `sendEmail` from the email adapter.
- **Story 4.7a (Moderator Route Guard):** GraphQL resolvers are gated with `requireModerator`. Follows same auth pattern.
- **Story 3-4i (Moderator UI):** Will consume `queryUnprocessedPayloads` and `reprocessPayload` mutations to build the unprocessed-payloads page.
- **AD-8 (Soft-Delete Convention):** Unprocessed payloads follow soft-delete pattern; no hard deletes.

### Known Limitations & Future Work

1. **Manual version registration (MVP):** Parser versions are seeded manually in migrations. Auto-detection via git tags is deferred to a follow-up story.
2. **No filtering by error type:** Moderators cannot yet filter anomalies by specific AJV error keywords (e.g., "required vs. type errors"). This can be added post-MVP with a derived `errorKeyword` field.
3. **No re-processing status tracking:** Re-processing enqueues to the queue but doesn't link the new result back to the original unprocessed payload. Story 3-4i can add this tracking post-MVP.
4. **Fixed daily digest schedule (08:00 UTC):** Email time is hardcoded; no per-moderator timezone handling. Post-MVP, digest time could be configurable per user.

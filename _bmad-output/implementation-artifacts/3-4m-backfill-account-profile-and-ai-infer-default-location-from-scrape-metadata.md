# Story 3.4m: Backfill account profile and AI-infer default location from scrape metadata

## Story Details

- Epic: 3
- Story ID: 3.4m
- Status: ready-for-dev

## Story

**As a** system,
**I want** every successful scrape to (a) keep a subscribed account's stored `displayName`/`username` in sync with what the source platform actually reports, and (b) when an account has no `defaultLocation` set, automatically infer one from the post's own scraped metadata and resolve it into real coordinates,
**so that** subscriber-facing account details stay current without manual re-entry, and event extraction for accounts with an implicit location (e.g. "at the mall") has a fallback location to use — without ever repurposing a subscriber's own saved location to label an unrelated account.

**Depends on:** Story 3.3c (`review`) — extends its `ScrapedPost` normalized-post shape. Story 0.13 (`review`) — adds a sibling function alongside its `callGemini` Adapter. Story 0.16 / 2.4b (`review`) — reuses its `resolveLocation` geolocation adapter as-is. Story 0.25 (`review`) — follows its established Secrets Manager credential pattern. Story 3.3b (source of `default_location_change_requests`, `review`) — amends its schema/GraphQL/resolver.

## Acceptance Criteria

1. **Given** `processScrapeJob` (`apps/backend/src/lib/scraper/process-scrape-job.ts`) completes scraping one or more posts for an account, **when** any scraped post's `ownerDisplayName` and/or `ownerUsername` differs from the account's currently-stored `displayName`/`username` (`social_media_account_profiles`), **then** the stored value(s) are updated to match — using the first scraped post in the batch that carries the differing field(s). [FR89]
2. **And** if no scraped post in the batch carries `ownerDisplayName`/`ownerUsername`, or both already match the stored values, no database write is made for the profile-backfill part of this story.
3. **Given** the account's `defaultLocation` is `null`, **when** at least one scraped post in the same batch carries a non-empty `locationName` and/or non-empty `content` (caption), **then** the system calls Gemini with **only** that post's own `locationName`/`content` — **never** any `UserLocationPreference` data (PRD §5 "Location Data Reuse Boundary") — to produce a place-description inference. [FR90]
4. **And** if the account's `defaultLocation` is already non-`null`, or no scraped post in the batch carries any usable `locationName`/`content`, no Gemini call for location inference is made for this job.
5. **Given** Gemini returns an inferred place description, **when** the system processes that response, **then** it is resolved into full `LocationDetails` (coordinates, formatted address) via the **existing** geolocation adapter's `resolveLocation({ kind: 'ADDRESS', address })` (`apps/backend/src/lib/geolocation/adapter.ts`) — the raw Gemini text is never written to `defaultLocation` or trusted as coordinates directly.
6. **And** the resolved `LocationDetails` is persisted to `SocialMediaAccountProfile.defaultLocation` through the **same** immediate-apply-with-moderator-oversight mechanism a human `editAccountDefaultLocation` edit uses — a `DefaultLocationChangeRequest` row is inserted (`status: PENDING_REVIEW`) and moderators are emailed via the existing `DEFAULT_LOCATION_CHANGE_MODERATOR_ALERT` template — except `changeSource` is `AI_INFERENCE` and `changedByUserId` is absent (`null`), never attributed to a subscriber whose key happened to be used. [FR90, FR92]
7. **Given** the location-inference Gemini call, **when** selecting which API key to use, **then** it prefers a contributing subscriber's own BYOK key via the **existing, unmodified** `callGemini`/`selectApiKey` Tier 1/Tier 2 rotation, and **only** on that call throwing `AiGatewayExhaustedError` does a **new** `callGeminiForLocationInference` sibling function fall back to exactly one attempt against a platform-funded `SYSTEM_GEMINI_API_KEY` — per AD-10, this key is read directly (no `usage-store`/`selectApiKey` candidate pooling) and is structurally unreachable from Story 3.6's general post-extraction call path (no shared call site). [FR91]
8. **Given** an account already has `defaultLocation` set (by a human or a prior AI inference), **when** any later scrape job runs for that account, **then** no location-inference Gemini call is attempted at all — the call fires at most once per account, never once per post. [AD-10 cost posture]
9. **Given** two scrape jobs for the same account run concurrently (or overlapping) and both attempt AI inference because both observed `defaultLocation` as `null`, **when** both complete their Gemini/geolocation calls, **then** only one write to `defaultLocation` and one `DefaultLocationChangeRequest` row succeeds — the write is guarded by a `WHERE default_location IS NULL` condition inside a transaction, and the losing attempt's result is discarded without inserting a duplicate audit row or sending a duplicate moderator email.
10. **Given** the Gemini call, the geolocation resolution, or the `DefaultLocationChangeRequest`/email write for either the profile-backfill or the location-inference part of this story throws, **when** `processScrapeJob` is running, **then** the error is caught and logged without failing the scrape job or the surrounding SQS batch item — mirroring the existing catch-and-log pattern already in `processScrapeJob`'s outer `try/catch` (Story 3.4's AC7 precedent).
11. **Given** a moderator opens Moderator Tools and reviews a pending `DefaultLocationChangeRequest`, **when** they choose **Revert** on one whose `changeSource` is `AI_INFERENCE` (and therefore has `previousLocation: null`, since inference only ever fires when `defaultLocation` was unset), **then** `resolveDefaultLocationChange`'s `REVERT` branch sets the account's `defaultLocation` back to `null` (instead of throwing `"Cannot revert... previous location was not recorded"`, which today incorrectly blocks reverting exactly this new case) — reverting a human edit whose `previousLocation` was already non-`null` is unchanged.
12. **Given** the `DefaultLocationChangeRequest` GraphQL type, **when** a moderator's client queries `pendingDefaultLocationChanges`, **then** each item exposes a new `changeSource: DefaultLocationChangeSource!` field (`USER` | `AI_INFERENCE`) and `changedByUserId` is now nullable (`ID`, not `ID!`) — so the client can visually distinguish an AI-inferred value from a human edit. [FR92]

## Dev Notes

### Architecture & UX Gate Findings

Epic 3's readiness sweep (`_bmad-output/planning-artifacts/epic-readiness/epic-3-readiness.md`, `swept: true`) is dated 2026-08-09 and its `stories_covered` list stops at `3.11` — it predates this story (created 2026-08-24, after a same-day PRD/architecture amendment) by two weeks and cannot have anticipated its new infra. Per the workflow's lightweight-guard rule, Gate 1, Gate 2, and Gate 3 were each run **fresh** for this story via persona subagents rather than trusted from the stale sweep.

- **Gate 1 (Winston/Architect persona) — real finding, resolved below, not deferred to a new story.** The reviewer correctly flagged that routing `callGemini`/geolocation calls through `processScrapeJob` (the `ScraperLambda`/"L_Scrape" Lambda) builds a second, parallel external-AI-service ingress alongside the existing `AIProcessingQueue` → `AIProcessorLambda` ("L_AI") pipeline, and suggested routing this story's work through that existing queue/Lambda instead, since L_AI already has `BYOK_KMS_KEY_ID`/KMS-grant and `GEOAPIFY_API_KEY` wired (Story 3.5's own precedent).
  - **Why that suggestion is rejected, with direct evidence:** Story 3.5's own AC2 (`_bmad-output/implementation-artifacts/3-5-add-new-posts-to-a-processing-queue.md`) explicitly states posts are enqueued onto `AIProcessingQueue` **only** "when a user selects it for extraction via Story 5.1a's `selectPostsForExtraction` mutation (PRD §3.10) — not automatically for every scraped post." Confirmed by reading the actual code: `enqueuePostForProcessing` (`apps/backend/src/lib/posts/enqueue-post-for-processing.ts`) is called **only** from a GraphQL resolver (`resolvers.ts`), never from anywhere in `apps/backend/src/lib/scraper/`. Story 5.1a (the manual-selection mutation that is the only thing that ever enqueues) is still `backlog`. This means L_AI is **not** invoked automatically on scrape at all today — routing this story's "on every scrape" requirement (FR90) through that pipeline would make it fire only when a user manually selects a post for extraction (which may never happen, especially given quota limits), directly contradicting FR90's "automatically." PRD §3.8's "all requests to external AI services... routed through a dedicated AI Gateway layer... using a decoupled, multi-queue architecture" describes the Adapter Pattern (`callGemini`) and the scrape→extract→ingest pipeline's own internal decoupling — it is not a blanket rule that every `callGemini` caller must be SQS-triggered; Story 0.13's own Dev Notes already name Story 4.2 (AI-assisted correction) as a **direct**, non-queued future `callGemini` caller, confirming direct callers are an established, sanctioned pattern.
  - **Resolution:** the design stays as originally drafted — `processScrapeJob` (L_Scrape) calls `callGeminiForLocationInference`/`resolveLocation` directly, synchronously, once per job, using the in-memory `ScrapedPost[]` batch already fetched in that invocation. `ScraperLambda`'s CDK environment gains the KMS grant, `GEOAPIFY_API_KEY`, the new `SYSTEM_GEMINI_API_KEY` secret, and an SES grant (Task 8) — new wiring, but necessary, not duplicative, since L_AI is not a viable substitute call site for an "on every scrape" requirement given Story 5.1a's not-yet-built gating.
  - The reviewer's secondary points were accepted as-is: the transient-fields decision (never persisting `locationName`/`ownerDisplayName`/`ownerUsername` to the `posts` table) is correct and consistent with not touching a table speculatively; extracting `applyDefaultLocationChange` into a shared helper is the right move and matches the existing shared-lib pattern (`persistScrapedPost`, `enqueuePostForProcessing`).

This story's AI-inference path only ever fires on the `null` case, so it cannot reuse `editAccountDefaultLocation`'s resolver as-is (its precondition is inverted) — hence Task 5's extraction of a shared `applyDefaultLocationChange` helper parameterized to support both "was null, now set" (AI path, always creates an audit row per PRD §3.7's explicit "written to Default Location exactly as a human edit would be... so moderators review an AI-inferred value the same way they review a human one") and "was set, now edited" (existing human path, unchanged).
- **`defaultLocationChangeRequests` (schema.ts)** — `changedByUserId` is `.notNull()` today; no `changeSource` column exists. `resolveDefaultLocationChange`'s `REVERT` branch throws `BAD_REQUEST` when `previousLocation` is falsy — today unreachable in practice (every existing change request comes from `editAccountDefaultLocation`, which always has a non-null `previousLocation`), but this story's `AI_INFERENCE` requests will **always** have `previousLocation: null`, making this branch newly reachable and requiring the fix in Task 6.

# Story 0.16: Set up Geolocation adapter with caching layer

## Story Details

- Epic: 0
- Story ID: 0.16
- Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a developer,
I want a dedicated Geolocation adapter that wraps all outbound calls to the Geoapify Geocoding/Places/Reverse-Geocoding API behind a single interface, with a caching layer for repeated lookups and a restricted, backend-only API key,
so that every feature that resolves coordinates, addresses, or timezones (map-based location picking, nearby-event search, timezone inference for extracted events) reuses the same client and cache instead of each feature calling the Geoapify API directly and re-incurring cost/quota.

## Acceptance Criteria

1. **Given** a feature needs to resolve a location (address, place ID, or coordinates) or infer a timezone, **when** it needs geolocation data, **then** it does so exclusively through this Adapter's exposed interface — never the raw Geoapify SDK/HTTP API from feature code. [epics.md AC1]
2. **And** the Adapter caches lookups for the same location so repeated queries are served from cache rather than re-calling the external API (NFR14) — Geoapify's terms explicitly permit indefinite storage/caching of returned place data, so the cache has no forced TTL/expiry beyond what NFR14's cost-management goal requires. [epics.md AC2]
3. **And** the Geoapify API key used by the Adapter is restricted in the Geoapify dashboard (domain/IP referrer restrictions) per the PRD's API key security requirements, to the extent practically enforceable for a backend-only, server-to-server key (see Dev Notes "API Key Restriction — Practical Limitation for a Backend-Only Key"). [epics.md AC3]
4. **And** the Adapter is backend-only — no direct Geoapify API calls are made from `apps/web`. [epics.md AC4]
5. **And** timezone resolution reuses the same Geoapify geocode/reverse-geocode/place-details response (Geoapify returns an IANA `timezone.name` field inline on all three) rather than requiring a separate Time-Zone-specific API call, unlike the Google-based design this story originally assumed. [epics.md AC5]
6. **Given** no feature story yet calls this Adapter (Story 2.3a "Build the saved-locations backend GraphQL API layer", `ready-for-dev`, explicitly cites this Adapter in its own AC; Story 2.4 "Set location by current location or map" and FR33's timezone-inference logic are further future consumers, all currently `backlog`), **when** this story ships, **then** the Adapter is a reserved, ready-to-consume capability — no product/pipeline code invokes it in this story. This story proves the Adapter end-to-end via 100%-covered unit tests of its pure cache-key-normalization logic (`packages/domain`) plus mocked-dependency/local-Postgres integration tests of the HTTP-calling orchestrator (`apps/backend`); a real call against a live Geoapify project is explicitly deferred (see Dev Notes "Geoapify Project Setup & Live API Verification"). [Derived — mirrors the "reserved slot" pattern from Stories 0.7/0.8/0.9/0.12/0.13/0.15]
7. **Given** `docs/infrastructure/high-level-overview.md`'s architecture diagram currently shows only `Gemini`/`FCM` under `External Services` and has no geolocation-service node, **when** this story ships, **then** the diagram is updated to show `L_API` resolving location via a `Geoapify` external-service node, and a new `docs/infrastructure/5-geolocation.md` shard documents the service choice — mirroring the existing per-service shard convention already used by `4-push-notifications.md`. [Derived — surfaced by this story's own lightweight escape-hatch guard, not an explicit epic-0-readiness.md finding; see Architecture & UX Gate Findings]
8. **And** every `LocationDetails` object the Adapter returns (all three of `geocodeAddress`/`reverseGeocode`/`getPlaceDetails`) includes a `provider: GeolocationProvider` value (`'GEOAPIFY'` today) tagging which geolocation provider resolved it, so that a `placeId` — an opaque token only valid against the provider that issued it — is never persisted or reinterpreted without knowing which provider's API it belongs to. [Derived — surfaced during this story's/2.3a's review: this project has already swapped geolocation providers once pre-launch (Google → Geoapify, Sprint Change Proposal 2026-08-03) with no data-migration cost only because no rows existed yet; a second provider or a post-launch swap would otherwise silently misinterpret every previously-persisted `placeId` against the wrong API. See Dev Notes "Why LocationDetails Gains a `provider` Field".]

- **Testing Framework: `node:test`, Not Vitest, for This Story's Packages.** Story 0.10 ("Set up testing frameworks foundation") has, in fact, already been substantially implemented in the codebase (a root `vitest.config.ts`, `packages/testing-config` with `msw`/`vitest-node`/`vitest-react` shared configs) despite still showing `review` (not `done`) in `sprint-status.yaml` — this story's prior draft's claim that "no test framework exists yet" is no longer accurate project-wide. However, the root `vitest.config.ts`'s `projects` array only includes `apps/web`, `packages/database`, `packages/analytics`, `packages/ui` — **not** `apps/backend` or `packages/domain`. Every existing test file in `apps/backend` (`context.test.ts`, `validate.test.ts`, `resolvers.test.ts`, `favorites-and-calendar.test.ts`) and in `packages/graphql-select` uses `node:test`/`tsx --test`, not Vitest. This story follows that actual, established, current-codebase precedent for its own new tests in `apps/backend`/`packages/domain`, rather than introducing Vitest into either package speculatively (which would be an unrequested, out-of-scope migration).
- **Why the cache-key normalization logic lives in `packages/domain`, but the HTTP/DB-calling code lives in `apps/backend`:** `buildLocationCacheKey` is a pure function over plain strings/numbers (no I/O, no SDK, no network) — exactly the "framework-agnostic business logic" `packages/domain` exists for, and the persistent "reusable mechanism → `packages/domain`" project rule applies cleanly (same precedent as Story 0.13's `selectApiKey`/Story 0.15's `renderEmailTemplate`). The Geoapify REST calls, the Drizzle cache-store reads/writes, and the env-var read are all I/O- and SDK-coupled — these stay in `apps/backend`, consistent with that same precedent. Neither module imports `drizzle-orm`/DB-client code or any other Node-runtime-only dependency, so `packages/domain`'s frontend-safety boundary (per `project-context.md`'s Code Organization rule) is preserved.
- **Why this Adapter reuses `@festgrid/shared-types`'s `Coordinates`/`LocationDetails` instead of defining new local types:** Both interfaces already exist in `packages/shared-types/src/index.ts` (`Coordinates { latitude, longitude }`, `LocationDetails { coordinates, placeName?, placeId?, formattedAddress?, timezone? }`), created by the PRD's data-model definitions and already consumed by `Schedule.locationDetails`. Reusing them keeps this Adapter's return shape identical to what `apps/web`/GraphQL will eventually expose for `Schedule.locationDetails` and Story 2.3a's `UserLocationPreference.locationDetails`, avoiding a future mapping-layer duplication — and matches what Story 2.3a's own (already-written) Dev Notes explicitly expect (`resolveLocation` returning the shared `LocationDetails` shape verbatim).
- **Only one adapter function, `resolveLocation` — no separate `resolveTimezone` (a genuine simplification enabled by the Geoapify provider swap).** This story's prior Google-based draft exposed two functions (`resolveLocation` returning `LocationDetails` with `timezone: undefined`, plus a separate `resolveTimezone(coordinates)` making a second, dedicated Time Zone API call) because Google's Geocoding/Places responses do not include timezone data. Geoapify's Geocoding, Reverse Geocoding, and Place Details APIs **all** return a `timezone.name` (IANA) field inline on the same response (confirmed via Geoapify's own API documentation and changelog — timezone data was added across Geocoding/Reverse Geocoding/Autocomplete/Place Details), which is exactly what epics.md's AC5 states. `resolveLocation` therefore returns a fully-populated `LocationDetails` (including `timezone`, when Geoapify's response includes one) in a single call, and no second function/cache-key/cache-table-entry-type is needed for timezone. No downstream story's actual code depends on a `resolveTimezone` export name today — `Story 3.6` (FR33's owner) does not exist as an implementation artifact yet, and Story 2.3a's Dev Notes mention `resolveTimezone` only as background narrative, not as a called function in its own Tasks — so this is a safe, un-breaking simplification, not a contract change.
- **Provider-driven "not found" shape difference from the prior Google-based draft:** Google's Geocoding/Places APIs return a distinct `status` field (e.g. `'ZERO_RESULTS'`) to signal no match. Geoapify instead returns a normal HTTP 200 with an **empty** `results`/`features` array. `geoapify-client.ts`'s `GeolocationNotFoundError` classification (Task 4) is based on this empty-array check, not a status-string check — a concrete, provider-specific detail worth flagging since it's easy to miss when adapting the old draft's error-handling shape naively.
- **API Key Restriction — Practical Limitation for a Backend-Only Key (accepted assumption, confirmed with the user during this story's creation, Pre-Coding Approval Gate item):** AC3 (epics.md, PRD §External API Management) calls for the Geoapify key to be restricted via domain/IP referrer restrictions in Geoapify's MyProjects dashboard. In practice, neither restriction type is meaningfully enforceable for this key today: HTTP-referrer restriction is a browser-call-site concept (this key is never called from a browser — AC4), and IP-address restriction would require a **static outbound IP** for the calling Lambda, which requires routing it through a NAT Gateway with an Elastic IP — infrastructure `epic-0-readiness.md`'s Gate 1 pass explicitly confirmed Story 0.14's current IaC resource list has no NAT Gateway ("Story 0.14's 4-Lambda IaC list is complete for the architecture diagram as drawn"). The user was presented this trade-off directly (Postgres-cache-vs-alternatives and key-restriction-vs-NAT-Gateway) during this story's creation and explicitly chose to **accept the limitation for MVP** rather than expand Story 0.14's scope to add a NAT Gateway solely to secure one low-risk, read-only, non-destructive API key. This mirrors the identical trade-off and identical conclusion this story's prior Google-based draft reached independently for Google Cloud Console's application-restriction equivalent — carried forward here with explicit, fresh user confirmation rather than assumed.
- **Caching has no TTL/expiration (confirmed with the user during this story's creation):** Geoapify's terms explicitly permit indefinite storage/caching of returned place data (this is, in fact, the exact ToS distinction that motivated Sprint Change Proposal 2026-08-03's Google→Geoapify swap in the first place — Google's terms only allowed indefinite storage of a bare `placeId`, not full place/address data, which conflicted with this project's design of persisting `LocationDetails` indefinitely in `UserLocationPreference`/`Schedule`). This story implements the cache as indefinite — a `geolocation_cache` row, once written, is served forever, with no TTL column, no invalidation path, and no background eviction job. The user confirmed this Postgres-backed, no-TTL design directly (over an in-memory-only cache, which would have poor cross-invocation hit rates in this stateless Lambda architecture, or introducing new Redis/ElastiCache infrastructure, which this project's stack has none of today) during this story's creation.
- **Geoapify Project Setup & Live API Verification (accepted forward dependency, not a Gate 1 gap):** Geoapify's free tier (3,000 credits/day, ~90,000/month, 1 credit per simple Geocoding/Places/Place-Details request — checked 2026-08-03) requires only a MyProjects sign-up, **no billing account**, unlike Google Maps Platform's requirement (which the prior draft flagged as a hard blocker for local verification). This lowers the setup friction Story 0.16 originally anticipated, but this development environment still has no real Geoapify project/API key configured. `geoapify-client.ts`'s API key is read lazily (mirrors Story 0.12/0.13/0.15's lazy-SDK-client-init pattern) so `apps/backend dev`/`build`/unit-tests all work without a real key; the full real-Geoapify round trip is deferred to whenever Story 2.3a (or a later consumer) runs against a real MyProjects key.
- **Package dependency isolation (project-context.md, persistent fact):** No new third-party npm dependency is introduced in `apps/backend` for this story (native `fetch` is used — see "Why Native `fetch`" below). `packages/domain` gains its first workspace dependency, `@festgrid/shared-types` (reasoned above) and its first devDependency, `tsx` (needed to run its own new test file) — still zero third-party SDK/runtime dependencies, consistent with the restriction.
- **Why Native `fetch` Instead of a Geoapify SDK:** Geoapify does not publish an official first-party Node.js client library (unlike Google's `@googlemaps/google-maps-services-js`, which the prior draft's research found and explicitly declined to use anyway, for its own separate reasons). Three simple `GET` calls with no complex request-building do not justify introducing an unofficial third-party wrapper package. This mirrors Story 0.13's identical reasoning for hand-rolling `backoff.ts` instead of pulling in an ESM-only `p-queue`, and Story 0.15's identical reasoning for hand-rolling `render-template.ts` instead of pulling in a templating library.
- **Why `LocationDetails` Gains a `provider` Field (confirmed with the user during this story's amendment):** `placeId` is an opaque token issued by whichever geolocation provider resolved it — it is only valid when handed back to *that same* provider's Place Details endpoint, not a universal identifier. Before this addition, `LocationDetails` (and everywhere it's persisted — `schedules.location_details`, and Story 2.3a's new `user_locations.location_details`) had no way to record which provider issued a given `placeId`. That was tolerable only because this project has, so far, ever had exactly one active provider at a time — Google was fully replaced by Geoapify pre-launch (Sprint Change Proposal 2026-08-03) with zero data-migration cost, specifically because no rows existed yet to migrate. A second concurrent provider, or any *future* swap after real users have saved locations, would silently misinterpret every previously-persisted `placeId` against the new provider's API with no way to detect it. Adding `provider: GeolocationProvider` (AC8) — populated by this story's `geoapify-client.ts` on every returned `LocationDetails`, optional at the type level for backward compatibility with `Schedule.locationDetails`'s pre-existing, provider-less rows — closes that gap now, while it's still cheap (this story and Story 2.3a are both `ready-for-dev`, no code or real data exists yet). No new DB column or migration is needed beyond what Task 3/2.3a's Task 1 already add: `provider` rides inside the existing `jsonb` `result`/`location_details` columns as part of the `LocationDetails` object stored verbatim — a flat, queryable `provider` column was considered and rejected as unneeded speculative infrastructure, since nothing in this project's current scope ever needs to query/filter cache or saved-location rows *by* provider; the tag exists purely so a `placeId` is never interpreted without knowing its origin.

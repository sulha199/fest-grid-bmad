# Story 1.i1o: Wire real next-intl label content into EventCard and WeeklyCalendarView

## Story Details

- Epic: 1.i1 (One card primitive for every event-card image slot and badge)
- Story ID: 1.i1o
- Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user browsing FestDaily on the `/id` locale,
I want the event card's TILL tag, 8-state status badge, favorite-toggle control, and nearby-distance badge — and their equivalents on the weekly calendar — to show real Indonesian text instead of the components' hardcoded English `defaultLabels`,
so that switching to `/id` doesn't silently ship English microcopy across every page that renders an `EventCard` or `WeeklyCalendarView` (Discovery, Feed, Favorites, Archive, Account, My Calendar) — confirmed live on `/id`, per `event-card-family-consolidated-acs.md` §2.5, as 100% of this label surface today, not a partial ("till" only) gap.

## Acceptance Criteria

1. **Given** `home-content.tsx`, `feed-content.tsx`, `favorites-content.tsx`, `archive-content.tsx`, and `account-content.tsx` already call `useTranslations()` for other page text but each build a `cardLabels` object passed to `EventListView` that omits `EventCard`'s `tillLabel`/8-state status badge/`favoriteToggle`/`nearbyBadge` (falling through to `EventCard.tsx`'s hardcoded `defaultLabels`), **when** this story ships, **then** each of these five files adds a `useTranslations('EventCard')` call (`tEventCard`) and merges its output into the existing `cardLabels` object literal each already passes to `EventListView` — `EventCard`'s `defaultLabels` fallback is no longer reached for any of these keys on any live locale.
2. **And** `CalendarView.tsx` (Discovery's calendar tab), `FeedCalendarView.tsx`, `AccountCalendarView.tsx`, and `my-calendar-content.tsx` each add a `useTranslations('WeeklyCalendarView')` call (`tCalendar`) and merge its output into the existing `labels` object literal each already passes to `WeeklyCalendarView`, covering `loadingText`, `favoritedBadgeLabel`, `addedToCalendarBadgeLabel`, `favoriteToggleLabel`, `tillLabel`, all 7 named status states (`statusEnded`/`statusHappeningNow`/`statusEndsToday`/`statusInHours`/`statusInDays`/`statusUpcoming`/`tomorrow`), and `nearbyBadge`. The pre-existing `calendarPrevWeekLabel`/`calendarTodayLabel`/`calendarMoreLabel`/`calendarClosePopoverLabel`/etc. keys these four files already wire from their own page namespace (`DiscoveryPage`/`FeedPage`/`AccountPage`/`MyCalendarPage`) are **not** touched or migrated — they are already correctly translated today; this story only adds the missing keys alongside them in the same `labels` object literal.
3. **And** two new shared top-level next-intl namespaces, `EventCard` and `WeeklyCalendarView`, are added to both `apps/web/locales/en.json` and `apps/web/locales/id.json` (mirroring the existing `EventCategory`/`EventType`/`NearbyFilter`/`FilterHub` shared-namespace precedent — resolved with the user during drafting; see Dev Notes), holding real, natural Indonesian content for every key below — not machine-translated-without-review, not placeholder text:
   - `EventCard`: `favoriteToggle`, `tillLabel`, `statusEnded`, `statusHappeningNow`, `statusEndsToday`, `statusInHours`, `statusInDays`, `statusUpcoming`, `tomorrow`.
   - `WeeklyCalendarView`: `loadingText`, `favoriteToggleLabel`, `favoritedBadgeLabel`, `addedToCalendarBadgeLabel`, `tillLabel`, `statusEnded`, `statusHappeningNow`, `statusEndsToday`, `statusInHours`, `statusInDays`, `statusUpcoming`, `tomorrow`.
   - Exact values for both locales are specified in Dev Notes → "Translation content (exact key/value pairs)" below.
4. **And** `EventCardMediaPrimitives.tsx` gains a new exported, pure, locale-parameterized helper `formatLocalizedNearbyBadgeDistance(locale: string, distanceKm: number): string`, placed alongside the existing `formatNearbyBadgeDistance` — same `>=2km` (0 fraction digits) / `<2km` (1 fraction digit) branching, but formatting the number via `Intl.NumberFormat(locale, { minimumFractionDigits, maximumFractionDigits })` instead of `Math.round`/`.toFixed(1)`, per `project-context.md`'s Locale-Sensitive Data Rendering rule for numeric values. Every content/calendar file's `nearbyBadge` closure (`(distanceKm: number) => formatLocalizedNearbyBadgeDistance(locale, distanceKm)`) calls this helper with the page's own `useLocale()` value (the same bare `'en'`/`'id'` string `EventDetailWrapper.tsx` already threads through as a `locale` prop — no new locale-resolution pattern introduced). On `/id`, this renders comma-decimal distances (e.g. `"1,2 km"`) instead of English's decimal point (`"1.2 km"`); the literal `" km"` unit suffix is unchanged (an SI abbreviation, identical in both locales, not itself translated content). The existing English-only `formatNearbyBadgeDistance` — the component's own internal safety-net default used only when no `labels.nearbyBadge` is supplied at all — is left unchanged and still exported.
5. **And** `EventCardLabels`/`WeeklyCalendarViewLabels`' `today`/`yesterday` fields are explicitly **not** translated in this pass: their only consumer, `formatRelativeDayOrDate` (`format-event-date.ts`), has no production call site anywhere in `apps/web`/`packages/ui` today (confirmed via grep — referenced only by its own direct unit tests), so authoring translated content for a dead-code label pair is out of scope, matching this epic's own `FIND-053` precedent (delete/ignore unreachable branches rather than spend further effort on them).
6. **And** `archive-content.tsx`'s existing `favoriteToggle: "", // not favoritable in Archive` placeholder is replaced with `tEventCard('favoriteToggle')`, matching every other page — this string is currently unreachable (Archive's `getCardProps` never supplies `onFavoriteToggle`, so `EventCard` never renders the button whose `aria-label` this would be), and the change is made purely for consistency; a one-line comment records that it is presently unreachable so a future reader doesn't wonder why Archive has a live favorite-toggle string with no visible favorite button.
7. **And** no visual, layout, or component-prop shape change occurs anywhere in this story — `EventCardStatusBadge`, `EventCardNearbyBadge`, `EventCardDateBox`, `EventCardFavoriteBadge`, and `CalendarCard` (inside `WeeklyCalendarView.tsx`) are all unchanged; only the string *values* flowing into their already-shipped `labels`/`label` props change, plus the one new pure formatter function in AC4.

  **Why no ICU plural handling for `statusInHours`/`statusInDays`:** `EventCard.tsx`/`WeeklyCalendarView.tsx` resolve these via a plain `.replace('{n}', String(n))` on the label string — not next-intl's `t(key, {n})` ICU interpolation — because the numeric value (`n`) is only known inside the component's own render (mirroring the existing `moreLabel`/`multiDaySegmentLabel` resolver-function precedent's rationale, except these two remain plain strings, not functions, since `EventCard.tsx`/`WeeklyCalendarView.tsx` already hardcode the `.replace()` call site themselves and this story does not change that mechanism). English's own default (`"In {n} hour(s)"`) already works around English's plural grammar with an ungainly `"(s)"` suffix rather than true ICU pluralization — this story does not "fix" that for English either, since doing so would require changing `EventCard.tsx`'s/`WeeklyCalendarView.tsx`'s own resolution mechanism from a plain-string-replace to a caller-supplied resolver function (a real API change, out of scope for a labels-content story — see Out of Scope). For **Indonesian specifically**, this limitation is a non-issue: Indonesian nouns do not carry grammatical number marking (there is no singular/plural distinction on "jam"/"hari" the way English has "hour"/"hours" — reduplication, e.g. "jam-jam", is a separate, optional construction not used in a numeric count phrase like this), so a single template with `{n}` substituted in is linguistically correct and natural for every value of `n`, with no plural-form branching required. This was confirmed, not guessed, before finalizing this story's translation content.

- **Namespace design decision (raised to the user before drafting, per this workflow's non-mechanical-tradeoff rule):** This project has two live, conflicting precedents for where a small set of shared UI-vocabulary strings should live: (a) `EventCategory`/`EventType`/`NearbyFilter`/`FilterHub` are single shared cross-page namespaces reused via `useTranslations()` everywhere they're needed, and (b) `calendarPrevWeekLabel`/`favoriteButtonLabel`/`priceFrom`-style strings are deliberately duplicated byte-for-byte into every one of `DiscoveryPage`/`FeedPage`/`FavoritesPage`/`ArchivePage`/`AccountPage`/`MyCalendarPage` separately. The user chose the shared-namespace approach (option (a)), reasoning: these ~12-15 strings are component-intrinsic vocabulary (till/status/favorite/nearby text means the same thing regardless of which page renders the card — unlike, say, an empty-state message that legitimately varies by page), and this session's own Event-Card family consolidation (BUG-047's shared date-box computation, BUG-048's shared status-badge/grid-item adoption, BUG-049's shared nearby-badge formatter) has been specifically about eliminating divergent copies of the same component behavior/text across surfaces — 6x-duplicating these same strings into every page namespace would directly contradict that effort's own point. The user further noted the existing `calendarPrevWeekLabel`-style duplication likely predates this consolidation effort rather than being a deliberate pattern worth extending here. This decision governs Task 1/3/4 above; it is not revisited by `bmad-dev-story`.

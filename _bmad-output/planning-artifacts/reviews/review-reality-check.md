# Reality-Check Review — AD-8 Soft-Delete Convention Extension

## Overall verdict

Most of AD-8's extended claims check out directly against the live codebase: `UserLocation` genuinely lacks `deletedAt` today (and its `deleteUserLocation` resolver is a real hard `db.delete()`, not just a missing column), the `toggleFavorite`/`toggleCalendarAddition` "legacy exception" description matches their resolver code and GraphQL schema verbatim, no `SoftDeleteAction`-shaped enum already exists to collide with, and the "returns the affected row's own type" contract is already precedented by `updateUserLocation(...): UserLocation!`. However, one load-bearing assumption is verifiably false today: the Drizzle partial-index pattern rule 3 points to as working precedent (`favorites`/`calendarAdditions`) does not actually produce partial indexes in the deployed database — the generated migration SQL and its Drizzle snapshot both silently drop the `WHERE deleted_at IS NULL` clause. The new `idx_user_locations_active` example added in this session inherits the same defect.

## Findings

- **high** AD-8 rule 3's cited precedent (`favorites`/`calendarAdditions` partial indexes) does not actually exist in the database this project ships. `packages/database/schema.ts` declares `.where(sql\`deleted_at IS NULL\`)` on `idx_favorites_active` and `idx_calendar_additions_active` (lines 160, 172), but the *generated* migration `packages/database/migrations/0004_optimal_frog_thor.sql` (lines 52-53) emits them with no `WHERE` clause at all: `CREATE INDEX IF NOT EXISTS "idx_favorites_active" ON "favorites" ("user_id");`. The corresponding Drizzle snapshot (`packages/database/migrations/meta/0004_snapshot.json`, the `idx_favorites_active` index entry) has no `"where"` key either — `drizzle-kit generate` (installed version 0.21.4, per `packages/database/package.json`'s `drizzle-orm@^0.30.10` / `drizzle-kit@^0.21.2`) silently dropped the partial-index predicate when diffing/emitting SQL, even though `drizzle-orm`'s index builder type (`.where(condition: SQL)`, `pg-core/indexes.d.ts`) accepts it. Since this project's workflow is `drizzle-kit generate` → `tsx migrate.ts` (not `drizzle-kit push`), the migration file is authoritative — the live Postgres indexes on `favorites`/`calendar_additions` are full (non-partial) indexes today, not the partial ones AD-8 rule 3 claims are the established, working pattern. *Fix:* Before treating rule 3 as settled, verify against this project's actual installed `drizzle-kit` version whether it now emits partial-index `WHERE` clauses (check its changelog/GitHub issues for partial-index support, or just re-run `pnpm --filter database generate` after touching an indexed table and inspect the output SQL). If it still drops the clause, either upgrade `drizzle-kit`, hand-write the `WHERE` clause into the migration after generation, or drop the partial-index claim from AD-8 and rely on a plain index instead. Whatever is decided should apply retroactively to the two existing indexes, not just the new `idx_user_locations_active` line.

- **medium** The new `idx_user_locations_active` example (`CREATE INDEX idx_user_locations_active ON user_locations (user_id) WHERE deleted_at IS NULL;`) doesn't reconcile with the pre-existing plain index already in `packages/database/schema.ts` line 52: `userIdIdx: index('idx_user_locations_user_id').on(t.userId)`. Unlike `favorites`/`calendarAdditions` (where the only other index is a `unique()` constraint, not a redundant plain btree on the same lookup column), `userLocations` would end up with two indexes covering the same column — one full, one (intended-)partial. AD-8 doesn't say whether `idx_user_locations_user_id` should be dropped, kept for moderator/all-rows queries, or left as accidental duplication. *Fix:* Add a line to rule 3 (or a UserLocation-specific note) stating whether the pre-existing plain index is superseded/removed or intentionally retained for the moderator "see soft-deleted rows" path.

- **low** Rule 4's own example, `deleteUserLocation(id: ID!, action: SoftDeleteAction!): UserLocation`, returns a nullable `UserLocation`, while the sibling mutation it's meant to parallel, `updateUserLocation(id: ID!, input: UpdateUserLocationInput!): UserLocation!` (`apps/backend/src/schema/user-locations.graphql` line 40), returns non-null. Minor inconsistency in the AD's own worked example versus the established pattern it's citing as precedent. *Fix:* Make the example non-null (`UserLocation!`) to match, or explicitly state why the soft-delete mutation should be nullable when its neighbor isn't.

- **low** The Binds line's domain names (`EventInfo`, `Schedule`, `Post`, `CalendarEntry`, `Subscription`, `ApiKey`, `UserLocation`) don't match the actual Drizzle table export names in `packages/database/schema.ts` (`events`, `schedules`, `posts`, `calendarAdditions`, `subscriptions`, `apiKeys`, `userLocations`). This predates this session's edit for `EventInfo`/`Favorite`/`CalendarEntry`/`Subscription`/`ApiKey` (confirmed via `git diff HEAD` — only `Schedule`, `Post`, and `UserLocation` were newly added, following the same pre-existing PRD-entity-name convention), so it's not a new problem introduced by this extension, but the newly-added names inherit the same drift from actual code identifiers. *Fix:* No action required for this AD specifically; worth a follow-up doc pass mapping PRD entity names to actual table/export names somewhere central, since new BMad-generated docs keep copying the PRD names forward.

- **informational** Confirmed accurate, no issue: `packages/database/schema.ts`'s `userLocations` table (lines 41-53) has no `deletedAt` column, and `apps/backend/src/schema/resolvers.ts`'s `deleteUserLocation` (lines 130-135) performs a genuine `db.delete(userLocations)` hard delete today — actually a more severe gap than "missing a column" (existing user data is irrecoverably destroyed on every delete call), which if anything strengthens the case for this AD rather than undermining it.

- **informational** Confirmed accurate, no issue: `toggleFavorite`/`toggleCalendarAddition` (`apps/backend/src/schema/resolvers.ts` lines 136-190ish) take no `action`/direction argument, infer restore-vs-delete from `existing.deletedAt === null`, and their GraphQL signatures (`favorites-and-calendar.graphql`) return custom `ToggleFavoriteResult`/`ToggleCalendarAdditionResult` types with boolean flags — not the row's own type and not the rule-4 shape. Matches AD-8's description of the "accepted legacy exception" exactly. Also independently corroborated by `design-artifacts/UX-festgrid-run-1/EXPERIENCE.md`'s "Event-list exception" note (line 129), which frames the same toggle behavior as "the precedent this pattern generalizes to... not a divergent case to reconcile."

- **informational** Confirmed accurate, no issue: no `SoftDeleteAction`-shaped (or differently-named DELETE/RESTORE) enum exists anywhere under `apps/backend/src/schema/*.graphql` today. Existing enums are `GeolocationProvider`, `EventType`, `EventCategory` (GraphQL-level) and `userRoleEnum`/`eventTypeEnum`/`eventCategoryEnum`/`geolocationQueryTypeEnum` (Drizzle-level) — none overlap in purpose. Introducing a new `SoftDeleteAction` enum is not duplicating an existing mechanism.

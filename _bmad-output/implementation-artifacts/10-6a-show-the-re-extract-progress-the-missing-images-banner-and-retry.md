# Story 10.6a: Show the Re-extract progress, the missing-images banner and Retry

## Story Details

- Epic: 10 (Background vendor jobs: one engine, one Jobs page)
- Story ID: 10.6a
- Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a moderator,
I want to see what Re-extract is doing, to minimize it and open it again where I left off, and to be told which images were missing,
so that a slow refresh never blocks me and I can retry it.

## Acceptance Criteria

Sources: Story 10.6a in `epics.md` (Epic 10), PRD 3.9.3 (FR125), 3.18 (FR116 to FR130, FR123), and the owner-confirmed UX spec of 2026-11-13 (`ux-designs/ux-festgrid-2026-11-13/`: `EXPERIENCE.md` section "Story 10.6a", `DESIGN.md`, `copy-keys.md` section 3, `graphql-read-shape.md`, `decisions.md`; all 12 design choices confirmed by the product owner on 2026-11-13, above all choice 10 (the banner names the missing images), 11 (one preview dialog, attachable to a job, also from the Jobs page and the Post URL tab) and 12 (a carousel longer than the preview cap gets its own line and no Retry)). Where the spec and this list differ, the spec wins for behaviour and this list wins for what is built.

**Backend: the refresh report and the per-image list (Part A)**

1. **Given** a Re-extract job that has run its refresh phase, **when** a moderator reads `job(id)`, `myJobs` or `activeJobs`, **then** the `Job` type has a new field `refresh: JobRefreshReport` (`graphql-read-shape.md`): `outcome`, `saved`, `lateResultPending`, `retryAfter`, `expiredLinks`, `images: [JobImage!]!` (`position`, `role` COVER or SLIDE, `state` READ, NOT_READ_EXPIRED, NOT_READ_UNAVAILABLE or NOT_SENT_OVER_CAP), `imagesAvailable`, `imagesRead` and `previewImageCap`. It is `null` for every other job type, for a job that has not run its refresh phase, and for any viewer who is not a moderator (re-extract is moderator-only, so an ordinary user never receives it and no query work is done for them).
2. **And** the field carries no caption, no image URL, no vendor name and no preview: the resolver reads `result_data` ONLY through named JSON paths (`{refresh,outcome}`, `{refresh,saved}`, `{refresh,lateResultPending}`, `{refresh,retryAfter}`, `{refresh,expiredLinks}`, `{imagesAvailable}`, `{imagesSent}`, `{imageCap}` and `#> '{images}'`, all through the existing `resultJson` helper), never the column whole; `images` entries are copied field by field (`position`, `role`, `state`) with each value checked against its enum and the array bounded, so a malformed or hostile stored entry (a `url` key, an unknown state) cannot reach the response. The path list is selected only when the client selects `refresh` (`getRequestedFieldNames`), exactly as `steps` is. `jobs-read-no-whole-json.ratchet.test.ts` stays green and is extended to pin the new lines.
3. **And** the engine's phase 2 (the AI-processor preview handler) writes the per-image list into the job's `result_data` beside `imagesAvailable` and `imagesSent`: `images` (one entry per image the post lists after the file-name de-duplication that already defines `imagesAvailable`, cover first, position 0 for the cover and 1 and up for slides in order) and `imageCap` (the slide cap the request used, `MAX_REEXTRACT_CAROUSEL_IMAGES`). Each entry's state is decided where the image is fetched: `READ` when it was inlined into the request, `NOT_SENT_OVER_CAP` for a slide beyond the cap (never fetched), `NOT_READ_EXPIRED` when its fetch or blur failed and its stored link is past its own expiry (`isImageUrlExpired`), `NOT_READ_UNAVAILABLE` for every other failure (a non-OK answer, a non-image content type, a blur that failed closed or had no time). The number of `READ` entries equals `imagesSent` and the number of entries equals `imagesAvailable` (a test asserts both). A job finished before this story has no `images` and reads as an empty list (the web then falls back to counts, Dev Notes decision 2).
4. **And** the pure rules live in `packages/domain/src/posts/` with 100% coverage: the image states and entry type, the failure classifier, the builder of the entry list from per-image outcomes, `summarizeMissingImages(images)` (cover yes or no, slide ranges, the over-cap count) and `pickReextractBannerCauses(refresh)` (the cause keys of `copy-keys.md` section 3, in order). The web and the AI-processor import them; nothing is re-derived in a component. No migration, no new table, no new environment variable and no new Lambda: `jobs.result_data` is jsonb and the cap travels inside the result.

**Web: the Re-extract dialog on the shared progress host (Part B)**

5. **Given** a stored post in the source-post panel (`ModeratorSourcePostsPanel`), **when** the moderator taps Re-extract, **then** the app starts the job through the existing `previewPostReextraction`, attaches to it through `useJobProgress().attach(jobId, { open: true })` and opens the shared progress dialog (stepper "Fetching fresh images" then "Reading the post and finding events", the refresh step shown as skipped when it was not needed). The private spinner line (`ReextractPreview.running`, "Extracting. This can take up to a minute.") is gone. A refused start (queue full, start failed) shows its plain message through `mapJobStartError` in the row, and the button stays.
6. **And** Minimize (the button, Escape and an outside tap) turns that post row's button into the shared chip ("Re-extracting: step 1 of 2" and its ended forms), the job keeps running, and tapping the chip opens the dialog at the last progress (current step and steps done), also after navigating away, reloading or opening another device, because each row finds its job again from the server with `activeJobs(subject: { type: REEXTRACT_REFRESH, postId }, endedWithinMinutes: 30)` on mount and never from browser storage. Closing or minimizing never discards the job: `reset()`-on-close is gone, and the panel's single shared dialog becomes one host per post row.
7. **And** the Re-extract job's detail page (`/jobs/{id}`) shows an **Open the preview** action (the slot Story 10.4 left empty) for an ended Re-extract job that has a preview, for a moderator. It opens the same dialog attached to that job id, at the result, with no new job and no restart. Moderator Tools, Re-extract (the Post URL tab, `reextract-content.tsx`) uses the same host: after Preview it attaches to the new job, the dialog can be minimized to a chip in the tab and re-opened, and the job is not dropped when the dialog closes. A preview that belongs to another moderator's job is not readable (the existing read is owner-scoped) and shows "This preview is not available to you." instead of an error.
8. **And** when the job ended with a result (Succeeded or Succeeded with limits), the dialog body is the preview result with Apply exactly as today (the existing `ReextractPreviewResult`, its confirmation and its once-only rule unchanged), read through the existing `postReextractionPreview(id)` only after the job has ended (the shared `useJob` supplies the steps and status while it runs, so there is one poll, not two). A Failed, Expired or Cancelled job shows the shared red or slate box with the plain reason and Retry where the server says so. The 30-minute Apply window is on the server: closing or minimizing an ended job never loses it, and a preview older than the window opened from Jobs reads "This preview is too old to apply. Start a new one." with a "Re-extract again" button (the existing `EXPIRED` apply refusal).
9. **And** the missing-images banner replaces the old single amber line (same box position, same `data-testid="reextract-images-warning"`): it shows when any image was not read, built from `Job.refresh` and the preview counts, in this order: a title "{read} of {available} images were read"; a line "Not read: the cover and slides 3 to 5." (cover, single slide, ranges, joined with `Intl.ListFormat` for the active locale; only when `images` is present); the cause sentence or sentences chosen by `pickReextractBannerCauses` (expired and refresh failed, still running, cooldown with the time, account type not scraped, post gone, in flight, took too long, no provider, quota, did not heal, or the extra "some images could not be loaded" of Dev Notes decision 5); the line "You can still apply this preview. Events shown only on unread images will be missing."; and Retry. For an old job with no `images` the banner shows the title and the cause only (counts-only fallback). The dialog moves focus to the banner title when the result opens with a shortfall, and the banner is a `role="status"` region.
10. **And** a carousel with more slides than `previewImageCap` shows its own line "Only the first {cap} slides are read in a preview." (`bannerOverCap`) with no Retry on its account and no cause line. When ONLY slides over the cap are missing, the banner is that one line (no "x of y" title, no cause, no Retry). When a failed refresh and the cap occur together, both appear and Retry follows the server's `canRetry`.
11. **And** Retry is the shared Retry: it shows only when the server says `canRetry` (never for "account type is not scraped" or "post is no longer available", never for a job that Succeeded), reads "Retry at {time}" and is `aria-disabled` with that time in its description during the 10-minute cooldown (`retryNotBefore`), starts a new job through `retryJob` (so reuse, admission, cooldown and the moderator-only rule are the server's), moves the dialog back to the progress view of the new job and announces "Started again." (a `REUSED` answer says "This is already running."). A refused Retry shows the shared notice (queue full, generic). `bannerRetryHint` ("Retrying fetches the images again, then reads the post again.") is the button's description.
12. **And** all copy is English and Indonesian in the existing `ReextractPreview` namespace (fixed by the spec and by this story), the keys listed in Dev Notes ("Copy keys"): the `copy-keys.md` section 3 keys plus the three extra keys of decisions 5, 9 and 10; the obsolete `running` and `imagesShortfall` keys are removed with their last use; `locales.test.ts` parity holds. Dates and times use the active locale's formatter, lists `Intl.ListFormat`; no raw enum, ISO string or number is interpolated (project-context, Locale-Sensitive Data Rendering).
13. **And** analytics are only the shared events the controller already sends (`job_progress_minimized`, `job_progress_reopened`, `job_retry_clicked`, with `jobType: REEXTRACT_REFRESH`); the banner and Apply add none, and no payload carries a handle, URL, caption or vendor name.
14. **And** layout and accessibility: the source-post row is `flex flex-wrap` with `min-w-0` (the chip or button wraps under a long title on a 320 px phone); the dialog is the shared bounded, scrolling `minmax(0,1fr)` dialog made wide (`sm:max-w-2xl`) for the result through an additive `size` prop; banner actions wrap; the stepper keeps `aria-current="step"` and state words; the shared announcer covers progress and endings (one polite region per page, a watched failure through the alert region); the banner's missing-image sentence is real text; the spinner is a static dot under `prefers-reduced-motion`; no page is wider than its viewport at 320 to 1440 px and the opened dialog fits and scrolls inside itself.
15. **And** e2e never starts a real re-extract and never calls Retry or Apply: the scenarios run with `E2E_FAKE_AUTH=1` on seeded job rows (Dev Notes, "E2E without a vendor call"), and the one existing scenario that clicks Re-extract (`responsive-popups.spec.ts`, "event detail (moderator): Re-extract dialog") is rewritten to open the dialog from a seeded job's chip.

**Documentation (Part C)**

16. **And** PRD 3.9.3 (FR125) says the banner names which images were not read and gives a longer-than-cap carousel its own line with no Retry; AD-40 Rule 9 and AD-53 Rule 18 get one sentence each about `result_data.images`, `result_data.imageCap` and the moderator-only `Job.refresh`; the Story 10.6a section of `epics.md` points at this file. `docs/infrastructure/architecture-diagram.md` and `high-level-overview.md` are NOT touched (no service, queue, Lambda, table or library is added; CLAUDE.md section 4).

## Dev Notes

### Owner-flagged decisions (conservative option chosen; please confirm or overrule)

1. **No split: one story, two parts.** A backend addition (about six small files) and a web change that reuses Story 10.4's shared host and Story 10.3a's notice. The banner is single-purpose and stays in `apps/web`. If the owner wants two pull requests, cut at the Part A / Part B boundary (a lettered suffix off this story); the API must deploy before the web build.
2. **Per-image data lives in `result_data.images` and `result_data.imageCap`, not inside `result_data.refresh`.** The refresh report is written by phase 1 and the images are a phase 2 fact (which images the extraction could read), so keeping them next to `imagesAvailable` and `imagesSent` avoids rewriting the report. GraphQL still presents them as `Job.refresh.images`, as the owner-confirmed read shape says. The cap is stored with the result so the API Lambda needs no new environment variable and cannot disagree with the Lambda that applied it. Rows from before this story have no `images`: `images` reads `[]`, `imagesAvailable` and `imagesRead` read from the preview counts, and the banner falls back to counts only (the fallback the owner confirmed in choice 10). Confirm or ask for a backfill (none is planned: previews live 30 minutes).
3. **How an unread image is classified.** `NOT_READ_EXPIRED` only when the stored link's own expiry (`isImageUrlExpired`) has passed; every other failure is `NOT_READ_UNAVAILABLE`, including a blur that failed closed or had no time left. Positions are those of the de-duplicated list that already defines `imagesAvailable` (a repeated cover or slide is dropped, BUG-101): position 0 is the cover, slides count from 1 in the de-duplicated order, so "slide 3" can differ from the platform's own slide number on a post whose list had repeats. A post that lists slides but no cover has no position 0 entry.
4. **`Job.refresh` is moderator-only and re-extract-only.** It is `null` for an ordinary user and for every other type, even though the existing preview queries are moderator-only already. The cost is that a demoted moderator sees no banner; the safer default was chosen.
5. **One extra cause sentence.** The spec's cause list has no sentence for a job that Succeeded with no reason but where a slide still failed to load (the refresh was not needed or saved, then one image answered an error). New key `causeImagesUnavailable` ("Some images could not be loaded."), no Retry (the server's `canRetry` is false for a Succeeded job, and `decideJobRetry` is not changed here).
6. **The preview stays on the old read.** The dialog reads the preview through `postReextractionPreview(id)` once the job has ended with a result; the shared `useJob` supplies steps and status. Nothing of the preview (events, `extracted`, caption) is added to `Job`.
7. **One host per source-post row.** Each row asks `activeJobs(subject, endedWithinMinutes: 30)` once on mount (no polling loop for the lookup), so an event with N source posts makes N small calls. The panel only renders for a moderator on the event page. If it proves chatty a later story can add a `postIds` filter.
8. **The Post URL tab attaches on the start result and keys the lookup by the URL typed at submit.** After a reload the field is empty and there is nothing to find it by (no browser storage, by the spec), so the job is reached from the Jobs page. A copy of the URL is never kept.
9. **"Open the preview" from Jobs** shows for a moderator on an ended Re-extract job with a preview. The read is owner-scoped, so another moderator's job answers `NOT_FOUND`: new key `previewNotAvailable` ("This preview is not available to you."). No ownership field is added to `Job`.
10. **Three copy keys beyond `copy-keys.md`:** `causeImagesUnavailable`, `previewNotAvailable` and `startRefused` (the start-refusal line in the row, when `mapJobStartError` has no number to show). English and Indonesian below; fold them into the spec file.
11. **A banner that is only the over-cap line.** When the only unread slides are over the cap, the banner is just "Only the first {cap} slides are read in a preview." (no "x of y" title, no cause, no Retry), as choice 12 says. When a failure and the cap occur together both show.
12. **A stale "refresh still running".** If a Bright Data snapshot outlived the budget (`lateResultPending`), the stored report keeps saying so after the late result healed the post. `causeRefreshRunning` is worded conditionally ("If it finishes later, the fresh images are saved to the post"), so it stays true; the report is not rewritten by the late-result handler (that is Story 10.5's code and untouched).
13. **Shared pieces change additively.** `JobProgressDialog` gains `size`, `JobProgressHost` gains `renderEndedBody`, `dialogSize` and `chipLabels`; a host that passes none behaves as in Story 10.4. Flagged because they are shared with every adoption story (10.7, 10.9 to 10.12a).
14. **The existing popups scenario that clicked Re-extract is replaced.** It started a real job on the local stack; with the engine it would try to invoke a Lambda. It now opens the dialog from a seeded job's chip. Retry and Apply are never clicked in e2e.
15. **Start and Retry use the calls that exist.** Start: `previewPostReextraction` (its result has no "reused" flag; a row that already has a job shows its chip, not the button, so a double start is not offered). Retry: `retryJob`. No new mutation.
16. **Backlog row: none matched.** The BUG-099 row (the preview that read 0 of 1 images) is already promoted with Story 10.6; its note names this story for the screen part but the row is not 10.6a's to close. No row is promoted and no child row carved. (Pre-existing row BUG-261112-d6v, the prod check of `/p/DcntzF0mB7z/`, stays open and post-deploy.)
17. **No new analytics, no new environment variable, no migration.**
18. **Review fix: an image reads "expired" only once its own expiry has passed (owner, please confirm).** `classifyUnreadImage` used `isImageUrlExpired`, which carries the 5-minute safety margin the REFRESH uses (it acts early because the job runs a moment later) and ignored the cover's stored `image_url_expires_at`. Now: the expiry is the link's `oe` parameter, else the stored expiry for the cover (the same fallback `postImagesNeedRefresh` uses), and a link is `NOT_READ_EXPIRED` only when that expiry is at or before now, with NO margin. So a cover with no `oe` and a past stored expiry reads expired (as the refresh logic says), and a link expiring in 3 minutes that failed for another reason reads unavailable (the banner reports what happened, not what the refresh feared). The stored expiry is passed from the preview handler through `generateReextractionPreview` and `extractEventsWithGemini` to a new builder option `coverExpiresAt`; other callers are unchanged.
19. **Accepted limitation: closing an ended dialog drops its chip.** Close, Escape or an outside tap on an ended job drops the chip until a reload (Story 10.4's shared rule). The way back is a reload within the 30-minute `activeJobs` window, or the job's page under Jobs ("Open the preview"). Not changed here.
20. **Accepted limitation: one `activeJobs` query per source-post row.** An event with N source posts makes N small calls on mount, moderator-only (decision 7). A `postIds` filter is a later option if it proves chatty.

### Architecture & UX Gate Findings

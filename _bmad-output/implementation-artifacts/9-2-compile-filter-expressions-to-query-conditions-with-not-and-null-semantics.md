# Story 9.2: Compile filter expressions to query conditions with NOT and null semantics

## Story Details

- Epic: 9
- Story ID: 9.2
- Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a developer,
I want `FilterNode` compiled to the existing query DSL, with `not` supported end to end,
so that Discovery, Feed, Favorites, account pages and Widgets all apply expressions through one path.

## Acceptance Criteria

1. **AC1 — AND/OR map to DSL groups; NOT maps to `ne`/`notIn` where native and to a `not` group otherwise; the SQL translation keeps events with no value for the negated field (NULL ≠ x) (epics.md AC1):** Given a `FilterNode`, when `compileFilterNodeToQueryCondition(node, ctx)` runs, then:
   - an `AND`/`OR` group compiles to a `QueryCondition` `GroupCondition` with `operator: 'and' | 'or'` over its compiled, defined children (an empty/all-undefined result collapses to `undefined`, never an empty group);
   - a `NOT` node compiles by first compiling its child, then inspecting the **compiled child's own shape** (not the leaf's field name): if the compiled form is a single `TerminalCondition` with `operator: 'eq'`, it inverts in place to `operator: 'ne'`; if `operator: 'in'`, it inverts to `operator: 'notIn'`; for every other compiled shape (a `GroupCondition`, or a terminal using `contains`/`overlaps`/`withinRadius`/`notEnded`) it is wrapped in a new DSL group `{ operator: 'not', conditions: [compiledChild] }` — `DSLOperator` (`packages/domain/src/query/queryDsl.ts`) widens to `"and" | "or" | "not"` to carry this;
   - `packages/graphql-select/drizzle-where.ts` translates the new `'not'` group operator as `NOT (<child SQL>)`, and makes the **`ne`/`notIn` terminal operators** null-inclusive at the SQL level (`IS DISTINCT FROM` for scalar `ne`; `col IS NULL OR col NOT IN (...)` for scalar `notIn`; the array-column `notIn` branch gets the equivalent `col IS NULL OR NOT (col && ARRAY[...])` guard) so that, e.g., `NOT venueType=CAFE` keeps events with no `venueType` at all (SPEC.md CAP-6 / `filter-vocabulary.md`'s expression-operators note) — this is the mechanism that actually delivers the null-inclusive guarantee; the `'not'`-group SQL fallback itself is a plain, non-null-aware `NOT (...)` (see Dev Notes decision 3 for why that's correct, not an oversight).

2. **AC2 — A flat filter and its expression form compile to identical conditions (epics.md AC2):** Given every fixture in `buildEventsQueryCondition.test.ts`'s exported `EVENT_FILTER_FIXTURES` (Story 9.1a), when each is (a) passed directly to `buildEventsQueryCondition({ filter, currentDate })` and (b) converted via Story 9.1a's `expressionFromFlatFilter(filter)` and passed to `compileFilterNodeToQueryCondition(expr, { currentDate })`, then the two results are deep-equal for every fixture, for the *same* `currentDate`. This is achieved by extracting one shared set of per-field "leaf builder" functions out of `buildEventsQueryCondition.ts`'s current monolithic `if (filter) {...}` block, called identically by both the legacy flat path and the new compiler — not by two independently-written implementations that happen to agree today.

3. **AC3 — Coordinates plus adminArea in different OR branches are legal; in one leaf they yield a caveat, not an error (epics.md AC3):** Given an `OR` group containing a `locationProximity` leaf and a `locationAdminArea` leaf as separate children, when compiled, then it returns a legal `{ operator: 'or', conditions: [...] }` with no thrown error (each leaf compiles independently through the shared `buildLocationCondition` helper, which only ever receives one of the two location shapes per call when driven by a `FilterLeaf`). The "within one leaf, caveat not error" half of this AC requires no runtime code in this story: Story 9.1a's `FilterLeaf` type already makes `locationProximity` and `locationAdminArea` two separate, mutually-exclusive leaf variants, so a leaf carrying both is not constructible — the existing throw in the shared `buildLocationCondition` helper (preserved from today's `buildEventsQueryCondition` behavior, Dev Notes decision 5 of Story 9.1a) remains reachable only via the legacy flat `EventFilterInput.location` shape, which still allows both fields on one object and must keep throwing for that case (regression-protected by AC2's parity test).

4. **AC4 — `explain-events-queries.ts` covers a wide OR tree and a NOT tree (epics.md AC4):** `apps/backend/src/explain-events-queries.ts` gains two new scenarios built via the new compiler — a 6-branch `OR` tree spanning 6 different locked-vocabulary leaf fields, and a `NOT` tree wrapping a `dateRange` leaf (exercising the `'not'`-group SQL fallback, the EXISTS-based `overlaps` path) — each run through the same `runGetEventsScenario` EXPLAIN-capture helper the script's existing scenarios use, confirming neither new DSL shape introduces an unindexed `Seq Scan` on the main `getEvents` select.

**Depends on:** Story 9.1a, Story 9.1b.

### Compiler design decisions (resolved defaults — minimised per this session's dispatch instruction, not left as open questions)

1. **The `dateRange`+`dayOfWeek` sibling-merge inside `compileAndChildren` is the one deliberate special-case in the whole compiler, and it exists purely to satisfy AC2's parity requirement.** The legacy flat `EventFilterInput` couples `dateRange` and `dayOfWeek` into **one** combined query condition (`dayOfWeek` narrows *within* `dateRange`'s resolved window, or within a 90-day default lookahead if `dateRange` is absent — never two independently-ANDed conditions). Story 9.1a's `expressionFromFlatFilter` converts a flat filter with both fields set into **two separate sibling leaves** under one top-level `AND` (by design — `FilterNode`'s leaf vocabulary keeps them as distinct fields, per Story 9.1a Dev Notes decision 4). Compiling those two leaves *independently* would silently produce a different, wrong condition (two ANDed conditions: one scoped to `dateRange`'s own window, one scoped to the unrelated 90-day lookahead) — breaking AC2 for every one of `EVENT_FILTER_FIXTURES`'s two combined fixtures. The merge is **AND-only, not OR**: a flat filter has no OR equivalent to round-trip against, and "dateRange OR dayOfWeek" (e.g. "this weekend, or any Friday in the next 90 days") is a genuinely different, independently-meaningful condition that a hand-built or Gemini-produced expression tree might legitimately want — collapsing it into the narrowing interpretation would be wrong there. This sibling-detection check runs on the **already-normalized** tree (normalize happens once, at the very top of `compileFilterNodeToQueryCondition`), so an incidentally-nested equivalent shape (`AND(AND(dateRange), dayOfWeek)`) still triggers the merge after flattening — a deliberate, documented consequence of normalizing before compiling, not an accident.
2. **NOT-inversion is driven by the *compiled condition's own shape*, not by a hardcoded per-leaf-field table.** The rule is: a compiled leaf that is a single `TerminalCondition` with `operator: 'eq'` inverts to `'ne'`; `operator: 'in'` inverts to `'notIn'`; anything else (a `GroupCondition`, or a terminal using `contains`/`overlaps`/`withinRadius`/`notEnded`) falls back to the new `'not'` DSL group wrapper. This was chosen over a per-field lookup table (`accountId`/`venueType`/`isFree`/`locationAdminArea` → native; `keyword`/`dateRange`/`dayOfWeek`/`locationProximity`/`temporalFilter` → wrapper) because it is **automatically correct for a leaf whose compiled shape is value-dependent**: `keyword` compiles to a single `{field:'hashtags', operator:'in', ...}` terminal when the text is `#`-prefixed, but to a 3-way `or`-of-`contains` group otherwise — a field-keyed table would have to special-case `keyword` explicitly to get both cases right, while the shape-driven rule gets both correct for free, and stays correct automatically if any other leaf's compiled shape ever changes (e.g. if a future story changes how `locationAdminArea` compiles). Task 6 includes a dedicated test for exactly this `#`-hashtag-keyword case to make this an enforced regression, not just a design note.
3. **The `'not'`-group SQL fallback in `drizzle-where.ts` is a plain `NOT (<child SQL>)`, deliberately *not* made null-aware.** `ai-filter-boolean-nested-query-upgrade-plan.md` §3 decision 1 says exactly this for the time/location leaves this fallback actually serves: "NOT on time/location leaves... Document, don't special-case." Concretely: every leaf that falls into this path (`dateRange`, `dayOfWeek`, `temporalFilter`) compiles to an `EXISTS`-subquery-based `overlaps`/`notEnded` condition against the `schedules` table — and every event has at least one schedule (`events.postId` → extraction always produces ≥1 `Schedule` row), so there is no real "event has no value for this field" case to special-case for dates. `keyword` falls into this path for plain (non-hashtag) text, compiling to an `or`-of-`contains`; every event has an `eventName`, so the same reasoning applies. `locationProximity` is the one leaf in this path where an event genuinely *can* lack coordinates — but SPEC.md's own worked example for null-inclusive NOT (`NOT venueType=CAFE keeps events with no venueType`) is an `eq`/scalar-field case, not a proximity/radius case, and the upgrade plan's decision explicitly groups "time/location" together under "document, don't special-case." The null-inclusive guarantee this story's AC1 actually requires is delivered entirely by the native `ne`/`notIn` inversion path (decision 2's "native" branch) instead — this fallback path's job is only to get the boolean logic structurally right (AND/OR/NOT nesting), not to add new three-valued-logic handling for compound subqueries.
4. **The `matchCondition`-descriptor branch of `drizzle-where.ts` (used today only by `socialMediaAccountProfileId`, Story 3.6v/AD-31 Rule 4) is left untouched.** Its existing `ne`/`notIn` cases already compute `NOT ${matchCondition([value])}` (an `EXISTS`-based boolean join check) — and `EXISTS`/`NOT EXISTS` in SQL is never `NULL`, it is always a crisp `true`/`false`. There is no "no value for the field" case to make null-inclusive here (every event has exactly one `sourceSocialMediaAccountId`/account-match path), unlike the scalar/JSON-extracted-text columns (`venueType`, `locationAdminArea`'s `adminArea`, `isFree`'s computed `ILIKE` expression) the scalar branch's `ne`/`notIn` changes actually target.
5. **`compileFilterNodeToQueryCondition` normalizes its input exactly once, at the top, rather than requiring the caller to pre-normalize.** `normalize()` (Story 9.1a) is already bottom-up and idempotent, so one top-level call is sufficient and cheap; this is a defensive default (the compiler stays correct even if a future caller — Story 9.3's resolver, Story 9.4's Gemini transform — forgets to normalize first) and does not affect AC2 parity, since `expressionFromFlatFilter`'s output for every `EVENT_FILTER_FIXTURES` case is already flat (no nested same-operator groups, no duplicate leaves) — normalizing it is a no-op.
6. **Groups are never collapsed to a bare child, even when they end up with exactly one compiled condition.** This mirrors the legacy flat path precisely: `buildEventsQueryCondition` always returns `{ operator: 'and', conditions }` regardless of `conditions.length` (never unwraps a single-element array to the bare condition). A compiler that *did* collapse single-child groups would produce a structurally different (and therefore non-deep-equal) result from the flat path for every single-populated-field fixture in `EVENT_FILTER_FIXTURES` — this is the single most important invariant for AC2's parity test to hold, and is called out explicitly in Task 3 rather than left implicit.

## Critical

### R4A-1 Option B has no carrier: Rules 4, 13 and 16 disagree on whether an unconfirmed series collapses, and "identical core" is a pairwise, non-transitive relation that no group-level column can hold

- **Spine:** 2536-2543 (Rule 4), 2677-2686 (Option B), 2825-2866 (Rule 13), 2964 and 2969 (detector table, `[OPEN: carrier for a mixed group]`), 2664-2672 (series definition).
- **Unit A (Discovery, Rule 13 as written):** partitions by `coalesce(g.id, e.id)` for active series. Rule 13 never mentions `confirmed_at`. Rule 4 says an unconfirmed group's "only effect is the 'part of' link on the event page **and the Rule 13 Discovery policy**". So every series member collapses, link-only joins included.
- **Unit B (group writer, Rule 16 table):** sets `confirmed_at` for identical-core pairs and leaves it null for 0.85 to 0.99 and tag joins, and reads `confirmed_at` as the collapse gate, because that is what Option B says.
- **Result, on real rows:**
  1. A0137 posts "Sports Station & Planet Sports Buy 1 Get 1 Promo" (a two-brand promo). It scores 0.864 against the five-event Sports Station BOGO family: link-only by Option B. Unit A collapses it behind whichever Sports Station store is nearest the user, so a Planet Sports shopper never sees it in Discovery. Unit B has only a group-level flag: if the group was created by an identical-core pair the flag is set and the event collapses too; if the group happened to be created by a 0.88 pair the flag is null and the five identical-core events stop collapsing. Neither unit can say "this member links, that member collapses".
  2. The relation is not a property of a group, nor transitive. International Coffee Day Promo at Dum Dum Thai Drinks: A0137 (place text is the mall, so "dum dum thai drinks" stays in its core) against A0138 = 1.000; A0138 against A0140 (Sleman City Hall) = 1.000; A0137 against A0140 = 0.449. Whether the three collapse depends on a closure rule nobody wrote and on arrival order (A0137 and A0140 first: separate; A0138 last: it bridges).
  3. `confirmed_at` now has two meanings: Rule 4's "lift the inheritance bound" and Option B's "collapse". A moderator "confirm" (Rule 5 amendment) would switch collapse on for every link-only member. And three detectors set `confirmed_at` at creation (series_stem, place_split, identical-core series_phrase), so Rule 9's audience-area inheritance, once built, would apply to series whose members are at different places by definition: the area of which member?
- **Fix:**
  1. Put the decision on the member: `events.group_collapse_key text null`, written only by `group-membership.ts`, non-null only when the member joined by identical core; its value is the per-event canonical core `deriveStem(name, ownPlace)` (own trailing place removed, no dependence on the other member). Rule 13 partitions active series by `coalesce(g.id::text || ':' || e.group_collapse_key, e.id::text)`; a null key means chip only. Equal keys collapse; there is no closure beyond equality, which gives the Dum Dum triple a deterministic answer (A0138 and A0140 collapse, A0137 does not) and states that limit.
  2. Amend Rule 4: the Discovery policy is per member by collapse key; `confirmed_at` keeps one meaning (inheritance and moderator confirm). Detector table: the `series_phrase` cell becomes "null; collapse is the key".
  3. Note for the author: identical-core scores are exactly 1.00 under any positive weights, so this tier is immune to the IDF drift of R4A-4; only the link tier needs a stored basis.

## High

### R4A-2 Cross-account attach is not serialised: the Rule 16 formula takes no lock when the organizer is NULL, Rule 12 and Rule 16 name different lock keys, and the nightly check cannot see these groups

- **Spine:** 2794-2795 (Rule 12: "the advisory lock is taken on the organizer alone, since a fuzzy key has no canonical string"), 2944-2952 (Rule 16: `hashtextextended(organizer || '|' || stem, 0)`), 3008 (OPEN: "the attach serialisation key when no organizer is shared"), 2481 (`organizer_account_id` nullable).
- **Unit A follows Rule 16, Unit B follows Rule 12.** For a cross-account series the group's `organizer_account_id` is NULL. `NULL::uuid || '|' || stem` is NULL; `hashtextextended` and `pg_advisory_xact_lock` are both STRICT (verified on PostgreSQL 16.15: `proisstrict = t` for both). The call returns NULL, raises nothing and holds nothing (`pg_locks` shows 0 advisory locks). Read per member instead (each mall account as "the organizer"), two accounts take two different locks, so nothing is serialised either.
- **Failure:** three mall accounts M1, M2, M3 post "Wacoal 25% Off Promo". E1 is committed. T2 and T3 run together at READ COMMITTED: each reads "no open series", each creates a group containing E1 (G2 = {E1, E2}, G3 = {E1, E3}); `UPDATE events SET group_id` has no `WHERE group_id IS NULL`, so the last writer wins. Result: G2 keeps one member (dormant), G3 = {E1, E3}, E2 shows its own cover. The nightly check looks for two active groups with one `(organizer, stem)` key: here the key is `(NULL, stem)` and the stem is "the normalized core", which depends on which pair created the group (line 2794), so the check mostly does not fire. The smaller variant (two first posts both see nothing and commit ungrouped) is never repaired: attach re-runs only on `becameOrganizerAuthored` (2807).
- **Likelihood, honestly:** low in production today. Prod drains the ingestion queue in one Lambda that awaits one message at a time on a 5-minute EventBridge tick (`apps/backend/src/lib/aws/poll-and-drain-queue.ts:85-103`, `apps/backend/src/lambdas/ingestor.ts:19`), and `processIngestionJob` is one `db.transaction` per message (`process-ingestion-job.ts:14`). It becomes real when the consumer scales out (dev and staging already use an SQS event-source mapping, `apps/infrastructure/lib/festgrid-backend-stack.ts:587-592`; async EventBridge retries can overlap a tick), when the IDEA-084 backlog job or `becameOrganizerAuthored` re-attach runs beside live ingestion, and when a moderator confirms, dissolves or merges groups from the API Lambda. The defect in the text is certain either way.
- **Fix:** the key must never be NULL and must not depend on a pair-dependent stem: `pg_advisory_xact_lock(hashtextextended(concat_ws('|', 'series', detector, country_key, coalesce(organizer::text, '*')), 0))`. For cross-account that is one lock per country (tens of attaches a day, held to commit). Add a test that the key is non-null for every input. After taking the lock, re-read the candidate groups; write membership as `UPDATE ... WHERE id = $e AND group_id IS NULL` and treat zero rows as "lost the race, re-run attach". Delete the contradicting sentence in Rule 12 or the formula in Rule 16. See R4A-12 for the nightly check.

### R4A-3 The same-country scope is not an invariant: `eventCountry()` answers `id` for foreign events that do not name their country, reads text that is the account default's or the geocoder's address, is computed in two places, and is enforced by nothing

- **Spine:** 2701-2720 (scope), 2860-2862 (read-time partition), 2705-2709 (`eventCountry()` tiers), 3399-3401 (AD-39: the account default's address is copied into `events.location`), 3008, 2981-2985 (Rule 16 "Enforced by": no country test), project-context (no mention).
- **Q5 answered with data (1,467 events; 56 place texts name a non-Indonesian country):**
  - 40 are the bare words "Denmark" (27) or "Egypt" (13): the text tier resolves them, so the BWF rounds do separate. This also settles AD-14's `[ASSUMPTION]` (452-455) for the export: the event text does name the country.
  - AKMU Asia Tour 2027 (9 dates). Seven of the eight foreign place texts name no country ("Taipei Music Center", "Macpherson Stadium", "The Star Theatre", "Phenix Grand Ballroom", "Gorilla Hall Osaka", "Toyosu Pit", "Zepp Kuala Lumpur"; only "...Resort Macau" does). Tiers: `area_keys` unknown (gazetteer is Indonesia-only), pin untrusted by AD-14 (e) because the expected country falls to the default, text names none, tier 4 `GEOAPIFY_DEFAULT_COUNTRY` = `id`. Those seven foreign dates resolve to `id`, the same as Jakarta, and their cores are identical ("akmu asia tour 2027"). The spine's stated consequence (2717-2718, "AKMU ... would not form one group") is false under the literal function. (They are curator stubs today and ineligible, see R4A-14; the shape applies to any tour or branch posted by an organizer-typed account.)
  - 13 are the address of a wrong answer or of the account default, not the poster's words: "Concert Hall, شارع فوزي قاوقجي, Tripoli 1300, Lebanon" on 4 events of account A0122 (three "21st Korean Day" children and one "EleCation Fest" event; the account's other 10 events have Indonesian places), "Menara, Allahabad, India" (2), "Fest, 62-052 Komorniki, Poland" (1), "Online, Croix d'Argent, Montpellier, Hérault, France" (1, the author's own "Online answered in France" case), "Denmark, IA, United States of America" (5, BWF's Denmark Open). `transformGeminiResponseToEventInfo` copies `defaultLocation.formattedAddress` into the event's location when the post names none (`packages/domain/src/events/transform-gemini-response-to-event-info.ts:34-36`). Tier 3 ("the country named in its location text") assigns these `lb`, `in`, `pl`, `fr`, `us`. That is the account-default leak AD-14 (e) forbids ("the account's default country is never the expected country"), re-entering through the text. So these 4 events of an Indonesian account get `lb`: a later child of the same programme with an Indonesian place text would be refused at attach, and an Indonesian series of the same account would refuse them.
- **Two implementations:** Unit A (attach, TypeScript `eventCountry()` with the default fallback) and Unit B (Discovery SQL, "the member's country key", 2861) disagree for every event with `area_status = unknown`: attach says `id`, the SQL column is NULL, and `PARTITION BY ..., country_key` puts NULL-country members in their own partition: two covers for one group. Legacy rows are NULL until the AD-39 derive job runs. Also undefined: how the country key is read out of `area_keys text[]` (position? level?).
- **Not an invariant:** membership is stored, country is computed. A floor or gazetteer change re-derives `pin_trust` (470-474), or the env default changes, and an attached member's country flips. Only the Discovery window applies the scope; the group page (Rule 15), `member_count`, `place_count`, Rule 14 notifications and Rule 4 inheritance do not. A group has no country of its own, so place-split siblings (j=0 Indonesia, j=1 Malaysia) decide it by commit order; a moderator who groups across countries by hand gets no defined result (Rule 12 says "every group attach ... moderator").
- **Fix:** store `events.country_key` (written by the one area writer; tiers: stated-text country, trusted-pin country, area key, default; never text whose `location_source` is `account_default`) and `event_groups.country_key` fixed at creation (a place split uses sibling j=0's). Attach refuses a differing key; Rule 13 partitions on the stored column only; a CI and nightly consistency query "group with members of 2 or more country keys"; a country change re-runs attach and detaches. See R4A-9 for the better source of the country.

### R4A-4 Group membership is not a function of the data: arrival order, chains, bridging, corpus drift, re-attach and non-sticky dissolve are all unspecified (Q1)

- **Spine:** 2754-2764 (weighted score, join "against any active member"), 2809-2817 (rolling), 2544-2552 and 2587-2592 (Rules 5 and 7), 2950-2956 and 2971-2973 (Rule 16 dissolve), 2807 (re-attach).
- **Which corpus, what is stored, is attach deterministic?** The corpus is "all live event names" at the moment of the call: global (not per country), past events included. Stored: `name` and `stem` only; no score, no join basis, no weights version. So attach is a function of (arrival order, the corpus now, the groups now). It is deterministic only for a frozen corpus, and `becameOrganizerAuthored` or the backlog run re-evaluates under different weights without saying whether a failing re-score detaches.
- **Measured, in-sample, at honest scale:**
  - Drift: replaying the 583 candidate pairs (310 at or above 0.85) with IDF from a random 25%, 50% or 75% of the corpus moves 0 or 1 pair across the bar. With "corpus = events dated up to the later member" (an arrival proxy): 2 lost, 1 gained ("Bangun Pagi Bahagia - Tegal/Kudus" against "- Yogyakarta" 0.88 to 0.84; "AKMU ... Taipei" against "... Jakarta" 0.83 to 0.85). About 0.5%, but it is exactly the pairs at the bar, and nothing records why a member is in. Growth of the brand's own document frequency lowers variant scores monotonically (S: "Wacoal 25% Off Promo" against "Wacoal Anniversary 25% Off Promo", 0.739 to 0.710 after 60 more Wacoal events): a growing series gets harder to join.
  - Order: the greedy rule over 300 random arrival orders leaves a member out of the six-event Sports Station cluster in 15 orders, and out of the seven-event Erafone cluster in 131 (inflated by the place stand-in). Cause: only the new member is evaluated, so an existing ungrouped event that scores 0.85 or more against a later joiner is never pulled in.
  - Chains: S "Sports Station Buy One Get One Free Promo" plus Weekend, Special, Edition, Halloween: adjacent pairs 0.878, 0.938, 0.912, 0.938 (all join), head against tail 0.701. Real: the Dum Dum triple of R4A-1 has an unrelated pair at 0.449. No real bridge exists in the data (the two-brand event scores 0.864 to Sports Station and 0.60 to Planet Sports), but the rule gives no answer when a member qualifies for two groups, and no way to join them except the moderator "merge groups", which needs a shared key that cross-account groups lack.
- **Sticky:** nothing remembers a moderator's decision. After a dissolve (members' `group_id` null) the next arrival that scores 0.85 or more against any freed member creates a new group around them; after a "detach a wrongly-suggested child" (Rule 4) the event is re-attached by the next `becameOrganizerAuthored` or backlog pass. `undoEventMerge` and dissolve-undo "restore only into an active group" (2592, 2972), which fails once the freed members have joined a successor.
- **Fix:** store per member `join_basis` (identical_core, score, tag, place_split, moderator), `join_score` and `weights_version`. Re-attach is add-only: it never moves or removes a member. IDF comes from a pinned snapshot refreshed on a schedule, with its version stored (the collapse tier does not use weights, R4A-1). When a new member qualifies for several groups it takes the best score and raises a bridge item; one pass also pulls in existing ungrouped events that score at or above the bar against it. Add `event_group_exclusions(event_id, group_key)` written by detach and dissolve, read by every detector, cleared only by a moderator; undo checks that the members are still ungrouped.

### R4A-5 Detector pool and precedence: `series_phrase` is missing from the precedence line, the candidate pool across detectors is undefined, and place-split groups are per post, not rolled

- **Spine:** 2953-2956 (precedence), 2959-2967 (detector table), 2479-2487 (Rule 1 enum list), 2734-2735 (identity key), 2947-2949 (place-split id).
- **Precedence omits the new detector.** `moderator > place_split > series_stem / title_pattern > keyword_organizer > extraction_field`. Unit A ranks `series_phrase` with `series_stem`, Unit B below `keyword_organizer`. SCH child "Zumba Anniversary" (Tier 2 programme, `confirmed_at` null) is later matched by a same-name event from another account: Unit A moves it into a series and collapses it (contradicting the user-directed "each SCH event promoted individually"), Unit B leaves it. Equal rank (two series detectors racing) is also undefined.
- **Pool.** "Joins an open series" does not say whether `series_phrase` looks at groups whose source is `series_stem`, `place_split` or a `title_pattern` series. The same Wacoal campaign posted by the brand (organizer = brand: same-account path) and by each mall (cross-account) becomes one group or two depending on the unit.
- **Place-split groups never roll.** The id is a UUID v5 of `(source post id, source ordinal k)`, so every post makes its own group; the rule never says the group carries `organizer_account_id` and `stem`. Riot Jogja's weekly "Wednesday Night Run" at three venues yields one group per week, and next week's single-place post (no split) finds no `(organizer, stem)` group and opens a `series_stem` group; `place_split` outranks `series_stem`, so nothing merges them. Result: a card per week where the series cap intends one.
- **Enum.** `series_phrase` is not in the Rule 1 amendment ("gains `place_split` and `series_stem`", 2485); a migration written from Rule 1 rejects the detector's insert.
- **Fix:** put `series_phrase` in the precedence line below `title_pattern` programmes and `keyword_organizer` (a programme member is never pulled into a series), state the pool (all open series regardless of source) and the equal-rank rule (earlier `created_at` wins), make the place split write `organizer_account_id` and `stem` and join the open series of that key instead of deriving a per-post id for it, and add `series_phrase` to Rule 1.

### R4A-6 Rule 14 with cross-account series: N pushes per promo for one user, an ambiguous "after the claim", no stored recipient, and "linked" where "primary" is meant (Q4)

- **Spine:** 2884-2917; code `process-ingestion-job.ts:138-157`, `notifications/get-subscribers-for-notification.ts`.
- **(a) One user, several malls.** One notification per `(group, source post)` is one per mall post. A user subscribed to three malls gets three pushes with the same title for a promo Discovery shows as one card. The stated reason ("a burst of N pushes for one poster") is per poster. The recipient query is by source account with no per-user history, and no sent-log table exists, so nothing can dedupe. **Needs a decision from the owner**: intended, or suppress per `(user, group)`.
- **(b) "A sibling that lands after the claim has `notified_at` set at attach and sends nothing" (2912).** In context "sibling" is a member of the same post. A cross-account member from another post also lands after an earlier claim (the first mall's event was notified inline as an ungrouped event). Read per group, mall B's subscribers never hear of the promo; read per `(group, post)`, they do. The first mall's event itself is fine: ungrouped at ingestion, so it notifies at once as today.
- **(c) Recipient account is not stored.** Ingestion notifies the subscribers of `message.sourceSocialMediaAccountId`, the scraped profile's platform id. At drain time there is no message: `notifyDueGroups()` must derive it from `posts.accountId`, the `SCRAPING_SOURCE` association or the publisher, which differ for collaboration posts (AD-31 Rule 2). Two units choose differently.
- **(d) `id IN (events linked to $post)` (2905).** Via `event_posts` this includes members for which `$post` is not primary (a roundup linking several members with other primaries). The first `(group, post)` iteration claims them and sends to the wrong account's subscribers; their own account hears nothing.
- **Fix:** write the per-user rule or accept N and say so; define the claim as "events whose primary post is `$post`"; persist `events.notify_source_account_id` at `notify_due_at` time; change "lands after the claim" to "lands after the claim of its own `(group, post)`".

### R4A-7 AD-30 Rule 7: the exact-repeat merge ignores a moderator's rejection and has no undo memory, and the two new candidate states collide with the unordered-pair unique index (Q7)

- **Spine:** 1923 (unordered-pair unique index), 1930-1956 (stub signal, exact repeats, insert bound), 1871-1872 (undo returns the suggestion to pending), 3258 (`superseded`), 3326-3337 (Rule 6 exclusions); `packages/database/schema.ts:524` (enum has `pending`, `accepted`, `rejected`).
- **Rejected pairs are re-merged.** An exact repeat is four predicates (same poster, same name, `isSamePlace = same`, overlapping dates; 1947-1951) and the sweep "merges it as `system-dedup` instead of queuing it". It never touches `event_match_candidates`, so the unique index that "stops a re-run re-queueing a pair a moderator rejected" (1923) does not apply. A pair a moderator rejected as two sessions is merged on the next sweep.
- **Undo does not stick.** A moderator undoes a `system-dedup` merge. `undoEventMerge` "returns the suggestion to pending", but no suggestion row exists (the merge never queued one), and nothing records "not duplicates". The next sweep merges again. The write path queues the same pair as `mid` forever in the unworked queue, so a repeat arriving tomorrow is queued and one that existed yesterday is merged.
- **"Overlapping schedule dates".** Range overlap or a shared date? In the export, 304 same-account, same-name, same-place pairs; 244 overlap by range, among them "Kelas Belajar Bahasa Jepang Arcadia" 2026-08-01 to 12-01 against 12-01 to 12-01 (one endpoint day) and "SWARANUSA 2026" 09-23 to 11-02 against 10-08 to 11-02. AD-38 Rule 6's key says "a date within 2 days" (3327); the 2026-10-18 amendment admits plus or minus 90 days (1883). Three definitions of "same date".
- **Exclusion (a) is not a precondition.** AD-38 Rule 6 (a) (both items of one post under different ordinals) is called a "candidate-generation exclusion" (3333). The exact-repeat rule is not said to pass through candidate generation, yet two items of one roundup with the same poster, name and place are exactly what the extractor declared distinct.
- **Index versus states.** `superseded` (AD-38 Rule 4: "closed as superseded and re-evaluated") and "expires" (1956) are two states the enum does not have. A status-agnostic unordered-pair unique index makes the re-evaluated pair (the original keeps its id after a split) hit `ON CONFLICT DO NOTHING` on its own superseded row, and an expired pair whose event later gains an open schedule is blocked the same way.
- **Insert bound.** Pending candidates leave the count on day 8, so a weekly re-run adds up to 50 more each week into a queue nobody works. Harmless for the one-time sweep; say it is one-time.
- **Fix:** exact repeat requires no `rejected` row for the pair and Rule 6 (a) and (b); the merge writes a `rejected`-on-undo marker (an `event_match_candidates` row with status `rejected` created by `undoEventMerge` when none exists); define "overlapping" as a shared schedule date; declare `superseded` and `expired` in the enum and make the unique index partial on `status IN ('pending','accepted','rejected')`.

### R4A-8 Hashtag evidence cannot be implemented from the text, and its guard does not separate the cases it was written for (Q6)

- **Spine:** 2765-2783.
- **Undefined terms.** "A mall or city tag" has no list and no function (unlike `isSamePlace`). "Spells words that are themselves rare in event names" needs a word segmenter for strings without spaces, and a threshold; neither is given. "Rare" is an absolute count (12) at evaluation time.
- **"Rare" filters almost nothing.** 1,992 of 2,025 distinct tags (98.4%) are on 12 events or fewer; the 33 excluded are the author's list. Variants of mall and venue tags stay rare: `#plazaambarrukmomalljogja` 11, `#galeriamall` 6, `#atriumgale` 7, `#malljogja` 6, `#jogjabay` 8, `#gikugm` 12, `#jogja24jam` 11 (83 of the 268 tags used on 3 to 12 events look like place or city tags). A small account's own tag counts as rare until its 13th event: 151 tags are carried by exactly one account on 3 to 12 events (`#kelasdaurah`, `#kegiatan`, `#oktober`, `#2026` for A0098).
- **The guard does not separate.** Hand-segmenting the tags the author names and taking the idf of their words over event names (`repro-output.txt`): `#iphone18pro` mean 5.46 (good), `#buymoresavemore` 5.06 (**generic**, a mall-wide campaign across DONINI, Skechers and Adidas), `#baycultureshow` 4.76, `#sportsstation` 4.50, `#internationalcoffeeday` 4.13 (good), `#buy1get1` 3.78 (generic), `#veteranfestival2026` 3.67 (good). No threshold on the mean admits all five good tags and rejects both generic ones; on the maximum word frequency in event names (7, 17, 25, 41 and 294 for the five good tags against 36 and 36 for the two generic ones) none does either: 41 and 294 sit above 36. The spine justifies the guard with `#sportsstation` against `#buy1get1` and does not say that the second generic tag it measured scores higher than `#sportsstation`.
- **"Only event of its post" (2783).** Siblings are separate messages, so the first sees a count of 1, and two siblings processed together both do. The value that exists at ingestion is `posts.extracted_event_count` (the pre-split count, AD-30 Rule 1). In the data I found no pair that the first-sibling hole admits: of 42 tag-sharing pairs in the 0.70 to 0.85 zone, 26 look like same-post siblings with identical tag sets (for example ESAI, MHQ, MSQ, MTQ of "Milad PAI Ke-64", 0.745 to 0.754 sharing `#miladpai2026`; a programme), excluded only because later siblings see a count of 2. So this is a hole in the text, not a measured defect.
- **When are tags read?** They are the primary post's: promotion changes them, an edited caption or re-scrape changes them. The text does not say whether they are read once at attach.
- **Fix:** keep the tag rule behind its own detector switch, default off, until `isEvidenceTag()` exists as one function with the seven tags above as its fixture and "admits `#buymoresavemore`" as a failing test; use `extracted_event_count`; read tags once at attach and store them in `join_basis`. Do not ship a word-rarity threshold that the table above refutes.

### R4A-9 AD-14 Rule 4 (e): a country-name list reads the geocoder's and the account default's own words, and mishandles collisions (Q8)

### R4A-11 Lock order across the advisory lock, the group row, event rows and the post row is unspecified; attach can join a dissolved group

- **Spine:** 2937-2939 (`FOR UPDATE` on the group row for `member_count`), 2944-2952, AD-30 Rule 9 amendment (lock on the candidate event), 3222-3228 (post row, original event).

Dissolve: group row, then members. "Merge groups": two group rows, order unspecified. Any two of these can deadlock; Postgres aborts one: ingestion retries, a moderator merge returns an error. ### R4A-12 The nightly "two active series groups with one key" check fires on every series roll and cannot see cross-account groups (Q2)

- **Spine:** 2950-2952, 2809-2817, 2544-2552.

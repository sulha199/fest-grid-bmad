# Reviewer Gate: adversarial two-units lens

Spine: `_bmad-output/planning-artifacts/festgrid-architecture-spine.md`, amended 2026-10-19 (AD-14 Rules 3a/4/5; AD-30 Rules 5/7/10 amendments; AD-36 Rules 1/3/4/6/7/9/10/11 amended and 12-15 new; AD-37; AD-38; AD-39).
Reviewed 2026-10-20. Review only; no spine, code or test file was modified.

**Verdict: the amended spine is not yet a spine for the group, split and place work: two teams can each follow every rule to the letter and ship incompatible group creation, sibling ordinals, organizer identity, place-state writes and Discovery collapse, because the new ADs name the mechanisms (group, place_key, pin_trust, area_status, notification claim) but leave their single owner, key space, writer set and precedence undefined.**

Count: 4 Critical, 10 High, 6 Medium, 2 Low (22 pairs).

How to read a finding: **Unit A** and **Unit B** are two units one level down (stories or modules) that each follow the cited rules literally. "Result" is the concrete incompatibility. "Fix" is the shortest new or tightened wording. Code references are to the repo as read on 2026-10-20.

## Critical

### ADV-1 Five creators fill one `events.group_id` slot, with no precedence, no uniqueness and no single writer

- **Unit A (ingestion, "group attach" step):** after the matcher, runs the series stem rule for each event (AD-36 Rule 3 amended, Rule 12) and, on a miss, Tier 1. Finds the open series for `(organizer_account_id, stem)`; if none, inserts an `event_groups` row.
- **Unit B (place normalizer + splitter, AD-38 Rules 2-4):** a place split "yields sibling events ... the group kind `series`", with the group created "with `source = place_split`" (Rule 4). The backfill and the moderator "split event" create the same group again.
- **Also in play:** Tier 2 seeded-anchor attach (AD-36 Rule 3 amended) and moderator create/edit (Rule 4), plus `mergeEvents` inheriting a group (Rule 7).
- **Result:**
  1. Ingestion is one SQS message and one transaction per event (`process-ingestion-job.ts:15`). Siblings of one post run in separate transactions. Two siblings both find "no open series" and both insert a group. Nothing prevents it: Rule 12 gives an identity key but no unique index, and a unique index on `(organizer_account_id, stem)` is impossible because the series rolls (several groups of one key over the years). So the same real series gets two groups, two Discovery caps, and two notifications (Rule 14 claims per group).
  2. The same three events can be claimed by `place_split` (kind series), by Tier 1 title pattern ("Wednesday Night Run - Kenes Soho" and "... - Fortuna Suites" is exactly an "Umbrella - Child" title with 2+ children; kind defaults to `programme`), and by the stem rule (kind series). `events.group_id` and `group_source_enum` hold one value, so the winner is whichever unit ran first. The kind, and with it the Discovery policy, flips by timing.
  3. Rule 1 (amended) says `member_count` is "maintained on membership change" and Rule 7 says a merge repoints `anchor_event_id`, but no rule names who writes `events.group_id`, `member_count` or `anchor_event_id`. Writers that exist or will: ingestion attach, splitter, `mergeEvents`, `undoEventMerge`, `undoEventSplit`, moderator detach/dissolve, and the existing soft-delete paths (`restoreEvent`, moderator delete, `shouldSoftDeleteFromCancelledReports`) that never call any group code. The counter drifts the first time any of them runs.
- **Fix:** add to AD-36 a new Rule 16, mirroring AD-30 Rule 2: "One module (`setEventGroup`/`recomputeGroup`) owns every write to `events.group_id`, `event_groups.anchor_event_id` and `event_groups.member_count`; `member_count` is recomputed from `events` in the same transaction, never incremented; a source-scan ratchet fails any other writer." Add: "Group find-or-create is serialised by a transaction advisory lock on `hashtext(kind || organizer_account_id || stem)` (series) or `(name, window)` (programme), and a partial unique index on the open series key." Add a creator precedence: `moderator > place_split > stem rule/Tier 1 > Tier 2`; an event already holding a group is never re-grouped by a lower creator; `source` records the winner. The place split passes its group in the message (a `groupKey` carried by every sibling) so the siblings of one post never race each other.

### ADV-2 The stem rule and Tier 1 are one pattern, but kind (series hard cap vs programme soft cap) is decided by which creator ran, and the stem is the umbrella, not the activity

- **Unit A (stem rule, AD-36 Rule 12):** same account, same stem before the first spaced dash, "a group made by ... the series stem rule is a `series`". Applied to SCH "8th Anniversary - Circus", "8th Anniversary - Line Dance", "8th Anniversary - Zumba": stem `8th anniversary`, kind series.
- **Unit B (Tier 1 + `program-lineup`, AD-36 Rule 3/6, AD-38 Rule 2):** the same titles are a programme (different activities under one umbrella). Rule 12 says a Tier 1 group of unclear kind defaults to programme.
- **Result:** Rule 12 defines series as "same activity" and programme as "different activities", but derives kind from the *creator*, and both creators key on the same string. The stem is whatever precedes the first spaced dash, which for "Umbrella - Child" is the umbrella (the programme), and for "Activity - Venue" is the activity (the series). A title cannot tell them apart. With kind = series the Rule 13 hard cap `k = 1` collapses Circus, Line Dance and Zumba behind one card in Discovery: exactly the event-hiding outcome the "unknown kind defaults to programme" rule was written to prevent, and it runs with no human in the loop (Rule 4 is notify-don't-block). A name that already contains a spaced dash ("Riot Jogja - Wednesday Night Run" + " - Kenes Soho") cuts to `riot jogja` and merges every Riot Jogja event into one series, while the place split (Unit B of ADV-1) keyed the same event on the full name. The next month's post computes a different key, so the series forks.
- **Fix:** replace "kind is derived from the creator" with a membership test in Rule 12: "kind = series iff every member's post-dash suffix resolves (same `isSamePlace` function, ADV-11) to that member's own place, or the members share a normalized activity name; otherwise programme. The stem is the longest common prefix of the members' normalized names, not the text before the first dash." Series may only be created from the place split (which knows the activity) or from members that pass this test; the bare stem rule never produces a hard-cap group.

### ADV-3 Three ordinal assigners for one `(post, extraction_ordinal)` slot space

- **Unit A (place normalizer, AD-38 Rule 3):** "the first place keeps the extracted event's index; each further place takes the next free ordinal after the post's last extracted index, in extracted-event order then earliest-date order."
- **Unit B (backfill splitter, AD-38 Rules 4-5):** splits existing events; "next free ordinal" can only be `max(event_posts.extraction_ordinal for the post) + 1` from the database (the extractor output is gone), and it copies the original's `event_posts` rows for every linked post, each needing a fresh ordinal in that post's own space.
- **Unit C (existing `assignExtractionOrdinals`, `assign-extraction-ordinals.ts:25-43`, AD-30 Rule 5/Story 3.6t):** renumbers the whole post densely `0..N-1` by earliest date, then normalized name, never by model order. `process-ai-job.ts:513` runs it after the per-event loop.
- **Result:** if the normalizer runs before Unit C, Unit C renumbers the siblings by date/name and Rule 3's "keeps the extracted event's index" never holds; if after, "extracted-event order" is undefined (model order is unstable; sorted order is Unit C's). The backfill assigns extras in whatever order it processes events (by id, by date); the live normalizer assigns them event by event. When live and backfill disagree, slot `(P, n)` holds event X's place B in the database while a re-run of the extractor expects it to hold event Y's place B. The idempotency lookup (`process-ingestion-job.ts:24-33`) hits and **skips**, so Y's place B is never created (or is created at a different slot as a duplicate). Both siblings link the same post, so matcher exclusion (a) (`match-event-to-existing.ts:122-125`) forbids ever matching them: the duplicate is undetectable by design. The post-split cap ("three times the extraction cap") also has no drop order, so a re-extraction truncates a different set.
- **Fix:** AD-38 Rule 3: "Ordinals are a pure function of the extracted event's final ordinal `k` (the output of `assignExtractionOrdinals`, run **before** the normalizer) and the place rank `j` (places of that event sorted by earliest schedule date then `place_key`): ordinal = `k` for `j = 0`, else `k + j * STRIDE`, `STRIDE = maxExtractedEventsPerPost`. The backfill computes the same function from the event's stored ordinal for each linked post; it never uses `max + 1`. The post-split cap drops the highest `j` first, then the latest dates."

### ADV-4 "Organizer account" has no key space, no source role and no stability rule

- **Unit A (stem rule / group identity, AD-36 Rule 12; `event_groups.organizer_account_id text null`):** needs one account per event. `events` has no organizer column (`schema.ts:428-484`); it has `source_social_media_account_id text` (the platform `account_id`, `process-ai-job.ts:259`), `organizer_name text`, and a derived "organizer" through `event_posts -> post_account_associations`. Unit A reads the primary post's `PUBLISHER`, stored as the platform account id text (the column is `text`).
- **Unit B (duplicate key and sweep, AD-38 Rule 6 "share the organizer account"; AD-30 Rule 7):** reuses the matcher's `resolveOrganizerMatch` / `buildEventAccountMatchCondition`, which matches **any** role including `SCRAPING_SOURCE` on any linked post, keyed on the profile UUID (`event-account-match.ts:37-46`), or the `organizerHandle`-resolved profile.
- **Result:**
  1. Key space: platform `account_id` text versus profile `uuid::text`. `WHERE organizer_account_id = $uuid` never matches a group written with the platform id, so every new post opens a new series (or the reverse).
  2. BUG-059 twins: one real account has two profile rows (handle-keyed and numeric). Siblings posted from different twins get different keys. The twin merge (`account_profile_merges.repointed`) does not know `event_groups.organizer_account_id` exists.
  3. Role: a curator roundup stub has `PUBLISHER` = the curator. Keyed on the publisher, two unrelated organizers listed by one curator ("Yoga - Studio A", "Yoga - Studio B") share `(curator, yoga)` and become one series. AD-30 Rule 7 deliberately discounts the curator as organizer (BUG-058) for the matcher; the stem rule has no such discount.
  4. Stability: `enrichAndPromoteEvent` changes the primary post (organizer-authored beats roundup). The event's organizer changes from curator to organizer; the group row keeps the old key. The next post of the real organizer opens a second group.
- **Fix:** AD-36 Rule 12: "`organizer_account_id` is `social_media_account_profiles.id` (uuid), taken from the event's primary post only when that post is organizer-authored (AD-31 Rule 3) and from its `PUBLISHER` association; stub/curator-sourced events neither create nor join a series until promoted. Promotion (`becameOrganizerAuthored`) re-runs group attach. Twin merges repoint `event_groups.organizer_account_id`." State the same single-source rule in AD-38 Rule 6, and name the matcher's any-role union as a different (broader) predicate.

## High

### ADV-5 Discovery collapse: no "Discovery only" discriminator, dissolved groups still collapse, the partition key does not type-check, and the "ranked list" is not on master

- **Unit A (backend, AD-36 Rule 13):** adds the window pass to `Query.events`, "Discovery only ... calendar, favorites, feed and account pages ... the collapse never runs there". `Query.events` has no surface argument: Discovery, Feed, Favorites, account pages and My Calendar all call the same `getEvents($limit,$offset,$query)` (`apps/web/src/features/events/queries.graphql:2-3, 38-39, 271-272`) and differ only in the condition tree (`isFavorited`, `isFromSubscribedAccount`, account id). The resolver's precedent is to sniff the tree (`hasFavoritedEqTrue`, `hasWithinRadiusCondition`, `resolvers.ts:3196-3210`), so Unit A infers "Discovery" from the absence of those leaves.
- **Unit B (web):** adds a `collapseGroups: true` variable to the Discovery hook, as the rule text suggests a request-level policy. A Discovery view with a "subscribed accounts" chip, or an AI-filter expression, now collapses on one side and not on the other.
- **Further incompatibilities in the same rule:**
  - `coalesce(group_id, -id)`: `events.id` and `group_id` are `uuid` (`schema.ts:429`); unary minus on uuid is a SQL error. Unit A writes `coalesce(group_id, id)`, Unit B writes `coalesce(group_id::text, 'e:' || id::text)`; ids are the same shape so neither collides, but the index and the `id` pagination tie-break differ.
  - Rule 1 gives `status: dissolved` a meaning, and Rule 5 says dissolving "never deletes the member events". If dissolve only flips `status` and keeps `events.group_id` (the cheap implementation), the Rule 13 partition (before the join to `event_groups`, "joined for the displayed rows") still collapses a dissolved series to `k = 1`: a moderator's revert hides events. `undoEventMerge` (Rule 7) restoring the loser's `group_id` into a dissolved group does the same.
  - Rule 13 says "the per-event score as today" and "rank". On master `Query.events` is a chronological `ORDER BY` of correlated subqueries (`resolvers.ts:3820-3836`); the score, `tierFor` and "seen" exist only in the unmerged personalization branch (`poc-event-insight/discovery-sort.ts`: order `(areaTier, sortDays, id)`). "Rank penalty" for a programme has no operand on master.
- **Result:** the same GraphQL document returns a collapsed list from one backend build and an uncollapsed one from another; a dissolved group keeps hiding events; two ranking implementations appear.
- **Fix:** Rule 13: "Collapse runs only when the request sets `collapseGroups: true` (default false); the backend never infers it from the condition tree. The partition key is `coalesce(g.id, e.id)` where `g` is `event_groups` joined **before** the window with `g.status = 'active'`; a dissolved group's members are ungrouped. `undoEventMerge` and `undoEventSplit` restore `group_id` only into an active group." Add a prerequisite line: "Rule 13 ships on top of a single ordering expression `rank(e)` that the personalization work owns; on the chronological order the penalty is `+ penalty_days`."

### ADV-6 `location_precision` has two owners, and `area_status`, `pin_trust`, `location_source` have undefined combinations

- **Unit A (ingestion/ladder, AD-39 Rule 1/4, Binds):** stores `schedules.location_precision` at ingestion from `pin_trust` and the event's keys; the retry ladder later writes `events.area_status` and area keys only (that is the column it owns).
- **Unit B (GraphQL, AD-39 Rule 6):** exposes `locationPrecision` on `Event`, either by reading the stored schedule column or by deriving it at read time from `pin_trust` + `area_status`.
- **Result:** precision is a pure function of `(pin_trust, area_status)` (Rule 1: EXACT only with a trusted pin, AREA with keys and no trusted pin, else UNKNOWN) yet is listed as a stored column on `schedules` while one of its inputs lives on `events`. After a ladder step resolves an area, a stored value keeps the card badged UNKNOWN; if instead B derives it, the stored column is dead and the "AST guard" (Enforced by) tests a field nothing reads. It is also schedule-level in storage and event-level in the API, with no rule for which schedule speaks for the event (the main schedule? the first? worst?). See the combination table at the end of this file.
- **Fix:** AD-39 Rule 1: "`location_precision` is derived, never stored: `trusted pin ? EXACT : area_status = 'known' ? AREA : UNKNOWN`, evaluated by one domain function and one SQL expression over the event's **main** schedule `pin_trust` and `events.area_status`. Remove it from the Binds column list." Add a CHECK/ratchet for the impossible combinations in the table.

### ADV-7 `pin_trust` needs the event's area keys; area keys need a trusted pin; `place_key` needs both; and all three are first computed before the split

- **Unit A (geocode time, AD-14 Rule 4):** `resolveAccountAndLocations` runs per extracted event inside the `process-ai-job.ts:252-299` loop and writes `pin_trust`; leg (c) intersects the pin's path with "the event's area keys (AD-39)". The only keys known at that moment are the stated ones for the **whole pre-split event**.
- **Unit B (area resolver, AD-39 Rule 2):** step 2 derives area keys **from** the trusted pin's administrative path; steps 3-4 add roundup-heading and account keys later (retry ladder, async). Re-evaluating (c) then uses the larger key set.
- **Unit C (normalizer, AD-38 Rule 1):** `place_key` = venue name + "the area key of the venue's city", needing the same keys, after the loop and before the matcher.
- **Result:** (1) circular: no unit can compute the first value without the other; a trusted pin yields keys that then "agree" with it by construction. (2) A three-place event whose text states "Sleman" gets its Kota Yogyakarta pin marked `untrusted` (path does not intersect the pre-split keys), then split into a sibling whose own city is Kota Yogyakarta with an untrusted pin. (3) The stored `pin_trust` differs depending on which unit wrote it last (ingestion vs ladder vs enrichment), and a floor change (start value 0.5, "uncalibrated") has no recompute rule.
- **Fix:** AD-14 Rule 4: "`pin_trust` is computed per **schedule after the place split**, from `(confidence, matchType, non-place guard, the keys of that schedule's own place)`; leg (c) uses only keys from sources that do not depend on the pin (stated area, roundup heading), never the pin-derived keys of AD-39 Rule 2 step 2. A floor change re-derives `pin_trust` from stored `location_details` in one migration." AD-38 Rule 1: "`place_key`'s city component comes from the stated city text through the gazetteer, else from a pin whose `pin_trust` is `trusted`."

### ADV-8 The place bundle has at least seven writers and no single-writer rule

- **Unit A (adds the AD-14/AD-39 columns, obeying Rule 4/AD-39 Rule 1):** writes `pin_trust`, `location_source`, `location_precision` on schedule insert at ingestion.
- **Unit B (existing writers, each obeying AD-30 Rule 9 and its own story):**
  - `mergeSchedules` enrichment overwrites `location`, `locationDetails`, `latitude`, `longitude`, `timezone` from the new post but not the new columns: the field list is closed (`set-event-primary-post.ts:283-297`), and `events.location` is in `ENRICHABLE_EVENT_FIELDS` (`:144-153`) while area keys/`area_status` are not.
  - `mergeEvents` Step 3 copies a loser schedule column by column (`merge-events.ts:122-142`), again without the new columns.
  - `submitCorrection` rewrites `schedules.location` text and `events.location` and never touches `location_details`, coordinates or trust (`resolvers.ts:1498-1541`).
  - The splitter (AD-38 Rule 4), the retry ladder (AD-39 Rule 4), and the moderator "needs location" backstop.
- **Result:** coordinates from post 2 with `pin_trust` and `location_source` from post 1; a copied schedule with NULL trust (reads as untrusted, so the winner of a merge loses its map link); a user correction that changes the venue text while the trusted pin and EXACT precision still point at the old venue. AD-39 "Enforced by" guards only one writer (the account default read).
- **Fix:** AD-39 new Rule 7: "The place bundle `{location, location_details, latitude, longitude, timezone, pin_trust, location_source}` is written only by `writeSchedulePlace()`; enrichment, merge copy, correction, split and ladder call it; a correction that edits `location` re-geocodes through it. A source-scan ratchet (AD-30 Rule 2 style) fails any other write to those columns. `ENRICHABLE` and the merge copy list import the bundle's column list from one constant."

### ADV-9 Pin consumers: the list in AD-14 Rule 4 is not the set of consumers, and the web recomputes trust from confidence

- **Unit A (backend, Rule 4):** gates the three named consumers (map link, radius filter, Nearby/paid distance) on stored `pin_trust`.
- **Unit B (everything else that reads a pin):**
  - Timezone: `resolveScheduleTimezones` tier 1 takes `resolvedScheduleLocations.get(i)?.timezone` unconditionally (`resolve-schedule-timezones.ts:20-26`), so a wrong-country pin (BUG-066) sets a wrong, `RESOLVED` timezone.
  - Matcher: `hasVenueMatch` treats coordinates within 150 m as a venue match with no trust check (`match-scoring.ts:117-132`), contradicting AD-38 Rule 1 ("coordinates count only when `trusted`").
  - Web: map link and account card gate on `isLocationTrustworthy(confidence, matchType)` computed in the browser (`LocationLink`, `SubscribedAccountCard`, `mapper.ts`); AD-39 Rule 6 exposes `locationPrecision` and `areaLabel` but not `pinTrust`, so the client cannot read the stored predicate and cannot evaluate legs (b) and (c).
- **Result:** the card shows a map link and "2 km away" for a pin the backend filter excluded, and vice versa. Also, Rule 4 calls the existing predicate "confidence-only"; it is not: it requires `matchType === 'full_match'` too (`is-location-trustworthy.ts`). A unit that implements leg (a) from the AD text ("confidence reaches the floor") trusts street-level matches; a unit that wraps `isLocationTrustworthy` as "the first leg" keeps the `full_match` requirement; `getPlaceDetails` returns synthetic `PLACE_ID_EXACT` with confidence 1 (AD-14 Rule 1) and fails the wrapped version.
- **Fix:** Rule 4: "Every reader of a pin, including timezone derivation, match scoring and account-default inference, reads `pin_trust`; GraphQL exposes `Schedule.pinTrust`, and `isLocationTrustworthy` is deleted from `packages/ui` in favour of it. Leg (a) is exactly: `matchType = 'PLACE_ID_EXACT'` or (`confidence >= floor` and `matchType = 'full_match'`)." Add the provenance leg (d): a pin whose `location_source` is `account_default` is trusted only under AD-39 Rule 3's venue-account conditions; otherwise it is `untrusted`, so a never-classified account's copied default cannot drive Nearby.

### ADV-10 The split moves schedules but not everything keyed to them; the sibling's column list is open-ended

- **Unit A (splitter, AD-38 Rule 4):** moves schedule rows to the new event "with schedule ids unchanged, so `calendar_additions` stay attached"; "new siblings copy the organizer, category, links and `event_posts` rows".
- **Unit B (existing readers):**
  - `calendar_additions.event_id` is `NOT NULL` and event-level readers match on it: `isAddedToCalendar` as a `Query.events` filter and virtual field (`resolvers.ts:3418-3426, 3904-3909, 4036-4041, 4855-4860`), including My Calendar (`buildMyCalendarQueryCondition.ts:14-17`). Only `mergeEvents` updates it (`merge-events.ts:166-170`). A user's entry stays on the original event while its schedule now belongs to the sibling: the original claims a calendar entry it has no schedule for; the sibling shows the schedule as added but the event as not added.
  - `mainSchedulesOnly` joins only `is_main_schedule = true` (`resolvers.ts:3716-3736`) and place filters (`scheduleLocation`, `scheduleCoordinates`, `adminArea`) read that join. A moved schedule set has no main schedule unless the splitter runs `normalizeMainSchedule` for both sides; the sibling never matches a place filter. AD-38 Rule 7 asserts "the main-schedule join is correct for place filters" only if every event keeps exactly one main schedule at its own place.
  - "Copy the organizer, category, links" is silent on `contact_info`, `has_private_contact`, `description`, `detail_level`, `source_social_media_account_id`, `confidence_score`, `location` (event-level text), `notified_at`, area keys and `area_status`. A unit that copies the row copies the original's union of areas to every child (strict "in Bantul" then matches the Kota Yogyakarta child); a unit that copies the listed fields drops `has_private_contact` while keeping `contact_info` (privacy flag lost) or both (`detail_level` default `full` for a stub).
- **Fix:** AD-38 Rule 4: "The split moves the schedules **and** repoints `calendar_additions.event_id` for every moved schedule, journalled and inverted by `undoEventSplit`; it re-runs main-schedule normalization on both sides in the same transaction. A sibling is `INSERT ... SELECT` of the original with an explicit override list: `id, slug, event_name, location, post_id/extraction_ordinal` (Rule 3), `area_*` and `pin_trust` recomputed from its own place, `notified_at` copied from the original (a split never notifies), `deleted_at` null; every other column is copied verbatim, including `contact_info` and `has_private_contact`."

### ADV-11 "The same place" has four definitions, and exclusion (b) reads the strictest

- **Unit A (matcher/sweep, AD-38 Rule 6 (b)):** "both have a resolved `place_key` and the keys differ" is a candidate exclusion, implemented as `a.place_key !== b.place_key`. The existing venue signal remains `hasVenueMatch` (same location string or 150 m).
- **Unit B (normalizer, AD-38 Rule 1):** two venue texts are the same place when "the `place_key`s are equal, or the area keys are equal and name similarity reaches a start value".
- **Unit C (Tier 2, AD-36 Rule 3 amended):** "the shares-its-venue test compares the normalized venue name plus account", a third definition.
- **Result:** "Kenes Soho" and "Kenes Soho Jogja" are one place for the normalizer (one event) and different places for the matcher (excluded forever), so the genuine duplicate that IDEA-085 exists to merge is never a candidate. The sweep's "duplicate key" (organizer + normalized name + date + `place_key`, an exact-equality key) and the write-path matcher's trigram-plus-score tiers disagree on the same pair, and the Rule 10 gate metric ("reachable pairs", `recall-classes.sql`) uses a third SQL normalization. The code already has three more: `assign-extraction-ordinals.ts` `normalizeEventName` (no diacritic strip), the stem normalizer (Rule 12) and `similarity()` on the raw `event_name`.
- **Fix:** AD-38 Rule 1: "`isSamePlace(a, b)` and `normalizeName(s)` are the only definitions, in `packages/domain`; `place_key` is only their cache. Exclusion (b) is `NOT isSamePlace`; the Tier 2 venue test, the sweep key and `hasVenueMatch` call it (the weight stays 0.15, the input changes; coordinates require `trusted`). The Rule 10 metric SQL is generated from the same normalization."

### ADV-12 Dedupe-first and split-then-group are circular, and backfill siblings never pass the matcher

- **Unit A (IDEA-085 sweep, AD-30 Rule 7 amended, gated first by AD-36 Rule 10):** merges `high` legacy pairs; applies exclusion (b), which needs a `place_key` per event. A legacy un-split event has a place **set**; "keys differ" has no meaning for sets.
- **Unit B (AD-38 Rule 5 backfill, "gated by AD-36 Rule 10"):** runs after the sweep, splits legacy multi-place events and creates groups.
- **Result:** a legacy three-place event E and a live-created single-place event E_A (from a later post) look excluded to the sweep (sets differ), so it merges nothing. The backfill then splits E, and E's place-A child and E_A are same-name, same-place, same-organizer duplicates created **after** the only sweep. The backfill inserts siblings directly (Rule 4) and the write-path matcher (`findMatchingEvent`) runs only inside `processIngestionJob`, so nothing re-checks them, and then grouping builds "groups of copies": the failure Rule 10 exists to prevent, caused by the ordering Rule 10 prescribes.
- **Fix:** AD-38 Rule 5 / AD-36 Rule 10: "Backfill is three separately gated steps: (1) split without creating groups; (2) re-run the sweep over the split output (every backfill-created event passes `findMatchingEvent`); (3) group attach. Exclusion (b) compares place sets with `isSamePlace` pairwise: excluded only when **no** place of A is the same as any place of B."

### ADV-13 Group notification: undefined covered set, carrier and count

- **Unit A (`notifyNewEvent`, AD-36 Rule 14, AD-30 Rule 10 amended):** the claim is atomic on `(group_id, source post)` and "the event rows it covers get `notified_at` set". Covers = all active members of the group with `notified_at IS NULL`.
- **Unit B (ingestion, Rule 10 + stubs):** a roundup/curator-sourced stub never notifies at ingestion; `notified_at` stays NULL on purpose, because Rule 10 sends exactly one notification when a later primary change makes it organizer-authored.
- **Result:** (1) Unit A stamps stub members of the same group (a roundup sibling in the series), consuming their one future notification; if covers = "members linked to the source post" instead, a member added by a different post is skipped. (2) "N sessions counted at send time": N is the batch for this post, or `event_groups.member_count`, which includes the series archive (past seasons); a weekly series reads "31 sessions". (3) The carrier: the ingestor is poll-and-drain every 5 minutes in prod (`ingestor.ts:17-23`), parsing **every** body as `ExtractedEventMessage` and calling `processIngestionJob`; a new notify message on that queue crashes the handler and ends in the DLQ, so a unit adds a fourth queue and Lambda instead (CLAUDE.md section 4 requires the diagram change). The local inline fallback (`process-ai-job.ts:551-558`) has no delay at all. The "60 to 120 s" is really "next tick after visibility". (4) A split child gets `notified_at = NULL` (not in the copy list), the "notified_at IS NULL and organizer-authored" state is reachable for an event that was already announced as the original.
- **Fix:** Rule 14: "Covered = members with `group_id = G`, a link to the source post, `notified_at IS NULL`, and an eligible primary post (Rule 10); stubs are never stamped. `N` = covered count. The delayed message is a discriminated union on `DataIngestionQueue` (`kind: 'event' | 'group-notify'`) parsed by one `parseIngestionMessage()` used by the SQS handler, poll-and-drain and the inline fallback; the delay is a minimum, not a promise. A split child inherits `notified_at`."

### ADV-14 Curator audience area: two writers of `CONFIRMED`, a once-only ladder, and "everything else is partial"

### ADV-15 Split-time favorite copies versus the merge dedupe direction

- **Unit A (`undoEventSplit`, AD-36 Rule 15 / AD-38 Rule 4):** "records the favorites it created so an undo removes exactly those" (by journal id).
- **Unit B (`mergeEvents`, AD-30 Rule 9):** keeps the winner's favorite and soft-deletes the loser's when a user holds both (`merge-events.ts:94-107`); the winner is whichever event the moderator or sweep chose.
- **Result:** user U favorited the original O; the split copied a favorite to child C. A moderator merges O into C as loser: U's original favorite is soft-deleted (deduped), the copy on C survives. `undoEventSplit` then deletes "exactly the favorites the split created" (the survivor on C) and the user ends with no favorite at all. Also `favoriteCount` is multiplied by the number of children on every child, which any popularity input will read as N times the interest.
- **Fix:** AD-38 Rule 4: "`undoEventSplit` restores by invariant, not by id: for each user with an active favorite on any child it ensures exactly one active favorite on the original and removes the rest. `favoriteCount` for a series reads `count(distinct user_id)` over the group's members where it is used as a ranking input."

### ADV-16 A moderator merge of siblings (and a pending suggestion accepted after the exclusions land) re-creates the multi-place event; the sweep cannot call `mergeEvents` as written

- **Unit A (`mergeEvents`, AD-30 Rule 9 / `resolveSuggestedEventMatch` ACCEPT):** has no place guard. Schedule mapping is by start date only (`schedule-date-match.ts:13`): a loser schedule at another place on the same date maps onto the winner's schedule and is not copied; calendar additions are repointed onto it. The 147 pending suggestions in the queue predate exclusion (b).
- **Unit B (splitter/backfill, AD-38):** keeps splitting events with more than one place.
- **Result:** a moderator "fixes a duplicate" by merging two series siblings; the next backfill pass splits them again (merge/split ping-pong), and in between a user's calendar entry silently changes venue. Rule 6 restricts "candidate generation" only, not the merge action. The sweep also cannot literally "merge through `mergeEvents()`": `event_merges.performed_by_moderator_id` is `NOT NULL` with an FK to `users` (`schema.ts:567`), and the winner of a sweep pair is never defined (the ingest-time path always picks the existing candidate).
- **Fix:** AD-30 Rule 9: "`mergeEvents` refuses (or warns and requires an override) when the two events have non-intersecting place sets; schedule matching is by `(start date, place)`. Automated merges use a seeded system user; the sweep's winner is the event with an organizer-authored primary, then more complete schedules, then the earlier `created_at`, then lower id." Re-validate pending suggestions against exclusion (b) when it ships.

### ADV-17 The Gemini quota: wrong key pool, a fence that forbids the use, and no arbiter

- **Unit A (backfill re-extraction, AD-38 Rule 5):** calls Flash Lite "through the AD-32 wrapper" on the "platform-funded `SYSTEM_GEMINI_API_KEY`, AD-10", budgeted as 500 minus live use measured from `extraction_audit_logs` (`gemini-usage.sql`).
- **Unit B (AD-10 and the code):** the system key is reachable only from `callGeminiForLocationInference` and `callGeminiForAccountClassification` (`system-key-adapter.ts`); AD-10 Rule 2 makes it "structurally unreachable" from the extraction path. Live extraction calls `callGeminiSeam` with subscriber keys (`process-ai-job.ts:142-146`).
- **Result:** the 500/day pool is consumed by classification and location inference, which write no `extraction_audit_logs` row; the backfill's budget query counts the wrong population and starves them, or Unit A routes through `callGemini` and finds no subscriber keys for a backfill job. "Yields to live traffic" has no mechanism: a daily number read at job start cannot yield to calls made later that day.
- **Fix:** AD-38 Rule 5 and AD-10: "Add a `system_key_reextract` entry point to the AD-10 fence; a counter row per UTC day (`vendor_call_locks` family) is incremented by every call on the system key; backfill may use `min(100, 500 - counter)` and re-checks per call." State which key live extraction uses, and correct the memlog premise.

### ADV-18 Strict area filter versus the existing `Query.events` location filters and the lane

- **Unit A (AD-39 Rule 5):** adds a strict area filter (same/inside) and a partial-match lane "in a radius filter's partial lane". Delivered as a second `Query.events` request by the client.
- **Unit B (existing filters):** `LocationFilterInput.adminArea` and `fieldMap.adminArea = locationDetails->>'adminArea'` on the main schedule (`resolvers.ts:3401`, `buildEventsQueryCondition.ts:331-340`; never written, BUG-063) stay, or are repointed to an area key. The lane is delivered as a union in the same query.
- **Result:** two filters named "area" with different semantics; a series with one strict and one area-only member shows twice (once per lane) when the lane is a second request, and the Rule 13 collapse cannot see across two queries. The default Discovery tier (`tierFor`: 0 for same, inside, covers **and sibling**) is "In your area" for the chip, while the strict filter and the lane exclude `sibling`. The POC `tierFor` that Rule "Enforced by" promotes returns tier 1 (national) for an empty key list because `[].every(...)` is true (`area-resolver.ts:148-150`), which is exactly the "null read as anywhere" the AD forbids.
- **Fix:** AD-39 Rule 5: "`LocationFilterInput.adminArea` is replaced by `areaKey` (strict); the partial lane is the same query with `matchLane: STRICT | PARTIAL` as an ordering tier, so the collapse sees both; the 'In your area' chip is tier 0 *minus* `sibling` or the siblings are named (decide once). `tierFor` first checks `area_status`; an empty key set is `unknown`, never national."

### ADV-19 Who writes `area_status`: no area provenance, no compare-and-set

- **Unit A (ingestion/enrichment):** writes keys from the stated area (ladder step 1) and `area_status = known`; `enrichAndPromoteEvent` overwrites `events.location` from a re-post but not the keys.
- **Unit B (retry ladder job, async; moderator action; audience-area fan-out):** writes lower-priority keys (heading, account) after a seconds-long external call.
- **Result:** last writer wins: a ladder result computed from the account area can overwrite stated keys written meanwhile. `location_source` describes the **place** (stated, geocoded, account default, audience), not the **area**, so heading-derived and pin-derived keys have no provenance value (there is none for "roundup heading"). Legacy rows have `location_source`, `pin_trust` NULL; the AD defines no meaning for NULL (strict venue-account leg requires `account_default`, so every legacy venue-account event falls out of the strict lane; "absence means untrusted" empties the radius filter right after deploy until a backfill runs).
- **Fix:** AD-39 Rule 4: "Area keys carry `area_source` with a rank (`stated > pin > heading > account`); every write is `UPDATE ... WHERE area_source_rank < :new` or `area_status = 'unknown'`. Legacy NULLs: `location_source` NULL is treated as `stated`; `pin_trust` NULL is recomputed by the migration before the radius filter reads the column."

### ADV-20 One group per event cannot hold both a programme item and its place split

- **Unit A (activity split, AD-38 Rule 2):** a `program-lineup` item "Circus" becomes an event in the programme group (kind `programme`).
- **Unit B (place split, AD-38 Rule 2):** the item "Circus" has schedules at two venues, so it splits into "Circus - Venue A" and "Circus - Venue B" in a `series` group.
- **Result:** Rule 1 gives each event one `group_id`. Whichever split runs second overwrites or fails; if place-first, the programme loses its children; if activity-first, the series is never created; the Rule 2 text lists both splits without composition order. Rule 12's "poster heading is not a second group" covers headings, not this.
- **Fix:** AD-38 Rule 2: "When both splits apply, `group_id` is the programme; the place siblings are tied by the shared source post and an identical normalized activity name (readable by `relatedEventIds`), not by a second group. Kind `series` groups exist only for activities that are not inside a programme."

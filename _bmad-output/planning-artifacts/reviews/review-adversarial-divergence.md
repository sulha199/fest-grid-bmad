# Adversarial Divergence Review — AD-8 Soft-Delete Convention Extension

## Overall verdict

AD-8's rule 4 extension is well-reasoned in isolation, but it was bolted onto rules 1–3 without reconciling them against the codebase they claim to describe — and that gap is not cosmetic. Two of the review's own factual claims ("each table carries deletedAt," "enforced once… never per-resolver") are false for the majority of the tables AD-8 names today, and the rule 4 flagship example (`deleteUserLocation`) is a live hard-delete mutation that a previous story explicitly justified as *outside* AD-8's scope — a justification the spine silently invalidated without telling anyone. Given this baseline, constructing two builders who each read AD-8 literally and still build incompatible things was not hard; several of the divergences below are not hypothetical at all, they are already latent in the shipped code and will surface the moment anyone extends soft-delete to a second resource.

## Findings

- **critical** `deleteUserLocation` — AD-8 rule 4 cites `deleteUserLocation(id: ID!, action: SoftDeleteAction!): UserLocation` as its worked example of the new mutation contract, but the mutation as shipped (`apps/backend/src/schema/user-locations.graphql:41`, resolver at `apps/backend/src/schema/resolvers.ts:130-135`) is `deleteUserLocation(id: ID!): Boolean!` performing a literal `db.delete(userLocations)` hard delete. Story `2-3a` (`_bmad-output/implementation-artifacts/2-3a-build-the-saved-locations-backend-graphql-api-layer.md`, Dev Notes) explicitly reasoned "AD-8 does not bind `user_locations`… the existing table has no `deletedAt` column, confirming a hard delete is the correct, already-established design" — true at the time, since AD-8's table list back then was `EventInfo, Favorite, CalendarEntry, Subscription, ApiKey`. The current spine (updated 2026-08-06) silently added `UserLocation` to that list and `packages/database/schema.ts`'s `userLocations` table (lines 41-53) still has **no `deletedAt` column**. Two builders picking this up: Builder A treats rule 4 as purely an API-shape change and adds the `action: SoftDeleteAction!` arg + `UserLocation` return type to the existing resolver while leaving `db.delete(userLocations)...` untouched — this compiles, satisfies the GraphQL contract, and is silently catastrophic: `DELETE` still physically destroys the row, so `RESTORE` can never succeed (there is nothing left to restore). Builder B does the full, correct rework — adds a migration for `deleted_at` + the rule-3 partial index, converts the resolver to an `UPDATE`. Both believe they implemented "rule 4." (`apps/backend/src/schema/resolvers.ts:130-135`, `apps/backend/src/schema/user-locations.graphql:41`, `packages/database/schema.ts:41-53`, `_bmad-output/implementation-artifacts/2-3a-build-the-saved-locations-backend-graphql-api-layer.md:26,104,116,171`). *Fix:* Rule 4 must not cite `deleteUserLocation` as if it already exists in the new shape — either mark it explicitly as "not yet migrated; requires a schema migration adding `deleted_at` + partial index before the resolver can be touched" with a named owning story, or pick a genuinely greenfield mutation as the worked example. Add a rule-4 sub-clause: "A mutation may not claim rule-4 compliance by signature alone — the underlying row must be reachable in both directions (verify by testing RESTORE after DELETE), and any table gaining an `action`-shaped mutation must first carry the `deletedAt` column and partial index from rules 1 and 3."

- **critical** Rule 1 ("Each table carries `deletedAt`") and rule 2 ("enforced once… never per-resolver") both describe a present state that doesn't exist. Of the 8 tables AD-8 rule 1 names (`EventInfo, Schedule, Post, Favorite, CalendarEntry, Subscription, ApiKey, UserLocation`), only 4 of the corresponding actual tables — `favorites`, `calendarAdditions`, `subscriptions`, `apiKeys` — have a `deletedAt` column today; `events`, `schedules`, `posts`, `userLocations` do not (`packages/database/schema.ts`, full read). Separately, there is no shared query-building enforcement point for the `deletedAt IS NULL` default: `apps/backend/src/schema/resolvers.ts` hand-writes `isNull(favorites.deletedAt)` / `isNull(calendarAdditions.deletedAt)` at six independent call sites (lines 297, 306, 349, 436, 451, 468) — one inside an `exists()` subquery in the `events` query's field map, one inside a sort-join's `and()`, and one each inside three separate type-field resolvers (`Event.isFavorited`, `Event.isAddedToCalendar`, `Schedule.isAddedToCalendar`). `buildDrizzleWhere`/`buildOptimizedDrizzleSelect` (`@festgrid/graphql-select`, referenced by AD-1/AD-2) only compile the DSL's explicit `where` clause — they never see or inject the implicit soft-delete filter. Two builders adding two new soft-delete-capable resources (say, an `ApiKey`-scoped list query and a `Subscription`-scoped list query) have no canonical enforcement point to wire into; the file already models three different techniques for the same two tables, so each builder will plausibly pick a different one (or, per rule 2's own "Prevents" clause concern, simply forget one of the sites — the failure mode rule 2 was written to prevent is already the file's steady state). *Fix:* Either (a) reword rule 2 to state the enforcement is currently per-call-site and mandate a single shared helper (e.g. `activeOnly(table)` exported from `@festgrid/graphql-select`) that every new resolver must import rather than hand-writing `isNull(...)`, with a tracked follow-up to retrofit the six existing sites; or (b) make `buildDrizzleWhere`/`buildOptimizedDrizzleSelect` auto-inject the filter for any table carrying `deletedAt`, so it is structurally impossible to omit. Until one ships, rule 2 should be marked aspirational, not descriptive.

- **high** RESTORE's error contract is unspecified beyond "errors on a mismatched call." `resolvers.ts` already has two different `GraphQLError` codes in play (`BAD_REQUEST` at lines 36/66/126, `NOT_FOUND` at lines 78/174) with no precedent for an "invalid state transition" case. Builder A implementing `deleteUserLocation`'s RESTORE reuses `NOT_FOUND` (reading "not currently soft-deleted" as "not found in a deletable state"); Builder B implementing a later `ApiKey`/`Subscription` mutation introduces a new `CONFLICT`/`INVALID_STATE_TRANSITION` code. Both "throw a GraphQLError," satisfying rule 4's literal text, but any shared frontend error-handling logic that switches on `extensions.code` now has to special-case two different codes for the same logical failure. A third plausible reading — return `null` from the (nullable-by-default) mutation field instead of throwing, since rule 4 only mandates returning "the row's own type" on success and doesn't say the field is non-null — would also technically avoid a "silent no-op" while producing an entirely different client contract (null is ambiguous between "not found" and "wrong state," whereas a thrown error is not). (`_bmad-output/planning-artifacts/festgrid-architecture-spine.md:148`, `apps/backend/src/schema/resolvers.ts:36,66,78,126,174`). *Fix:* Add a rule-4 sub-clause naming the exact contract: e.g. "The mutation field is non-null; a mismatched state transition throws `GraphQLError` with `extensions.code = 'INVALID_STATE_TRANSITION'` (a new shared code, distinct from `NOT_FOUND`, which remains reserved for the row not existing or not being owned by the caller)."

- **high** `SoftDeleteAction` enum ownership is unspecified, and the codebase's actual GraphQL schema layout makes collision the likely outcome, not just a risk. The schema is hand-split into one `.graphql` file per resource (`events.graphql`, `user-locations.graphql`, `favorites-and-calendar.graphql`, `geolocation.graphql`, `auth.graphql`), merged into one global schema via a thin root (`typeDefs.graphql`, 4 lines, declares only `type Query { health: Boolean! }`) — there is no shared/common file for cross-cutting types today, and the established convention (e.g. `EventType`/`EventCategory` in `events.graphql`) is "declare the enum in the file of the resource that first needs it." AD-8 doesn't override that convention for `SoftDeleteAction`. Builder A, implementing an `ApiKey` delete mutation, adds `enum SoftDeleteAction { DELETE, RESTORE }` to a new `api-keys.graphql` (Epic 3). Builder B, implementing `Subscription` delete in parallel (Epic 4), does the same in `subscriptions.graphql`. GraphQL SDL has one global type namespace once files are merged — this is a duplicate-type schema build failure, or a silent last-file-wins merge depending on tooling, the textbook "two owners of one entity" case the review lens asks for. *Fix:* Add a rule-4 sub-clause: "`SoftDeleteAction` is declared exactly once, in [a named shared file, e.g. `apps/backend/src/schema/shared.graphql` or `typeDefs.graphql`'s root] — resource-specific schema files reference it, they never redeclare it."

- **medium** The "legacy exception" carve-out is textually narrow (names exactly `toggleFavorite` and `toggleCalendarAddition`, and states "every new… mutation… must use the rule 4 shape") but has zero code-level enforcement and, per Finding 1, zero *working* reference implementation of the new shape to copy from. A builder building a genuinely new resource's soft-delete mutation who greps `resolvers.ts` for prior art finds two fully working implicit-toggle examples (lines 136-167, 168-210) and no working explicit-`action` example — `deleteUserLocation` is still `Boolean`-returning and hard-deleting on disk. Nothing (no lint rule, no shared TypeScript type, no codegen check) would stop a builder from shipping a new `toggleApiKeyStatus`-shaped mutation and rationalizing it as "consistent with existing patterns," which is a defensible-sounding but AD-8-violating reading. *Fix:* Once Finding 1 is fixed and `deleteUserLocation` genuinely implements rule 4, that becomes the copyable precedent — reference it by name in the exception clause ("see `deleteUserLocation` for the canonical rule-4 shape") so grep-driven pattern-matching favors the compliant path. Consider a shared TypeScript helper/type (e.g. a `SoftDeletableMutationResolver<T>` shape in `@festgrid/graphql-select` or similar) that structurally requires the `action` argument, making the toggle shape mechanically harder to fall into by accident for new resolvers.

- **medium** Naming drift between AD-8's illustrative identifiers and the real schema risks migrations written against tables that don't exist. Rule 1's bound-table list uses domain names (`EventInfo`, `Schedule`, `Post`, `CalendarEntry`) that don't match `packages/database/schema.ts`'s actual exports (`events`, `schedules`, `posts`, `calendarAdditions`/table `calendar_additions`). Rule 3's example SQL is worse — it's copy-pasteable and wrong: `CREATE INDEX idx_favorite_active ON favorite (user_id)...` and `CREATE INDEX idx_calendar_entry_active ON calendar_entry (...)` reference tables `favorite` and `calendar_entry`, neither of which exists (the real tables are plural: `favorites`, `calendar_additions`, and the *actual* partial indexes already in `schema.ts` are named `idx_favorites_active` / `idx_calendar_additions_active` — lines 160, 172). A builder who trusts AD-8's SQL example over checking `schema.ts` first writes a migration against a nonexistent relation. (`_bmad-output/planning-artifacts/festgrid-architecture-spine.md:134,141-146`, `packages/database/schema.ts:160,172`). *Fix:* Replace rule 1/3's illustrative names with the literal Drizzle export + Postgres table names, or add a footnote mapping domain name → actual table (`Favorite → favorites`, `CalendarEntry → calendarAdditions`/`calendar_additions`, etc.), and correct the rule-3 SQL block to match the already-shipped index names/tables exactly.

- **medium** Cascade gap left entirely open, including an undocumented column. `favorites`, `calendarAdditions`, `userLocations`, `subscriptions`, and `apiKeys` all declare `onDelete: 'cascade'` FKs to `users.id` (`packages/database/schema.ts:43,57,154,155,165,166`), but under AD-8 a user is never hard-deleted, so that DB-level cascade can never fire — a "soft-deleted" user's dependents stay fully live and queryable through every existing path. Compounding this, `users` itself already has a `deletedAt` column (`packages/database/schema.ts:37`) despite not appearing anywhere in AD-8 rule 1's binding list — so there is no spine position on whether soft-deleting a user should soft-delete (or hide) their favorites/locations/api keys/subscriptions, and no owner for that logic. Two builders independently implementing "soft-delete a user" (moderator ban vs. self-service account deletion, plausible in different epics) would each have to invent an answer from scratch: one assumes the FK cascade already handles it and ships nothing further (data leak — the "deleted" user's favorites/locations remain fully active and visible wherever those tables are joined); another hand-writes an application-level cascade touching some subset of the 5 dependent tables in some order, with no spec to check against, so a third builder later touches a different subset. *Fix:* Add a new AD-8 rule (or explicit non-goal) stating whether cascading soft-delete is in scope, and if so, which table owns the cascade logic (e.g., "soft-deleting a `users` row is out of MVP scope; if implemented later, it must explicitly enumerate and soft-delete every dependent row across all 5 referencing tables in a single transaction — DB-level `onDelete: cascade` never fires for a soft delete and must not be relied upon"). Also fold `users.deletedAt` into rule 1's binding list or explicitly explain why it's excluded despite carrying the column.

# Accessibility Review — FestDaily Soft Delete with Undo

**Reviewed:** EXPERIENCE.md (State Patterns § Soft Delete with Undo, lines 125–141; Interaction Primitives § Swipe-to-delete, line 93; Accessibility Floor, lines 167–177) and DESIGN.md (`components.notification.*` tokens, lines 62–73) as of the 2026-08-06 revision.

## Overall verdict

The revision correctly fixes the reliability flaw (deferred-commit-on-unmount silently losing deletes on tab close) and gets the visual pending-state and hover/focus timer-pause basics right. But the toast itself is currently accessibility-invisible in the spec: no live region is specified anywhere in EXPERIENCE.md — the Accessibility Floor section is explicitly scoped to Global Navigation only ("Scoped to Global Navigation for this pass," line 169) and never mentions notifications — so as written, a screen reader user has no specified way to learn a delete happened, that Undo exists, or that the item was later removed. The hover/focus timer-pause satisfies WCAG 2.2.1 for mouse and keyboard-focus users but leaves touch-only and mobile assistive-technology users with no stated way to extend or stop the 6-second window. Focus management at the moment of Trigger, the toast's place in tab order, and the failure-path toast's parity with the happy path are all unaddressed. None of these require relitigating the 6000ms duration, the immediate-commit-at-Trigger decision, or the local-splice-not-refetch timeout behavior — the findings below are gaps in *how* those decisions get exposed to assistive technology, not objections to the decisions themselves.

## Findings

- **critical** No live region or screen-reader announcement is specified for any of the four toast-relevant moments: (a) the delete happening at Trigger, (b) the Undo option becoming available, (c) the eventual removal from the list at timeout, or (d) the failure-path error. EXPERIENCE.md's State Patterns text only describes visual appearance ("A toast notification appears with an 'Undo' action") and the Accessibility Floor section (lines 167–177) is explicitly scoped to Global Navigation only, never mentioning notifications; DESIGN.md's `notification.*` tokens (lines 62–73) are pure Tailwind classes with no ARIA notes. Without an explicit `aria-live`/`role` requirement, a screen reader user who isn't already focused on the deleted item's row has no way to know the delete happened at all. (EXPERIENCE.md lines 125–141, 167–177; DESIGN.md lines 62–73.) *Fix:* Specify that the undo toast renders inside a `role="status" aria-live="polite" aria-atomic="true"` region (this matches what the underlying `sonner` `Toaster` component already provides by default in `packages/ui/src/core/soft-delete-toaster.tsx`, but the spec should state the requirement rather than leave it to an implementation detail/library default) so SR users hear e.g. "Item deleted. Undo." when it appears. Give the failure-path toast a distinct assertive announcement (see next finding). State that the eventual timeout-removal from the list does not require a second announcement beyond the toast's own dismissal, as a deliberate documented decision — not silence.

- **high** WCAG 2.2.1 (Timing Adjustable): "timer pauses while the toast is hovered or focused" (EXPERIENCE.md line 136) only accommodates mouse users and keyboard users whose focus happens to land on the toast. It gives no accommodation to touch-only users (no `:hover` state exists) or to screen-reader users navigating by swipe (mobile VoiceOver/TalkBack) who haven't specifically swiped onto the toast — the two groups named in the review brief as most at risk here. A keyboard user who has already tabbed past the toast before it appears, or who never tabs to it, also has no residual way to extend the 6s window once it's ticking. The spec is also silent on what happens if an AT user is still mid-announcement of the toast's content when the 6s timer fires. (EXPERIENCE.md line 136; DESIGN.md line 73.) *Fix:* Add an explicit non-hover, non-mouse-focus mechanism to satisfy 2.2.1's turn-off/adjust/extend requirement for all input modalities — e.g., treat any assistive-technology virtual-cursor entry into the toast's live region as equivalent to "focus" for pause purposes (not just DOM `:focus`), and/or state the timer does not start counting down until the live-region announcement has had time to complete. At minimum, state a manual dismiss/keep-open affordance (see hit-target finding below) that any user, regardless of input method, can reach.

- **high** No focus-management rule is stated for the moment of Trigger. If a keyboard/screen-reader user's focus is on the item's own Delete button (via Swipe-to-delete, EXPERIENCE.md line 93, or a direct Delete action) when Trigger fires, the item greys out/strikes through in place while a toast appears elsewhere on screen (portal-rendered, `fixed bottom-5 right-5` per DESIGN.md line 63) — but the spec never says what happens to focus. Does it stay on the now-repurposed Delete control (which may become inert or relabeled), silently fall off if that control is removed from the DOM, or get force-moved to the toast? (EXPERIENCE.md lines 132–136; DESIGN.md line 63.) *Fix:* State explicitly that focus is not moved to the toast automatically (matching APG guidance that non-modal toasts must not steal focus), and that the triggering control either remains focusable in an updated state (e.g., disabled/relabeled, not removed) or, if it is removed as part of the pending-state DOM change, focus is deliberately moved to a sensible fallback (e.g., the item's container) rather than left to fall through to whatever the browser defaults to.

- **medium** The Undo action's position in tab order and its keyboard reachability from a portal-rendered toast are unspecified, and there is no minimum hit-area token for it (unlike Global Navigation's `{components.nav.item_hit_area}`, `notification.*` has no analogous sizing token). (EXPERIENCE.md line 136; DESIGN.md lines 62–73.) *Fix:* State that Undo is a real, tab-reachable `<button>` inside the live region and specify roughly where it lands in tab order (e.g., appended near end of DOM/body, reached by continuing to Tab forward from wherever focus currently is — not assumed to be the very next stop after the triggering item). Add a minimum touch-target token for the toast's action/close controls (e.g., `min-h-11 min-w-11`, mirroring the nav pattern) since `notification.close_button` currently has no such minimum.

- **medium** The failure-path toast (EXPERIENCE.md line 139) is under-specified relative to the success/undo toast: no stated live-region politeness level (errors should generally interrupt via `role="alert"`/assertive rather than share the undo toast's polite region), no stated duration or persist-until-dismissed behavior, and no mention of the `notification.close_button` token (DESIGN.md line 69) being wired up for it even though the token exists generically. (EXPERIENCE.md line 139; DESIGN.md line 69.) *Fix:* Give the failure toast its own explicit spec: assertive announcement (`role="alert"` or `aria-live="assertive"`), a visible/keyboard-reachable close control using `notification.close_button`, and either a stated auto-dismiss duration or an explicit "persists until dismissed" rule — don't leave it to inherit whatever the undo toast does by default.

- **medium** Multiple concurrent pending items (rapid successive deletes, each producing its own toast — already supported by `useSoftDeleteWithUndo`'s `pendingMap`/multi-id design in `packages/ui/src/hooks/useSoftDeleteWithUndo.ts`) aren't addressed for announcement collision or tab-order predictability: if a second toast's live-region content is inserted while the first is still being announced, does it interrupt or queue, and in what order do the resulting Undo buttons sit in tab order? (EXPERIENCE.md lines 125–141 — concurrency not mentioned.) *Fix:* State that stacked toasts' live-region announcements queue in trigger order (not interrupt each other) and that their Undo buttons are reachable via Tab in the same order they appeared, so a user who fires three quick deletes can still identify and reach each Undo unambiguously.

- **low** The non-color pending-state cue's wording is ambiguous, though not actually dropped (see informational note below). The revised bullet reads "(greyed out / strikethrough)" (EXPERIENCE.md line 135), where the slash is ambiguous between "either, implementer's choice" and "both together as one compound style" — less clear than the original's explicit "or has a strikethrough." Separately, the Failure-path bullet re-describes the same state as only "greyed-out/pending appearance" (line 139), dropping the strikethrough half of the shorthand entirely, so an implementer reverting the failure path may not realize a strikethrough cue (if applied) also needs removing. (EXPERIENCE.md lines 135, 139.) *Fix:* Use explicit "or" phrasing consistently (e.g., "greyed out and/or struck through — at least one non-color cue required") in both the pending-state bullet and the failure-path revert bullet.

- **informational — no issue found** Contrary to what a surface reading of "greyed out" alone might suggest, the revision did not actually drop the pre-revision pattern's non-color cue: "(greyed out / strikethrough)" in the current pending-state bullet (EXPERIENCE.md line 135) still names strikethrough as an available cue alongside greying out, addressing the spirit of WCAG 1.4.1 even though a pure opacity/lightness change like "greyed out" would arguably not be a strict color(hue)-only signal in the first place. No structural change needed here beyond the wording-consistency fix noted above.

# Story 3.6r: Add the event–post link table and multi-event schema

## Story Details

- Epic: 3
- Story ID: 3.6r
- Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a platform operator,
I want an event to be linkable to several posts and a post to yield several events,
So that multi-event posts (BUG-051) and cross-post matching (BUG-052) have a data model that does not slow the highest-traffic endpoints.

## Acceptance Criteria

1. **Given** Architecture Spine AD-30, **when** the migration runs, **then** `event_posts(event_id, post_id, extraction_ordinal, created_at)` exists (PK `(event_id, post_id)`, index `(post_id, event_id)`, full unique `(post_id, extraction_ordinal)`, both FKs cascade), `events.post_id` is kept as the **primary-post pointer** with its `unique()` dropped, and `events.extraction_ordinal`, `events.detail_level` (`stub|full`), `events.merged_into_event_id`, `events.notified_at` (the single notification marker, AD-30 Rule 10), `posts.grouping_reason`, `posts.extracted_event_count` and `event_slug_aliases` exist. (`schedules.applicable_days_of_week` is **not** added here — it already shipped with Story 1.3k, so this migration must not re-create it.)
2. **And** a unique index on `events (post_id, extraction_ordinal)` (unconditional on `deleted_at`) backs ingestion idempotency; existing rows backfill to ordinal 0 on both tables and get a matching `event_posts` row; a hand-written `CHECK (post_id IS NULL OR extraction_ordinal IS NOT NULL)` prevents a null ordinal from bypassing the unique index.
3. **And** one write helper sets `events.post_id` and inserts the matching `event_posts` row in a single transaction, and a consistency check asserts every non-null `events.post_id` has its `event_posts` row with an equal ordinal; a source-scan test (AD-14 ratchet style) fails if any file other than the helper's module writes `postId` in an `events` insert or update.
4. **And** deleting a post (including profile/account erasure) promotes the next linked post to primary by the primary rule, else sets `events.post_id` null; because `events.post_id` is `ON DELETE SET NULL`, promotion runs in the same transaction **before** the post is deleted, and promoting to a manually linked post (null ordinal) assigns that post's next free ordinal (`max + 1`). **Scope decision (decided by the user, not re-asked):** the "primary rule" this story implements is **AD-30 Rule 7's legs 1, 3 and 4 only** — (1) organizer-authored (via the shared AD-31 Rule 3 predicate, which **this story builds as its first consumer**) beats a non-organizer-authored candidate; (3) otherwise the earlier post (`posts.publishedAt` ascending); (4) otherwise the lower post id (deterministic final tie-break, `ORDER BY id ASC`). **Leg 2 ("the post whose extraction has more schedules with a complete date and location") is explicitly NOT implemented here** — it is match-time-only (comparing two still-separate candidate events during Story 3.6v's matching pass, where "more complete extraction" is a meaningful signal about which candidate to keep), and has no meaning when choosing among posts **already linked to the same event** (every linked post already contributed to that one event's own schedules — there is no second, still-separate extraction to compare against). Story 3.6v adds leg 2 when it builds the matching-time comparison; this story's promotion helper must not invent a schedule-completeness comparison to fill the gap.
5. **And** `pg_trgm` (`CREATE EXTENSION IF NOT EXISTS`, default schema), a partial trigram GIN index on `events.event_name`, the `CHECK` above and every partial predicate are **hand-written** in the migration SQL (drizzle-kit 0.21 drops `WHERE` predicates; operator-class support is unverified), used for write-path matching only.
6. **And** EXPLAIN plans for `Query.events` and `Query.eventBySlug` on representative seed data show the same join count and no new Seq Scan; `event_post_id_idx` is dropped only if EXPLAIN shows it is not needed beside the composite unique index.

**Depends on:** Story 3.6b, AD-30. Coordinate migrations with Story 3.15 (independent, either order — AD-31 Rule 5, already verified in the readiness sweep).

## Dev Notes

- **This is a schema-only story with two small, genuinely new backend modules — resist scope creep toward 3.6s/3.6t/3.6v.** The only production behavior change is: (a) the migration itself, (b) `process-ingestion-job.ts` now writing through the new helper instead of inserting `events` directly (same observable behavior, different call path), and (c) a brand-new, not-yet-wired-to-any-caller promotion function. Nothing in this story changes what `Query.events`/`Query.eventBySlug` return, touches any GraphQL type, or builds any part of multi-event extraction/ingestion (3.6s/3.6t) or matching (3.6v) beyond the one shared predicate AC4 explicitly requires.
- **Read in full before finalizing this design:** `packages/database/schema.ts`'s full `events`/`posts`/`postAccountAssociations`/`schedules` definitions and relations block (current state, post-3.15); `apps/backend/src/lib/ingestor/process-ingestion-job.ts` and its test (current state — the one write site this story must redirect); `packages/domain/src/events/build-event-insert-values.ts` and `packages/domain/src/events/types.ts` (confirms `EventInsertValues` has no `extractionOrdinal` field today, and that this story deliberately does not add one — see Data Type Compatibility below); `apps/backend/src/lib/posts/persist-post-account-associations.ts` (the query/insert style precedent for `post_account_associations` this story's new predicate reads from); `apps/backend/src/schema/schema-consistency.test.ts` (the source-scan-style test precedent Task 8 follows); migration `0064_soft_snowbird.sql` and its owning story's Dev Agent Record (the most recent hand-edited-migration precedent: `DO $$ ... EXCEPTION WHEN duplicate_object THEN null; END $$;` idempotent guards, partial-unique-index hand-edits, backfill `INSERT ... SELECT` placement); `packages/database/seed.ts`'s `FIXTURE_EVENTS`/`FIXTURE_POSTS` and `seed-volume.ts`'s event-row generation loop (both break under the new `CHECK` without Task 9's fix); `_bmad-output/planning-artifacts/cc-024-explain-baseline-2026-10-01.md` in full (the exact methodology and comparison target for Task 10).
- **Why the organizer-authored predicate lives in `apps/backend/src/lib/posts/`, not `packages/domain`.** It queries two DB tables (`post_account_associations`, `social_media_account_profiles`) directly — this is exactly the "DB/ORM-coupled logic" `project-context.md`'s Code Organization rule says must stay out of `packages/domain` (which may be imported by `apps/web` and must stay dependency-free of Drizzle/DB-client code). `apps/backend/src/lib/posts/` already holds the sibling `persist-post-account-associations.ts`, which queries the same two tables — same home, same reasoning.
- **Why the write helper lives in a new `apps/backend/src/lib/events/` directory, not `apps/backend/src/lib/ingestor/` or `apps/backend/src/lib/posts/`.** It is owned by neither existing directory's concern (ingestion-specific vs. post-specific) — it is an `events`-table-centric, cross-cutting primitive that both the ingestion path (Task 6) and the promotion path (Task 7) call into, and that Story 3.6v will later extend for match-driven promotion too. A new, narrowly-scoped directory avoids forcing a false ownership choice between the two existing ones.
- **The `AnyPgColumn`-typed self-reference on `mergedIntoEventId` is a genuinely new pattern in this file** — there is no existing self-referencing FK anywhere in `packages/database/schema.ts` to copy from. Drizzle requires the lazy, return-type-annotated callback form (`references((): AnyPgColumn => events.id, ...)`) specifically because a plain `references(() => events.id, ...)` would try to reference the `events` table object while it is still being constructed (a genuine TDZ/circular-reference problem, not a style preference) — do not simplify this to the normal `references(() => otherTable.column, ...)` form used everywhere else in this file.
- **Composite primary key and full (non-partial) multi-column unique constraints are also new to this file**, but are ordinary, well-supported drizzle-kit features (unlike the `WHERE`-clause-dropping bug that affects every *partial* index/unique in this schema) — Task 3.1 explicitly calls for confirming this by diffing the generated SQL rather than assuming it, since this story is the first to exercise that code path in this specific codebase/drizzle-kit-version combination.
- **`buildEventInsertValues()` (`packages/domain`) is intentionally left unchanged.** It still returns an `EventInsertValues` with `postId` but no `extractionOrdinal` field — adding real per-event ordinal plumbing through `ExtractedEventMessage`/`EventInsertValues` is Story 3.6t's own AC ("one queue message per event... carrying `extractionOrdinal`"), not this one's. `insertEventWithPrimaryPost` (Task 4) defaults the ordinal to `0` purely at the DB-write boundary, which is indistinguishable from "the real thing" for as long as ingestion only ever produces one event per post (true until 3.6t ships). Resist the temptation to "future-proof" `EventInsertValues` now — that is exactly the kind of absorbed-future-story scope the readiness sweep and this project's split-gate discipline exist to prevent.
- **Why AC4's promotion function has no caller yet, and that is correct, not a gap.** AD-30 Rule 8 describes the *mechanism* ("deleting a post... promotes the next linked post"), which this story is explicitly tasked with building (`Depends on: ... AD-30`), but no story in `epics.md` (checked directly, not assumed) currently builds an actual post-deletion or account-erasure *mutation*. Building the mechanism now, fully tested in isolation via direct `event_posts` manipulation in Task 7.3's tests, and leaving it uncalled until that future mutation exists, is the same shape as this story's own `event_slug_aliases` table (created now, populated later by 3.6v) — infrastructure built ahead of its first real caller because AD-30 specifies its exact contract now, not deferred speculative design.
- **The EXPLAIN-gated `event_post_id_idx` decision (Task 10.4) must not be pre-decided here.** AD-30 Rule 4 is explicit that this is an empirical question ("dropped only if EXPLAIN shows it is not needed"), and the readiness sweep did not pre-answer it either — it only confirmed the *harness* (`seed:volume` + the baseline doc) exists and is reusable. Whichever way Task 10.4 resolves, record the actual captured plan evidence in Dev Agent Record, not just the conclusion — a future story (3.18, which also reads `event_post_id_idx`-adjacent query shapes per its own dependency on this one) may need to re-derive why the index was or wasn't kept.

### Data Type Compatibility & Migration Requirements

- **Compatibility finding:** A genuine new DB migration is required — two new enums, two new tables, six new/changed columns across `events`/`posts`, one dropped constraint, two new unique constraints, one hand-written `CHECK`, and one hand-written extension + partial trigram index. This is the largest single-story schema change in the CC-024 slice so far (3.13 needed none, 3.14 added four columns, 3.15 added one table).
- **Impacted fields/contracts:**
  - `packages/domain/src/events/types.ts` — new `EventDetailLevel`/`EVENT_DETAIL_LEVELS` (plain literal array, no branches, not independently unit-tested, matching `POST_ACCOUNT_ROLES` precedent). `EventInsertValues`/`ExtractedEventMessage` are **unchanged** — no `extractionOrdinal` field added (see Dev Notes).
  - `packages/domain/src/posts/types.ts` — new `PostGroupingReason`/`POST_GROUPING_REASONS` (same, plain literal array).
  - `packages/database/schema.ts` — new `eventDetailLevelEnum`, `postGroupingReasonEnum`; `events` gains `extractionOrdinal`, `detailLevel` (NOT NULL with a `'full'` default — see rollout note below), `mergedIntoEventId`, `notifiedAt`, loses its `postId` `unique()`, gains the new `(post_id, extraction_ordinal)` unique; `posts` gains `groupingReason`, `extractedEventCount`; new `eventPosts`/`eventSlugAliases` tables.
  - GraphQL schema/resolvers — **unchanged**. No new field is exposed on the `Event`/`Post` GraphQL types by this story (`detailLevel`, `mergedIntoEventId`, `notifiedAt`, `groupingReason`, `extractedEventCount` are all internal-only until a later story's AC requires exposing one) — see Out of Scope.
- **Required DB migration changes:** full DDL per AC1/AC2/AC5 and Tasks 2-3 above: two `CREATE TYPE`s; `CREATE TABLE event_posts`/`event_slug_aliases`; six `ALTER TABLE ... ADD COLUMN`s (including one self-referencing FK); a data backfill (`UPDATE events SET extraction_ordinal = 0...` then `INSERT INTO event_posts ... SELECT ...`) that must run **before** the hand-written `CHECK` and the new unique constraints are added; `CREATE EXTENSION IF NOT EXISTS pg_trgm` plus a `SET LOCAL search_path`-guarded partial trigram GIN index; one dropped constraint (`events` old `postId` unique); conditionally, one dropped index (`event_post_id_idx`, EXPLAIN-gated, Task 10.4).
- **Required TypeScript type changes:** `EventDetailLevel`/`PostGroupingReason` (new, `packages/domain`); `eventDetailLevelEnum`/`postGroupingReasonEnum`/`eventPosts`/`eventSlugAliases`/the six new `events`/`posts` columns (new, `packages/database/schema.ts`, auto-exported via the package's existing wildcard barrel). No breaking change to any existing exported type — `EventInsertValues`, `ExtractedEventMessage`, and every GraphQL-generated type are untouched.
- **Backward compatibility and rollout notes:** `events.detailLevel` is added `NOT NULL DEFAULT 'full'` specifically so every pre-existing row (and any row inserted by code that hasn't been updated yet) gets a valid, correct-by-construction value with zero backfill risk — there is no sense in which a pre-3.6s event could ever have been a `'stub'`. Every other new column is nullable with no default, purely additive. The one genuinely behavior-changing piece is `events.postId`'s `unique()` removal, which is safe precisely because nothing in this story (or any currently-`done`/`review` story) ever creates a second event pointing at the same post — that only becomes possible once 3.6s/3.6t ship, which is the entire point of relaxing the constraint now, ahead of that need. `packages/database/seed.ts`/`seed-volume.ts` are the one piece of **existing, already-shipped code** this migration breaks outright (the new `CHECK`) — Task 9 is a required fix, not optional polish, for the system to keep working end-to-end.

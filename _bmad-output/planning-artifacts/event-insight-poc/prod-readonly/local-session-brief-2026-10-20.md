## 4. Job B — why does a subscribed moderator never get a push or an e-mail?

Facts the cloud session read from the code (**not verified on production**; check each, do not assume):

* Push goes only to users who (a) subscribe to the event's source account, (b) have `user_settings.push_notifications_enabled`, and (c) have a row in `fcm_tokens`: `apps/backend/src/lib/notifications/get-subscribers-for-notification.ts`, three inner joins, and the join is `social_media_account_profiles.account_id = <the event's source account id>`. **Lead:** BUG-059 twin profiles (a handle-keyed profile and a numeric-id profile for one account): a subscription to the twin never matches the events' numeric id.
* Nothing notifies for an event unless `notifyNewEvent` claims it: only organizer-authored, non-roundup, non-curator events at first ingestion; a stub never notifies; the claim happens **before** the send and is never retried, so an event with no subscribers at that moment is lost for good (`apps/backend/src/lib/events/notify-new-event.ts`, `process-ingestion-job.ts`).
* The token is saved only from Settings → Account → Notifications and from the onboarding step (`apps/web/src/lib/push-notifications.ts`, `notifications-content.tsx`), through the authenticated mutation `registerFcmToken`. It is **per browser or installed app**, not per user, and nothing re-registers it elsewhere in the app.

## 5. Job C — is the session lost, and is that the cause?

The owner's observation: **"I usually open the app in the browser and I am unknowingly logged out."** Hypotheses to test (cloud session's reading of the code; none confirmed):

* **H1, the global forced logout.** `apps/web/src/lib/graphql-client.ts` signs the user out on the first GraphQL response with `extensions.code = UNAUTHENTICATED` (project-context rule "Force Logout on Auth Failure"). If the access token has simply expired and a refresh would have worked, the first request still signs out a recoverable session. Also: `registerFcmToken` needs that session; a token registered while logged out is never saved.
* **H2, no session-refresh middleware.** `@supabase/ssr` ^0.12 is used with a browser client and a server client (`apps/web/src/lib/supabase/{client,server}.ts`). The active middleware is `apps/web/src/middleware.ts`, which only runs `next-intl`; a second, larger `apps/web/middleware.ts` (widget framing logic) sits beside it, and Next.js normally ignores a root-level middleware when a `src/` directory exists. Check which one Next uses (the `next build` route table, or Next's docs for the installed version), and read the `@supabase/ssr` README in `node_modules` for whether cookie refresh in middleware is required with server components.
* **H3, cookie attributes and OAuth.** Cookie names, expiry, `SameSite`, `Secure`, domain, path of the `sb-*` cookies; the OAuth callback under `apps/web/src/app/auth/`; whether the sign-in redirect lands in the same context (browser or installed app) that started it.
* **H4, separate storage between the browser and the installed app.** On iOS an app added to the Home Screen has its own storage; on Android and desktop Chrome it usually shares with the browser. If the notification opens the installed app (or the browser) in a context where the user never signed in, the user looks logged out there, and the token registered in one context is useless in the other.
* **H5, the service workers.** There are exactly two: `firebase-messaging-sw.js` (receives pushes; it never reads the session and calls no API) and `instagram-embed-cache-sw.js` (caches Instagram's `embed.js` only, scope `/<locale>/events/`). Confirm from the source that **neither intercepts navigation, `/api` or Supabase requests**. If so, say plainly: *receiving a push does not depend on the SW having the session*; what depends on the session is **saving the token** (`registerFcmToken`) and **the page the notification opens**.
* **H6, refresh-token rotation.** Two tabs, or the browser plus the installed app, refreshing the same token can trip reuse detection and revoke the session. Read the Supabase project's documented settings; you cannot read the owner's dashboard, so list what the owner must look at (JWT expiry, refresh-token reuse interval, "detect and revoke potentially compromised refresh tokens").
* **H7, the API's JWT check.** How `apps/backend` verifies the bearer token (library, audience, clock tolerance, secret rotation) and whether a verification failure is reported as `UNAUTHENTICATED` (which would trigger H1) instead of a distinct error.

What to do: read the code for H1 to H5 and H7 (cite file and line); with the owner's permission (rule 4) observe on production, **while the owner reproduces the logout in the normal way**: the names and expiry of the `sb-*` cookies and of any Supabase keys in `localStorage`, every request to Supabase auth (path and status only) and to `/api/graphql` (operation name and status only), console messages around the moment the session disappears, and whether `onAuthStateChange` reports `SIGNED_OUT` and what triggered it. If no browser tool is available, give the owner a five-step script for their browser's developer tools and ask for the redacted result. State for each hypothesis: **confirmed, refuted, or not testable from here (and what would settle it)**.

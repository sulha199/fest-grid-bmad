# Story 4.4a: Add soft-delete to the events table and extend the events resolver and moderator mutations

## Story Details

- **Epic:** 4
- **Story ID:** 4.4a
- **Status:** ready-for-dev

## Story

**As a** developer,
**I want** a soft-delete column on `events` plus resolver/mutation support to exclude, restore, and permanently delete soft-deleted events,
**So that** Story 4.4's threshold-triggered removal and Story 4.7's moderator actions have real backend support, and every other epic's event queries stop surfacing removed events by default.

## Acceptance Criteria

1. **Given** Story 1.1's `events` table, Story 4.3a's `reports` table and `submitReport` mutation, and Story 0.22's shared `activeOnly(table)` helper exist, **when** the migration script runs, **then** `events` gains only a `deletedAt: timestamp | null` column (AD-8 rule 1) — no separate `status` enum; `null`/absent means active, matching every other AD-8-bound table (`favorites`, `calendarAdditions`, `userLocations`).
2. **And** Story 1.3a's events resolver filters via `activeOnly(events)` (Story 0.22) by default on every query — not a hand-written `status`/`isNull` check; a moderator-only argument (guarded by `requireModerator`, Story 0.17) allows including soft-deleted rows, backing Story 4.7's list view.
3. **And** `submitReport` (Story 4.3a) is extended so that when a `cancelled`-reason report brings the count of unique reporters for an event to a configurable threshold (default 3) within a configurable window (default 7 days), the mutation sets that event's `deletedAt=now()` synchronously in the same call — no separate scheduled job is introduced, since the per-report check is cheap at write-time.
4. **And** a moderator-only `restoreEvent(id: ID!, action: SoftDeleteAction!): Event!` mutation is exposed per AD-8 rule 4's shared-enum shape (guarded by `requireModerator`, Story 0.17) — only the `RESTORE` direction has a live caller (Story 4.7), matching the `deleteUserLocation` precedent of an asymmetric-but-compliant mutation; the resolver still validates both transitions server-side and throws `INVALID_STATE_TRANSITION` on mismatch.
5. **And** a moderator-only `deleteEventPermanently(id: ID!): Boolean!` mutation is exposed (guarded by `requireModerator`, Story 0.17), backing Story 4.7 — this performs a genuine hard `DELETE` on the `events` row (and cascades to dependent `schedules`/`corrections`/`reports`/`favorites`/`calendarAdditions` rows), which is a **documented, named exception to AD-8's "no hard deletes on bound tables" rule** (Architecture Spine AD-8, "Accepted hard-delete exception") rather than a soft-delete/restore-cycle mutation — it is irreversible and distinct from `restoreEvent`.

**Note:** This story exists because of Gate 1 and Gate 3 (`story-split-gate.md`), surfaced by the Epic 4 readiness sweep (`bmad-epic-readiness-check`). This is also a Gate 3 cross-epic finding: the new `deletedAt` column redefines what "visible" means for every epic that already reads events through Story 1.3a's resolver (Epic 1's listing/search/filter, Epic 2's favorites via Story 2.1a, Epic 3's feed via Story 3.7) — Story 1.3a carries a forward-reference `Note:` pointing here, since the filter itself can't be implemented until this story's migration exists. Classified as a shared data-ownership gap originating in Epic 4 (matching the Story 1.1/3.3a precedent of scoping originating tables to the epic that first needs them, not Epic 0), positioned immediately before Story 4.4.

**Correction (2026-08-11, Epic 4 readiness re-sweep):** The original AC invented a parallel `status` enum and a bare-boolean `restoreEvent`/`deleteEventPermanently` pair, diverging from AD-8 rule 1 (single `deletedAt` field) and rule 4 (shared `SoftDeleteAction` enum shape) — re-forking the exact "each resource invents its own bespoke soft-delete mechanism" problem AD-8 rule 2 and Story 0.22's `activeOnly()` helper exist to close. Corrected to use `deletedAt` + `activeOnly(events)` and the rule-4 mutation shape for `restoreEvent`. `deleteEventPermanently` was confirmed (via `AskUserQuestion` with the user) to stay a genuine hard delete, now recorded as an explicit named AD-8 exception rather than an unremarked conflict.

**Depends on:** Story 0.17, Story 1.1, Story 1.3a, Story 4.3a.

### Partial Index Retrofit Decision

`events` will gain a `deletedAt` filter applied on effectively every public `events`/`event`/`eventBySlug` call — the app's highest-traffic query path. AD-8 rule 3 and `project-context.md`'s indexing rule call for partial indexes scoped to active rows on soft-delete-bound tables' hot lookup columns, but epics.md's AC1 doesn't explicitly require one, and it requires the AD-8 rule 3 `drizzle-kit` `WHERE`-clause hand-edit workaround five times (once per existing `events` index) rather than once. Presented to the user via `AskUserQuestion` with the concrete tradeoff: a single new standalone partial index on `deletedAt` alone would rarely be selected by the query planner over the existing, more selective column indexes (near-no-op); retrofitting the 5 existing indexes (`event_name_idx`, `event_types_idx`, `event_categories_idx`, `event_location_idx`, `event_post_id_idx`) to carry `WHERE deleted_at IS NULL` is the only option that delivers a real benefit (the filter is applied for free within the same index scan those queries already use), at the cost of a larger diff and 5x the hand-edit surface. **User chose to retrofit all 5 existing indexes** (Task 1) rather than skip indexing or add a single low-value standalone index. The separate `postIdUnq` unique constraint on `events.postId` is explicitly **not** touched by this retrofit — see Task 1's note.

### includeSoftDeleted Semantics Decision

AC2's "a moderator-only argument... allows including soft-deleted rows" doesn't specify whether that means "return both active and soft-deleted together" or "return only soft-deleted" — the latter is what Story 4.7's future moderator review list will actually want, but Story 4.7 doesn't exist yet and its exact query/filter shape isn't pinned down. Presented to the user via `AskUserQuestion`: bypass-the-filter semantics (matches the literal AC wording, defers the exact moderator-list shape to Story 4.7 when it's created — mirroring `epic-4-readiness.md`'s own explicit precedent for Story 4.8's `isFromSubscribedAccount`-style field: "build the exact shape in the consuming story, not speculatively here") vs. only-soft-deleted semantics (directly usable by Story 4.7 as-is, but locks in an assumption about that story's UI/query needs before it exists). **User chose bypass-the-filter semantics** (Task 2) — `includeSoftDeleted: true` simply removes the default `activeOnly(events)` filter; it does not expose any new field to distinguish which returned items are soft-deleted (e.g. no `deletedAt`/`isDeleted` added to the `Event` GraphQL type in this story). Story 4.7 will decide its own precise filtering/display needs when it is created.

### deleteEventPermanently Precondition Decision

Unlike `restoreEvent`, which validates a `DELETE`/`RESTORE` state transition, `deleteEventPermanently`'s epics.md AC5 text has no analogous precondition language ("a moderator-only `deleteEventPermanently` mutation is exposed... this performs a genuine hard `DELETE`"). This story implements it as callable regardless of the target event's current `deletedAt` state (only `NOT_FOUND` is checked) rather than inventing an unstated "must already be soft-deleted first" requirement — a literal reading of the AC, not an independent design tradeoff, so not raised via `AskUserQuestion`. If Story 4.7's own UI design later wants to restrict permanent deletion to already-soft-deleted events, that is that story's own scope to add (e.g., client-side gating on the Moderator Items page), not a backend precondition this story invents speculatively.

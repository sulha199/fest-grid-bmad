# Story 3.6s: Extract multiple events per post with grouping rules

## Story Details

- Epic: 3
- Story ID: 3.6s
- Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a subscriber,
I want a post that advertises several distinct events to produce several events, and a single event with several schedules to stay one event,
So that events are neither merged nor needlessly split.

## Acceptance Criteria

1. **Given** PRD §3.7 "Multi-Event Posts", **when** extraction runs, **then** the Gemini response is `events[]` (each with its own `schedules[]`, `organizerHandle`, per-event `expectedScheduleNames`) plus post-level `groupingReason` (`single-event | program-lineup | dependent-stages | separate-events | roundup`), `minEventCount` and `skippedItems`; `hasFaceImage`/`faceImageCount` stay at the payload root (a forward-compatibility constraint only — see Dev Notes, Story 3.6m has not shipped these fields yet); `groupingRationale` is requested but never persisted.
2. **And** the prompt encodes the ordered grouping rules (strong signals; two weak signals; bounded window; dependent stages and registration windows are schedules) and the roundup rules (event per item only with a readable date **and** location — items missing either go to `skippedItems`; per-post cap, default 10, configurable; reduced confidence for a missing location applies only to non-roundup separate events, AD-30 Rule 5).
3. **And** the per-event schedule schema carries `applicableDaysOfWeek` (BUG-026) and any other schedule field shipped at that time; an output cap is set for the response.
4. **And** timezone inference (3.6a), private-contact classification (3.6i) and performer-leakage guards (3.6j) run **per event**.
5. **And** `poc-ingestion-preview.ts` handles N events, and the four reference posts are regression fixtures: each is run several times and the grouping decision must match on every run.
6. **And** the AJV schema (`extracted-event.schema.ts`) validates the new shape; the extraction call count per post stays exactly one.
7. **(Amendment, readiness-sweep correction, 2026-10-01)** The extraction call (`callGemini` → `callGeminiGenerateContent`) has no timeout today, and the Epic 0 guarded vendor-call wrapper (Story 0.i2a/0.i2c) cannot be built yet (no Architecture Spine decision exists for it). This story carries a **minimal inline guard** instead: an `AbortController`-based request timeout on the extraction call, and an explicit response-size cap (`maxOutputTokens`), with a timeout surfaced as a **retryable job failure** (the exception propagates out of `processAiJob`, never swallowed), never a silent hang. A unit test covers both. Story 0.i2c, when it later lands, supersedes and deletes this guard rather than stacking on it.
8. **(Resolved by this story, interim production behavior)** Because Story 3.6t (per-event `extractionOrdinal` and one-queue-message-per-event ingestion) does not exist yet, `process-ai-job.ts` must not enqueue more than one message per post: doing so today would make every event default to `extractionOrdinal` 0 at insert time (Story 3.6r's `insertEventWithPrimaryPost`), so only the first event would survive `onConflictDoNothing` and the rest would be silently dropped — worse than today's "all schedules merged into one event" behavior. **Decided with the user (`AskUserQuestion`, this session):** when extraction yields more than one event, `processAiJob` logs a structured warning (post id, `groupingReason`, event count) and returns **without enqueueing or marking the post extracted** — the same retriable pattern the existing AJV-validation-failure branch already uses. Single-event posts (the large majority) flow through the existing one-message pipeline completely unchanged. This deferral is removed the moment Story 3.6t ships.
9. **(Resolved by this story, regression-fixture strategy)** **Decided with the user (`AskUserQuestion`, this session):** the four reference posts are tested two ways, not one — (a) a fast, deterministic, CI-included test replaying a **committed, one-time-captured real Gemini response** per fixture through AJV validation and the per-event guard pipeline (zero cost, no live call, catches parsing/wiring regressions on every `pnpm test` run); and (b) a new opt-in **live** test, gated exactly like this codebase's existing `build-gemini-request.live-carousel.test.ts` (`RUN_LIVE_GEMINI_TESTS=true` + a real key, skipped by default, never part of CI), that calls the real Gemini API against all four posts **repeatedly (N runs per post, default 3, overridable with `CC024_LIVE_RUNS`) and asserts `groupingReason`/event count match the expected values in `cc-024-reference-posts/README.md` on EVERY run — one divergent run fails the test** (the proposal's prototype saw Vifation collapse to one event in one of two runs, so a single run per post would miss exactly the instability this test exists to catch) — run manually to catch future prompt-drift. Both tests are required deliverables of this story.

**Depends on:** Story 3.6l, Story 3.6r (both `review`, build-against-review is the standing project rule).

This story is that deferred extraction-side half. Reusing the existing enum (rather than inventing e.g. full weekday names) is what keeps the two ends of this one logical feature from drifting.
- **Why `organizerHandle` is threaded onto `ExtractedEventMessage` now even though nothing in this story reads it back.** AD-30 Rule 5 requires it be "captured at extraction time" specifically because Story 3.4o nulls a `CURATOR_GUIDE` post's caption **after** extraction — by the time Story 3.6v's matching pass would want to read an organizer handle, the caption may already be gone. Shipping the field on the message now (even though no consumer exists until 3.6v) is the same "infrastructure ahead of its first caller" pattern Story 3.6r used for its promotion function and `event_slug_aliases` table — not speculative scope-creep, but the only point in the pipeline where this value is still recoverable at all.
- **The `maxItems`-on-Gemini-schema-but-not-AJV-schema split (Task 2.2 vs 3.2) is the key defensive-design decision in this story's schema work.** A hard AJV cap would convert "the model ignored the cap" into "we lose the entire post," which is a strictly worse failure mode than "we keep the first N and log a warning." This mirrors every other best-effort-degrade pattern already in this pipeline (image-fetch failures, location-resolution failures, backfill failures) rather than introducing a new all-or-nothing failure mode.
- **`resolveAccountAndLocations`/`resolveScheduleTimezones` need zero signature changes.** Both already operate on exactly one `schedules: GeminiSchedulePayload[]` + one top-level `location`/subscriber list per call — the only change needed is calling them once per event inside `process-ai-job.ts`'s new loop (Task 7.3), each time with that event's own `schedules`/`location`. This was confirmed by reading both files in full during this story's creation; do not refactor either function's signature to accept an events array — that would be unnecessary surface-area growth for no behavioral benefit.
- **GeminiTimeoutError propagation is the one part of `adapter.ts` this story must get exactly right.** `callGemini`'s retry loop treats `GeminiRateLimitedError`/`GeminiInvalidKeyError` as "try another key," looping rather than throwing. `GeminiTimeoutError` must take the same path as today's `GeminiUnknownError` — an unconditional re-throw, no key exclusion, no retry — because a timeout says nothing about whether the *key* was bad, only that *this specific call* took too long; retrying immediately with another key would not fix a genuinely oversized/slow request and would burn a second key's quota for no benefit. Letting it propagate out of `processAiJob` entirely (rather than catching it there) is what makes it a "retryable job failure" (AC7) — the SQS-triggered Lambda invocation fails, and the message becomes eligible for standard queue redelivery, exactly like any other unhandled exception in this Lambda today.
- **Verify the `@google/genai` SDK's actual timeout/abort support before committing to the `AbortController` path (Task 5.2).** This story's creation did not independently verify whether `^2.14.0`'s `ai.models.generateContent(...)` call accepts a `signal`/`AbortSignal` option in its request config — the dev agent must check this directly against the installed version's TypeScript types (or its changelog/README) rather than assuming. If it is not supported, the `Promise.race` fallback is an acceptable, explicitly-documented interim (the Lambda itself stops waiting even if the underlying HTTP call is not truly cancelled) — record which path was actually taken in Dev Agent Record, since it affects whether a timed-out call also wastes the full quota cost of a completed-but-unused generation server-side.

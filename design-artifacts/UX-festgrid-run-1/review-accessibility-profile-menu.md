# Accessibility Review — FestDaily Profile Auth Menu

**Reviewed:** EXPERIENCE.md (Information Architecture § Profile item — authentication states, lines 50–70; Component Patterns § Global Navigation, lines 104–110; Responsive & Platform, lines 140–150; Accessibility Floor, lines 152–162) and DESIGN.md (`components.nav.*` tokens, lines 73–89; `components.modal`, lines 59–61) as of the 2026-08-05 draft.

## Overall verdict

The spec gets the big structural things right (single persistent `<nav>`, `aria-current`, focus-ring/active-indicator separation, tooltip hover/focus parity) but the new Profile-menu addition has a wrong default ARIA pattern (menu/menuitem semantics implied for what is fundamentally a list of page links), an incorrectly-specified focus trap on a non-modal disclosure, and several unstated behaviors (login modal's dialog a11y floor, bottom-sheet touch dismissal, focus-return branching, and Profile's interaction at the icon-only rail tier) that need to be pinned down before this is implementation-ready. None of these are cosmetic — they change what markup and keyboard behavior get built.

## Findings

- **critical** No ARIA pattern is specified for the authenticated dropdown/sheet trigger and its contents, and the default choice a team reaches for here (Shadcn/Radix `DropdownMenu`, which assigns `role="menu"`/`role="menuitem"`) is the wrong pattern per WAI-ARIA APG: menu/menuitem is reserved for widgets that mimic desktop application command menus, not for groups of navigation links. Ten of this menu's eleven rows (all except Log Out) are plain navigations to full pages. (EXPERIENCE.md lines 55–70, 110; DESIGN.md `profile_menu`/`profile_menu_item` tokens, lines 85, 88). *Fix:* Spec the trigger explicitly as `aria-haspopup="true"` + `aria-expanded` on a `<button>` (not `aria-haspopup="menu"`), and the popup contents as a plain list of links (`<ul><li><a>…</a></li></ul>`), with `Log Out` as a real `<button>` in that same list — not `role="menu"`/`"menuitem"`. If the team uses Radix's `DropdownMenu` primitive for convenience, call out that it must be swapped for `Popover` + a native list, since `DropdownMenu` hard-codes menu/menuitem roles and Home/End/typeahead/roving-tabindex behavior meant for command menus.

- **critical** "Traps focus while open" is stated for the authenticated menu (EXPERIENCE.md line 110), but a focus trap is the wrong behavior for a disclosure of navigation links — it fights normal Tab-order expectations for keyboard/screen-reader users and is explicitly not part of the APG menu-button (or disclosure) pattern; trapping is a dialog/modal-only requirement. *Fix:* Remove the focus-trap requirement from the authenticated dropdown/sheet. Tabbing past the last item (Log Out) should close the menu and move focus to the next focusable element after the nav in DOM order, same as any other disclosure. Escape should still explicitly close it and return focus to the trigger. Keep focus-trap language exclusively for the login modal (see next finding), where it is correct.

- **high** The login modal's dialog accessibility floor is never stated. EXPERIENCE.md line 54 only says it "opens a login modal (`{components.modal}`)"; the one behavioral sentence covering dismissal (line 110) bundles the login modal and the authenticated menu together generically ("dismissed on Escape and on an outside click/tap … returns focus to the Profile nav item on close") without stating `aria-modal`, `aria-labelledby`, initial-focus placement, or the (correct, here) focus-trap requirement. DESIGN.md's `modal` token (lines 59–61) is purely visual (`overlay`/`dialog` Tailwind classes) with no ARIA notes. (EXPERIENCE.md lines 54, 110; DESIGN.md lines 59–61). *Fix:* Add an explicit modal a11y floor, mirroring the style of the existing Global Nav "Accessibility Floor" section: `role="dialog"` + `aria-modal="true"`; `aria-labelledby` pointing to a visible heading (e.g. "Log In"); initial focus placed on the dialog's first focusable control (or the `GoogleLoginButton` itself) on open; a real focus trap engaged while open; Escape and backdrop-click both dismiss and return focus to the Log In nav trigger. Since `{components.modal}` is reused elsewhere (e.g. the event-detail modal in Interaction Primitives), consider stating this once as a shared modal floor rather than only for this instance.

- **high** Focus-return on close doesn't distinguish the three cases it actually needs to: (a) Escape / outside dismiss, (b) activating a navigation item (Profile, Locations, Subscribed Accounts, API Keys, Notifications, Reports, Moderator Items), and (c) Log Out. The spec states one rule for all — "returns focus to the Profile nav item on close" (EXPERIENCE.md line 110) — which is only correct for case (a). (EXPERIENCE.md line 110). *Fix:* State explicitly: Escape/outside-dismiss → focus returns to the Profile trigger. Activating a navigation item → menu closes and focus follows the app's standard route-change focus management (e.g. moves to the destination page's main heading/landmark), not back to the nav item that's no longer relevant to the new page — otherwise a screen reader user gets no indication navigation occurred beyond a URL change. Log Out → focus returning to the trigger is reasonable since the same DOM node persists (now relabeled "Log In"), but call this out as the deliberate exception, and if Log Out ever redirects to a different route, apply the same destination-page rule as other items instead.

- **high** Ambiguous/contradictory touch behavior for the Profile item at the icon-only rail tier (768–1279px). The Responsive & Platform table and the "Touch on the icon-only rail" bullet describe a single tap as "navigates and flashes label" for that tier's items generically (EXPERIENCE.md lines 106–107, 147), but Profile doesn't navigate on tap — it opens a menu (line 55). The spec never carves Profile out of the generic tap-to-flash rule, so it's unclear whether a touch user's first tap on Profile flashes the label only (requiring a second tap to open the menu, inconsistent with mouse/keyboard parity) or opens the menu immediately (inconsistent with the stated tier-wide rule). Separately, the existing "opening either while the other nav's tooltip is showing dismisses the tooltip first" bullet (line 110) only covers cross-item conflicts — it doesn't say what happens to Profile's *own* hover tooltip when its *own* menu opens via mouse click while the cursor stays stationary over the icon (CSS `:hover` persists independent of focus, so "dismisses on Escape or focus-out" per line 106/160 may not fire). *Fix:* Explicitly exclude Profile from the generic tap-to-flash behavior at the 768–1279px tier — state that tap (like click) opens the menu directly, since Profile's target is a disclosure trigger, not a navigation link. Also add a rule that any interaction (click, tap, Enter, Space) which opens the menu dismisses that same item's own tooltip immediately, independent of hover/focus-out state, not only the already-stated cross-item case.

- **medium** No explicit dismiss affordance for the bottom sheet beyond outside-tap and Escape. Escape isn't reliably producible on pure-touch devices (no keyboard), and once a screen-reader user's touch focus is inside the sheet, finding "outside" content to tap is not a discoverable dismissal path. (EXPERIENCE.md line 110; DESIGN.md `profile_sheet` token, line 86). *Fix:* Add a visible, always-reachable close control (e.g. an "X"/"Close" element as the first or last focusable item in the sheet) in addition to outside-tap, and honor the Android back gesture/button to close the sheet. Optionally add drag-down-to-dismiss as a touch enhancement, but it must not be the only non-Escape path.

- **medium** `profile_menu_item` (`"flex items-center gap-2 rounded-md px-3 py-2 text-sm hover:bg-muted focus-visible:bg-muted min-h-11"`) sets a minimum height (44px) but no minimum/full width, unlike the primary nav's `item_hit_area` token which explicitly pairs `min-h-11` with `min-w-11`. Short-label rows (e.g. "Reports", "Log Out") risk a tappable region no wider than their text/padding rather than spanning the menu/sheet, while "Subscribed Accounts" — the longest label — will naturally be wide. This isn't a strict WCAG 2.1 AA failure (target size is AAA-only at 2.1; the minimum-size SC is WCAG 2.2) but is a real touch-reliability gap given the token's own established width precedent elsewhere in the same file. (DESIGN.md line 88, cf. line 78). *Fix:* Add a full-container-width rule (e.g. `w-full`, block-level) to `profile_menu_item` so every row's tappable region spans the full `profile_menu`/`profile_sheet` width regardless of label length.

- **low** Divider placement produces two adjacent dividers with nothing between them for regular (non-moderator) users. Menu order is: …Reports, *divider*, Moderator Items (conditional), *divider*, Log Out (EXPERIENCE.md lines 64–68). When Moderator Items is absent, the two dividers sit back-to-back before Log Out. (EXPERIENCE.md lines 65–68). *Fix:* Pair the second divider with the conditional item — render both together only when `role === MODERATOR` — so regular users see exactly one divider directly before Log Out, matching the "absent entirely, not disabled" intent already stated for the link itself.

- **informational — no issue found** The "absent entirely (not disabled/greyed) for regular users" choice for Moderator Items is the correct accessible pattern and matches APG guidance: a disabled item would still be exposed to AT as a named, focusable-or-announced control with no explanation of why it's unusable, which is worse than simply not being in the DOM. No change needed here.

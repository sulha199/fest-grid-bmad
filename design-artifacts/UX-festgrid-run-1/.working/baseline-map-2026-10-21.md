## A. What the spines already specify

### A0. Cross-cutting: card anatomy, badge row, density (constrains all four areas)

Three card families; all `event_card_*` tokens were moved out of DD into EC (DD:121-131). Event card is one focusable region (`<a>`/`<button>` RootTag, `EventCard.tsx:318`).
- **Masonry card** (EX "Masonry EventCard: Date Box, TILL Badge, and Status/Nearby Badge Row" L191-223; EC `event_card_masonry` L262): top row = date box + thumbnail (EC:300-341), then `caption` `"p-3 flex-1 flex flex-col gap-2"` (EC:280) holding, in this order: `badge_row`, title, venue. `badge_row`: `"flex items-center gap-1.5 flex-wrap"` (EC:299; code `EventCard.tsx:533`). Title `text-sm font-bold ... line-clamp-2` (EC:281). Venue `"text-sm text-muted-foreground text-center break-all line-clamp-1"`, no icon, centered (EC:298). Card keeps `overflow-hidden`; outer `w-full`, no max width (EC:277). Masonry is the only family with a reserved image slot (EX "Reserved space, not reflow" L509).
- **Calendar Row Card** `event_card_compact` (EC:36-95; EX L225-247): date box | content | thumbnail+favorite. `content` = `"flex-1 min-w-0 flex flex-col gap-1 justify-center"` and reuses status and nearby badges as-is (EC:90); title `text-sm font-bold line-clamp-2` (EC:91), venue `text-xs text-muted-foreground truncate`, 1 line (EC:92; code `line-clamp-1 break-all`, `EventCardCompact.tsx:220`). Badge span `flex items-center gap-1.5 flex-wrap mt-0.5` (`EventCardCompact.tsx:227`).
- **Calendar Grid Item** `event_card_calendar_grid_item` (EC:110-240; EX L249-275): no date box; title wraps freely, venue `line-clamp-2` (EC:235-236). Nearby badge sits in `side_stack` (multi-day, EC:237) or `location_row` (single-day, EC:240); a status badge appears **only** for `inHours`/`endsAt`, under venue, never in `side_stack` (EC:202-211). It has the fewest badge slots of the three.
- **Order of badges**: status, then repeat, then nearby (EC:299; EX:304 "Placement is per card family"; AD-24 header 1267-1271 reserves the insertion point). On compact and grid-item cards the repeat icon joins the **leading icon row before the title**, not the badge row (EX:305).
- **Max badges / truncation of badges**: no rule exists. Masonry `badge_row` simply wraps (`flex-wrap`); badge bases are `shrink-0` with no max-width/truncation (EC:635-638, 658).
- **Category/type badge removed** from all three families; the same slot shows only the nearby badge, `<8km`, omitted entirely otherwise, "no placeholder" (EC:650-657; EX:223; ML:74).
- **Status badge** (`event_card_status_badge`, EC:599-638): 8 states; neutral `bg-muted text-muted-foreground`; emerald-600 for `happeningNow` (label "Now"), amber-700 for `endsAt`/`endsToday`, sky-600 for `inHours`; deliberately not the review-outcome `status_badge` palette (EC:601-606).
- **Nearby badge** (EC:639-665): `bg-secondary text-secondary-foreground`, `Navigation` icon `w-3 h-3`, text = computed distance (>=2km no decimal, <2km one decimal). Self-gates on `distanceKm < thresholdKm` (default 8) in the primitive (AD-24 Rule 2, 1295-1304; `EventCardMediaPrimitives.tsx:581-612`). Never interactive, no independent focus stop (AD-24 Rule 4, 1312-1315; EX:507). Consumer owns badge-row ordering and spacing (AD-24 Rule 3, 1305-1308).
- **Accessibility floor for badges** (EX "Masonry EventCard Badge Row" L499-509): text never below 11px (503); favorite font >= TILL font (504); never distinguished by color alone, each badge needs unique self-describing text and nearby also an icon (221, 506); badges are non-interactive supplementary metadata read in DOM order inside the card's single focusable region (507). Skeletons must mirror real component shape (project-context:145).
- **i18n**: `next-intl`; enums resolve through a namespace keyed by exact enum member (project-context:174); en.json and id.json must define identical namespaces and keys (`apps/web/locales/locales.test.ts`). Existing namespaces: `EventCard` (status*, tillLabel, favoriteToggle; en.json:546), `EventDetailsPage`, `PostCollectionPage`, `DuplicateEventsPage`, `ModeratorItemsPage`, `ModeratorToolsPage`, `ModeratorAccountsPage`, `UserMenu`, `NearbyFilter`, `AmbientLocationBanner`, enum namespaces `EventType`, `EventCategory`, `DayOfWeek`, `AccountType`, `DefaultLocationChangeStatus`, `ReportReason`, `ReportStatus`. A gazetteer area label is data, not an enum key (AD-39 Rule 6, 3904-3906).
- **Layering**: new popovers/dialogs use named tiers (`OVERLAY_MODAL_Z`, `packages/ui/src/core/overlay-z.ts`); DD `z-50/z-40` literals predate AD-33 (DD:9-13).

## C. Conflicts and gaps

**Place, area, precision (card and detail)**
- **C1. Nearby threshold, stale text.** EX:195 still says the nearby badge is "conditional on `distanceKm <= 5`"; EX:223, EC:646, AD-24 Rule 2 (1295-1301), code default `thresholdKm = 8` and PRD:41 (amended) all say 8 km. Fix EX:195; do not introduce a second threshold.
- **C2. Nearby needs a precision gate the primitive does not have.** PRD:41 and AD-39 Rule 5 (3891) say Nearby is a pin-only claim (EXACT only). EC:646-657/EX:223 gate on distance alone, and `EventCardNearbyBadge` self-gates only on `distanceKm` (`EventCardMediaPrimitives.tsx:600`). The UX rule must state "caller passes `distanceKm` only for a verified pin" (or a new prop), since AD-24 Rule 2 forbids consumers re-deriving the threshold.
- **C3. Area badge versus the nearby slot.** The nearby badge "replaces" the category badge and renders nothing when absent (EC:650-657). The area badge (PRD:37; AD-39 Rule 6, 3900-3903: "whenever precision is not EXACT") is mutually exclusive with Nearby by construction (EXACT vs not), so it can take the nearby slot; but an EXACT card in the viewer's area can still carry status + repeat + nearby + "in your area". No spec for position, icon, or max count of the new elements on each family. Grid-item cards only have `side_stack`/`location_row` slots and a restricted status badge (EC:202-211).
- **C4. No "max badges" or priority rule exists.** Masonry wraps freely (EC:299); the compact row appends a wrapping span (`EventCardCompact.tsx:227`); grid-item has fixed slots. With status, repeat, nearby, area badge, "in your area", "part of", "+N more", "closest matches"/"no exact location" and the stub "details coming" copy (EX:423) a card can exceed any limit the docs imply. A max count with a drop order is needed, per family.
- **C5. Interactive chip versus the non-interactive badge rule.** EX:507 and AD-24 Rule 4 (1312-1315) fix badges as non-interactive with no focus stop inside one `<a>/<button>`. PRD:371/372 ("part of …" is a link; "+N more matching") require something clickable. A link nested in the card's RootTag is invalid; `EventCard.tsx:368` already notes the favorite control is a DOM sibling of RootTag for that reason. A chip/link needs the same sibling treatment and its own focus stop and 44px target, which contradicts the "no independent focus stop" floor.
- **C6. Map link contradiction.** PRD:383: AREA/UNKNOWN has "no map link"; the event detail "always shows the place text". EX:417 says location "always renders as a map link", and `LocationLink` always links (search fallback). New rule needed: plain text, no link, for AREA/UNKNOWN; the search-link fallback is retired for those.
- **C7. Placeholder text.** `'Location not specified'` stays in `events.location` (AD-39 Rule 4, 3867-3868; readers must use area status). Card venue line and detail must not render it as a place; EC:298 venue shows whatever string is given.
- **C8. UNKNOWN has no area label.** AD-39 Rule 6 shows the badge for "not EXACT" (incl. UNKNOWN) but `areaLabel` does not exist for UNKNOWN; PRD:383 says the card is "marked as having no exact location", wording at UX. The same phrase "no exact location" is also the radius-filter partial-lane label (PRD:52, 387; AD-39 Rule 5, 3891-3893) for AREA events that already carry an area badge: one phrase, two meanings (event state vs result lane).
- **C9. Lane labels have no list pattern.** "closest matches" (PRD:38, 387; AD-39 Rule 5, 3877-3883) and "no exact location" follow strict matches in the same query. Discovery is a flat masonry `GridContainer` with shortest-column placement and `key={itemIndex}` children (DD:42; `EventListView.tsx:23`); no full-width divider/heading item is specified, and per-card labels would repeat on every card of the lane.
- **C10. Area filter control is unspecified.** EX:86 lists only type/category triggers; the radius filter has no EX entry (A3); nothing on where "in Sleman" lives, how an area is picked from a gazetteer, whether it can combine with the radius filter and the Temporal Filter row (EX:316), its URL state (`nuqs`, project-context:161), active/clear states.
- **C11. "In your area" depends on a viewer area the UX does not model.** Area comes from the saved location or, if allowed, the current location; a visitor with neither gets no label (PRD:347; AD-39 3886-3889). The ambient location ask and its copy ("Enable nearby distances", DD:162) are about distances and silently omit on denial (EX:402); whether that ask also covers the label, and how an anonymous visitor learns why there is no label, is open.
- **C12. Long gazetteer names.** Badge bases are `shrink-0` with no max width (EC:635-638, 658); a name like a province or regency can overflow the 175px masonry card, the compact content column or the 174px day cell. Need truncation, a title/aria text, and a localized-name rule (data field, not enum namespace).
- **C13. Non-color cue for the area badge.** EX:221/506 require unique text plus, for nearby, an icon. The `Navigation` icon was chosen to differ from the caption `MapPin` (EX:221), but the masonry and compact venue lines no longer carry a MapPin (EC:288-298). The area badge needs its own icon/text so it is not confused with nearby (same indigo `bg-secondary`?) or the neutral status badge.
- **C14. Curator audience area is not a location.** `AccountLocationField`/`SetDefaultLocationDialog` (EX L163-172) edit a geocoded place with a Pending Review flow; the audience area is a gazetteer area, never geocoded (PRD:389), applies immediately, with the moderator's edit being the review, and triggers a one-time re-check of the account's unknown-area events. Needs an area picker, a source/state display (unresolved, proposed by model/posts, set by moderator) and feedback after save. PRD:388 `[ASSUMPTION]` hides or disables the Default Location control for curators; X2 Q6 shows `audience_area_source` is `model|moderator` in one place and `model|posts` in another.
- **C15. Calendar surfaces.** Collapse is Discovery-only, but whether the area badge, "in your area" and "part of" appear on the calendar cards, favorites, feed is unstated (AD-39 Rule 6 says "the list card"). The 174x128 day cell and the banded grid (EX L345-361) leave little room.

**Groups and duplicates**
- **C16. Related Events versus group section.** Related Events: by shared post, heading "Events from [post/account]", ended hidden, ordered by end/start, cap 5 then a collection page, empty = hidden, compact card unchanged (EX:417). Group section: by group, "part of <group>", **active** members (series by place and date, programme by activity), **every member reachable**, separate on-demand query, concurrent series with distance (AD-36 Rule 15, 3093-3097). Conflicts: no group collection page exists in IA to back a "See all" (cap 5 would break "every member reachable"); the compact card "unchanged" rule cannot show place/distance per member; dormant groups (one active member) and archive members have no display rule; loading/aria-busy and heading levels are only defined for Related Events; order of the two sections on one page is open.
- **C17. Two-state Discovery card.** Until the Discovery backend gate (AD-36 Rule 13, 2990-2994) ships, every occurrence lists with a "part of …" label (PRD:40, 371); afterwards a series shows one cover plus a count. The same card needs both states, and the count means **matching** members only (3028-3031), so the card must not read as the series total.
- **C18. "+N more" naming collision.** DD:94 `more_link` is the superseded calendar overflow link; EX banded grid has "Show more" and "Showing X of Y" (EX:353). - **C23. Grouped event shown to users after an automatic merge.** A user's favorite or calendar entry may silently move to the surviving event (X1 B4/B6); no user-facing message is specified.

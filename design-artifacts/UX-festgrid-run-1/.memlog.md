- (decision) Soft Delete with Undo state pattern revised (EXPERIENCE.md State Patterns): delete now commits immediately at Trigger (real backend delete call at T+0), not deferred to unmount/navigate-away. Reason: deferred-commit meant closing the browser tab (not navigating within-app) silently skipped the commit entirely -- unmount never fired, so the item was never actually deleted despite the user believing it was. Applies to all Soft-Delete-with-Undo surfaces (Saved Locations today; API Keys/Subscriptions future) EXCEPT Favorites/event-list, which already implements immediate-commit informally (toggleFavoriteAsync fires at trigger, undo re-toggles) and is the precedent this revision generalizes, not a new exception.
- (decision) Soft Delete with Undo timing: undo toast/popup duration is 6000ms (chosen over sonner's ~4s default since a real backend delete now finalizes when it expires, not merely a notice; chosen over 10s/no-timeout to avoid multiple stacked toasts on rapid successive deletes). Timer pauses on hover/focus (WCAG 2.2.1 timing-adjustable). New DESIGN.md token: components.notification.undo_duration_ms.
- (decision) Soft Delete with Undo full state sequence: T+0 (Trigger) fires the real delete mutation immediately AND optimistically flips the item to its greyed-out/pending visual in the same moment (does not wait for the mutation response). If Undo is clicked within the 6s window, a separate reverse/restore mutation commits and the item reverts to normal. If the toast times out unactioned, the item is removed from the client's already-loaded list data with NO further network call (the delete already committed at T+0) -- chosen over a server refetch to avoid an extra round trip and avoid disrupting scroll position/pagination state on infinite-scroll lists (Locations today; API Keys/Subscriptions future).
- (decision) Soft Delete with Undo failure path (new -- prior spec had none, since prior deferred-commit design had no optimistic-before-confirmation window): if the T+0 delete mutation itself fails, the item reverts from greyed-out back to its normal visible state, the undo toast/timer is cancelled, and a distinct error toast is shown -- since nothing was actually deleted, there is nothing to undo.

- (decision) Mobile day-list drops the desktop grid's maxEventsPerDay cap + '+N more' popover entirely -- always renders every schedule for a visible day inline, uncapped. - (decision) Visual treatment: a repeated small badge ('Day X of N' + a calendar-range icon), not a connecting bar/line. Reason: the desktop grid's continuity cue (suppressed border/rounding between adjacent day columns, WeeklyCalendarView.tsx multiDayRoundingClass) only works because those columns are directly touching; the vertical list's day-rows are each preceded by their own day-header, breaking DOM/visual adjacency between a multi-day event's consecutive segments -- neither that trick nor a literal connecting line is implementable without new absolute-positioning/measurement machinery, and no existing packages/ui/src/core primitive (PageContainer/GridContainer/WeekPicker/BlockingLoader/MultiSelect/etc.) provides timeline/connector layout. Badge numbering (X = calendar-day offset from the schedule's true eventStartDate, N = total inclusive span length) is computed from the schedule's actual date range, not clamped to the visible week -- consistent with how isFirstSegment/isLastSegment already work today.

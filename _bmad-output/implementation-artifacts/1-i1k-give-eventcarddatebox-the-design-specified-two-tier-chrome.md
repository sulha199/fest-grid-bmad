## Story

As a developer,
I want the shared `EventCardDateBox` primitive (`packages/ui/src/features/events/EventCardMediaPrimitives.tsx`) restyled from its shipped single-line `text-xs` box into DESIGN.md's two-tier stacked chrome (a small uppercase month/weekday line over a large bold day number) plus an amber `till_label` corner tag reusing `event_card_till_badge`'s classes — and the shared AD-15 icon-scale token recalibrated to match — so both of the primitive's real consumers (masonry's `EventCard.tsx` and the compact row's `WeeklyCalendarView.tsx`) finally render the chrome DESIGN.md's 2026-09-14 pass validated against real reference screenshots,
so that the masonry card's own date box and the compact row's date box — both consumers of this one shared primitive — finally match the reference screenshots DESIGN.md's 2026-09-14 pass validated against, instead of the pre-2026-09-14 shape neither prior doc-correction pass was ever applied to in code (backlog.yaml `IDEA-042`, `FIND-025` finding (1)).

## Acceptance Criteria

1. **Given** `EventCardMediaPrimitives.tsx`'s `EventCardDateBox` renders a single-line `base`/`month`/`day`-less `text-xs` treatment today (unchanged since Story 1.i1a), **when** this story ships, **then** `EventCardDateBox` exposes a `size: 'default' | 'compact'` prop (`'default'` = masonry's `base_default`, `'compact'` = the compact row's `date_box`) so both real consumers get their own token-specified two-tier sizes from one component, not a second copy — matching DESIGN.md's `event_card_date_box.base_default` (`base`: `"relative flex flex-col justify-center gap-0.5 px-4 py-3 rounded-md bg-slate-800 text-white shadow-sm shrink-0 leading-none"`, `month`: `"text-lg font-bold uppercase tracking-wide"`, `day`: `"text-5xl font-extrabold leading-none"`) and `event_card_compact.date_box` (`base`: `"relative flex flex-col justify-center gap-0.5 px-3 py-2 rounded-md bg-slate-800 text-white shadow-sm shrink-0 leading-none"`, `month`: `"text-sm font-bold uppercase tracking-wide"`, `day`: `"text-3xl font-extrabold leading-none"`) token blocks exactly.
2. **And** `EventCardDateBox` replaces its current free-form `children: ReactNode` prop with structured `month: ReactNode` / `day: ReactNode` slots (still caller-formatted content — the component does not reimplement any date/locale formatting, unchanged from its existing docstring contract) plus an optional `tillLabel?: ReactNode` slot: when provided, it renders as the amber corner tag (`"absolute -top-1.5 -left-1.5 z-20 px-1.5 py-0.5 rounded-full bg-amber-700 text-white text-[10px] font-semibold leading-none shadow-sm whitespace-nowrap"` — the exact literal already shipped as `EventCard.tsx`'s local `TILL_BADGE_CLASS` constant and matching DESIGN.md's `event_card_compact.date_box.till_label` token verbatim) internally, so no caller hand-wraps a `<span>` with a duplicated literal class string.
3. **And** masonry's `EventCard.tsx` (`isMasonryDefault` branch) adopts `size="default"`, passing `month`/`day` from a new `formatShortEventDateTimeParts()` (new function, `format-event-date.ts`) instead of the current flat `formatShortEventDateTime()`-derived `dateBoxText`, and `tillLabel={tillBadgeText}` (unchanged computation) instead of its own hand-wrapped span — migrating base_default's till badge onto the new internal slot and retiring that one call site's use of the local `TILL_BADGE_CLASS` constant (which stays defined and in use, unchanged, for the untouched `prominentPoster=true` overlay path — see AC7).
4. **And** the compact row (`WeeklyCalendarView.tsx`'s `CalendarCard` `variant='list'`) adopts `size="compact"`, passing `month`/`day`/`tillLabel` from a new `computeCalendarSegmentDateBoxContent()` (new function, `format-event-date.ts`) instead of the current flat `computeCalendarSegmentTillText()`-derived `tillText`, per this exact content rule (resolving DESIGN.md's own "deferred to the amendment story" open item, and the redundant-date conflict discovered and resolved via `AskUserQuestion` during this story's own drafting — see Dev Notes):
   - **Continuing segment** (`currentDayStr < effectiveEnd`, i.e. not yet the schedule's last day): `month`/`day` show the segment's real effective-end-date month abbreviation + day-of-month number (genuinely new information, since it differs from the day this card is rendered under) via `Intl.DateTimeFormat`; `tillLabel` (the amber tag) carries the bare till label text (e.g. `"till"`), matching `computeCalendarSegmentTillText`'s own continuing-segment value.
   - **Last/only day** (`currentDayStr >= effectiveEnd`): showing the effective end date's month/day here would exactly repeat the start date the surrounding day-row header already shows (`WeeklyCalendarView.test.tsx`'s existing `"never repeats the start date"` regression guard covers exactly this case) — instead, `month` carries the till label text (e.g. `"till"`, styled uppercase by the existing `month` line's own classes) and `day` carries the specific end time when known (e.g. `"9:00 PM"`, via the existing `formatEventTime`) or an empty string when no time is known; `tillLabel` (the amber tag) is omitted (`undefined`) in this branch — showing it too would duplicate the exact same "till" text already shown via `month`/`day`.
5. **And** `event-card-media-tokens.ts`'s AD-15 icon-scale CSS-custom-property token (`EVENT_CARD_BADGE_FONT_SIZE`, currently one flat `0.75rem` matching the old single-line box) is recalibrated to the new month/day text sizes: a new size-keyed value pair (`default` → `1.125rem`/`text-lg`, `compact` → `0.875rem`/`text-sm` — each variant's own `month`-line size, the closest analog to the old single-line box's own font-size role) is declared onto `EventCardDateBox`'s and `EventCardMediaSlot`'s CSS-custom-property roots (both need the matching value — they're DOM siblings that communicate icon scale only via this one shared custom property, per the token's own documented mechanism) via a new `size` prop added to `EventCardMediaSlot` too. The existing flat `EVENT_CARD_BADGE_FONT_SIZE` constant (`0.75rem`) is **unchanged** and keeps its distinct role as `eventCardBadgeIconSizeStyle`'s own inline calc() fallback, used by the untouched `prominentPoster=true`/`variant='standard'` corner badge (which renders outside any slot/date-box root and never had a `size` variant to begin with).
6. **And** Story 1.i1a's own `event_card_date_box.base` (`prominentPoster=true`, the overlay variant) is explicitly confirmed unaffected — this story only touches `base_default` (`prominentPoster=false`) and the compact row's `date_box`, per DESIGN.md's own scoping. Verified via test: the existing `renders a blank, correctly-sized fallback on masonry with prominentPoster=true` test and any other `prominentPoster=true`-scoped assertions pass unmodified.
7. **And** no future dynamically-interpolated Tailwind arbitrary-value class (the exact root cause of the 2026-09-14 dead-CSS bug this file family already shipped and fixed once, `eventCardBadgeIconSizeClass`'s `` `w-[${sizeExpr}] h-[${sizeExpr}]` ``) can be silently reintroduced anywhere in `packages/ui/src/features/events/` undetected: a new package-local ESLint rule (`local/no-dynamic-tailwind-arbitrary-value`) is added, wired to actually run in CI (folding in `FIND-025` finding (2), per this story's own dispatching command). Verified via test: the rule fires on a deliberately-reintroduced instance of the exact historical pattern (a template-literal-interpolated Tailwind bracket utility) and does not fire on any of this file family's existing legitimate template-literal usages (className concatenation, `calc()` style-value construction).

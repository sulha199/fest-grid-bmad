Curator repeated posts: one event, twelve rows

Explainer for the proposed stub-repeat rule (AD-30 Rule 7 amendment, design of 2026-10-25). Status: built (PR #102). Companion to event-dedup-flow.html, which shows the rest of matching.

What happened to "Yonex French Open 2026"

A badminton curator account (badminton.ina) posted about one tournament eleven times in three days. Each post became its own event. None reached a moderator, none was linked. Every pair had the same name, the same dates (20 to 25 Oct) and the same venue (the same text, or the same coordinates), and no links.

The proposed rule

Add one check beside the score: if the same event shows up again as a stub, link it. Weights and thresholds do not change, and the account, organizer and links are not inputs. All four tests must pass.

What it will not link

  • Same name and date, different venue (several "Christmas Market" listings on one day in different places). A venue that differs, or is unknown on either side, never matches, so they stay separate. The scan lists these as near-misses so a moderator can see them.
  • A one-word name such as "Bazaar" or "Christmas": the name needs at least two words.
  • "Yonex French Open 2026 - Quarterfinals". Different name (similarity 0.62) and a different start date. Stays its own event.
  • A morning and an evening session with the same name, day and venue: bracketed text is kept in the name, and differing start times block it.
  • A weekly recurrence of the same name at the same venue: the start date differs.
  • A curator post about an organizer's event (one side not a stub): out of scope; the normal score applies.
  • Posts from the same curator in the same post (a multi-event post): unchanged, one item per post per event.

Why the link is "additive"

Today's auto-link lets the newest post overwrite the event's fields and deletes any schedule the new post leaves out. That suits an organizer's post, but a thin curator repost listing one date would erase the others. For a stub repeat the link only adds: it fills empty fields, inserts new schedules, and keeps everything already there. Empty means null, a blank string, an empty list, or the "Location not specified" placeholder.

Catching what already exists, and what slips through

The 11 Yonex events have no suggestion row to drain, so the backlog script gets a scan mode (--scan-stubs). It finds clusters with the same four checks, keeps the oldest event, and merges the rest through the journaled merge, so those merges can be undone. It also prints a near-miss list: same name and date that were not merged, and why. Dry run by default; --evaluate-only works with the read-only prod role. It is also the backstop for two posts ingested in the same few seconds, which neither can see yet (the Yonex events were created seconds apart).

Decided, and still open

  • Decided: auto-link as high (not undoable); stub to stub on name + date + venue, whichever account; strict name of at least two words, same start date, venue match; scan mode for the backlog.
  • Gate before merge: run the scan with --evaluate-only against prod read-only from the branch, attach the cluster list to the PR, and have a moderator spot-check it.
  • Accepted risk: a generic two-word name ("Christmas Bazaar") at the same venue and day from two curators still links. The spot-check and the scan's near-miss list are the controls.
  • Open, follow-up: the 2026-10-25 mid-to-high promotion still uses the overwrite-and-delete link; moving it to the additive link is a separate change.

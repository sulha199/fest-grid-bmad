# Story 10.13: Notify when a job finishes

## Story Details

- Epic: 10 (Background vendor jobs: one engine, one Jobs page)
- Story ID: 10.13
- Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a moderator (and as any user who starts a job),
I want to be told when a long job finishes,
so that I do not have to keep the page open.

## Read this first

Owner decisions of 2026-11-14 settle the three open points of the first draft. Remaining choices are listed under "Decisions flagged for the owner" (Dev Notes).

1. **Migration 0104 is approved** (owner approved 2026-11-14): three columns on existing tables, no new table. The latest migration on master is **0103** (`0103_job_vendor_snapshots.sql`), so this story's migration is **0104**, generated by `drizzle-kit` only.
2. **The moderator channel is IN this story, and not blocked.** Story 0.i1a (build the notifyAllModerators helper with escaped, throttled templates) is built, reviewed and committed on `feat/moderator-notify-helper` (tip `ba1c0ba`), with its single-recipient mode. This story is stacked on that branch. **No split.**
3. **The Scraper Lambda gets the Firebase variables and the Firebase private-key secret read** (owner approved 2026-11-14), so the push is sent from the 5-minute sweep. The Scraper Lambda already holds the mail variables and the SES send grant the moderator helper needs; the exact CDK changes are Task 4.

## Acceptance Criteria

Taken from `epics.md` Story 10.13 and PRD 3.18 (FR124, FR130); the numbering and the wording of the behaviour are the epic's. Sub-points marked "(design)" are this story's chosen mechanism.

1. **Given** a job that ended in any way (Succeeded, Succeeded with limits, Failed, Expired, including a late result marked "completed after deadline"), **when** its owner was not watching it, **then** the owner is told **in-app always**: the "Jobs" entry in the profile menu shows a `CountBadge` of the owner's jobs that ended since the owner last opened the Jobs page (design: a per-user "last opened" time on `user_settings`, set by a mutation the Jobs page calls when it is opened, so the count clears on every device).
2. **And** the owner is told by **push** through the existing FCM channel and the existing `pushNotificationsEnabled` setting (default on; no new consent screen; no email): one push per job, merged into one push that links to the Jobs page when several jobs end within `JOB_NOTIFY_WINDOW_MINUTES` (default 10). A user who turned push off, or has no registered device token, is told in-app only. A user "watching" the job (design: the web client, on a visible tab, saw it end and said so through `acknowledgeJobEnded`) is not also pushed.
3. **And** the push names only the job type and the account handle (or, with no single account, the number of posts), never a vendor, a caption, a post URL or any post content, and links to the job (`/jobs/{id}`), or to `/jobs` when merged.
4. **And** a system job (`trigger = SYSTEM`, no owner) is announced to no user: it adds nothing to any count and sends nothing (FR130).
5. **And** the notice is raised from **one shared function** that no job-ending call site names: a job reaches a terminal state in at least nine places today (see Dev Notes, "Every place a job ends"), and the announcer reads the resulting row state, so a tenth place cannot forget it. A ratchet test pins that no other file under `apps/backend/src/lib/job-engine/` sends a push.
6. **And**, additionally, **when** the job's owner is a **moderator**, a templated, throttled mail goes to that moderator through Story 0.i1a's helper in its single-recipient mode: `notifyAllModerators('JOB_FINISHED_MODERATOR_NOTICE', vars, { recipientUserId: <the job owner> })`. The mail names only the job type and the account handle (or the number of posts), in English and Indonesian, and links to the Jobs page (decision 5); the helper escapes every value and builds the link. A non-moderator owner never reaches the helper (the announcer does not call it, and the helper would answer `refused_not_moderator` and spend no throttle slot if it were called), and a system job notifies no one. The mail follows the same grouping as the push (one mail per group, so at most one per owner per `JOB_NOTIFY_WINDOW_MINUTES`, decision 6). A moderator who owns a job also gets AC1 and AC2 (in-app and push).

### Every place a job ends (traced 2026-11-13)

The ending hook `afterJobEnded(job, terminal)` (`apps/backend/src/lib/job-engine/after-job-ended.ts`, Story 10.3: promote the next queued job, settle followers) **already exists but is not the single ending**: it is called from `run-job.ts` (the run's own ending and the WAITING hand-off), `late-results.ts` (a collected late result and `endWaitingJob`), `cancel-job.ts`, `start-job.ts` (start failure) and `readmit-waiting-job.ts` (with `ownerUserId: null`). These terminal writes do **not** call it:

| Terminal write | File | Calls `afterJobEnded`? |
|---|---|---|
| Sweep: overdue admitted job to `EXPIRED / TIMED_OUT` | `sweep-expired-jobs.ts` | No |
| Sweep: queued job to `EXPIRED / WAITED_TOO_LONG` | `sweep-job-queue.ts` | No |
| Follower copies its leader's ending | `settle-followers.ts` | No (and the follower has its OWN owner, who must be told) |
| Orphaned follower to `FAILED / LEADER_LOST` | `settle-followers.ts` | No |
| Start invoke failed (`START_FAILED`) | `job-host.ts` `markJobStartFailed` | Caller does |

So a notice raised in `afterJobEnded` would miss the sweep expiries and every follower. That is why this story reads the **row state** (`finished_at` set, owner set, `owner_notified_at` null) from one sweep step instead of hooking call sites. The in-app count has the same property (a query, no hook). This satisfies the brief "one shared ending function, never per call site" without refactoring nine writes into one `endJob()`; that refactor is out of scope (Out of Scope) and a candidate follow-up if the owner wants the writes themselves unified.

### SQS, Lambda and the push

`project-context.md` says the processing pipeline decouples Lambdas with SQS and allows a scoped best-effort `Event` Lambda invoke (precedent `invoke-ai-processor.ts`, and the engine's own `invokeJobEngineWorker`). This story needs **neither**: the announcer is a database read inside a Lambda that already runs every 5 minutes, and it sends FCM over HTTPS and SES mail (through the helper) from there. No queue, no invoke, no new Lambda. The cost is latency (decision 3) and the Scraper Lambda's Firebase variables and secret read (Task 4; the mail variables and the SES grant are already there).

### Can "the owner was not watching" be decided on the server?

Not directly: the Jobs reads are polls with no session notion and nothing is written on a read (writing a "last polled" time on every poll would put a write on the hottest read path). Conservative rule chosen: **the client tells the server it saw the ending** (`acknowledgeJobEnded`, visible tab only) and the announcer waits a grace period (`JOB_NOTIFY_GRACE_SECONDS`, default 45, longer than the slowest watching poll of 10 s plus one retry) before it decides. A hidden tab, a closed app and an offline phone never acknowledge, so they are treated as not watching, which errs towards one extra push rather than a missed one. The in-app badge does not depend on it (it counts every ending since the page was last opened, as PRD FR124 says).

### Throttling and merging within `JOB_NOTIFY_WINDOW_MINUTES`

State is `user_settings.last_job_push_at`. Each sweep tick, per owner: the first eligible ending is pushed on its own (SINGLE); while the last push is younger than the window, further endings are held (left unmarked) and, once the window closes, all held endings go out as ONE merged push linking to `/jobs`. Result: at most one push per owner per window, a lone job is never delayed by the window, and each job is covered by exactly one push. The epic's wording ("one push per job, merged when several end within the window") is satisfied; the one visible consequence is that a job ending 1 minute after a push waits up to the window for its own merged push (the in-app badge shows it at once).

### Moderator channel (in scope; Story 0.i1a is built)

Story 0.i1a is built on `feat/moderator-notify-helper` (tip `ba1c0ba`) and this story is stacked on it. The real contract, read from the code: `notifyAllModerators(templateKey, vars, { recipientUserId?, entityKey? })` returns a typed `NotifyModeratorsResult` (`sent`, `failed`, `throttled`, `no_moderators`, `refused_not_moderator`, `error`) and never throws. With `recipientUserId` it mails only that user and only if they are an active moderator, otherwise it answers `refused_not_moderator` and spends no throttle slot. It escapes every value in the html part, strips control characters from the subject, builds `moderatorReviewUrl` itself from `WEB_APP_BASE_URL` and a **static path per template** (so a caller cannot pass a URL and the link cannot carry a job id), claims one `alert_email_rate_limits` slot per template, entity and recipient with a 60-minute fixed window, releases it if every send fails, and awaits SES. The epic's earlier "extend 0.i1a or build a thin helper" is settled by 0.i1a's single-recipient mode; this story adds only a template key, a review path and an entity rule in `packages/domain/src/email/` (Task 2.3), then one call from the announcer (Task 3.3).

- **Link:** the helper's review path is per template, so the mail links to **`/jobs`** (the Jobs page), not `/jobs/{id}` (decision 5). The push, which the story controls, does link to `/jobs/{id}`.
- **Entity rule:** the job id (`vars.jobId`; for a merged group the smallest job id of the group), so the throttle is per job and recipient.
- **Interplay with the push merge window (decision 6):** the helper's cooldown is fixed at 60 minutes per (template, job id, recipient), which does not merge anything: ten jobs would be ten mails. So the announcer applies the push's grouping to the mail too (one call per group, the group's smallest job id as the entity): at most one mail per owner per `JOB_NOTIFY_WINDOW_MINUTES`, and the helper's slot is only the safety net against a repeat of the same group (an overlapping run, a revived job inside 60 minutes). `user_settings.last_job_push_at` is the one window state for both channels.
- **Who never reaches it:** a non-moderator owner (the announcer reads the role first, and the helper would refuse), a system job (no owner, never selected), a job already seen in the app.
- **Content:** only `summaryEn` and `summaryId` (job type label and `@handle`, or "N posts" / "N jobs finished"), built by the same pure function as the push; never a vendor, caption, URL or error text. The helper escapes the values.

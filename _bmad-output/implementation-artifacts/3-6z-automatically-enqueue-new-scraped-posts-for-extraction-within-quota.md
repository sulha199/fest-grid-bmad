# Story 3.6z: Automatically enqueue new scraped posts for extraction within quota

## Story Details

- Epic: 3
- Story ID: 3.6z
- Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a subscriber,
I want newly scraped posts from my subscribed accounts to be extracted automatically,
So that events appear without my selecting each post (BUG-039; PRD §3.7/§3.10).

## Acceptance Criteria

1. **Given** a scrape completes and `persistScrapedPost` returns a post with `alreadyExisted: false` (a genuinely new row, not a re-scrape of something already stored), **when** the post is persisted, **then** it is automatically enqueued onto `AIProcessingQueue` via the existing `enqueuePostForProcessing(postId)` (Story 3.5/5.1a) — but **only** after a pre-flight check confirms the post's account has at least one usable API key among its active subscribers, reusing the same building blocks `callGemini`'s Tier 1/Tier 2 selection already uses (`getActiveSubscriberUserIds`, `fetchCandidateKeys`, `selectApiKey`, Story 0.13). A post whose account currently has **no** usable key (zero active subscribers, or zero valid keys among them) is **not** enqueued and is left exactly as today — `isExtracted: false`, visible and selectable on the Manual Post Selection screen (PRD §3.10), the same path that already covers posts predating a subscription. This applies uniformly to every `persistScrapedPost` call site in `processScrapeJob`, including a newly-added subscription's initial historical backfill — not only the ongoing steady-state scrape path (explicit product decision, see Dev Notes).
2. **And** this pre-flight check only answers "is there a key at all" — it does not pre-compute per-cycle usage totals the way Story 5.3's manual-selection "remaining quota" display does. The actual Tier 1/Tier 2 round-robin, fairness ordering, rate-limit retry/exclusion, and `AiGatewayExhaustedError` handling inside `processAiJob`/`callGemini` run completely unchanged for an auto-enqueued message — there is no "auto" vs. "manual" branch anywhere downstream of `enqueuePostForProcessing`. Multi-event/roundup rules (Stories 3.6s/3.6t) and `CURATOR_GUIDE` minimization (Story 3.4o) therefore apply to auto-extracted posts by construction, not by any new code this story adds.
3. **And** `enqueuePostForProcessing` itself is made idempotent so the same post is never enqueued twice while a prior attempt is still in flight — not just "3.6z's own call site only calls it once per post" (which was already structurally true), but closing the previously-accepted Story 3.5 gap now that two independent call sites exist (manual `selectPostsForExtraction` and this story's auto-enqueue) and collide far more often than the single-caller world that gap was accepted in. This is implemented as an atomic, TTL-bounded claim (`posts.queued_for_extraction_at`) — see Dev Notes for the full design and why a bare "claimed forever" column would be worse than today's gap.

**Note (resolved via `AskUserQuestion` during this story's creation, see Dev Notes "User-confirmed design decisions"):** Two real, non-mechanical tradeoffs in the epics.md AC text were raised with the user and explicitly decided: (1) whether the idempotency fix in AC3 should be a full TTL-reclaimable claim, a non-expiring claim, or left as the Story 3.5 accepted gap — **decided: full TTL-reclaimable claim**; (2) whether the auto-enqueue trigger in AC1 should exclude a newly-added subscription's initial historical backfill (which PRD §3.10 frames as its own "predates the subscription" category reserved for manual/wizard selection) — **decided: no exclusion, auto-enqueue applies everywhere** a post is genuinely new, including the initial backfill.

**Depends on:** Story 3.5 (`enqueuePostForProcessing`, `review`), Story 3.6t (per-event ingestion pipeline downstream of `AIProcessingQueue`, `review`; and Story 3.6s's inline Gemini timeout guard on the shared extraction call, `review`). Soft: FIND-061 diagnosis (resolved, commit `ac45b27`).

### User-confirmed design decisions (this story's own creation, via `AskUserQuestion`)

Three real tradeoffs, not resolvable from the epics.md AC text alone, were raised with the user across two rounds and explicitly decided during this story's creation:

1. **Idempotency guard depth (AC3).** epics.md's AC3 names `enqueuePostForProcessing` directly and says it "is idempotent so a post is never enqueued twice" — a stronger claim than Story 3.5 shipped (which only guards on `isExtracted`, explicitly accepting the narrower "same not-yet-extracted post enqueued twice while in flight" race as low-probability with a single caller). Three options were surfaced across two question rounds as the full cost/benefit picture emerged: (a) close the race completely with a TTL-reclaimable claim column; (b) add a claim column with no expiry (simpler, but risks permanently stranding a post if its extraction attempt terminally fails — `processAiJob` has no catch-all around `callGemini`, so an uncaught `AiGatewayExhaustedError` rides 3 SQS redeliveries into the DLQ with nothing to ever release the claim); (c) keep the Story 3.5 accepted-gap guard as-is, since Story 3.6t's DB-level ingestion idempotency (`(post_id, extraction_ordinal)` unique constraint + `onConflictDoNothing`) already means a double-enqueue can only waste one Gemini call, never corrupt data. **Decided: (a), the full TTL-reclaimable claim** (Tasks 1, 2, 5) — matches the AC's literal wording and this project's spec-fidelity default, at the accepted cost of a new nullable column, a new error class, and a non-trivial rewrite of Story 3.5's already-`review`-status `enqueuePostForProcessing` (and its test suite).
2. **Auto-enqueue trigger scope (AC1).** PRD §3.10 ("Relationship to Automatic Extraction," 2026-10-01 BUG-039 clarification) names "older posts that predate the subscription" as its own category manual selection exists for, distinct from "no key had quota" — which maps fairly directly onto `processScrapeJob`'s `isInitialNewSubscription` branch (the one-time historical backfill feeding the wizard's Manual Post Selection step). Excluding that branch from auto-enqueue would keep a new subscription's backlog exclusively for manual/wizard triage, avoiding a popular first subscription silently consuming most of a user's quota before they ever see that screen. **Decided: no exclusion — auto-enqueue applies to every `persistScrapedPost` call site uniformly**, including the initial historical backfill, subject only to the same key/quota pre-check as the steady-state path (Task 6 applies the hook inside the shared `persistScrapedPosts` helper rather than branching on `job.isInitialNewSubscription`). The quota-consumption risk this accepts is a deliberate, recorded tradeoff, not an oversight.
3. **Pre-flight key-availability check vs. unconditional enqueue (AC1/AC2 reading, decided by source-evidence rather than a question — see below).** Not put to the user as a question: the evidence made the answer unambiguous. `AIProcessingQueue` has a DLQ with `maxReceiveCount: 3` (`festgrid-backend-stack.ts`); `processAiJob` has no `try/catch` around `callGemini` today, so a zero-candidate `AiGatewayExhaustedError` for an account with no usable key propagates uncaught through 3 full SQS redeliveries before landing in the DLQ — three wasted Lambda invocations per doomed post, compounding exactly the "auto-enqueue increases ingestion volume" concern the wave plan already flags. AC1's explicit phrasing ("posts without an available key or quota stay for manual selection") reads as a gate on enqueueing, not a description of the natural `isExtracted`-false fallback state. **Decided: pre-check with `hasAvailableApiKeyForAccount` (Task 4) before ever calling `enqueuePostForProcessing`.**

### Design note: why the claim needs a TTL, not just a boolean

A naive non-expiring "claimed" flag would make `enqueuePostForProcessing`'s guard worse than the gap it replaces in one specific scenario: `processAiJob` (line ~64, `apps/backend/src/lib/ai-processor/process-ai-job.ts`) calls `callGemini` with no surrounding `try/catch`. If every subscriber key for the account is invalid/rate-limited at call time, `callGemini` throws `AiGatewayExhaustedError` uncaught; the Lambda's SQS batch handler treats the thrown error as a failed item, the message becomes visible again after the queue's 300s visibility timeout, and after `maxReceiveCount: 3` it lands in `AIProcessingQueueDlq` — roughly 900s (15 min) worst case — with nothing in that failure path ever clearing a "claimed" flag. A non-expiring claim would then permanently lock that post out of both auto-enqueue (future scrapes never re-offer an already-persisted post) and manual selection (the UI has no "force re-claim" affordance), which is strictly worse than today's "accepted gap" — today, the post is at least always selectable once it's not `isExtracted`. The TTL (default 30 minutes, comfortably above the ~15-minute worst case, Task 7) makes an expired claim automatically reclaimable by either path again, closing the race during normal operation while never creating a permanent dead end.

## Out of Scope

- **Exposing "currently queued/processing" state via GraphQL or any frontend UI.** `postsByAccount` already returns raw `isExtracted` with no server-side filtering, relying entirely on client-side visual disabling (PRD §3.10) — this story follows that same precedent and does not add `queuedForExtractionAt` (or a derived boolean) to the `Post` GraphQL type. A future story could add a "currently processing" visual state to Manual Post Selection if the product wants one; no AC here asks for it, and Gate 2 confirmed this story has no UI surface.
- **Building the guarded Gemini vendor-call wrapper (Story 0.i2a→0.i2c).** This story's BUG-012/Finding 1 exposure (higher auto-enqueue volume compounding the still-missing real timeout wrapper) is explicitly tracked on that separate, already-blocked-on-AD-32 track per the swept batch readiness report — not absorbed here.
- **Changing Story 5.3's per-user `myExtractionQuota` remaining-quota arithmetic.** That is a separate, user-scoped "how many Gemini calls has this user's key(s) made this cycle" display/enforcement concern for manual selection, untouched by this story's account-scoped "does a usable key exist at all" pre-check.
- **Changing the existing quota-warning-email mechanism** (`send-quota-warning-emails.ts`, PRD §3.7's "`X` posts queued for `Y` days" notification) — a separate, already-built feature; this story does not need to special-case auto-un-enqueued posts for it, since that mechanism's own counting is based on `isExtracted`/`publishedAt`, which this story's "stay for manual selection" fallback already satisfies identically to a never-auto-attempted post.
- **A real-time/stronger quota check that predicts actual Gemini rate-limit exhaustion before calling.** This story's pre-check only answers "does a valid key exist"; whether that key is *currently* rate-limited is only discoverable by the real call inside `processAiJob`/`callGemini`, unchanged by this story.
